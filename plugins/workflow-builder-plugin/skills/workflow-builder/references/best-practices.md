# ワークフロー設計ベストプラクティス

## ID 参照の確認手順

ワークフローに埋め込む各種 ID のうち、`serviceId` / `autoWebinarId` は MCP に検索・一覧取得ツールが無い。それ以外（`inflowActionId` / `creatorLineChannelId` / `contactTagId` / `lineRichMenuId`）は対応する一覧取得ツールで取得・実在確認できる。`benefitId` は特典提供終了により新規設定しない（既存ワークフローの維持時のみ）。

| ID | MCP で取得できるか | 取得経路 |
|---|---|---|
| `inflowActionId` | ✅ | `getCreatorScenariosInflowActions` |
| `creatorLineChannelId` | ✅ | `getCreatorLineChannels` |
| `contactTagId` | ✅ | `getCreatorContactTags`（無ければ `postCreatorContactTags` で新規作成できる。同名は既存 id を返す冪等動作） |
| `lineRichMenuId` | ✅ | `getCreatorLineRichMenus`（`creatorLineChannelId` で絞り込み可） |
| `autoWebinarId` | ❌ | ユーザーから受け取る（管理画面のオートウェビナー） |
| `serviceId` | ❌ | ユーザーから受け取る（管理画面のプラン・サービス管理） |

`serviceId` / `autoWebinarId` が必要な trigger/condition（`SERVICE_APPLIED` / `SERVICE_SCHEDULE_REMINDER` / `CONDITION(SERVICE_APPLICATION_STATUS)` / `CONDITION(BANK_TRANSFER_STATUS)` / `CONDITION(AUTO_WEBINAR_PARTICIPATION)` / `CONDITION(AUTO_WEBINAR_WATCH_TIME)`）では、要件ヒアリングの段階で「**該当リソースの ID を教えてください**」を必ず聞き、MCP からは検索・実在確認ができないことを踏まえてユーザー申告のまま扱う（下書き保存時は実在検証されないため、公開前レビューで改めて口頭確認する）。それ以外の ID は対応する一覧取得ツールで実在するものを選んでもらう（一覧を提示する際は名前で選んでもらい、生の ID を会話の主役にしない）。`MARKETING_LEAD_BENEFIT_RECEIVED` は特典提供終了により**新規設定しない**。

## ライフサイクル運用

基本フロー: **`INACTIVE` で作る → ユーザー確認 → 公開（`ACTIVE` 化）**

- **作成直後**: 必ず `INACTIVE`
- **stages 構築中**: `INACTIVE` のまま何度でも更新する。下書き段階では `benefitId` / `serviceId` の実在はチェックされない（他の参照 ID は PATCH 時にも検証され不正なら 400）ので、`serviceId`（および既存ワークフローの `benefitId`）は公開前にユーザーへ口頭で確認する
- **公開（`ACTIVE` 化）**: 公開時に参照リソースの実在・同時稼働数の上限が確認され、満たさない場合は理由を示すエラーが返る
- **停止（`INACTIVE` 化）・廃止（`ARCHIVED`）**: `patchCreatorScenariosLifecycle` で行う

## 動作仕様

### 公開（`ACTIVE` 化）時の検証

- `ACTIVE` 化（公開）時に、参照リソースの実在と同時稼働数の上限が確認される。満たさない場合は理由を示すエラーが返る
  - 同時に稼働できるワークフロー数の上限に達している場合
  - 「指定された特典が見つかりません。特典が削除されていないか確認してください。」（トリガーの特典が削除済み等）
  - 「LINE関連の開始条件またはステップを使用するには、ワークフローにLINE公式アカウントを設定してください。」（LINE公式アカウント未設定）
- 対処: エラーの原因（参照リソース不足・稼働数上限）を解消してから再度 `ACTIVE` 化する。ユーザーには平易な日本語で原因と対処を伝える

### 下書き（`INACTIVE`）中は検証が緩い

- 存在しない `benefitId` 等を入れても保存できてしまう
- 「保存できた」＝「動く」ではないので、参照 ID の実在をユーザーに口頭確認する
- 下書き中は不正な ID でも保存できてしまうので、公開前のレビュー段階で必ず ID 内容をユーザーに見せて確認する（公開時に検証され弾かれるが、手戻りを避けるため事前確認する）

### レスポンス JSON は送信時と形が違う

- `getCreatorScenario` のレスポンスでは、triggerType に該当しない trigger サブフィールドは `null` で返る
- ただし **`lineChannelContactRegisteredTrigger` だけはレスポンスから完全省略**される
- 受け取った JSON をそのまま PATCH に戻したい場合は、欠落フィールドを `null` で補完してから送る

### `getCreatorScenarios` の `lifecycle` クエリは2値のみ

- `"INACTIVE_ACTIVE"`（稼働 or 停止）か `"ARCHIVED"` のみ
- `"ACTIVE"` 単体や `"INACTIVE"` 単体は指定できない（クエリパラメータの enum）

## トリガー × アクションの相性

**識別子（コンタクト ID / MOSH ID）の適合は [content-schema.md](content-schema.md) の「コンテキスト適合表」が正本**。ここではその表を前提に、表の △ を実務でどう扱うかと、識別子以外の相性だけを書く。

- **`LINE_CHANNEL_CONTACT_REGISTERED` / `CONTACT_TAG_ADDED` トリガーで `SEND_EMAIL` を選ぶ前に、配信先がメールアドレスを持つか確認する**（適合表の ○※4）。`SEND_EMAIL` の宛先は実行時にコンタクトのメールアドレスから解決される。メールアドレスが紐付いていないコンタクト（LINE 友達追加だけで登録されたコンタクト等）は配信失敗（実行履歴に「送信先コンタクトなし」）となり、**そのコンタクトの後続ステップも打ち切られる**（保存・公開はエラーにならない）。LINE 友達追加起点は原則 `SEND_LINE_MESSAGE` を選ぶ。タグ付与起点でメールを使う場合は、対象コンタクトがメールアドレスを保有している前提（特典のメール取得経由等）かをユーザーに確認する
- **適合表の △ は両方向にある**。どちらも保存・公開は通り、実行時に対象を解決できず失敗する（後続ステップも打ち切り）。紐付けの成立条件は適合表の ※3
  - **コンタクト起点 → MOSH 前提の CONDITION**（LINE友だち追加・タグ付与・流入経路CV・既存の特典取得 × `SERVICE_APPLICATION_STATUS` / `AUTO_WEBINAR_*` / `BANK_TRANSFER_STATUS`）: 使えるが、コンタクトに MOSH アカウントが紐付いていないと CONDITION 自体が失敗する
  - **MOSH ゲスト起点 → コンタクトを要求するステップ**（`SERVICE_APPLIED` / `SERVICE_SCHEDULE_REMINDER` / `INSTALLMENT_PAYMENT_FAILED` / `SUBSCRIPTION_PAYMENT_FAILED` × `SEND_LINE_MESSAGE` / `ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG` / `LINK_LINE_RICH_MENU` / `UNLINK_LINE_RICH_MENU` / `CONDITION(CONTACT_TAG)`）: 申込者・決済失敗者の MOSH ID からコンタクトを引くため、**そのゲストがコンタクトとして紐付いていなければ LINE 配信・タグ操作は 1 件も実行されない**。「申込のお礼を LINE で送りたい」「決済失敗者にタグを付けたい」という自然な要望で最も起きやすい。ユーザーには「申込者が事前に LINE 配信やメールの計測付きリンクをタップし、ログインしたことがある方に限られます。そうでない方には届きません」と伝え、確実に届けたいなら `SEND_EMAIL`（MOSH アカウントのメールに届く）を選ぶか、先に紐付けが発生する導線（トラッキング有効なメッセージの URL タップ → MOSH ログイン）を設計する
- 予約リマインド（`SERVICE_SCHEDULE_REMINDER`）の最初のメッセージは WAIT_TIME を挟まずトリガー直後に置く。リマインド対象日時を跨ぐ大きな WAIT_TIME を設定しない（開催後に届くリマインドになる）
- 開催前に複数タイミングでリマインドしたい場合は、**1本のワークフローに WAIT_TIME で繋がず、タイミングごとに別ワークフローへ分ける**。理由と組み方は次節「予約リマインドは複数のトリガーに分ける」が正本
- `INFLOW_ACTION_CONVERTED` トリガーの流入経路は LINE 公式アカウントに属する。**ワークフロー最上位の `creatorLineChannelId` を、流入経路が属するアカウントと一致させる**（`getCreatorScenariosInflowActions` のレスポンスの `creatorLineChannelId` で確認する。不一致だとトリガーと配信のアカウントがずれ、公開時に API が弾く。[content-schema.md](content-schema.md) の「検査の二層構造」の確認済みの事実）
- `LINK_LINE_RICH_MENU` の `lineRichMenuId` も同様に、**ワークフロー最上位の `creatorLineChannelId` と同じチャンネルのリッチメニューを選ぶ**（`getCreatorLineRichMenus` のレスポンスの `creatorLineChannelId` で確認する）。API はクリエイター所有なら別チャンネルのメニューでも保存・公開を通してしまうが、実行時は**リッチメニュー側**のアカウントの友だちかどうかで対象コンタクトを探すため（[content-schema.md](content-schema.md) の適合表 ※5）、ワークフロー側のアカウントの友だちしかいない対象は失敗する。一致を強制するのは編集画面のみなので、MCP 経由で組むときは自分で確認する
- `CONTACT_TAG_ADDED` トリガーのワークフロー内で、その起動タグ自体を `REMOVE_CONTACT_TAG` → `ADD_CONTACT_TAG` の順で操作しない（対象コンタクトに対して自分自身を再トリガーし、無限に往復しうる）。起動タグと同じタグを終端で付け直す設計は避け、進捗管理には別タグを使う

## 予約リマインドは複数のトリガーに分ける（`SERVICE_SCHEDULE_REMINDER` の再評価タイミング）

`SERVICE_SCHEDULE_REMINDER` は、1件の予約に対して**トリガーが指す時刻（開催日時から `beforeDays`/`hours`/`minutes` を引いた時刻）に到達した瞬間、1回だけ**評価される。その時刻に予約が存在していれば発火し、存在していなければ発火しない。**予約された時点で、その時刻がすでに過去なら、そのトリガーはその予約に対して二度と発火しない**（後から追いつく・巻き戻って発火する、ということが無い）。

`WAIT_TIME` はこの1回きりの発火を「時間的に後ろへずらす」だけで、**新しい独立した評価ポイントを作らない**。したがって「開催3日前・前日・3時間前・15分前」のように複数のタイミングでリマインドしたい場合、**1本のワークフロー（`SERVICE_SCHEDULE_REMINDER` 1個 + `WAIT_TIME` チェーンで後続メッセージを繋ぐ構成）で組んではいけない**。3日前トリガーを起点に前日・3時間前・15分前を `WAIT_TIME` で繋いだ場合、**開催3日前を過ぎてから予約した人には、前日・3時間前・15分前を含めリマインドが一通も届かない**（3日前の時点で予約が存在しないため、起点のトリガー自体が発火しない）。予約は開催直前に集中しやすく、この層を取りこぼす設計は参加率に直結する。

- **正しい組み方**: リマインドしたいタイミングの数だけ**別々のワークフロー**を作り、それぞれに独立した `SERVICE_SCHEDULE_REMINDER` トリガー（`beforeDays`/`hours`/`minutes` をタイミングごとに指定）を持たせる。こうすれば「3日前を過ぎてから予約した人」でも、前日・3時間前・15分前の各トリガーがそれぞれ独立に評価されるため、そのタイミング以降に予約していれば届く
- **最低限守ること**: 参加率に最も直結する**直前のリマインド（15分前など）は、他のリマインドとは必ず独立したワークフローにする**。直前のリマインドが早いタイミングのトリガーと `WAIT_TIME` で連結されていると、開催直前に駆け込みで予約した人（最もリマインドが必要な層）ほど何も届かなくなる
- **確認の聞き方**: 「開催前に複数回リマインドしたい場合、それぞれのタイミング（3日前・前日・15分前 等）より後に予約した方にも、そのタイミング以降のリマインドを確実に届けたいですか？1本のワークフローで `WAIT_TIME` を使って繋ぐと、一番早いタイミングのトリガーより後に予約した方には、それ以降のリマインドが一通も届きません」
- **`SERVICE_APPLIED` 起点との違い**: `SERVICE_APPLIED`（申込直後の1通、[content-schema.md](content-schema.md)）は申込という単一の出来事に対して1回発火すればよいので `WAIT_TIME` チェーンで問題ない。問題になるのは `SERVICE_SCHEDULE_REMINDER` のように「開催日時までの残り時間」という**予約時点によって過去にも未来にもなりうる基準**でチェックポイントを複数持つ設計だけ

## 単一ワークフローで閉じない要件（ヒアリングで見抜く）

要件の中には、**作ろうとしているワークフロー 1 本をどう組んでも満たせず、テナント内の別のワークフロー・一斉配信の有無で成否が決まる**ものがある。SKILL.md Step 1 の「タイミング」「紐付け導線」の項目はこの 2 つを見抜くための質問で、ここに確認文と判断の仕方を置く。

### 1. 「直後に」「いつでも」は CONDITION では実現できない — 専用トリガーの別ワークフロー

`CONDITION` は到達時点の 1 回だけ評価される（[content-schema.md](content-schema.md) の「CONDITION は一時点の判定」と専用トリガーの対応表が正本）。次の兆候が揃ったら、設計に入る前に確認する:

- 要望に **即時反応の言葉**（「申し込んだらすぐ」「申し込んだ人には即座に」「タグが付いたらその場で」「タグが付いたらいつでも」）がある
- かつ、会話上のトリガーがその出来事自体ではない（例: `LINE_CHANNEL_CONTACT_REGISTERED` で友だち追加 → 申込 URL 送付 → WAIT_TIME → `CONDITION(SERVICE_APPLICATION_STATUS)` で申込者を拾う設計）

確認文（そのまま使ってよい）:

- 申込: 「申し込んだ方への LINE を**申込直後**に届けたいなら、この 1 本では実現できません。この分岐は◯日待ったあとの一時点で『申し込み済みか』を見るだけで、申込の瞬間には何も起きず、その後に申し込んだ方も拾えません。『プラン・サービス申込』から始まる別のワークフローが必要ですが、**既にありますか、それともこの場で一緒に作りますか**」
- タグ: 「『◯◯』タグが付いた方に**付いた時点ですぐ**反応したいなら、この分岐では実現できません。◯日待った時点で付いていた方しか拾えず、その後に付いた方は取りこぼします。『タグ追加』から始まる別のワークフローが必要ですが、**既にありますか、それともこの場で作りますか**」（`CONTACT_TAG_ADDED` は新規付与のときだけ発火するため、既に付いている人への付け直しには反応しないことも添える）

判断:

- 「既にある」→ `getCreatorScenarios` で全件を取り（`limit` 既定 20 なので `offset` でページングして全件確認する）、先頭ステージの trigger が同じ `serviceId` / `contactTagId` を指す専用トリガーのワークフローが**稼働中**（`lifecycle: ACTIVE`）であることを `getCreatorScenario` で確認する（下書きなら公開が必要）。確認できたら、今作るワークフローの `CONDITION` は「後日時点で該当していた人を拾う」役割に限定して設計する
- 「無い」→ 今のワークフローとは**別に**専用トリガーのワークフローを新設する提案をし、ユーザーが望めば同じセッションで続けて作る。今のワークフローの `CONDITION` だけで「直後」を代替しようとしない
- 適用範囲は `SERVICE_APPLICATION_STATUS` ↔ `SERVICE_APPLIED`、`CONTACT_TAG` ↔ `CONTACT_TAG_ADDED` の 2 組だけ。`BANK_TRANSFER_STATUS` / `AUTO_WEBINAR_*` には専用トリガーが無いので、即時反応の要望には「該当するトリガーが無い」事実を伝える（代用案を捏造しない）

### 2. △ の設計（申込・リマインダー・決済失敗 × LINE 配信・タグ操作）— 紐付け導線の有無

適合表の △（[content-schema.md](content-schema.md)。実務上の扱いは上記「トリガー × アクションの相性」）を含む設計を検討しているときは、要件ヒアリングの段階で次を確認する:

「対象の申込者・購入者は、**事前にトラッキング付きの URL（LINE 配信やメールのリンク）をタップして MOSH にログインしたことがありますか**。既存のワークフローや一斉配信で、そういう導線はありますか」

判断:

- 導線がある（トラッキング有効な URL を含む LINE・メール配信が稼働中／配信済み）→ △ のまま進めてよいが、「そのリンクをタップしてログインした方にしか届かない」「導線より前に申し込んだ方には効かない」を設計上の前提として伝える
- 導線が無い・分からない → 2 択を提案する。①確実に届けたいなら `SEND_EMAIL`（MOSH アカウントのメールに届く）に倒す。②LINE で届けたいなら、**紐付けを先に作る導線**（トラッキング有効な URL を含む LINE 配信を、申込より前に届く場所＝友だち追加起点のワークフローや一斉配信に置く）を一緒に設計し、その後に △ のワークフローを公開する
- ユーザーの記憶より MCP の裏取りが確実なので、「分からない」と言われたら次の手順でテナント内を探してから判断する（本スキルは読み取りにも同じツールを使える）:
  1. `getCreatorScenarios` で全ワークフローを取得し（`offset` でページングして全件）、各ワークフローを `getCreatorScenario` で開いて `SEND_LINE_MESSAGE` の `TEXT` メッセージに `isTrackingEnabled: true` かつ本文に URL があるものを探す（`CAROUSEL` / `IMAGE_CAROUSEL` / `RICH_MESSAGE` のタップ遷移先 URL はトグル無しで常にトラッキングされるので、これらの存在も入口として数える）
  2. 一斉配信（`postCreatorContactMessagesLineSearch` / `postCreatorContactMessagesEmailSearch` で一覧、`getCreatorContactMessagesLine` / `getCreatorContactMessagesEmail` で詳細）も同じ観点で確認する。**一覧アイテムには `isTrackingEnabled` も本文も含まれない**ため、必ず詳細を開いて確認する
  3. 見つかった入口が**配信済み・公開中**（`lifecycle: ACTIVE` かつ実行実績がある、または一斉配信が送信済み）かを確認する。下書き・未配信のものは「入口の候補」であって、まだ機能していない
  4. 入口が見つかっても、**紐付けはその入口より前に申し込んだ人には遡って効かない**ことを設計上の前提として伝える

## ノード接続ルール

全パスが最終的にメッセージ系ステップ（`SEND_EMAIL` / `SEND_LINE_MESSAGE` / `ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG` / `LINK_LINE_RICH_MENU` / `UNLINK_LINE_RICH_MENU`）で終端する構造にする。

- **WAIT_TIME で終わる「待って終わり」のパスを作らない**（トップレベル末尾・CONDITION の branch 末尾とも）。中間の WAIT_TIME の後にメッセージが来ない宙ぶらりん構造も同様
- CONDITION の**両 branch を同時に空にしない**。両方空なら存在意義がないので、「CONDITION を削除しますか？それとも条件マッチ時の処理を追加しますか？」とユーザーに確認する
- **片方の branch が空なのは valid**。マッチ側を空にすれば「該当者は早期終了」、不マッチ側を空にすれば「条件外の人だけ終了」という正当な設計パターンで、頻繁に使う。「両 branch を必ず埋めるべき」と過剰反応せず、ユーザーの意図に従う
- **CONDITION は、それを含む stages 配列（トップレベルまたは分岐内の `branches[].stages`）の最後の要素にする**。CONDITION の後に別のステージを続ける構成（＝両方の branch が下流の共通ステージへ合流する構成）は `patchCreatorScenario` が 400 エラーで拒否する（管理画面の編集UIにもこの構成を作る手段が無く、それに合わせて API 側でも明示的に禁止している）。全員に共通の処理を続けたい場合の対処は下記「分岐への追加位置の確認」を参照
- 連続するメッセージステップの間に WAIT_TIME を挟まない場合は、それが意図的か確認する（同時に複数通届く）
- stages を組んだら **`patchCreatorScenario` で送る前に配列を上記の観点で点検**し、保存後は `getCreatorScenario` で読み戻して再点検する

## メッセージ内容の参照整合性

- **`urlActions[].url` は本文中に実際に書いたURLと一字一句完全一致させる**（[content-schema.md](content-schema.md) の「TEXT の `urlActions`」参照）。大文字小文字・末尾スラッシュ・トラッキングパラメータ（`?utm_...`）の有無が1文字でも違うと不一致になり、**保存・公開はエラーにならないままタップ時のタグ操作が無言で発火しない**。本文を後から編集してURLを変えたときに `urlActions.url` の更新を忘れる事故が典型
- **`SEND_LINE_MESSAGE` の `messages` を空配列のまま残さない**。スキーマ上は0件でも保存できるが（[content-schema.md](content-schema.md)）、稼働させても何も配信されない。ステージを追加した直後に本文入力を忘れたまま次に進むと発生する

## 分岐への追加位置の確認（曖昧なら1段聞いてから）

「分岐のあとにメッセージを足して」という指示は解釈が割れやすい:

| 解釈 | stages 上の場所 | 意味 |
|---|---|---|
| (a) 枝の中 | `condition.branches[].stages` に追加 | matchValue ごとの別ルート（例: タグ持ちの人だけに送る） |
| (c) 分岐のネスト | branch 内に CONDITION 型 action | 既存の枝をさらに条件分岐 |

**「分岐の後」（CONDITION ステージの次の stage として置き、両 branch を合流させて全員へ共通実行する形）は選択肢として存在しない**。上記「ノード接続ルール」の通り、CONDITION の後に別ステージを続ける構成は `patchCreatorScenario` が 400 エラーで拒否するため、そもそも構造として作れない。

ユーザーの意図が実質的に「条件に関わらず全員に共通の処理を続けたい」である場合は、**その処理を該当する branch それぞれの中に複製して置く**（(a) の形を複数の branch に対して行う）。一部の対象を早期終了させたい（そちらの branch には複製しない）のか、全 branch に複製するのかは着手前にユーザーへ確認する。

## 机上デバッグチェックリスト（公開前レビューで必ず実行）

SKILL.md の Step 4 レビュー時（および「見直して」「懸念点は」「机上デバッグして」と言われた時）に、`getCreatorScenario` で取得した stages を以下の観点で点検する。問題があれば修正してから公開に進み、懸念点と修正内容を1〜3行でユーザーに報告する。

点検の順序は**構文 → 意味**（[content-schema.md](content-schema.md) の「検査の二層構造」）。まず content-schema の構造規律と 2〜6（ノード接続・日程・重複・埋め込み変数・参照整合性。いずれも対象者を選ばず JSON と設定だけで決まる構文側）で形が成立していることを確かめ、そのうえで 1 のコンテキスト適合表（△・※4・※5＝対象者の紐付け・メール保有・友だち状態で結果が変わる意味側）を見る。形が壊れている状態で意味を判定しない。

1. **トリガー×アクション整合**: 識別子の適合は [content-schema.md](content-schema.md) の「コンテキスト適合表」で判定し（△ があればユーザーに紐付け前提を確認。ヒアリングで未確認なら上記「単一ワークフローで閉じない要件」の 2 を今ここで行う）、識別子以外の相性は上記「トリガー × アクションの相性」参照
2. **ノード接続**（上記「ノード接続ルール」参照）
3. **日程の矛盾**: ローンチ型＝ローンチ日に間に合わないリマインド配信・販売終了後に届く CTA / リマインド系＝イベント開催日時を跨ぐ待機時間 / WAIT_TIME の計算結果が過去時刻になる設定（後続ステップが通知なく停止する。[content-schema.md](content-schema.md) の「WAIT_TIME」参照）。**`SERVICE_SCHEDULE_REMINDER` トリガーに複数の `WAIT_TIME` チェックポイントがぶら下がっていないか**（上記「予約リマインドは複数のトリガーに分ける」参照。1本のワークフローに複数のリマインドタイミングを詰め込むと、最初のトリガーより後に予約した人にそれ以降のリマインドが一通も届かない）
4. **メッセージ重複・抜け**: 同じ内容のメッセージが連続していないか、空文字メッセージが残っていないか
5. **埋め込み変数の不整合**: トリガーで提供されない変数を本文に使っていないか、`subject` に変数を使っていないか（[content-schema.md](content-schema.md) の「埋め込み変数」対応表が正）
6. **メッセージ内容の参照整合性**（上記「メッセージ内容の参照整合性」参照）: `urlActions[].url` と本文URLの完全一致、`messages` が空配列のまま残っていないか、**`urlActions` があるのに `isTrackingEnabled: false` になっていないか**（保存は通るが実行時に必ず失敗する。[content-schema.md](content-schema.md) の「TEXT の `urlActions`」）

## 代表ケース（骨子の参考）

ヒアリング結果に応じて取捨選択する。コピペせず、ユーザーの状況に合わせて再構成する。

- **ケースA ローンチ型**: タグ追加トリガー → ウェルカム配信 → 数日のナーチャリング配信（自己紹介・実績・価値観。1〜2日間隔）→ ウェビナー・個別相談へ誘導 → サービス案内・販売
- **ケースB リテンション型**: プラン・サービス申込トリガー → お礼＋当日案内 → 開講前日リマインド → 開講翌日フォロー → 終了後アンケート
- **ケースC セグメント型**: タグ付与トリガー → CONDITION（タグ・視聴履歴等）で分岐 → 該当セグメントだけに限定オファー配信（片方 branch 空の早期終了を活用）

配信間隔の目安（ユーザーに希望が無いと言われたら提示する一般値）:

- ローンチ型ナーチャリング: 1日後 → 3日後 → 5日後 → 7日後 のように1〜2日間隔
- リマインダー: 前日 / 当日1時間前 / 直前 の組み合わせ。**`SERVICE_SCHEDULE_REMINDER` を使う場合はタイミングごとに別ワークフローにする**（上記「予約リマインドは複数のトリガーに分ける」参照）
- リテンション: 申込直後 → 開講前日 → 開講翌日 → 終了1週間後
