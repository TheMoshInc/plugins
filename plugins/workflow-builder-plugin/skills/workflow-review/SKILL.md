# MOSH ワークフローレビュー

## Overview

**ワークフローが「意図通りに組めているか」を点検し、設定ミスの疑いを洗い出す読み取り専用スキル。** BigQuery は使わない（MCP ツールだけで完結する）。

主役は**レイヤー0＝構造レビュー**。`getCreatorScenario` が返す構造には条件分岐の `matchValue` と各分岐で実行される子ステージがそのまま入っているため、**実行データが1件も無くても「true なら何が起きるか / false なら何が起きるか」を確定できる**。したがって公開前の下書きワークフローでもレビューが成立する。公開済みで実績があれば、レイヤー1で実測を重ねる。

| レイヤー | 使うもの | 分かること | 使える状態 |
|---|---|---|---|
| **0. 構造レビュー**（主軸・必須） | `getCreatorScenario` ＋ 一覧系ツール（タグ・流入経路・LINE公式アカウント・オートウェビナー）＋ テナント横断の裏取りが要るときはワークフロー全件と一斉配信の検索・詳細（`postCreatorContactMessages*Search` / `getCreatorContactMessages*`） | 構造だけで分かる誤設定（タグの供給元が無い・付与前に判定している・分岐が機能していない・参照先の取り違え・実績上リスクの高い組み合わせ・テナント内に紐付けの入口や専用トリガーのワークフローが無い・予約リマインドの単一トリガー化・埋め込み変数の使用条件違反） | **いつでも**（下書き `INACTIVE` / 公開済み `ACTIVE` を問わない） |
| **1. 実績の重ね合わせ**（あれば実施） | ＋ `getCreatorScenariosExecutions` | 実際に動いた結果とのズレ（未発火・特定ステージの失敗・分岐の偏り） | 公開して稼働実績があるときのみ |

> **`workflow-builder` との役割分担**: builder は**ワークフロー単体の構造が仕様として妥当か**（ノード接続・日程の矛盾・トリガー×アクション整合）の可否判定が正本で、修正・公開も担当。本スキルが見るのは**それ以外**——①複数ワークフロー横断の整合（タグの供給元・受け皿・ループ）②同一ワークフロー内の順序の整合（付与前に判定していないか）③参照先が意図通りか（ID を名前に直して確認）④母集団実績から見たリスクの高さ⑤埋め込み変数の使用可否（S-11。判定材料は builder の content-schema.md からの複製 [references/embedded-variables.md](references/embedded-variables.md) を自スキルで持ち、builder への確認待ちにせず自己完結で判定する）。**本スキルは一切の書き込み操作（`patch*` / `post*`）を行わない。**

## When to use

- 作りかけ・公開前のワークフローを「公開して大丈夫か」見てほしいとき
- 既存ワークフローの定期点検・健康診断を頼まれたとき
- 公開済みワークフローの動作が疑わしいとき（「発火しない」「届いていない」「分岐が効かない」）
- 複数ワークフローをタグで連携させていて、途中で人が消える原因を知りたいとき
- 他人（クリエイター）が作ったワークフローの意図と実装のズレを洗い出したいとき

## When NOT to use

- ワークフローの新規作成・編集・公開・複製 → `workflow-builder`
- 「構造そのものが仕様として妥当か」の可否判定（ノード接続・日程の矛盾・トリガー×アクションの構造的整合）→ `workflow-builder` の机上デバッグ（必須ルール D）。埋め込み変数の使用可否は S-11 として本スキル側で判定する（builder への丸投げではない）
- ワークフロー機能全体の採用率・ファネル・クリエイター数の定量分析（本スキルは**個別ワークフローの正しさ**が対象）
- LP・リッチメニュー・一斉配信など他ドメイン → 各ドメインスキル

## Workflow

基本フロー: **対象の特定 → レイヤー0（構造レビュー・必須） → レイヤー1（実績があれば） → レポート**。読み取りのみなので人ゲートは不要だが、**推測を断定として書かない**（根拠なき原因断定は禁止。§「ユーザーへの提示・コミュニケーション規約」）。

### 1. 対象の特定と状態の確認

1. 対象ワークフローを特定する。ID が分からなければ `getCreatorScenarios` で一覧を取得し、名前で選んでもらう（`creatorLineChannelId` は生 ID で出さない — 提示規約 §2）
2. **ユーザーの意図**を1〜2問で聞く（「このワークフローで最終的に何をしたいか」「誰に**いつ**何を届けるつもりか」）。構造レビューの指摘はすべて「意図と実装のズレ」なので、意図が分からないと `要確認` を出す判断ができない。「いつ」は S-9b の適用判断に使う——「申し込んだらすぐ」「タグが付いたらいつでも」のような**即時性・タイミング不問**の言葉が出たら控えておく
3. `lifecycle` を確認する。`INACTIVE`（下書き・停止中）ならレイヤー0のみ、`ACTIVE`（稼働中）ならレイヤー1も実施する

### 2. レイヤー0: 構造レビュー（必須）

[references/data-model.md](references/data-model.md) の「構造（`getCreatorScenario`）の読み方」で分岐・親子関係の読み方を確認してから着手する。

1. `getCreatorScenario` で構造を取得する
2. **構造を日本語のフローに書き起こす**（分岐は「◯◯に当てはまる人 → …／当てはまらない人 → …」と両側とも書く。`stages: []` の側は「そこで終わり」）。ここでユーザーの意図とのズレが大半見つかる
3. [references/mistake-patterns.md](references/mistake-patterns.md) の検査カタログ **S-1〜S-11** を適用する。順序は**まず構文**（対象者を選ばず JSON とテナント設定だけで決まるもの＝S-2 / S-3 / S-8 / S-10 / S-11、および S-4 の参照先の消失・流入経路のチャンネル不一致、S-7 の公開状態・循環・自己ループ）**→ 次に意味**（対象者の紐付け・メール保有・友だち状態で結果が変わるもの＝S-1 / S-5 / S-6、および S-4 のリッチメニューのチャンネル不一致、S-7 の供給元無し。S-5 では [builder の content-schema.md](../workflow-builder/references/content-schema.md) の「コンテキスト適合表」を引く）**→ 最後にテナント横断の裏取り**（S-9。S-5 で適合表の △ を見つけたときは S-9a、`CONDITION(SERVICE_APPLICATION_STATUS)` / `CONDITION(CONTACT_TAG)` があり Step 1-2 の意図に即時性・タイミング不問が含まれるときは S-9b。いずれも S-7 の全件巡回に相乗りし、意味側の `要確認` を和らげるか `要修正` に確定させる）。形が壊れていれば意味の指摘は保留して builder に引き継ぐ。参照 ID を名前に直す一覧系ツールの使い分けも同ファイルに記載

### 3. レイヤー1: 実績の重ね合わせ（公開済みで実績があるときのみ）

1. `getCreatorScenariosExecutions` で実行実績を取得する
   - **404 は「一度も稼働していない」の意味**。エラー扱いせず、レイヤー0の結果だけでレポートを完成させる（[§エラーが返ったとき](#エラーが返ったとき)）
2. **最後に公開（稼働ON）した日**をユーザーに確認する。実績は**最新の稼働スナップショット1件分しか集計されない**ため、編集して再公開した直後は 0 件に見える（[references/data-model.md](references/data-model.md) の「最新スナップショット制約」）。ここを確認せずに「発火していません」と報告するのが最大の誤診断。分からないと言われたら「観測期間は推定」と明記して進める
3. [references/review-checks.md](references/review-checks.md) の検査カタログ **L1-1〜L1-5** を適用する

### 4. レポート

[references/review-checks.md](references/review-checks.md) の「判定の付け方」と「レポート構成」に従って出力する。完成形は構造レビューのみなら [examples/structure-review-report.md](examples/structure-review-report.md)、実績ありなら [examples/review-report.md](examples/review-report.md) を見本にする。

## 必須ルール

### A. 構造から言えるのは「意図とのズレの疑い」まで

構造レビューの指摘は、**ユーザーの意図を聞かずに `要修正` と断定しない**。「手動でタグを付けている」「該当者がごく少数で正常」など、正常な運用として説明がつくパターンが必ずある。例外は「運用では救えないと構造から確定できるもの」だけで、詳細な理由・S-9の扱いは [references/mistake-patterns.md](references/mistake-patterns.md) 冒頭の規定が正本。**下記の例外リストはSKILL.md本体にも意図的に直接記載している**（references側だけの記載では読み込まれずに判断を誤った実例があったため。二重記載は正本一本化の例外として許容する）。

**例外に該当する検査（S-2 / S-3 / S-4 / S-7 / S-8 / S-10 / S-11、およびS-9で裏取りが「無し」と確定したもの）は、意図を聞かずに断定してよい。** 特に **S-7「稼働中の上流に対して、そのタグで起動する下流が下書き・停止中」は、「まだ公開する予定が無いだけかもしれない」という留保をつけて `要確認` に格下げしない**。下流が未公開であるという事実そのものが「今は誰も進めない」という確定した結果であり、将来公開する意図の有無はこの結果を変えない。「要修正」と言い切った上で、必要なら「意図的に一時停止中であれば無視してよいが、公開する意図があるなら誰も進めていない」と付け加える。

### B. 実績が少なければ「判定しない」（レイヤー1のみ）

稼働（最後の公開）から **7日未満**、または対象ステージの実行数が **20件未満**のとき、「0件だから壊れている」と断定しない。`要確認（観測不足）` として扱い、必要な観測期間を添える。

### C. `FAILED` は「条件に合わなかった」ではない

条件分岐で false 側になった人は `FAILED` にならない（CONDITION 自体は `COMPLETED` のまま、進む先が変わるだけ）。`FAILED` は「対象コンタクト／ゲストが実行時点で解決できなかった・配信が拒否された」という別種の異常。また `totalCount` は **COMPLETED + FAILED のみ**で待機中（SCHEDULED）を含まないため、WAIT_TIME 直後の件数の落差を「離脱」と読まない（[references/data-model.md](references/data-model.md)）。

### D. 構造の「仕様としての妥当性」判定は builder が正本（埋め込み変数を除く）

ノード接続（WAIT_TIME 終端・両 branch 空）・日程の矛盾・トリガー×アクションの可否は `workflow-builder` の机上デバッグチェックリストが正本。本スキルは兆候を見つけたら**指摘して「`workflow-builder` の机上デバッグで確認してください」と案内するだけ**にとどめ、判定基準を再実装・再掲しない。**唯一の例外が埋め込み変数**（S-11）: 判定材料（対応変数一覧と使用可否）を [references/embedded-variables.md](references/embedded-variables.md) として builder の content-schema.md から複製済みなので、本スキルは builder への確認待ちにせず自分で `要修正`/`要確認` を判定する。builder 側の対応表が更新されたときは embedded-variables.md も同期する。

### E. `serviceId` は「商品」経由で確認を試みるが、確認できないことも多い

`serviceId` は `getCreatorProducts` → 各商品の `getCreatorProductPlans` が返す `moshServiceId` と突き合わせれば実在確認・名称解決ができる**ことがある**（[references/mistake-patterns.md](references/mistake-patterns.md) の「前提: 参照IDを名前に直す」）。ただし「商品」として作られていない旧来のサービス（イベント・プライベートタイプ・予約）を指している場合はこの方法では見つからず、売上明細（`getCreatorPaymentSalesOrders` の `moshServiceIds` 絞り込み）で該当注文を探しても購入実績が無ければ空振りする（2026-09-03 実例で確認: 商品化されていないサービスIDはどちらの経路でも解決できない）。**見つからない＝削除されたとは断定せず、`ACTIVE`/`INACTIVE` を問わず `要確認` にとどめる**（判定の詳細は mistake-patterns.md の S-4 が正本）。見つからなかった場合は他の参照 ID と違い名前を出せないので、「このステップが対象にしているのは『どのプラン・サービス』ですか」とユーザーに直接確認する。

## ユーザーへの提示・コミュニケーション規約

このスキルの出力を読むのは MCP / JSON の専門知識を持たない人である前提で書く。

1. **JSON / ステータスコード / 内部表現を出力に出さない**。`handle`・`404`・`INACTIVE` などはユーザー向け文面に書かず、「◯通目のLINE配信」「一度も稼働していません」「下書きのまま（公開されていません）」と平易な日本語に翻訳する。ユーザーが「生データを見せて」と明示的に求めたときだけ出す
2. **参照 ID を生のまま出さない**。`contactTagId` はタグ名、`creatorLineChannelId` は LINE公式アカウント名、`inflowActionId` は流入経路名、`autoWebinarId` はオートウェビナー名に、一覧系ツールで変換して提示する（`null` は「未設定」）。`getCreatorScenariosExecutions` の trigger には表示名が同梱されているので引き直し不要（[references/data-model.md](references/data-model.md)）
3. **原因を断定しない**。言えるのは「構造がこうなっている」「この現象が起きている」まで。原因は「〜の可能性があります」「〜だとするとつじつまが合います」と仮説として書き、確認方法（ユーザーに聞くこと・見るべき画面）を添える
4. **ステージは番号と中身で呼ぶ**。「ステージ3」ではなく「3ステップ目（1日待機のあとのLINE配信）」

## よくあるミス

上のセクション・references でカバー済みの事項は再掲しない。ここは他セクションでカバーされない落とし穴のみ（追記前に既存セクション・references でカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| 「実績が無いのでレビューできません」と返す | 実績が無くてもレイヤー0だけで大半の誤設定は洗い出せる。**本スキルの主用途は公開前レビュー**。実績の有無で断らない |
| `getCreatorScenarios` で一覧を1回取って全ワークフローを見たつもりになる | `limit` の既定は 20。ハンドオフ検査（S-7）と横断の裏取り（S-9）では `offset` でページングして全件取得する（[workflow-builder の references/mcp-tools.md](../workflow-builder/references/mcp-tools.md)） |
| 一斉配信の一覧（`postCreatorContactMessages*Search`）を見て「トラッキング付きの配信は無い」と結論づける | 一覧アイテムには `isTrackingEnabled` も本文も無い。トラッキング有無・URL の有無は `getCreatorContactMessagesEmail` / `getCreatorContactMessagesLine` で**詳細を開いて**初めて分かる（S-9a） |
| 構造を読み上げただけで「問題ありません」と返す | 構造レビューの価値は**意図とのズレの検出**。ユーザーの意図（Step 1-2）を聞かずに「問題なし」と結論づけない |
| 全ワークフローの失敗件数を合計して「メール配信は9割失敗する」と結論づける | 失敗件数は特定の単一ワークフローに極端に偏ることがある。**合計・全体平均で結論を出さず、必ずワークフロー単位／ステージ単位で見る**（[references/review-checks.md](references/review-checks.md) の「実績の一般的な傾向」） |

## エラーが返ったとき

| 症状 | 意味 | 対処 |
|---|---|---|
| `getCreatorScenariosExecutions` が 404 | 一度も稼働（公開）していない。実行実績がそもそも存在しない | エラー扱いしない。「まだ一度も稼働していないので、実績からの確認はできません」と1行添え、**レイヤー0の構造レビューだけでレポートを完成させる** |
| 公開状態は稼働中なのに 404 | トリガーステージが特定できていない可能性（構造不正） | `getCreatorScenario` で先頭ステージに trigger があるか確認し、無ければ構造の問題として `workflow-builder` に引き継ぐ |
| すべてのステージで `totalCount` が 0 | 未発火、または再公開直後のリセット | Step 3-2 の「最後に公開した日」を必ず確認してから判定する（必須ルール B） |
| 一覧系ツール（タグ・流入経路等）が空を返す | そのリソースが1件も無い | 構造が参照している ID は実在しないことになる。S-4 の「参照先の消失」として報告する |

## 未解決の制約・新規ツールリクエスト

MCP 側に以下が無いため、本スキルには原理的に埋められない穴がある。**ユーザー（PM）が MCP へ開発依頼するための記録**であり、本スキルでは実装しない。

1. **`getCreatorScenariosExecutions` の拡張**: 現状はステージごとに `totalCount` / `completedCount` / `failedCount` しか返らない。①`errorCode` / `errorDetailCode` 別の件数（＝「なぜ失敗したか」の原因診断。メール未登録／LINEブロック／配信上限の切り分けが今は不可能）②`scheduledCount` / `canceledCount`（待機中の人数が見えず、WAIT_TIME を跨ぐ落差を実数で説明できない）③各ステージエントリへの構造側 `handle` の同梱（実績と構造・分岐の対応づけが今は確定できない）——の3点が欲しい
2. **「商品」として作られていない旧来のサービス（イベント・プライベートタイプ・予約）を ID で検索・取得する MCP ツールが無い**: `serviceId` は「商品」化されていれば `getCreatorProducts`→`getCreatorProductPlans` の `moshServiceId` で解決できる（2026-09-02 確認）が、**商品化されていないサービスはこの方法では見つからない**。売上明細（`getCreatorPaymentSalesOrders` の `moshServiceIds` 絞り込み）で該当注文を探す代替も、購入実績が無ければ同様に空振りする（2026-09-03、実在するがどちらの経路でも解決できない `serviceId` の実例で確認）。`productId`/`productPlanId` を必要とせず `serviceId` 単体で商品名・プラン名（またはイベント等の名称）を引ける手段が無い
3. **紐付けの入口の有無を一覧だけで判別できない**（S-9a）: ①一斉配信の一覧アイテム（`contactEmailMessagesItem` / `contactLineMessagesItem`）に `isTrackingEnabled` と本文が無く、詳細を 1 件ずつ開く必要がある（「トラッキング有効かつ URL を含む配信済みメッセージ」を一覧側で絞れるフィルタが欲しい）②リッチメニューの一覧・詳細からゲートウェイリンク化の有無が読めない（要検証）
