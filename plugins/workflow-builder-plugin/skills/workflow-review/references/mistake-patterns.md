# レイヤー0 検査カタログ（S-1〜S-11）— 構造だけで分かる誤設定

Step 2（構造レビュー）で必ず読む。**すべて実行データ不要**で、下書き（`INACTIVE`）でも公開済みでも同じように使える。

各検査は **何を見る → 判定 → 疑う原因 → 確認の聞き方** の4点セット。判定に使う一般的な傾向は [review-checks.md](review-checks.md) の「実績の一般的な傾向」が正本（ここには再掲しない）。判定ラベル（`要修正` / `要確認` / `問題なし`）の定義も同ファイル。

見出し末尾の **（構文）／（意味）** は、その検査の判定が**個々の対象者（コンタクト／ゲスト）のデータに依存せず、ワークフローの JSON と同一テナントの設定状態（参照リソースの実在・他ワークフローの公開状態・タグ依存）だけで一律に決まる**もの（構文）か、対象者の属性・状態（メールアドレス保有・MOSH ID 紐付け・LINE 友だち状態）によって結果が変わるもの（意味）かを示す。API が保存・公開で弾くかどうかは分岐点ではない。1 つの検査に両方の性質のサブ項目が混在するものは **（構文・一部意味）** とし、サブ項目ごとに注記する。まず構文、次に意味の順で適用する（定義は [builder の content-schema.md](../../workflow-builder/references/content-schema.md) の「検査の二層構造」）。意味側のうち S-9 だけは**ワークフロー単体では判定できず、テナント内の他のワークフロー・一斉配信を横断して裏取りする**検査で、S-5（△）と S-1/S-3 系の意図確認の結論を確定させるために最後に適用する。

> **構造から言えるのは「意図とのズレの疑い」まで**（SKILL.md 必須ルール A）。`要修正` を出してよいのは、**運用では救えないと構造から確定できるもの**——S-2（順序矛盾）／S-3（両 branch とも空）／S-4（参照先の消失・流入経路のチャンネル不一致）／S-7（稼働中の上流に対する下流未公開・ワークフロー間の循環・自己ループ）／S-8（メッセージ内容の参照整合性）／S-10（予約リマインドの単一トリガー WAIT_TIME チェーン）／S-11（埋め込み変数の使用条件違反）——と、**S-9 で裏取りが「無し」で確定したもの**（S-9a: テナント内に紐付けの入口が一つも無い／S-9b: 意図が確認済みなのに専用トリガーのワークフローが無い）だけ。前者はすべて**構文**側の検査（対象者を選ばず一律に決まるから確定できる）。S-9 は意味側だが、対象者ごとの不確かさ（紐付け済みか）を「テナント内に紐付けの経路そのものが無い」というテナント設定レベルの事実に置き換えられたときだけ確定扱いにする。構文側でも意図次第のもの（S-3 の片側空＋合流、S-4 の名前の食い違い）と、S-9 の裏取り前の意味側の検査はすべて `要確認` にとどめ、ユーザーへの質問で終える。

## 前提: 参照 ID を名前に直す

構造中の ID をそのままユーザーに見せない（SKILL.md 提示規約 §2）。一覧系ツールで名前に変換してから読み上げる。**この変換作業そのものが S-4 の実在確認を兼ねる**。

| 構造中のフィールド | 変換に使うツール | 得られる表示名 |
|---|---|---|
| `contactTagId` | `getCreatorContactTags` | タグ名 |
| `inflowActionId` | `getCreatorScenariosInflowActions` | 流入経路名（＋その流入経路が属する `creatorLineChannelId`） |
| `creatorLineChannelId` | `getCreatorLineChannels` | LINE公式アカウント名 |
| `autoWebinarId` | `getCreatorAutoWebinars` | オートウェビナー名 |
| `lineRichMenuId` | `getCreatorLineRichMenus` | リッチメニュー名 |
| `serviceId` | `getCreatorProducts` → 各商品を `getCreatorProductPlans` → プランの `moshServiceId` と突き合わせる（下記コラム）。**見つからなければ「商品化されていない旧サービス」の可能性があり、その場合は実在確認できない** | 商品名＋プラン名（見つかった場合のみ） |

> **`serviceId` は「商品」経由で実在確認できる場合とできない場合がある**。`serviceId` は `getCreatorProduct(s)` の商品ID・プランIDとは別の値だが、そのプラン・サービスが「商品」として作られていれば `getCreatorProductPlans` が返す各プランの `moshServiceId` フィールドと一致する（実例: ある商品のプランが持つ `moshServiceId` の値が、そのままワークフローの `conditionServiceApplicationStatus.serviceId` の値と一致する形で確認できた）。`getCreatorProducts`（`status`未指定で全件）を1回取得し、各商品について `getCreatorProductPlans(productId)` を呼んで `moshServiceId → 商品名+プラン名` の対応表を作ってから照合する。
>
> **ただし「商品」を作らずに旧来の「サービス」（イベント・プライベートタイプ・予約。[`product-catalog`](../../../.claude/skills/product-catalog/SKILL.md) の対象外領域）のまま運用しているクリエイターも多く、その `serviceId` はどの商品のプランにも現れない**（あるクリエイターへの確認で、対象のプラン・サービスは商品として作成していないとの回答が得られた実例があり、`getCreatorProductPlan` を正しい `productId` で呼んでも解決せず、`getCreatorProducts` 側にもそもそも対応する商品が無いケースを確認した）。**この場合は実在確認・名称解決の手段が無い**（§未解決の制約）。「商品一覧のどのプランにも見つからない」だけでは「削除された」とは断定できない——**未商品化のサービスである可能性を先に疑う**。件数が多いクリエイターでは呼び出し回数がかさむので、対象ワークフローが参照する `serviceId` が確定してから着手する（総当たりで先に作らない）。

各フィールドがどの `actionType` / `conditionType` に属するかの網羅表は [`workflow-builder` の references/content-schema.md](../../workflow-builder/references/content-schema.md) が正本。

## S-1. タグ条件が空振りする（条件に使うタグの供給元が無い）（意味）

- **見る**: `CONDITION(CONTACT_TAG)` の `conditionContactTag.contactTagId` と、同じタグを付与する `ADD_CONTACT_TAG` の所在（①同一ワークフロー内 ②S-7 で洗い出した他ワークフロー内）
- **判定**: どちらにも見当たらない → `要確認`。加えて `REMOVE_CONTACT_TAG` で消しているのに再付与が無いなら、より疑わしい
- **疑う原因**: ①手動運用のタグ（管理画面・一斉配信・LINEのボタン操作で付ける）なので正常 ②付けているつもりのタグと条件のタグが別物（名前が似ている・重複作成した）③タグを付ける側のワークフローをまだ作っていない
- **確認の聞き方**: 「この分岐は『◯◯』というタグが付いている人だけを分けています。このタグはどこで付く想定でしょうか（このワークフロー内では付けていません）」。手動運用だと分かれば `問題なし` に落とす
- **補足**: LINE配信のボタン（postback）でタグを付ける設計もある。`SEND_LINE_MESSAGE` の `postbackActions` に同じ `contactTagId` があれば供給元として数える

## S-2. タグを付ける前に、そのタグで判定している（順序矛盾）（構文）

- **見る**: 同一ワークフロー内で、`CONDITION(CONTACT_TAG)` と同じタグの `ADD_CONTACT_TAG` の**前後関係**（親子・配列順。判定方法は [data-model.md](data-model.md) の「親子・前後関係の読み方」）
- **判定**: 付与が条件より**下流**にある、または**別の分岐サブツリーの中**にあって条件ステージからは到達しない → `要修正`。判定時点でタグは必ず未付与なので、その分岐は構造上 100% false 側に倒れる
- **疑う原因**: 画面上は「上に置いたつもり」でも、分岐の中に入れると別ルートになる。分岐の中に足すか後ろに足すかの取り違え（builder の「分岐への追加位置」の (a)/(b) 混同）
- **確認の聞き方**: 意図を聞かずに断定してよいパターン。「『◯◯』タグを付けるのが分岐より後になっているため、この分岐は必ず『付いていない』側に進みます。順序の入れ替えが必要です」と伝え、修正は `workflow-builder` に引き継ぐ
- **同型の見落とし**: `REMOVE_CONTACT_TAG` の後で同じタグを条件にしている場合も同じく常に false になる

## S-3. 分岐が機能していない（構文）

`branches[]` の各要素は `matchValue`（true / false）と、その分岐で実行する `stages[]` を丸ごと持つ。`stages: []` は「その側は何もせず終わり」。

- **見る**: 両 branch の `stages` の中身、および CONDITION ステージの**次に来る同階層のステージ**（＝合流先。両側の人が最終的にここへ来る）
- **判定**:
  | 形 | 判定 | 意味 |
  |---|---|---|
  | 両 branch とも `stages: []` | `要修正` | 分岐する意味が無い。可否判定は builder が正本（必須ルール D）なので、指摘して引き継ぐ |
  | 両 branch の中身が実質同じ（同じ本文の配信） | `要確認` | 分けている意味が無い可能性 |
  | 片側が `stages: []` で、CONDITION の後に同階層のステージが続く | `要確認` | **「該当者はここで終わり」のつもりが、合流して全員に届く**。片側が空なこと自体は正常な設計（builder のノード接続ルール）なので、合流先の有無とセットでしか判定できない |
  | 片側が `stages: []` で、CONDITION の後に何も無い | `問題なし` | 「片方だけ処理して終わり」の正常な設計 |

- **合流構成は新規保存では作れない**: `patchCreatorScenario` は CONDITION がそれを含む stages 配列（トップレベル／branch 内とも）の最後の要素でない構成を 400 エラーで拒否するようになった（builder の [best-practices.md](../../workflow-builder/references/best-practices.md) の「ノード接続ルール」参照）。したがって上記の「CONDITION の後に同階層のステージが続く」形が見つかった場合、この制約が入る前に保存されたワークフロー（＝以後に一度も `patchCreatorScenario` で再保存されていないもの）であることを意味する。指摘には「この構成は現在の保存機能では新規に作れないため、いつ頃作られたワークフローか」を確認に含めてもよい
- **確認の聞き方**: 「条件に当てはまる人はここで終了させたいですか。それともこの後の配信は全員に届けますか」
- **ループ**: 分岐構造そのもの（branch のネスト）は木なので、構造上のループは起こらない。ただし**タグを起点にした自己再トリガー**（`CONTACT_TAG_ADDED` 起動のワークフローが自分の起動タグを外して付け直す）は構造の分岐ループとは別物で、同一ワークフロー内でも起こる — S-7 の「自己ループ」で見る。ワークフローをまたぐループも S-7

## S-4. 参照先が実在しない・取り違えている（構文・一部意味）

- **見る**: 前提の表で ID → 名前に変換した結果
- **判定**:
  - 一覧に**存在しない ID** → `要修正`（構文: テナントのリソース一覧だけで決まる）。保存時に検証される ID（タグ・流入経路・LINE公式アカウント・オートウェビナー・リッチメニュー）が実在しないのは、**保存後に削除された**ことを意味する（[builder の content-schema.md](../../workflow-builder/references/content-schema.md) の「INACTIVE 状態の PATCH 検証」）
  - 存在するが**名前が意図と食い違う** → `要確認`。実務ではこちらの方が多い。名前を読み上げて確認する（失敗の判定ではなく意図確認なので構文／意味の区分外）
  - `INFLOW_ACTION_CONVERTED` トリガーの流入経路が属する `creatorLineChannelId` と、ワークフロー最上位の `creatorLineChannelId` が**不一致** → `要修正`（構文: 両者の設定値だけで決まり、公開時に API が弾く。理由と正しい設定は builder の「トリガー × アクションの相性」が正本）
  - `LINK_LINE_RICH_MENU` の `lineRichMenuId` が属する `creatorLineChannelId`（`getCreatorLineRichMenus` のレスポンスに同梱）と、ワークフロー最上位の `creatorLineChannelId` が**不一致** → `要確認`（**意味**: 実行時は**リッチメニュー側**のアカウントの友だちかどうかで対象コンタクトを探すため、そのアカウントの友だちでもあるコンタクトだけ成功し、ワークフロー側のアカウントの友だちしかいない対象は失敗する。成否が対象者ごとに分かれる。builder の「トリガー × アクションの相性」と content-schema の適合表 ※5 参照）。INFLOW_ACTION_CONVERTED の不一致と違い対象者の友だち状態次第のため `要修正` にはせず、「このリッチメニューは別の LINE 公式アカウントのものですが、対象の方はそちらのアカウントも友だち追加していますか」と聞く
- **`serviceId` はまず前提の表の手順（商品一覧→各商品のプラン一覧→`moshServiceId`突き合わせ）で商品名・プラン名への変換を試みる**。見つかったら他の ID と同じく「このステップが見ているのは『◯◯（商品名）』の『△△（プラン名）』で合っていますか」と名前で確認する
  - **見つからなくても「削除された」「入力ミス」と断定しない**。`serviceId` は「商品」として作られていない**旧来のサービス（イベント・プライベートタイプ・予約）を指している場合、商品一覧のどのプランにも最初から現れない**。売上明細（`getCreatorPaymentSalesOrders` の `moshServiceIds` 絞り込み。`productId`/プランIDは不要）で該当注文を探しても、購入実績が無い・古すぎる期間に集中しているサービスは同様に空振りする。どちらの手を尽くしても見つからない場合は**実在確認不能**として一律 `要確認` にとどめ、稼働状態による判定の格上げはしない（公開時の検証は「サービス」テーブルに対して行われ、「商品」テーブルには存在しなくて当然のため、`ACTIVE` でも「商品化されていないだけ」を「削除された」と誤診断しない）
  - **確認の聞き方**: 「このステップが対象にしているのは『どのプラン・サービス』ですか。管理画面で照合していただけますか」と、ID を出さずに口頭で確認する（§未解決の制約）
- **確認の聞き方**: 「このワークフローは『◯◯（タグ名）』を見て分けています。この名前で合っていますか」と、ID ではなく名前で確認する

## S-5. トリガーとアクションの組み合わせがリスクの高い形になっている（意味）

構造だけで、母集団実績上「よく壊れる形」に該当するかを判定できる。**可否判定の正本は builder の [content-schema.md](../../workflow-builder/references/content-schema.md) の「コンテキスト適合表」（識別子の適合）と「トリガー × アクションの相性」（それ以外）**。ここでは実績数値を添えて優先度を示すだけで、ルールを再掲しない。

- **見る**: トリガー種別 × ワークフロー内に含まれるアクション種別
- **判定**: LINE友だち追加・タグ追加・流入経路CV 起点のワークフローに `SEND_EMAIL` が含まれる → `要確認`（公開前）／実績があって全滅していれば `要修正`（[review-checks.md](review-checks.md) の L1-5）
- **添える実績**: LINE友だち追加起点で `SEND_EMAIL` を使うと、メールアドレスを持たないコンタクトが大半を占めるテナントでは配信の大部分が失敗しうる。実測で単一ワークフローに失敗が極端に集中した例も確認されている。**最大級の失敗要因になりうる**ので、公開前に必ず伝える
- **確認の聞き方**: 「このワークフローはLINEの友だち追加から始まりますが、途中でメール配信があります。**対象の方はメールアドレスを登録していますか**（していない方には1通も届かず、その方はそこから先のステップにも進みません）」
- **同型（コンタクト起点 → MOSH 前提の条件）**: コンタクト起点のトリガーと、MOSHアカウント前提の条件（`SERVICE_APPLICATION_STATUS` / `BANK_TRANSFER_STATUS` / オートウェビナー系）の組み合わせも、アカウント未連携のコンタクトでは失敗する（[data-model.md](data-model.md) の原因コード辞書 `GUEST_NOT_FOUND`）。適合表では △。こちらも紐付けの入口の有無で確信度が動くので S-9a を適用する
- **逆方向（MOSH ゲスト起点 → コンタクトを要求するステップ）**: `SERVICE_APPLIED` / `SERVICE_SCHEDULE_REMINDER` / `INSTALLMENT_PAYMENT_FAILED` / `SUBSCRIPTION_PAYMENT_FAILED` 起点のワークフローに `SEND_LINE_MESSAGE` / `ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG` / `LINK_LINE_RICH_MENU` / `UNLINK_LINE_RICH_MENU` / `CONDITION(CONTACT_TAG)` が含まれる → `要確認`（公開前）／実績があって全滅していれば `要修正`。これらのトリガーは申込者・決済失敗者の MOSH ID しか供給せず、コンタクトは MOSH ID との紐付けから引くため、**紐付けの無いゲストには LINE 配信・タグ操作が 1 件も実行されず、後続ステップも打ち切られる**（原因コード辞書 `CONTACT_NOT_FOUND`。適合表では △、紐付けの成立条件は同表 ※3）。「申込のお礼を LINE で送る」「決済失敗者にタグを付ける」という自然な要望で最も起きやすい
  - **確認の聞き方**: 口頭確認の**前に S-9a でテナント内の紐付けの入口を探す**（ユーザーは「計測付きリンクをタップしてログインしたか」を正確には答えられないことが多く、入口の有無は MCP で裏取りできる）。裏取り結果を添えて「このワークフローはプラン・サービスの申込から始まりますが、途中で LINE 配信（またはタグ付け）があります。**申込者の方は、事前に LINE 配信やメールの計測付きリンクをタップして MOSH にログインしたことがありますか**（無い方には 1 通も届かず、そこから先のステップにも進みません）」と聞く。判定の確信度の調整（入口あり→和らげる／無し→`要修正` に格上げ）は S-9a。確認できなければ `SEND_EMAIL` への置き換え、または紐付けが先に発生する導線の設計を builder で検討してもらう

## S-6. 長い待機のあとに配信がある（意味）

- **見る**: `WAIT_TIME` の `actionAfterDays`（1ステージ最大30日。連続すればそれ以上）と、その下流の配信ステージ
- **判定**: 合計待機が長いほど、届く前に対象者が失われる（LINEブロック・コンタクト削除・LINE連携解除）。**それ自体は誤設定ではない**ので `問題なし` を基本とし、注意喚起として1行添える
- **添える実績**: LINE配信の失敗要因にブロックが実在することは母集団で確認できている。**ただし「待機日数と失敗率の相関」は未計測**なので、「長いほど増えます」と数値で断定しない
- **あわせて見る**: 待機の計算結果が過去時刻になる設定（後続が通知なく停止する）は builder の机上デバッグが正本。長期待機を見つけたら「日程の矛盾も builder で確認してください」と案内する

## S-7. ワークフロー間の受け渡し（ハンドオフ）（構文・一部意味）

対象ワークフローが `ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG` を含む、または `CONTACT_TAG_ADDED` で起動する場合は**必ず実施する**。実行データ不要で、下書きのワークフローも検査対象に入る。

1. `getCreatorScenarios` で同一クリエイターの全ワークフローを取得する（`limit` 既定 20。`offset` でページングして全件。ページング仕様は [builder の references/mcp-tools.md](../../workflow-builder/references/mcp-tools.md)）
2. 各ワークフローを `getCreatorScenario` で開き、「付与するタグ」と「起動条件・分岐条件のタグ」の対応表を作る。**S-9 もこの 1〜2 で開いた全ワークフローをそのまま使う**ので、S-9 の適用条件に当たるときは同じ巡回で「トラッキング有効 URL を送るステージ」「先頭ステージの triggerType と参照 ID」も一緒に控えておく（二度巡回しない）
3. 見るべきこと:

| 形 | 判定 | 伝え方 |
|---|---|---|
| 対象が**稼働中**で、そのタグで起動する下流が**下書き・停止中**（`INACTIVE`） | `要修正` | 「◯◯でタグを付けた方は△△に進む設計ですが、△△が公開されていないため誰も進みません」。母集団でも最頻の連携ミスの一つ（具体的な発生率は運用組織側で実測して補う）。**この行は構文側（SKILL.md必須ルールAの例外）— 意図を聞かずに断定してよい。「まだ公開する予定が無いだけかもしれない」という留保をつけて`要確認`に格下げしない**（下流が未公開である事実そのものが「今は誰も進めない」という確定した結果であり、公開予定の有無は結果を変えない） |
| 対象も下流も**下書き**（これから公開する） | `要確認` | 誤設定ではない。「公開するときは△△を先に（または同時に）公開してください。上流だけ公開すると、その間に来た方は行き止まりになります」と**公開手順として**伝える |
| タグを付けているが、**そのタグで起動するワークフローが存在しない** | `要確認` | 分析用・手動運用のタグなら正常。「このタグは何に使う想定ですか」と聞く |
| A が付けるタグで B が起動し、B が付けるタグで A が起動する（**循環**） | `要修正` | 同じ人が無限に往復しうる。母集団でもごく稀なはずのパターンなので、見つけたら異常を疑う |
| 起動条件のタグに供給元が無い（受け側から見た S-1） | `要確認` | S-1 と同じ聞き方 |

- **構文／意味の内訳**: 表の上 4 行（下流未公開・両下書き・受け皿無し・循環）と下記の自己ループは、各ワークフローの公開状態とタグ依存グラフ（テナントの設定状態）だけで対象者を選ばず決まるので**構文**。最後の行「供給元が無い」だけは、手動運用（管理画面・一斉配信・LINE ボタン操作）でタグが付く可能性が JSON にもテナント設定にも現れず構造から確定できないため、S-1 と同じ**意味**側の `要確認` にとどめる
- **公開済みの上流に対する補足**: すでに行き止まりになった人は、下流を公開しても**遡って進まない**。この事実を必ず添える（一斉配信での救済を案内する）
- **循環は2ワークフロー間の相互参照に限らない**。「タグを付ける→起動する」の関係を有向グラフとして見ると、A→B→C→A のように3つ以上を経由する循環も同じ考え方（グラフの閉路検出）で見つかる。2つずつのペアだけを見て「循環なし」と結論づけない
- **自己ループ（同一ワークフロー内での自己再トリガー）も同じ観点で見る**: 対象ワークフローが `CONTACT_TAG_ADDED` で起動し、かつワークフロー内で同じタグを `REMOVE_CONTACT_TAG` → `ADD_CONTACT_TAG` の順で操作している → `要修正`。対象コンタクトに対して自分自身を再トリガーし、無限に往復しうる（A=B の特殊形として上と同じ手順で検出できる）

## S-8. メッセージ内容の参照整合性（構文）

`SEND_LINE_MESSAGE` のメッセージ本文とタップ操作の対応関係は、構造だけで「発火しうるか」を機械的に確定できる。実行データ不要。

- **見る**: 各 `messages[].urlActions[].url` と、同じメッセージの `text` 本文中に含まれるURL文字列
- **判定**: `urlActions.url` が本文中のどのURLとも**一字一句完全一致しない** → `要修正`。タップしても対応する `postbackActions`（タグ付与・削除）が発火しない、構造から確定できる不具合（[content-schema.md](../../workflow-builder/references/content-schema.md) の「TEXT の `urlActions`」が正本）
- **疑う原因**: 本文を後から編集してURLを変えたときに `urlActions.url` の更新を忘れた／末尾スラッシュやトラッキングパラメータ（`?utm_...`）の有無が本文とズレている
- **確認の聞き方**: 意図を聞かずに断定してよいパターン。「本文中のこのURLと、タップ時にタグを操作する設定のURLが一致していないため、タップしてもタグは変わりません」と伝え、修正は `workflow-builder` に引き継ぐ
- **もう一つの検査**: `SEND_LINE_MESSAGE` ステージの `messages` が**空配列** → `要修正`。稼働させても何も配信されない（[content-schema.md](../../workflow-builder/references/content-schema.md)）
- **三つ目の検査**: `TEXT` メッセージに `urlActions` が 1 件以上あるのに **`isTrackingEnabled: false`** → `要修正`。保存・公開は通るが、実行時に「トラッキング無効ではアクションは使用できません」で必ず失敗し、そのコンタクトの後続ステップも止まる（[content-schema.md](../../workflow-builder/references/content-schema.md) の「TEXT の `urlActions`」が正本）。「タップ計測はしたくないがタグは付けたい」という意図で OFF にされていることが多いので、「タグ付けの仕組み自体が計測付きリンクを前提にしています」と説明して ON にしてもらう

## S-9. クロスワークフロー充足性（テナント横断の裏取り）（意味）

単一ワークフローの構造だけでは「失敗しうる」「意図と合わないかもしれない」までしか言えない指摘のうち、**テナント内の他のワークフロー・コンタクト向けメッセージ配信（一斉配信）を横断すれば白黒を付けられる**ものを扱う。巡回は S-7 の手順 1〜2 に相乗りする（同じ全件取得を二度しない）。実行データ不要で、下書きのワークフローも対象に入る。

適用条件（どちらかに当たるときだけ実施する）:

- **S-9a**: S-5 で適合表の △（MOSH ゲスト起点 × コンタクト要求ステップ、またはコンタクト起点 × MOSH 前提の CONDITION）を見つけた
- **S-9b**: 対象ワークフローが `CONDITION(SERVICE_APPLICATION_STATUS)` または `CONDITION(CONTACT_TAG)` を含み、かつ Step 1-2 で聞いた意図に**即時性**（「申し込んだらすぐ」「申込直後に」）または**タイミング不問**（「タグが付いたらいつでも」「付いた時点で」）の要素がある

### S-9a. 紐付けインフラの裏取り（△ の確信度を動かす）

△ が失敗するのは「対象者にコンタクト↔MOSH ID の紐付けが無い」ときで、紐付けが成立する入口は**トラッキング有効な URL をコンタクトがタップして MOSH にログインすること**（[content-schema.md](../../workflow-builder/references/content-schema.md) の適合表 ※3 が正本。一斉配信も同じ経路で紐付く）。入口がテナント内に一つも無ければ、対象者が誰であっても紐付けは成立しえない＝ほぼ全員が失敗する。

- **見る**（「入口」と数えるもの。※3 の種別ごとのトグル有無に従う）:

  | 場所 | 入口と数える条件 | 確認手段 |
  |---|---|---|
  | 他のワークフローの `SEND_LINE_MESSAGE` | `TEXT` で `isTrackingEnabled: true` かつ本文に URL がある／`CAROUSEL`・`IMAGE_CAROUSEL`・`RICH_MESSAGE` にタップ遷移先 URL（`buttonUrl` / `url` / cell の `url`）がある（こちらはトグル無しで常にトラッキング） | S-7 の巡回で開いた `getCreatorScenario` |
  | 他のワークフローの `SEND_EMAIL` | `isTrackingEnabled: true` かつ本文に URL がある | 同上 |
  | 一斉配信（メール） | 詳細の `isTrackingEnabled: true` かつ `body` に URL がある | `postCreatorContactMessagesEmailSearch` で一覧 → `getCreatorContactMessagesEmail` で詳細 |
  | 一斉配信（LINE） | 詳細の `contents[]` に、`type: "text"` で `isTrackingEnabled: true` かつ `text` に URL があるもの、または `carousel` / `image_carousel` / `rich_message` でタップ遷移先 URL があるもの | `postCreatorContactMessagesLineSearch` で一覧 → `getCreatorContactMessagesLine` で詳細 |
  | リッチメニューのゲートウェイリンク | ※3 上は入口だが、**MCP の一覧・詳細ではゲートウェイリンク化の有無を判別できない**（要検証） | ユーザーに 1 問だけ聞く |

  - 一斉配信の**一覧レスポンスには `isTrackingEnabled` も本文も含まれない**（一覧アイテムのスキーマ `contactEmailMessagesItem` / `contactLineMessagesItem` が持つのは `taskName` / `isSent` / `isDraft` / `sentCount` / `scheduledAt` / `failureReason` のみ。確認日 2026-09-02）。トラッキング有無・URL の有無は**詳細を 1 件ずつ開いて**初めて分かる。呼び出し回数を抑えるため、①一覧は `sort: "scheduledAtDesc"`・`limit: 100` で取り、②`isSent: true` かつ `isDraft: false`（配信済み）だけを候補にし、③新しいものから詳細を開いて**1 件見つかった時点で打ち切る**（入口が 1 つあれば「仕組みはある」と言える）。`keyword` に `"http"` を入れると本文に URL を含む配信に絞れる（メール＝件名・本文、LINE＝本文・代替テキスト・カルーセル文言が検索対象。LINE のカルーセル／リッチメッセージのタップ先 URL が検索対象文言に含まれるかは未検証なので、絞り込みで 0 件でも全件を開き直す）
  - ワークフロー側は**稼働実績**まで見る: `lifecycle: ACTIVE` で当該ステージの `getCreatorScenariosExecutions` の `completedCount` が 1 以上なら「配信実績のある入口」、`INACTIVE` や実績 0 なら「入口の候補はあるが動いていない」と区別する（404 は未稼働。SKILL.md「エラーが返ったとき」）
  - **ワークフロー側にも同じ「1件見つかったら打ち切る」を適用する**（早期終了を明記しないと、入口が1本目で見つかった後もテナント内の残りを律儀に全部開いてしまい、レビュー1件で数十回規模の無駄な `getCreatorScenario` 呼び出しが発生しうる）。対象ワークフローが **S-7 の適用条件（`ADD_CONTACT_TAG`/`REMOVE_CONTACT_TAG` を含む、または `CONTACT_TAG_ADDED` で起動）に当たらない場合、S-7 の全件巡回に相乗りする前提が無いため、S-9a 単独の目的でテナント全件を開く必要は無い**。`lifecycle: ACTIVE` のものから優先して開き、**「配信実績のある入口」が1件見つかった時点で打ち切ってよい**（S-7 が適用される＝タグ授受のグラフ構築のためにどのみち全件を開く必要がある場合は、そのついでに入口を探せばよく、S-9a のためだけに追加で巡回範囲を広げない）
- **判定**:

  | 裏取り結果 | 判定 | 伝え方 |
  |---|---|---|
  | 配信実績のある入口が 1 つ以上ある（稼働中ワークフローの実績あり／配信済みの一斉配信） | `要確認`（S-5 のまま。確信度を**和らげる**） | 「紐付けの入口はあります（例:『◯◯』の LINE 配信の計測付きリンク）。ただし、そのリンクをタップして MOSH にログインした方に限られるため、申込者全員に届く保証はありません。届かなかった方は、そこから先のステップにも進みません」 |
  | 入口の候補はあるが動いていない（下書き・停止中のワークフロー、下書き・未配信の一斉配信のみ） | `要確認`（入口「無し」に準じて扱う） | 「紐付けの入口になりうる配信（『◯◯』）はありますが、まだ配信されていません。これを先に配信・公開しないと、申込者への LINE 配信はほぼ全員に対して実行されません」 |
  | どこにも無い | **`要修正` に格上げ** | 「LINE 配信やメールの計測付きリンクを送っている場所が、他のワークフロー・一斉配信のどこにも見当たりません。この状態では申込者と LINE を結び付ける手段が無く、この LINE 配信（タグ付け）は申込者のほぼ全員に対して実行されず、そこから先のステップも進みません」。次の一手は `SEND_EMAIL` への置き換え、または紐付けが先に発生する導線（トラッキング有効 URL を含む配信）の設計で、いずれも builder に引き継ぐ |

  - `要修正` に格上げするときも、MCP で見えない入口が 1 つ残る（リッチメニューのゲートウェイリンク）ので、**「LINE のリッチメニューから MOSH のページに飛ばすボタンはありますか」を 1 問だけ添える**。「ある」と答えられたら上の 1 行目に戻す
  - 入口があっても**紐付けは事後に遡らない**（※3）。入口の配信より前に申し込んだ人は失敗したままなので、「この配信より前の申込者には効きません」を必ず添える
- **疑う原因**: LINE 友だち向けの配信を全部トラッキング OFF で運用している／URL を含む配信をそもそもしていない（テキストだけの配信）／紐付けの仕組み自体を知らずに「申込のお礼を LINE で」を組んでいる

### S-9b. 「直後・いつでも」の専用トリガー充足性

`CONDITION` は到達時点の 1 回だけ評価される（[content-schema.md](../../workflow-builder/references/content-schema.md) の「CONDITION は一時点の判定」が正本。専用トリガーの対応表も同節）。「申し込んだらすぐ LINE を送りたい」「タグが付いたらいつでも反応したい」という意図は、この判定を使うワークフローを**どう直しても実現できず**、その出来事を起点にする別ワークフローの有無で決まる。

- **見る**: S-7 の巡回で開いた全ワークフローの**先頭ステージの trigger**に、対象の CONDITION と同じリソースを指す専用トリガーがあるか
  - `CONDITION(SERVICE_APPLICATION_STATUS)` → `triggerType: SERVICE_APPLIED` かつ `serviceAppliedTrigger.serviceId` が条件の `serviceId` と一致（文字列比較。名前解決はできないが同一 ID なら同一プラン・サービス）。`paymentMethod` が絞られていれば「その支払い方法の申込だけ」と注記する
  - `CONDITION(CONTACT_TAG)` → `triggerType: CONTACT_TAG_ADDED` かつ `contactTagAdded.contactTagId` が条件の `contactTagId` と一致。`CONTACT_TAG_ADDED` は新規付与のときだけ発火するので、「既に付いている人に付け直しても反応しない」も添える
  - **この 2 組以外には適用しない**。`BANK_TRANSFER_STATUS` / `AUTO_WEBINAR_*` には専用トリガーが存在しないので、即時反応の要望が出ても「該当するトリガーが無い」事実だけを伝える（代用トリガーを捏造しない）
- **判定**:

  | 裏取り結果 | 判定 | 伝え方 |
  |---|---|---|
  | 一致する専用トリガーのワークフローが**稼働中**（`ACTIVE`） | `問題なし` | 「申込直後の LINE は『◯◯』という別のワークフローが担っています。このワークフローの分岐は『◯日後の時点で申し込んでいた方』を拾う役割で、両方で成立しています」 |
  | 存在するが**下書き・停止中**（`INACTIVE`） | `要修正`（S-7 の下流未公開と同型） | 「申込直後に反応するワークフロー『◯◯』はありますが公開されていないため、今は誰にも届きません」 |
  | 存在しない・`serviceId` / `contactTagId` が別物 | 意図が確認済みなら `要修正`、未確認なら `要確認` | 「『申し込んだらすぐ』は、このワークフローの分岐では実現できません。分岐は◯日待ったあとの一時点で『申し込み済みか』を見るだけで、申込の瞬間には何も起きず、その後に申し込んだ方も拾えません。すぐ届けるには『プラン・サービス申込』から始まる別のワークフローが必要ですが、今は見当たりません」。直すのはこのワークフローではなく**新設**なので builder に引き継ぐ |

- **確認の聞き方**（意図に即時性・タイミング不問が含まれるか曖昧なとき）:
  - 申込: 「申し込んだ方への LINE は、**申込直後**に届けたいですか。それとも **◯日後の時点で申し込んでいた方**に届けば十分ですか。今の構成では後者しか実現できません。前者なら『プラン・サービス申込』から始まる別のワークフローが必要です」
  - タグ: 「『◯◯』タグが付いた方には、**付いた時点ですぐ**反応したいですか。今の構成では ◯日待った時点で付いていた方しか拾えず、その後に付いた方は拾えません。すぐ反応するには『タグ追加』から始まる別のワークフローが必要です」
- **疑う原因**: 「申込者にも LINE を送りたい」を、既にある LINE 友だち追加起点のワークフローの分岐で済ませようとした／「タグが付いたら」を分岐と起動条件で混同している

## S-10. 予約リマインドが単一トリガーからの WAIT_TIME チェーンになっている（構文）

`SERVICE_SCHEDULE_REMINDER` は、1件の予約に対して起点の時刻（`beforeDays`/`hours`/`minutes` が指す、開催日時からの相対時刻）に到達した瞬間だけ**1回**評価される。予約された時点でその時刻がすでに過去なら、その予約に対して二度と発火しない。`WAIT_TIME` はこの1回きりの発火を後ろへずらすだけで、新しい独立した評価ポイントを作らない（[builder の content-schema.md](../../workflow-builder/references/content-schema.md) の `SERVICE_SCHEDULE_REMINDER` 行、および [best-practices.md](../../workflow-builder/references/best-practices.md) の「予約リマインドは複数のトリガーに分ける」が正本）。

- **見る**: 対象ワークフローの先頭トリガーが `SERVICE_SCHEDULE_REMINDER`。そのあとに `WAIT_TIME` を挟んで、複数の `SEND_LINE_MESSAGE` / `SEND_EMAIL` ステージ（＝「開催◯日前」「◯時間前」「◯分前」のような、開催日時までの残り時間が異なる複数のリマインドタイミング）が続いていないか
- **判定**: 該当する → `要修正`。**起点のトリガーが指す時刻より後に予約した対象には、`WAIT_TIME` チェーン内のメッセージが（最初の1通も含めて）一通も届かない**——起点のトリガー自体がその対象に対して発火しないため。対象者のデータに関わらず構造だけで確定できる（他のワークフロー・実行実績を見なくてもワークフロー単体の JSON だけで判定可能）
- **疑う原因**: 「開催3日前・前日・3時間前・15分前」のように複数タイミングでリマインドしたい意図を、`SERVICE_APPLIED`（申込という単一の出来事に1回発火すればよいトリガー）と同じ感覚で `WAIT_TIME` チェーンに落とし込んでしまった
- **確認の聞き方**: 意図を聞かずに断定してよいパターン。「このワークフローは開催◯日前のトリガーを起点に、以降のリマインドを `WAIT_TIME` で繋いでいます。◯日前を過ぎてから予約した方には、このワークフロー内のリマインドが一通も届きません。特に直前（◯分前）のリマインドが失われるため参加率に影響します。タイミングごとに独立したワークフローへ分ける必要があります」と伝え、修正（分割）は `workflow-builder` に引き継ぐ
- **見分け方の注意**: `SERVICE_SCHEDULE_REMINDER` トリガーの直後に**1通だけ**送って終わる構成（`WAIT_TIME` を挟まない、または `WAIT_TIME` の後にメッセージが1つだけで終わる）は対象外（`問題なし`）。問題になるのは、その後さらに `WAIT_TIME` を挟んで「別タイミングのリマインド」を表す配信が複数続く形だけ
- **母集団実績**: 未計測（[review-checks.md](review-checks.md) に追加予定）。件数の裏取りができるまでは実測を添えず、構造だけで `要修正` と判定してよい（このパターンは対象者を問わず確実に発生するため実績値を待つ必要が無い）

## S-11. 埋め込み変数が使用条件を満たさない組み合わせで使われている（構文）

`{{variable_name}}` 形式の埋め込み変数は、対応する5つの変数名だけが存在し、それぞれ使える trigger × action の組み合わせが決まっている。条件を満たさない場合はエラーにならず**空文字**（対応表にある5変数）または**プレースホルダ文字列がそのまま残る**（対応表に無い変数名）という無言の失敗になる。詳細対応表は [embedded-variables.md](embedded-variables.md)（`workflow-builder` の content-schema.md からの複製。正本は builder 側）。

- **見る**: 各 stage の `action` 内の `sendEmail.message` / `sendLineMessage.messages[].text` / `sendEmail.subject` から `{{...}}` パターンを全て抽出し、そのステージが従う先頭 stage の `triggerType` と、そのステージ自身の `actionType` の組み合わせで embedded-variables.md の対応表と照合する
- **判定**:
  | 形 | 判定 |
  |---|---|
  | 変数名が対応表の5つに無い（例: `{{reservation_datetime}}` のような創作された変数名） | `要修正` |
  | `sendEmail.subject`（件名）に `{{...}}` がある | `要修正`（件名では条件に関わらず一律に解決されない） |
  | 変数名は対応表にあるが、trigger × action の組み合わせが「使える条件」列を満たさない（例: `SEND_EMAIL` の本文に `{{line_name}}`、`CONTACT_TAG_ADDED` 起点の配信に `{{service_name}}`） | `要修正` |
  | `reservation_time_range` / `zoom_url` を `SERVICE_APPLIED` 起点で使っており、対象プラン・サービスの `serviceType`（予約/個別か否か）や `locationType`・Zoom連携有無が未確認 | `要確認`（プラン・サービス側の設定に依存するため trigger × action だけでは断定できない） |
- **疑う原因**: Notion 等の外部ドキュメントから文面を転記する際に存在しない変数名を創作した／件名に変数を入れてしまった／トリガーを変更したのに本文の変数を直し忘れた
- **確認の聞き方**: `要修正` の行は意図を聞かずに断定してよいパターン。「本文のこの `{{◯◯}}` は、このトリガー・アクションの組み合わせでは値が入らず、空欄（またはそのままの文字列）で配信されます」と伝え、修正は `workflow-builder` に引き継ぐ。`要確認` の行は「このプラン・サービスは予約または個別タイプですか」のように対象プラン・サービスの種別を確認する
