# 実績検査カタログ（L1）・判定とレポート構成

このファイルは3つの役割を持つ。**判定の一般的な傾向と、判定・レポートの規約はすべてのレビューで読む**（構造レビューだけのときも）。L1 の検査は公開済みで実績があるときだけ読む。

- 実行データ不要の構造検査（S-1〜S-9）は [mistake-patterns.md](mistake-patterns.md) が正本
- 観測不足のときに判定を出さないルール（7日 / 20件）は SKILL.md 「必須ルール B」が正本。各検査では再掲しない

## 実績の一般的な傾向（実数値は非公開・失敗しやすさの相対順位で判定する）

以下は「業種的に普通か」を判断するための目安。**実測の絶対値（件数・率）は公開しない**が、判定に必要なのは絶対値ではなく**アクション種別間の相対的な失敗しやすさの順位**なので、それだけで判定できるように整理している。数値を計測・維持する運用負担も発生しない。

- **未発火はどのトリガーでもある程度は普通に起きる**。**未発火それ自体は異常の証拠にならない**。異常と言えるのは「同じ期間に上流の出来事（申込・友だち追加・タグ付与）が実際に起きているのに 0 件」のときだけ
- **アクション種別は、対象者解決の失敗しやすさに大きな差がある**。失敗しにくい順に並べると次の2グループに分かれる:
  - **グループ1（ほぼ失敗しないのが普通）**: `WAIT_TIME` ／ `CONDITION` ／ `SEND_EMAIL` ／ `SEND_LINE_MESSAGE`。対象者を確実に解決できる限り、対象者側の一時的な事情（LINEブロック等）以外で失敗する理由が無いため、**失敗はほぼ0件が普通**。ごく少数でも継続的に失敗が出ていたら、それだけで疑ってよい
  - **グループ2（構造的に失敗しやすい）**: `ADD_CONTACT_TAG` ／ `REMOVE_CONTACT_TAG`。対象コンタクトの解決に失敗しやすい構造的な理由があり、**グループ1よりはっきりと失敗率が高くても珍しくない**。多少〜中程度の失敗率があること自体は即異常ではないが、全滅（`failedCount == totalCount`）や大半が失敗している状態は必ず報告する
  - この2グループの差は「対象者を最初から解決できているか」に由来する：グループ1は多くの場合すでに解決済みの対象に配信・待機・分岐するだけだが、グループ2（とくに MOSH ゲスト起点でのタグ操作）は実行のたびにコンタクト解決を試み、紐付けが無ければ毎回失敗しうる（S-5 の△参照）
- **タグ条件（`CONTACT_TAG`）の分岐は「一度も true にならない」ケースが比較的よくある誤設定候補**（構造レビューでは S-1 / S-2 がその主因を先回りで検出する）。ただし「クリックした人だけ除外する」など true が数%で正常な設計も多い。**常に false = 即異常ではなく、ユーザーに「この分岐は誰も通っていないが意図通りか」を必ず問う**

## L1: 実績の重ね合わせ（公開済みで実績があるときのみ）

各検査は **何を見る → 判定条件 → 疑う原因 → 直し方** の4点セット。すべて `getCreatorScenariosExecutions` の値を、レイヤー0で確定した構造の上に重ねて読む。

### L1-1. トリガーが発火しているか

- **見る**: `steps[0]`（トリガーステージ）の `totalCount`
- **判定**: 0 件 かつ 稼働 7日以上 → `要確認`。上流の出来事が起きている確証がユーザーから得られたら `要修正`
- **疑う原因**: ①最後の公開が最近で実績がリセットされた ②トリガーの参照先が違う（S-4 で名前を確認する）③流入経路が属する LINE 公式アカウントとワークフローのアカウントが不一致（S-4）④単に対象イベントが発生していない ⑤`SERVICE_APPLIED` の `paymentMethod` で支払い方法を絞っていて、実際の申込の支払い方法と合わない（サブスクリプション型は常にクレジットカード扱いのため、銀行振込・現金を指定すると一度も発火しない） ⑥`CONTACT_TAG_ADDED` は**新規付与のときだけ**発火する — 既にタグが付いている人への再付与や、外部ツール移行時の一括付与では発火しない（いずれも [builder の content-schema.md](../../workflow-builder/references/content-schema.md) の trigger 表）
- **直し方**: まず「最後に公開した日」と「この期間に申込／友だち追加／タグ付与は実際にあったか」をユーザーに確認する。参照先の取り違えが疑われたら `workflow-builder` で設定を確認してもらう

### L1-2. 途中で完全に止まっていないか

- **見る**: 上流ステージの `completedCount` と、その直下ステージの `totalCount`
- **判定**: 上流 `completedCount` ≧ 20 なのに直下が 0 件 → `要修正`。ただし**間に WAIT_TIME がある場合は判定しない**（待機中は数えられない。SKILL.md 必須ルール C）
- **疑う原因**: 直前ステージが全員 FAILED で後続が打ち切られている（L1-3 とセットで見る）／条件分岐の片側に全員が倒れていて、こちら側には誰も来ていない（L1-4）
- **直し方**: 原因を L1-3 / L1-4 で特定してからでないと直せない。単独では報告のみ

### L1-3. 特定ステージだけ失敗が突出していないか

- **見る**: 各ステージの `failedCount / totalCount` とアクション種別
- **判定**: `failedCount` が 5件以上ある前提で、上記「グループ1／グループ2」で扱いを変える
  - `failedCount == totalCount`（全滅）→ `要修正`（アクション種別を問わず最優先）
  - **グループ1**（`WAIT_TIME` / `CONDITION` / `SEND_EMAIL` / `SEND_LINE_MESSAGE`）: 失敗はほぼ0件が普通のグループなので、**全滅でなくても`failedCount`が5件以上あるだけで`要修正`**（率の大小は問わない。「1000件中5件」でも「本来ゼロのはずが5件出ている」こと自体が異常）
  - **グループ2**（`ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG`）: 元々失敗しやすい傾向があるため、全滅でない部分的な失敗（5件以上あっても`totalCount`の一部にとどまる場合）だけでは断定せず `要確認` にとどめる。目安として「対象の半数を大きく超えて失敗している」ような極端な偏りが見えたら、全滅でなくても `要修正` に格上げしてよい
  - **件数の下限（5件）を必ず併用する**。下限未満の失敗は「500件中1件の失敗」のような偽陽性を避けるため判定しない
- **疑う原因**: メール配信ならメールアドレスを持たないコンタクトが対象／LINE配信ならブロック・配信上限・LINE連携解除、または**MOSH ゲスト起点（申込・リマインダー・決済失敗）のワークフローで、対象ゲストに MOSH ID とコンタクトの紐付けが無い**（全滅しやすい。S-5 の逆方向）／タグ操作・リッチメニュー操作・タグ条件なら対象コンタクトが解決できない（同じく MOSH ゲスト起点での紐付け無しが典型）
- **直し方**: **原因コードは MCP では取得できない**（[data-model.md](data-model.md) の原因コード辞書）。断定せず「◯通目のメール配信が全件届いていません。LINE友だち追加から始まるワークフローでメール配信を使っていると、メールアドレスを持たない方が対象になり全件失敗します」のように**最も確からしい仮説を1つだけ**提示し、確認方法を添える。**失敗したコンタクトはその先のステップも打ち切られる**ことを必ず伝える

### L1-4. 条件分岐が構造どおりに振り分けられているか

レイヤー0で「true 側／false 側で何が起きるか」は確定済み（[data-model.md](data-model.md)）。ここで見るのは**実際に何人ずつ通ったか**だけ。

- **見る**: CONDITION ステージの `completedCount`（＝評価された人数）と、分岐先ステージの `totalCount`
- **判定**:
  - 実績エントリに構造側と同じ `handle` があり対応づけできる場合 → どちらの側が 0 人かを確定して判定する（0 人 かつ 母数20件以上 → `要確認`）
  - 対応づけできない場合 → **推測で「こちらが true 側」と決めつけない**。「この分岐を通った◯人のうち、△△の配信に進んだのは□人でした」と実数だけ示し、意図と合っているかを問う
  - 片側が `stages: []`（何もせず終わり）なら、もう一方の実測だけで振り分けが読める（差分が終端側）
- **疑う原因**: 構造側の原因は S-1（タグの供給元が無い）／S-2（付与前に判定）が大半。**実績を見る前にこの2つを潰しておく**
- **直し方**: 「この分岐は◯人中0人しか通っていません。意図通りですか？」と必ず問う。順序の問題なら `workflow-builder` に引き継ぐ

### L1-5. トリガー×アクションのリスクが実績に出ていないか

- **見る**: S-5 で洗い出したリスクのある組み合わせ（LINE友だち追加・タグ追加・流入経路CV 起点 × `SEND_EMAIL`、および適合表 △＝MOSH ゲスト起点 × LINE 配信・タグ操作）の実測失敗率
- **判定**: 全滅（`failedCount == totalCount`）→ `要修正`。S-5 の懸念が実証された状態なので、公開前の注意喚起から**確定した指摘に格上げする**。△ の全滅は S-9a の裏取り結果と突き合わせる（入口が無ければ「紐付けの経路が無いので全滅している」と原因まで言える。入口があるのに全滅なら「入口の配信より前に申し込んだ方だけが対象になっている」可能性を仮説として添える）
- **直し方**: LINE配信に置き換えるか、メールアドレスを保有している対象だけに絞る。△ なら `SEND_EMAIL` への置き換えか紐付け導線の先行。設定変更は `workflow-builder` に引き継ぐ

## 判定の付け方

| 判定 | 条件 | 出力での書き方 |
|---|---|---|
| **要修正** | 構造上または実データ上、対象者が確実に届かない／進まないことが確定した箇所 | 何がそうなっているか（事実）＋ 最も確からしい原因の仮説 ＋ 次の一手 |
| **要確認** | おかしく見えるが、正常な設計・運用としても説明がつく（意図的な片側分岐・手動運用タグ・観測不足等） | ユーザーに問う質問文を必ず添える。断定しない |
| **問題なし** | 母集団の範囲内、または観測不足で判定を保留 | 「見た範囲では問題は見つかりませんでした」と、見た範囲を明記 |

- 1つのワークフローに複数の指摘が出たら、**要修正 → 要確認 → 問題なし** の順に並べる
- 全体の総合判定は最も重い個別判定に合わせる
- 構造だけを見ているときに `要修正` を出せる範囲は [mistake-patterns.md](mistake-patterns.md) 冒頭の規定が正本（S-2 / S-3 / S-4 / S-7 / S-8、および S-9 でテナント横断の裏取りが「無し」で確定したものに限る）

## レポート構成

出力の完成形は [../examples/structure-review-report.md](../examples/structure-review-report.md)（構造レビューのみ）と [../examples/review-report.md](../examples/review-report.md)（実績あり）。構成は次の6ブロック固定。

1. **総合判定と要約**（2〜3行）: 判定 ＋ 一番の問題 ＋ 直したときに何が変わるか
2. **見た範囲**: 公開状態（下書き／稼働中）／実績を見たなら最後に公開した日と観測期間／構造だけで見たのか実績も重ねたのか。**推定した箇所は「推定」と明記**
3. **このワークフローの動き**: 構造を日本語のフローで書き下す（分岐は両側とも。ここが構造レビューの主成果物で、ユーザーが意図とのズレに気づく最大のきっかけになる）
4. **指摘**（判定の重い順）: 見出しは平易な日本語のステージ名。各指摘に「何がそうなっているか → 考えられる原因 → 次の一手」
5. **問題が見つからなかった箇所**（1〜3行）: 全部を疑っているわけではないと分かるように
6. **確認したいこと**: ユーザーへの質問（`要確認` があるとき必須）

提示の作法（JSON・生ID・ステータスコードを出さない／原因を断定しない／ステージは番号と中身で呼ぶ）は SKILL.md 「ユーザーへの提示・コミュニケーション規約」が正本。
