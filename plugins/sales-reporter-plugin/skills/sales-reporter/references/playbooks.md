# 用途別プレイブック

よくある依頼への進め方。数値の定義は [metrics-definitions.md](metrics-definitions.md) を参照する。

## 共通の下準備

どのプレイブックでも、最初に**期間を確定**する。

- 「今月」「先月」は日本時間の暦月として解釈する
- 「最近」「このあいだ」「ちょっと前」は推測せず、ユーザーに確認する
- 期間は両端を含めて最長 365 日。超える依頼は分割するか、期間を狭めてよいか確認する（申込者数は分割すると合算できない。プレイブック 6）

## サマリーの `unit` は内訳の有無を決める

サマリーを呼ぶとき、`unit` の指定有無で返るものが変わる。

| `unit` | `summary`（期間合計） | `rows`（期間別の内訳と、その中の `plans`） |
|---|---|---|
| 指定しない | 返る | **空配列**。プラン別内訳は得られない |
| `monthly` / `daily` | 返る | 返る |

**商品別・プラン別の内訳が必要なときは必ず `unit` を指定する。** 合計金額だけでよいときは指定しない（余計な行を取らずに済む）。

## `postCreatorPaymentSalesAggregate` の呼び出し形

申込者数・ゲスト・支払いタイプが要るとき（プレイブック 6〜8）だけ使う。**body の 7 項目はすべて必須**で、絞らない項目にも「絞らない値」を入れる。

```json
{
  "bodyParams": {
    "startDate": "2026-09-01",
    "endDate": "2026-09-30",
    "period": "monthly",
    "serviceIds": [],
    "paymentMethod": null,
    "paymentType": null,
    "guestKeyword": ""
  }
}
```

| 項目 | 絞らないとき | 絞るとき |
|---|---|---|
| `serviceIds` | `[]` | `["<moshServiceId>", ...]`（文字列の配列。カンマ区切り文字列にしない） |
| `paymentMethod` | `null` | `"card"` / `"bankTransfer"` / `"cash"` |
| `paymentType` | `null` | `"oneTime"` / `"moshInstallment"` / `"cardInstallment"`（1 回に 1 つだけ） |
| `guestKeyword` | `""` | 名前・メールアドレスの一部（部分一致。プレイブック 7） |

- `period` は省略できない。1 ヶ月以内なら `daily` でも `monthly` でもよく、数ヶ月以上なら `monthly` にする
- `serviceIds` に入れる値は、サマリーの内訳 `rows[].plans[].moshServiceId`。商品単位で絞るときは、その商品のプランの `moshServiceId` を全部並べる（`productId` での絞り込みは無い）
- 返る `rows` は申込があった期間だけ（仕様上は新しい期間が先頭だが、返却順に依存せず `period` ラベルで並べ替える）。0 の期間を見せたいときは「申込なし」として補って並べる

## 1. 月次会議の資料を作る

**依頼例**: 「今月の売上まとめて」「月次会議の資料作って」

1. 当月のサマリーを `unit=monthly` で取得する（合計と内訳を一度に得るため）
2. 前月のサマリーを同様に取得する
3. 前月比を計算する（金額・件数の両方）。合計は `summary` の値を使う
   - **前月の実績が 0 のときは前月比（％）を出さない。** 割合が定義できないため。増減額・増減件数だけを示し、「前月実績が無いため前月比は算出できません」と添える
4. `rows[].plans` から売上上位の商品・プランを拾う
5. 表にまとめて提示する

提示するときは、金額に「申込ベース・税込・手数料控除前」を必ず添える。

**明細は取得しない。** ユーザーが個別の注文を見たいと言った場合のみ、プレイブック 3 に進む。

> 前月比がマイナスのとき、原因を推測して断定しない。「どのプランが減ったか」を内訳から示すまでに留め、理由の解釈はユーザーに委ねる。

## 2. キャンペーン・商品の振り返り

**依頼例**: 「このキャンペーン期間の売上は？」「あの商品どれくらい売れた？」

1. キャンペーン期間のサマリーを `unit=monthly` で取得する（絞り込みなし。内訳が必要なので `unit` は必須）
2. `rows[].plans` に並ぶ `serviceName` / `productName` / `planName` から、対象の商品・プランを特定する
   - **商品名から探すなら `getCreatorProducts`（商品一覧）を使う。** 返る `id` をそのまま `productId` に指定できる。**期間内に売上が無い商品もこの方法なら見つかる**
   - プラン単位で絞りたい場合は、このサマリーの内訳から `moshServiceId` を拾う（プラン単位の検索ツールは無い）
3. 特定できたら、`productId`（商品配下の全プランが対象）または `moshServiceIds`（プラン個別。複数はカンマ区切り）で絞ったサマリーを取得する
   - **この 2 つは同時に指定できない**
   - 内訳の `productId` が null のときは、その行に対応する商品が無いということ。`moshServiceId`（必ず入っている）で絞る
4. 比較したい期間（キャンペーン前・前年同期など）でも同じ絞り込みのサマリーを取得する
5. 並べて提示する

> 内訳に該当する名前が見つからない場合、まず `getCreatorProducts` で商品一覧を引いて対象が存在するか確かめる。存在するなら「その期間は売上が無い」と言える。商品一覧にも無ければ「**サマリー上では確認できない**」と伝える。**いきなり売上が無かったと断定しない。** サマリーには回数券などサービス以外の商品と、銀行振込の振込待ちが含まれないため、明細には出てくる可能性がある。必要なら期間を絞った明細で確認するか、管理画面へ誘導する。ID を推測して指定しない。

## 3. 特定の注文を確認する

**依頼例**: 「7月の決済一覧見せて」「この商品で売れた注文を見たい」

1. まずサマリーで規模感を把握する。**ただしサマリーの件数は契約単位**で、明細の行数（注文単位）とは一致しない
2. ユーザーに件数を伝えるときは単位を明記する
   - 「7月は契約ベースで 342 件です。分割払いがあると明細の行数はこれより多くなります」
3. 実際の取得量は、絞り込んだうえで明細を 1 回呼び、`pageInfo.totalCount`（注文単位）で判断する
4. その件数が多い場合（目安として 100 件超）は、全件取得せずユーザーに確認する
   - 「明細は 480 件あります。商品やプランで絞りますか？期間を狭めますか？」
   - 取得すると決めたら `limit=100`（上限）を指定する。既定は 20 なので、指定しないと往復回数が 5 倍になる
5. 絞り込み条件が決まったら残りを取得する
6. `paymentStatus` の意味を添えて提示する（[metrics-definitions.md](metrics-definitions.md) 参照）

### ページング

- `pageInfo.hasMore` が `true` のときだけ続きがある
- 続きを取るときは `pageInfo.nextCursor` を `cursor` に渡す
- **`hasMore` が `false` なら追加取得しない**
- 全件を機械的に取り切らず、必要な範囲で止める

### 絞り込めないもの

- **決済ステータス**では絞り込めない。取得後に `paymentStatus` で判断する
- **支払い方法**は `card` / `bankTransfer` / `cash` のみ。PayPay・LINE Pay・au PAY・コンビニ払い・回数券は明細に現れるが絞り込めない
  - これらで絞りたいと言われたら「絞り込みには対応していないため、取得した明細から該当分を拾います」と伝えて対応する

## 4. 売上推移を見る

**依頼例**: 「直近半年の推移」「売上グラフ作って」

1. 期間を確定する（最長 365 日）
2. サマリーを `unit=monthly`（月次）または `unit=daily`（日次）で取得する
3. `rows` が期間別の集計行。`period` が期間の起点日（月次なら各月 1 日、日次なら各日）
   - **`rows` は返却順に依存しない**（仕様上は新しい期間が先頭）。時系列に並べて見せるときは `period` ラベルで古い順に並べ替える（そのまま出すとグラフが逆向きになりうる）
4. `summary` は期間全体の合計。**`rows` を足し合わせて合計を出す必要はない**

> 日次を選ぶと行数が多くなる。1 ヶ月を超える期間では月次を既定とし、日次が必要かユーザーに確認する。

## 5. 「管理画面と数が違う」と言われたとき

1. **まず仕様である可能性を説明する。** バグと決めつけない
2. どの画面のどの数字と比較しているかを確認する
3. [metrics-definitions.md](metrics-definitions.md) の「サマリーと明細が一致しない理由」を使って説明する
4. 特に多い誤解を先回りして伝える
   - 明細を足した金額とサマリーの金額は一致しない（対象範囲が違う）
   - 分割払いは申込月に満額計上される（毎月の入金額とは違う）
   - 回数券などサービス以外の商品は、明細には出るがサマリーには入らない
5. 説明しても差異が説明できない場合は、**推測で原因を断定せず**、管理画面のスクリーンショットを添えてサポートへ問い合わせるよう案内する

## 6. 申込者数（ユニーク購入者数）を見る

**依頼例**: 「今月何人が買ってくれた？」「ユニーク購入者数を知りたい」「申込者数の推移」

1. 期間を確定する。**365 日以内**に収まるか確認する
2. `postCreatorPaymentSalesAggregate` を呼ぶ（絞り込みが無ければ `serviceIds: []`・`paymentMethod: null`・`paymentType: null`・`guestKeyword: ""`）
3. 期間全体の人数はトップレベルの `applicantsCount` を使う。**`rows[].applicantsCount` を足して出さない**（同じ人が複数の月に出てくる）
4. 「申込者数（ユニーク購入者数）」として提示し、件数（`grandTotalCount`・契約数）と並べるときは単位の違いを 1 行添える
   - 「9月の申込者数は 35 人、件数は 42 件です（同じ方が複数回申し込むと件数だけ増えます）」
5. 月ごとの推移を見せるときは `rows[].applicantsCount` を月ごとの人数として並べ、「各月の人数を足しても期間全体の人数にはなりません」と添える

> **365 日を超える期間**（「過去 2 年の購入者数」など）は、申込者数を正しく出せない。分けて取得した人数を合算せず、「1 年以内に縮める」か「1 年ごとの人数として並べる」かをユーザーに選んでもらう。金額・件数だけなら分けて取得して合算してよい。
>
> **「2 年分の人数は管理画面で確認できる」とは案内しない**（管理画面で期間全体の重複なしの人数が出るかは確認できていないため）。このツールでは出せない、と伝えるだけにとどめる。

## 7. 特定のゲストの売上を見る

**依頼例**: 「山田さんの売上はいくら？」「taro@example.com の人はいくら買ってくれた？」

1. 期間を確定する（指定が無ければ「いつからいつまでか」を確認する。最長 365 日）
2. `customer-manager` の手順で、`postCustomersSearch` の `searchQuery` に**同じキーワード**を入れて一致する顧客を確認する（`searchQuery` は MOSH ID にも一致するため、`guestKeyword` より人数が多めに出ることがある。多めの側で「複数いる」と伝えれば取りこぼしは無い）
   - 一致人数は応答の `totalCount`（ページ前の総件数）で読む。`customers` の長さは1ページ分なので人数に使わない
   - 一致が 0 人 → 「該当する顧客が見つかりません」と伝え、表記を確認する。売上の取得には進まない
   - 一致が 2 人以上 → 「『山田』に一致する顧客が 3 人います。合算の売上になります」と伝え、合算でよいか、キーワードを絞るか（メールアドレス全体など）を確認する
3. `postCreatorPaymentSalesAggregate` の `guestKeyword` にそのキーワードを入れて呼ぶ
4. 金額（申込ベース・税込・手数料控除前）・件数・申込者数を提示する。複数一致なら「◯人の合算」と必ず添える

注意:

- `guestKeyword` は**部分一致**。メールアドレス全体を入れても、それを含む別のアドレスにも一致する（`a@example.com` は `aa@example.com` にも一致する）。そのため「1 人だけ」と言い切れるのは手順 2 で一致が 1 人だったときだけ
- 前後の空白だけのキーワードは絞り込みなしと同じ扱いになる（全ゲストの売上が返る）。空のまま呼ばない
- 検索に使った名前・メールアドレスや、手順 2 で見えた他の顧客の情報は、依頼された用途以外に出力・転記しない
- 誰が買ったかの一覧（ゲスト名つき）は返らない。名前で一覧したい場合は管理画面の申込者一覧へ誘導する

## 8. 支払いタイプ別（一括 / 分割）の売上を見る

**依頼例**: 「分割払いだけの売上」「一括で払った人の売上」「カード会社の分割の分だけ」

1. 期間を確定する
2. 依頼の言葉を `paymentType` に対応づける

   | 依頼の言葉 | `paymentType` |
   |---|---|
   | 一括・一括払い | `oneTime` |
   | MOSH の分割払い | `moshInstallment` |
   | カード会社の分割払い・カードの分割 | `cardInstallment` |
   | 「分割払い」とだけ言われた | どちらの分割か確認する。両方なら下記のとおり 2 回呼ぶ |

3. `postCreatorPaymentSalesAggregate` を呼ぶ。`paymentType` は 1 回に 1 つしか指定できない
   - 「分割払い全部」なら `moshInstallment` と `cardInstallment` で 2 回呼び、**金額・件数は合算してよい**。申込者数は同じ人が両方にいる可能性があるため合算しない（それぞれの人数として並べる）
4. 支払い方法（`paymentMethod`: カード / 銀行振込 / 現金）とは別の軸。「カードで払った分」は `paymentMethod: "card"`、「分割で払った分」は `paymentType` で絞る。両方を同時に指定してもよい
5. 提示では「申込月に契約満額を計上」を必ず添える（分割払いでも毎月の支払額ではなく契約満額が申込月に入る）

> PayPay・LINE Pay など、`paymentMethod` の 3 種以外では絞り込めない（制約は SKILL.md の制約表）。サブスクかどうかでも絞り込めない。
