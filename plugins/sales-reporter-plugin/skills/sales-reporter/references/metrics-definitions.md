# 売上数値の定義

このツールが返す数値の意味。ユーザーに数値を提示するとき、および「管理画面と数が違う」と指摘されたときの説明根拠として使う。

## 申込ベースとは

**申込が成立した月に、契約の満額を計上する**方式。MOSH 管理画面の「売上一覧」ページと同じ定義。

具体的には次のように扱われる。

| ケース | 計上のされ方 |
|---|---|
| 分割払い（12回払いなど） | **申込月に契約満額**を計上。以降の支払回では計上しない |
| キャンセル | **遡って取り消さない**。申込月の計上は残る |
| 支払い期限切れ | **計上される**。決済されていないが申込は成立しているため |
| 銀行振込 | **振込の実績があるものだけ**計上。振込待ち・振込期限切れ・振込前のキャンセルは計上しない |
| サブスクリプション | 各回の請求のうち**決済済みになったもの**だけを計上。キャンセル・未決済の請求は計上しない |

**未決済の扱いは決済手段によって変わる。** キャンセル・支払い期限切れでも計上が残るのはカード決済などの通常の申込で、銀行振込とサブスクリプションは決済実績が無いものを一切計上しない（表の下 2 行が優先される）。

「今月いくら入金されたか」ではなく「今月いくら売れたか（契約が成立したか）」を表す数値である点に注意する。キャッシュフローとは一致しない。

## 金額の定義

- 単位は**円**
- **税込**
- **手数料控除前**（MOSH の手数料や決済手数料を引く前の金額）

**手数料控除後の金額（クリエイターの手取り）は取得できない。** 聞かれたら管理画面へ誘導する。

**実際の支払額も取得できない。** 返るのは注文の金額であり、銀行振込で過不足があったケースの実支払額は含まれない。

## 件数の定義

サマリーと明細で**数える単位が違う**。

| | 単位 | 分割払い 12 回の契約 1 件は |
|---|---|---|
| サマリー (`summary.totalCount` / `rows[].count` / `plans[].count`) | 契約単位 | **1 件** |
| 明細 (`pageInfo.totalCount`) | 注文単位 | 支払回ごとに 1 行（未決済の将来回は含まない） |

## サマリーと明細が一致しない理由

数値が食い違うのは仕様。主な要因は次の通り。

| 要因 | サマリー | 明細 |
|---|---|---|
| 数える単位 | 契約単位 | 注文単位 |
| 分割払いの各支払回 | 申込月に満額を 1 件として計上 | 支払回ごとに 1 行として出る |
| 回数券など、サービス以外の商品 | **含まれない** | **含まれる**（`moshServiceId` が null になる） |
| 銀行振込の振込待ち | 含まれない | 含まれる（`paymentStatus` が `pending`） |
| キャンセル済みの注文 | 申込月の計上は残る（銀行振込・サブスクを除く） | 行として出る（`paymentStatus` が `canceled`） |
| 支払い期限切れの注文 | 申込月の計上は残る（銀行振込・サブスクを除く） | 行として出る（`paymentStatus` が `rejected`） |

**合計金額を出すときは必ずサマリーを使い、明細を足し合わせない。**

## 期間の扱い

- すべて**申込日**が基準。決済完了日での絞り込みはできない
- タイムゾーンは**日本時間（JST）**
- `startDate` と `endDate` は**どちらもその日を含む**
- 指定できる期間は**両端を含めて最長 365 日**

「過去 1 年」を指定するときは、`startDate` を 1 年前の**翌日**にする。1 年前の同じ日にすると 366 日となりエラーになる。

```text
✅ startDate=2025-08-20  endDate=2026-08-19   （365 日）
❌ startDate=2025-08-19  endDate=2026-08-19   （366 日 → エラー）
```

## `paymentStatus` の意味（明細のみ）

| 値 | 意味 |
|---|---|
| `approved` | 決済フローが完了した状態（下記のとおり 4 通りの意味がある） |
| `unapproved` | 申込時点で付く初期値 |
| `pending` | 支払い待ち（銀行振込の振込待ち） |
| `canceled` | キャンセル（返金の有無は問わない） |
| `rejected` | 支払い期限切れ |
| `estimate` | 見積もり（通常このツールのレスポンスには現れない） |

**この値で「決済済みかどうか」を判定してはいけない。** 1 つの列に「決済フェーズ」「決済プロバイダの違い」「MOSH 内部の送金進捗」の 3 つが混ざっているため。

- `approved` は 4 通りの意味を持つ。①プロバイダ上での送金が完了した ②送金管理の対象外のプロバイダで決済が完了した ③**現金払い**（対面での受け渡しを前提としており、システムは決済処理を一度も行わない＝未収でも `approved`） ④**0 円決済**（金銭の移動そのものが無い）
- `unapproved` は申込の時点で無条件に付く初期値。決済結果の確定を表す値ではない
- 逆に**決済済みでも `canceled` になっている注文がある**（振込後のキャンセル、返金を伴うキャンセル）

この値では絞り込みもできない。「決済済みの売上だけ」のような依頼には、**このツールでは判定できないと伝えて管理画面へ誘導する。**

### 「入金」を聞かれたとき

MOSH で**入金**とは、決済プロバイダからクリエイターの銀行口座へ着金することを指す。ゲストが支払ったこと（決済）とも、プロバイダ上のアカウント間で資金を動かすこと（送金）とも別の概念。

**入金はこのツールの守備範囲外。** 売上は「いつ契約が成立したか」を表す数値で、「いつ口座に入ったか」は一切含まない。入金について聞かれたら、管理画面の入金一覧へ誘導する。

## 日時フィールドの違い（明細のみ）

| フィールド | 意味 |
|---|---|
| `orderedAt` | 申込日時。**期間の絞り込みはこちらが基準** |
| `paidAt` | 決済完了日時。ただし後述の理由で決済の判定には使えない |
| `canceledAt` | キャンセル日時。キャンセルされていなければ null |

**`paidAt` が入っていても決済済みとは限らない。** 実際の決済日時を取得できないとき、申込日時にフォールバックする実装になっているため。一度も決済されていない支払い期限切れ（`rejected`）の注文にも、申込日時が `paidAt` として入る。振込待ち（`pending`）のときだけは null になる。

## 分割払いの見分け方（明細のみ）

| フィールド | 意味 |
|---|---|
| `paymentType` | `oneTime`（一括） / `moshInstallment`（分割入金型） / `cardInstallment`（一括入金型） |
| `totalPaymentCount` | 契約の総支払い回数（一括なら 1） |
| `currentPaymentNumber` | その注文が何回目の支払いか（1 始まり） |

## 取得できないもの

以下は**このツールでは取得できない**。推測して答えず、管理画面へ誘導する。

- 返金額・返金の有無
- 手数料控除後の金額（クリエイターの手取り）
- 分割払いの残債・未回収額
- ゲストの名前・メールアドレス（`guestId` のみ返る）
- 購入者のユニーク人数（件数は延べ）
- 入金の状況（クリエイター口座への着金。売上とは別概念で、管理画面の入金一覧の領域）
- **決済済みかどうかの判定**（`paymentStatus` も `paidAt` も決済の確認結果ではない）
- 実際の支払額（過入金・金額不足の判別）
