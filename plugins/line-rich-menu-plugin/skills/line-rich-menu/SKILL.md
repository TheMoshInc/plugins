# MOSH LINE リッチメニュー

## Overview

MCP ツール7本（＋背景画像のアップロード枠1本）で、MOSH クリエイターの LINE リッチメニュー（トーク画面の下部に固定表示されるメニュー）を**作成・確認・編集・デフォルト設定/解除・削除**する。タブで別メニューに切り替わる「タブあり」レイアウトも扱う。

**作成・更新は公開操作。** 更新は LINE 上でメニューを作り直す重い操作で、公開中のメニューが即座に差し替わる。しかも**全置換**なので、既存の値を1つでも埋め忘れると壊れたまま友だち全員に反映される。

> **ツール名表記について**: 本スキル内では MCP ツールを OpenAPI の `operationId`（例: `patchCreatorLineRichMenu`）で参照する。実際のツール名にはサーバー識別子のプレフィックスが付くが、その形は環境により異なるため付けない。

## When to use

- リッチメニューを新しく作りたいとき（タブあり・2つのメニューを行き来させる構成を含む）
- 一覧・中身を確認したいとき
- ボタン（エリア）のリンク先・タップ時の動作・切り替え先を変えたいとき
- 背景画像を差し替えたい、レイアウト（分割数・タブの有無）を変えたいとき
- メニューバーの文言・開閉初期状態を変えたいとき
- デフォルトにしたい・外したい、削除したいとき
- 別の LINE公式アカウントに同じメニューを用意したいとき（→ 移動はできないので作成）
- 「ボタンを押しても反応しない」と相談されたとき（→ Webhook の確認案内）

## When NOT to use

- **特定のコンタクトにだけリッチメニューを出し分ける** → MCP に個別付与のツールは無い。ワークフローの「個別リッチメニューの付与」で行う `workflow-builder`
- **ファイル共有に画像を登録して共有URLを配る** → `file-share`。リッチメニューの背景にするだけなら本スキルで上げる（共有URLは作らない）
- **LINE の一斉配信・ステップ配信の本文** → `contact-broadcast` / `workflow-builder`
- **LINE公式アカウント自体の接続・設定** → 対象外。管理画面での操作を案内する

## ツールの選び方

| やりたいこと | ツール |
|---|---|
| 一覧を見る（デフォルト設定・個別リンク数を含む） | `getCreatorLineRichMenus` |
| 中身を見る（レイアウト・エリア・文言・切り替え先） | `getCreatorLineRichMenu` |
| 新しく作る | `postCreatorLineRichMenu` |
| 中身を変える（全置換） | `patchCreatorLineRichMenu` |
| デフォルトに設定する / 解除する | `postCreatorDefaultLineRichMenu` / `deleteCreatorDefaultLineRichMenu` |
| 削除する | `deleteCreatorLineRichMenu` |
| 背景画像を上げる（アップロード枠の発行） | `postCreatorMaterialImageUpload` |
| 補助: アカウント一覧 / タグの確認 | `getCreatorLineChannels` / `getCreatorContactTags` |

- 各ツールの引数・返り値・副作用・エラーは [references/mcp-tools.md](references/mcp-tools.md) が正本
- メニューの構造（レイアウト10種とエリア数・位置、画像解像度、アクション・切り替えの書き方、文字数上限、Webhook が要るボタン）は [references/menu-schema.md](references/menu-schema.md) が正本

## Workflow

基本フロー: 対象の特定 → **現在の内容を取得**（更新時）/ **必要な情報をそろえる**（作成時）→ 内容を提示 → **ユーザーの承認** → 実行 → 結果の報告。読み取りだけなら承認は不要。

### 承認の判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 作成（`postCreatorLineRichMenu`） | **必ず停止して承認** | LINE に登録され、同じ内容で2回呼ぶと2つできる。タグ・切り替え先・画像の取り違えはそのまま残る |
| 更新（`patchCreatorLineRichMenu`） | **必ず停止して承認** | 公開中のメニューが即時に差し替わる。全置換のため埋め忘れが他の項目を壊す |
| デフォルト設定（`postCreatorDefaultLineRichMenu`） | **必ず停止して承認**。既存のデフォルトがあれば**名前で示して**置き換えの承認を取る | 確認なしで上書きし、全友だちの初期表示が変わる |
| デフォルト解除（`deleteCreatorDefaultLineRichMenu`） | **必ず停止して承認** | 個別リンクの無い友だちにメニューが出なくなる |
| 削除（`deleteCreatorLineRichMenu`） | **必ず停止して承認**。影響範囲（§C）を示す | 復元できない |
| 背景画像のアップロード（`postCreatorMaterialImageUpload` ＋ 送信） | **作成・更新の承認に含める**（単独では止まらない）。承認後、作成・更新の直前に行う | 単体では何も公開されない |
| 参照（一覧・詳細・アカウント・タグ） | 停止しない | 読み取り |

**依頼文がどれだけ具体的でも、上表で「承認」の操作は承認なしに実行しない。** 「〇〇に変えといて」「作っておいて」のような一任表現も承認の代わりにならない。1回の承認で複数の操作をまとめるとき（タブで行き来する2つのメニューの作成＋仕上げの更新など）は、**全操作を列挙して**承認を取る。

### 1. 依頼内容と対象の確認

`getCreatorLineRichMenus` で一覧を取る。**どの LINE公式アカウントか曖昧なら絞り込む**（`getCreatorLineChannels`。作成先は連携中のアカウントに限る）。

対象が特定できない依頼（「古いリッチメニュー消して」等）では対象を確認する。**どのメニューがワークフローから使われているかは MCP から判定できない**（§C）。

「新しく作りたい」のか「既存を作り替えたい」のかが曖昧なら確認する（作成は新しいメニューが増え、更新は公開中のものが変わる）。

### 2a. 更新: 現在の内容を取得（必須）

`getCreatorLineRichMenu` で全項目を取得する。**これを省いて body を組み立てない**（§A）。

### 2b. 作成: 必要な情報をそろえる

7項目（アカウント・名前・レイアウト・背景画像・各ボタンの動作・メニューバーの文言・開閉初期状態）をそろえる。ボタン数・用途からレイアウトを提案し（[references/menu-schema.md](references/menu-schema.md)）、**分からない値（URL・タグ・切り替え先）は推測せず聞く**。名前・文言・開閉初期状態など補ってよい値は補い、補ったと明示する。タブありで2つのメニューを行き来させるなら、作成順（§F）を先に決める。

背景画像を新しく用意・差し替える依頼、またはレイアウト変更で描き直しが要るなら、ここで [references/image-preparation.md](references/image-preparation.md) を読む。**承認前に行うのは実測・加工まで。アップロードは承認後。**

### 3. 内容の提示

- 作成: アカウント名・レイアウト（「6分割（タブあり）」のように）・各ボタンの位置と動作・文言・画像。**作っただけでは誰にも表示されないこと**と、続けてデフォルトにするか
- 更新: **変更前 → 変更後**を項目ごとに。変えない項目は「そのまま」と明記。レイアウト変更なら消えるボタン設定と画像への影響
- デフォルト設定: 設定するメニュー名。**既存のデフォルトがあればその名前と、置き換わること**（例: 「『通常メニュー』が現在のデフォルトです。『キャンペーンメニュー』をデフォルトにすると置き換わります」）
- デフォルト解除: 解除するメニュー名と、個別リンクの無い友だちにメニューが出なくなること。**変更・解除の前には必ず一覧で現在のデフォルトのメニュー名を調べて書く**（解除対象がデフォルトでないなら、例: 「現在のデフォルトは『通常メニュー』で、『キャンペーンメニュー』はデフォルトではないため、解除しても何も変わりません」と伝えて実行しない）
- 削除: §C の項目

エリアは「左上のボタン（A）」「左のタブ」のように**位置と動作を日本語で**書く。**承認を得るまで次に進まない。**

### 4. 実行

- 作成: （必要なら画像を上げてから）`postCreatorLineRichMenu`。完成形の例は [examples/tab-pair-create-trace.md](examples/tab-pair-create-trace.md)
- 更新: 「取得 → 取得した値をそのまま載せる → 変更点だけ差し替える → `patchCreatorLineRichMenu`」（§A）。body の形は [examples/patch-body-six-split.clean.json](examples/patch-body-six-split.clean.json)（パターンの解説付きは [patch-body-six-split.json](examples/patch-body-six-split.json)）、1項目だけの変更は [examples/chatbar-text-update-trace.md](examples/chatbar-text-update-trace.md)
- 更新は個別リンク中の友だちが多いほど時間がかかる。途中失敗時の巻き戻しは保証されない（[references/mcp-tools.md](references/mcp-tools.md) の副作用）
- デフォルト設定・解除・削除は1回の呼び出しで完了する

### 5. 結果の報告

何がどうなったかを平易な日本語で伝える。作成・更新後は**LINE アプリ側の表示が切り替わるまで時間差がある**ことを添える。作成後にデフォルト設定していなければ、まだ誰にも表示されていないことを伝える。

## 必須ルール

### A. 更新は全置換。必ず `getCreatorLineRichMenu` から始める

`patchCreatorLineRichMenu` は部分更新できない。`name` / `layout` / `backgroundMoshImageId` / `areas` / `chatBarText` / `chatBarOpenByDefault` の**6項目すべてが必須**。文言だけ変えるときも、取得した他の5項目をそのまま載せ直す。

**思い出しや推測で埋めない。** `areas` は全エリアを、各 `action` の3キー（`url` / `postbackActions` / `richMenuSwitch`）ごとそのまま持ち回る。ただし**取得値の切り替え先が削除済みだと、そのまま載せても拒否される**（エラー表 → 切り替え先を直すか外すかをユーザーに確認）。

`creatorLineChannelId` は更新できない。「別の LINE公式アカウントに移して」は、移動先で同じ内容を**作成**する案を出す（作成の承認が要る。元を消すかは別に確認）。

### B. レイアウトを変えるなら、エリアと背景画像も一緒に変える

- **エリア数**: レイアウトの要求数と `areas` の件数が違うと拒否される（loud fail）。**タブありはタブ2つを含めた数**（6分割タブありは8件）
- **背景画像**: 大↔小、**タブなし↔タブあり**は描き直しが必須。同じサイズで分割だけ変わる場合も画像の区画がズレるので原則描き直す。**サイズは分割数の印象で判定しない**（小は3分割・1ブロック小の2つだけ。左右2分割・タブあり4種は大）。数値は必ず [references/menu-schema.md](references/menu-schema.md) の表で答える（要約: **大＝1200×810、小＝1200×405**。LINE 一般の 2500×1686 は使わない。現在の画像が別の値に見えても、必要サイズはこの表で答える）。レイアウトは10値のみで、5分割など表に無いものは存在しない。**サイズが合わない画像でも MOSH は素通しする**ため、原因の分からないエラーになるか、ズレたまま公開される
- **エリアの並び順**: 位置は配列の順序で決まり `label` では決まらない。並べ替えると**ラベルと位置がズレたまま公開される**（silent fail）。タブありは先頭2件がタブ

### C. 削除は復元できず、他からの参照は残る

自動で解除されるのはデフォルト設定と個別コンタクトへのリンク。**残るもの**:

- **ワークフローの「個別リッチメニューの付与」に設定されたID** — そのステップは付与できないメニューを指し続ける（silent fail）。**MCP からは参照の有無を調べられない**ので、削除の承認時に「このメニューを使っているワークフローがあれば、そのステップは動かなくなります。管理画面での確認をお願いします」と必ず添える（「参照は無いようです」と断定しない）
- **他のメニューのタブ・ボタンの切り替え先** — 押しても切り替わらなくなり、そのメニューは切り替え先を直すまで更新できない。**同じアカウントのメニューを詳細取得して調べられる**ので、削除前に該当の有無を確認して提示する

提示する項目: メニュー名、**復元できないこと**、**個別リンク中の人数**、**デフォルト設定中か**、切り替え先として使っているメニュー（あれば名前）、ワークフローの参照は確認できないこと。

切り替え先として使っているメニューがあれば、**必ず「そのメニューのタブ・ボタンは押しても切り替わらなくなり、切り替え先を直すまで更新も拒否される」と名前つきで書く**（例: 「『はじめての方向け』の右タブが『受講生向け』を切り替え先にしています。削除するとそのタブは切り替わらなくなり、『はじめての方向け』は切り替え先を直すまで更新できません」）。削除の完了報告でも1行で繰り返し、直すかを尋ねる。

### D. タップして何も起きないボタンを作らない

各エリアの `action` は3キーが常に必須で、使わないキーは `null`。**3つとも `null` でも保存され、タップしても何も起きない**（silent fail）。未設定のタブも同様に切り替わらない。**こちらから作らない。** 「使わないので空にして」と言われたら、何も起きないことと代替案を伝え、ユーザーが理解したうえで明示的に選んだ場合のみ3つとも `null` で進める。代替案にレイアウト変更を挙げるときは、10値のレイアウト（[references/menu-schema.md](references/menu-schema.md)）の範囲で出す（ボタン5つのレイアウトなど、表に無いものは提案しない）。

URL を開かないボタン（メッセージ送信・タグの付け外しだけ、切り替えに付けたアクション）は **LINE の Webhook が MOSH に向いていないと動かない**。保存も表示も正常なまま無反応になる。**反応しないと相談されたら、最初の返信で** [references/menu-schema.md](references/menu-schema.md) の「ボタンを押しても反応しないとき」の3ステップ（①管理画面「LINE公式アカウント管理」の設定で「Webhook が OFF です」の表示確認 ②LINE Developers の「Webhookの利用」が ON か ③Webhook URL が MOSH の設定画面のものと同じか）を書く。**どのメニューか・どのボタンかを聞き返すだけで終えない**（聞くなら3ステップの後に添える）。キャッシュ・再起動の案内から始めない。

タグを付ける/外す動作は、`getCreatorContactTags` でタグIDを確かめてから入れる。見つからなければ推測せずユーザーに聞く（誤ったIDは保存時に拒否される）。

### E. 文字数は目視で数えない

`chatBarText`（上限14）・`name`（上限300）は **UTF-16 コードユニット数**で判定され、絵文字の多くは**2**と数えられる（例: 「👍タップしてメニューを開く」は目視13に見えるが実際は **14**）。**絵文字を含む文言は1文字ずつ内訳を書き出して数える**（[references/menu-schema.md](references/menu-schema.md)）。

**文言（メニューバー・名前）を変える依頼の書き込み前の提示は、次の定型で書く。「確認いらない」と言われても省かない。数字（文字数・合計）は書かない**（数え間違いがそのまま誤情報になる。数えるのは内部の確認用）。
- 通常: 「メニューバーの文言: 『◯◯』→『△△』（上限14以内に収まります）」
- 絵文字を2と数えて13〜14相当で余裕がほぼ無い: 「メニューバーの文言: 『◯◯』→『△△』（上限14以内に収まりますが、ほぼ上限です）。短縮案: 『□□』」
- 収まらない: 「『△△』は上限14を超えるため送れません。短縮案: 『□□』『◇◇』のどちらにしますか？」

### F. タブで行き来する2つのメニューは「作成 → 作成 → 更新」の順

先に作るメニューのタブには、まだ存在しないもう一方を指定できない。**①メニューXを作成（相手側のタブは空けておく）→ ②メニューYを作成（タブの一方に X を指定）→ ③ X を更新して空けたタブに Y を指定**。③は全置換の更新なので §A に従う。切り替え先は**同じ LINE公式アカウントのメニューだけ**。タブの見た目は LINE が描かないので、それぞれの画像に「どちらのタブが選択中か」を描き分ける。完全な流れは [examples/tab-pair-create-trace.md](examples/tab-pair-create-trace.md)。

## ユーザーへの提示・コミュニケーション規約

- **内部用語・フィールド名を出さない**: `layout` / `areas` / `chatBarText` / `backgroundMoshImageId` / `postbackActions` / `richMenuSwitch` / `SIX_SPLIT` 等の値 / `creatorLineChannelId` / `moshMediaId` / エイリアス。使う言葉は「レイアウト（6分割など）」「ボタン」「タブ」「メニューバーの文言」「背景画像」「タップしたときの動き」「切り替え先」「LINE公式アカウント」。例外として「Webhook」「Webhook URL」は、ユーザーが LINE Developers 等の設定画面で目にする語なので確認手順の案内で使ってよい
- エリアは「左上のボタン（A）」「右のタブ」のように**位置が伝わる形**で示す
- JSON・HTTP用語・ステータスコード・ツール名を出さない
- **完了形で書けるのは、対応するツールが成功した後だけ。** 承認待ちは「以下の内容で進めてよいですか」と書く
- **ID を創作しない。** リッチメニューID・タグID・アカウントID・画像の識別子は、ツールの返り値かユーザーから受け取った値だけを使う
- 取得した情報に無い事実（表示回数、どのワークフローが使っているか、Webhook の状態等）を補って語らない
- **できない理由も仕組みで説明しない。** ユーザーから見える事実だけで説明する

## エラーが返ったとき

**原則、自分の判断で再試行しない。** 原因と対処を平易な日本語で伝え、再試行するかはユーザーに決めてもらう。原因と対処の一覧は [references/mcp-tools.md](references/mcp-tools.md) の「エラーの読み方」が正本。

- **入力に原因があるエラー**（件数不一致・文字数・URL形式・タグ・切り替え先・アカウント）は、内容を直さずに再送しない。直してから改めて承認を取る
- **「LINEへのリッチメニュー操作に失敗しました。」**は、まず画像の解像度・容量・形式を確かめる。それでも分からなければ、時間を置いて試すかをユーザーに確認する。自動で連続再送しない
- **例外（唯一の自動再試行）**: 画像を上げた直後の「背景画像の取得に失敗しました。」は準備待ちの可能性が高く、リッチメニューとしては何も変わっていない（タブの切り替え用の別名だけ先に作られることがあるが無害）。準備待ちとする根拠は実装では確認できていない（画像取得は失敗を一括で返すのみ）。**再送の前に毎回 `getCreatorLineRichMenus`（一覧）を呼んで同じ名前のメニューが作られていないことを確かめ**（作られていれば再送しない）、**承認済みの同じ内容のまま、10秒ほど待って最大3回まで**再送してよい。3回とも同じなら止め、識別子の誤りか画像の変換失敗の可能性を伝える
- **準備待ちの再送が成功しても、報告の前に必ず `getCreatorLineRichMenus`（一覧）を呼ぶ**（詳細取得では重複作成が分からない）。同じ名前のメニューが1件だけであることを確かめてから「作成しました」と書く。
- **状態を確認するまで結果を報告しない。** 作成なら一覧（作りかけ・重複が無いか）、更新なら詳細取得、削除なら一覧を呼び直す（巻き戻しも削除の失敗も、エラーメッセージだけからは確定できない）
