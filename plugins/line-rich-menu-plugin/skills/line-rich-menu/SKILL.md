# MOSH LINE リッチメニュー

## Overview

MCP ツール6本で、MOSH クリエイターの LINE リッチメニュー（LINE トーク画面の下部に固定表示されるメニュー）を操作する。扱えるのは **既存メニューの確認・編集・デフォルト設定/解除・削除**。

**新規作成は MCP からできない。** 作成専用のツールは提供されていない（[references/mcp-tools.md](references/mcp-tools.md) の「MCP に無いもの」）。「リッチメニュー作って」には、**MOSH 管理画面（LINE公式アカウント > リッチメニュー > 新規作成）での作成を案内し、作成後の仕上げ（画像差し替え・ボタン設定・文言・デフォルト化）を MCP で引き受ける**、という役割分担で応える。

**編集はすべて全置換。** そして編集は LINE 上でリッチメニューを作り直す重い操作で、公開中のメニューが即座に差し替わる。既存の値を1つでも埋め忘れると、意図しない箇所が壊れたまま本番の友だち全員に反映される。

> **ツール名表記について**: 本スキル内では MCP ツールを OpenAPI の `operationId`（例: `patchCreatorLineRichMenu`）で参照する。MCP クライアントが提示する実際のツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため本スキルでは付けない。

## When to use

- リッチメニューの一覧・中身を確認したいとき
- ボタン（エリア）のリンク先・タップ時の動作を変えたいとき
- 背景画像を差し替えたい、レイアウト（分割数）を変えたいとき
- メニューバーの文言（chatBarText）・開閉初期状態を変えたいとき
- リッチメニューをデフォルトにしたい・デフォルトを外したいとき
- リッチメニューを削除したいとき
- 「リッチメニュー作って」と言われたとき（→ 管理画面での作成案内 + 作成後の仕上げ）
- `*LineRichMenu*` 系ツールが必要な文脈

## When NOT to use

- **背景画像のアップロードそのもの**（手元の画像ファイルを MOSH に上げて識別子を得る） → `file-share`スキル。本スキルは受け取った識別子を使うだけで、アップロード手順を再実装しない（[references/image-preparation.md](references/image-preparation.md)）
- **特定のコンタクトにだけリッチメニューを出し分ける** → MCP に個別付与のツールは無い。ワークフローの「個別リッチメニューの付与」アクションで行うため `workflow-builder`スキル
- **LINE の一斉配信・ステップ配信の本文** → `contact-broadcast`/ `workflow-builder`
- **LINE公式アカウント自体の接続・設定** → 本スキルの対象外。管理画面での操作を案内する

## ツールの選び方

| やりたいこと | ツール |
|---|---|
| 一覧を見る（デフォルト設定・個別リンク数を含む） | `getCreatorLineRichMenus` |
| 中身を見る（レイアウト・エリア・文言） | `getCreatorLineRichMenu` |
| 中身を変える（全置換） | `patchCreatorLineRichMenu` |
| デフォルトに設定する | `postCreatorDefaultLineRichMenu` |
| デフォルトを解除する | `deleteCreatorDefaultLineRichMenu` |
| 削除する | `deleteCreatorLineRichMenu` |

- **新規作成のツールは無い**（Overview 参照）
- 各ツールのパラメータ・返り値・可否条件・副作用は [references/mcp-tools.md](references/mcp-tools.md) が正本
- リッチメニューの構造（レイアウトとエリア数の対応・画像解像度・アクションの書き方・文字数上限）は [references/menu-schema.md](references/menu-schema.md) が正本

## Workflow

基本フロー: 対象の特定 → **現在の内容を取得** → 変更後の内容を提示 → **ユーザーの承認** → 実行 → 結果の報告。読み取りだけなら承認は不要。

### 承認の判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 更新（`patchCreatorLineRichMenu`） | **必ず停止して承認** | 公開中のメニューが即時に差し替わり、友だち全員に反映される。全置換のため埋め忘れが他の項目を壊す |
| デフォルト設定（`postCreatorDefaultLineRichMenu`） | **必ず停止して承認**。既に別のメニューがデフォルトなら、**どれを置き換えるかを名前で示して**承認を取る | 確認なしで既存のデフォルトを上書きする。全友だちの初期表示が変わる |
| デフォルト解除（`deleteCreatorDefaultLineRichMenu`） | **必ず停止して承認** | 解除するとデフォルト表示が無くなり、個別リンクの無い友だちにメニューが出なくなる |
| 削除（`deleteCreatorLineRichMenu`） | **必ず停止して承認**。影響範囲（§C）を示す | 復元できない。個別リンク中の友だちのメニューも消える |
| 参照（`getCreatorLineRichMenus` / `getCreatorLineRichMenu`） | 停止しない | 読み取り |

**依頼文がどれだけ具体的でも、上表で「承認」となっている操作は承認なしに実行しない。** 「〇〇に変えといて」のような一任表現も承認の代わりにはならない。

### 1. 依頼内容と対象の確認

`getCreatorLineRichMenus` で一覧を取る。LINE公式アカウントを複数持つクリエイターがいるため、**どのアカウントのメニューかが曖昧なときは絞り込む**（一覧は `creatorLineChannelId` で絞れる。アカウントの一覧は `getCreatorLineChannels`）。

対象が特定できない依頼（「古いリッチメニュー消して」等）では、削除・更新に進まず対象を確認する。**どのメニューが使われていないかを MCP から判定することはできない**（ワークフローからの参照有無を調べる手段が無い。§C）。

### 2. 現在の内容を取得（更新するなら必須）

`getCreatorLineRichMenu` で全項目を取得する。**これを省いて更新の body を組み立ててはならない**（§A）。

背景画像を差し替える依頼、またはレイアウトのサイズ系統を変える依頼なら、ここで [references/image-preparation.md](references/image-preparation.md) を読む。

### 3. 変更後の内容の提示

提示する項目:

- 更新: **変更前 → 変更後**を項目ごとに。エリアは「A: 〇〇のページを開く」のように**ラベルと動作を日本語で**書く。変えない項目は「そのまま」と明記する
- デフォルト設定: 設定するメニュー名。**既存のデフォルトがあるならその名前と、置き換わること**
- デフォルト解除: 解除するメニュー名と、解除後は個別リンクの無い友だちにメニューが表示されなくなること
- 削除: メニュー名と、**復元できないこと**、**個別リンク中の友だちの人数**（一覧の個別リンク数）、**デフォルト設定中かどうか**、**ワークフローからの参照は確認できないこと**（§C）

自分で補った値（既定値を仮に入れた等）は「補った」と明示する。**承認を得るまで次に進まない。**

### 4. 実行

- 更新は「取得 → 取得した値をそのまま載せる → 変更点だけ差し替える → `patchCreatorLineRichMenu`」（§A）。body の組み立てに迷ったら [examples/patch-body-six-split.json](examples/patch-body-six-split.json)、変更が1項目だけのときの通し方は [examples/chatbar-text-update-trace.md](examples/chatbar-text-update-trace.md)
- 更新は LINE 上でメニューを作り直すため、個別リンク中の友だちが多いほど時間がかかる。**途中で失敗した場合は元に戻そうとするが、その巻き戻し自体は保証されない**（[references/mcp-tools.md](references/mcp-tools.md) の副作用）。失敗しても勝手に再試行せず、まず現在の内容を取得し直す（「エラーが返ったとき」）
- デフォルト設定・解除・削除はそれぞれ1回の呼び出しで完了する

### 5. 結果の報告

何がどうなったかを平易な日本語で伝える（「ユーザーへの提示・コミュニケーション規約」）。更新後は**LINE アプリ側の表示が切り替わるまで時間差がある**ことを添える（LINE 側の反映タイミングは MOSH からは制御できない）。

## 必須ルール

### A. 更新は全置換。必ず `getCreatorLineRichMenu` から始める

`patchCreatorLineRichMenu` は名前が PATCH でも**部分更新できない**。`name` / `layout` / `backgroundMoshImageId` / `areas` / `chatBarText` / `chatBarOpenByDefault` の**6項目すべてが必須**で、送らなかった項目は「変更なし」ではなく**エラー**になる。文言だけ変えるときも、取得した他の5項目をそのまま載せ直す。

**思い出しや推測で埋めない。** 直前の会話に出た値であっても、`getCreatorLineRichMenu` の返り値を正とする。とくに `areas` は全エリア分の配列をそのまま持ち回る（項目の意味は [references/menu-schema.md](references/menu-schema.md)）。

`creatorLineChannelId` は body に存在せず**更新できない**。「このメニューを別の LINE公式アカウントに移して」はできないので、移動先アカウントで管理画面から作り直す案内をする。

### B. レイアウトを変えるなら、エリアと背景画像も必ず一緒に変える

`layout` は「分割数」と「画像サイズ系統」の両方を決める。片方だけ変えると壊れる。

- **エリア数**: レイアウトが要求する数と `areas` の件数が一致しないと、更新は 400 で拒否される（**loud fail**）
- **背景画像**: レイアウトのサイズ系統（大 / 小）が変わると必要な解像度も変わる。**サイズが合わない画像でも MOSH 側は素通しする**ため、拒否されるとしても LINE 側の一般的なエラーとしてしか返らない（**原因が分からないエラーになる**）
- **エリアの並び順**: 位置は `areas` の並び順で決まり、`label` では決まらない。並べ替えても保存され、**ラベルと実際の位置がズレたまま公開される**（**silent fail**）

レイアウトごとのエリア数・位置・必要な画像解像度は [references/menu-schema.md](references/menu-schema.md) が正本。背景画像の差し替え手順は [references/image-preparation.md](references/image-preparation.md)。

### C. 削除は復元できず、ワークフローからの参照は残る

`deleteCreatorLineRichMenu` は物理削除。以下は**自動で解除される**:

- デフォルト設定
- 個別コンタクトへのリンク（対象の友だちはメニューが消える）

一方、**ワークフローの「個別リッチメニューの付与」アクションに設定されたIDは消えない。** 削除後もそのステップは残り、実行しても付与できないメニューを指し続ける（**silent fail**。ワークフロー側にエラー表示は出ない）。

**MCP からはどのワークフローが参照しているかを調べられない。** したがって削除の承認を求めるときは、**「このメニューを使っているワークフローがあれば、そのステップは動かなくなります。管理画面のワークフロー側の確認をお願いします」と必ず添える**（「参照は無いようです」と断定しない）。

### D. タップして何も起きないエリアを作らない

各エリアの `action` は `url` と `postbackActions` の**両方のキーが常に必須**で、使わない側は `null` にする。**両方 `null` でも保存され、エラーにならない。** その場合タップしても何も起きない（**silent fail**）。

タグを付ける/外すアクションを入れるときは、**必ず `getCreatorContactTags` でタグIDの実在を確認してから入れる。確認できなければ推測せずユーザーに聞く**（保存時に検証されないため、誤りは公開後のタップ時まで表面化しない。**silent fail**）。

書き方の全仕様（`url` と `postbackActions` を併用したときの挙動、件数・文字数の上限）は [references/menu-schema.md](references/menu-schema.md)。

### E. 文字数は目視で数えない

`chatBarText`（上限14）・`name`（上限300）は **UTF-16 コードユニット数**で判定される。絵文字の多くは見た目1文字でも**2**としてカウントされる（例: 「👍タップしてメニューを開く」は目視だと13文字に見えるが、実際は 👍=2 + 残り12文字 = **14**）。

**絵文字を含む文言を確定する前は、暗算・目視で「大丈夫」と判断しない。** 必ず1文字ずつ書き出して内訳を数え直す（数え方の詳細・検証手順は [references/menu-schema.md](references/menu-schema.md)）。

## ユーザーへの提示・コミュニケーション規約

- 応答は平易な日本語で行う。**内部用語・内部フィールド名をそのまま出さない**: `layout` / `areas` / `chatBarText` / `backgroundMoshImageId` / `postbackActions` / `SIX_SPLIT` / `creatorLineChannelId`。ユーザーが目にしている言葉は「レイアウト（6分割など）」「ボタン」「メニューバーの文言」「背景画像」「タップしたときの動き」「LINE公式アカウント」
- エリアは `label` そのままではなく「左上のボタン（A）」のように**位置が伝わる形**で示す（位置の対応は [references/menu-schema.md](references/menu-schema.md)）
- JSON・HTTP用語・ステータスコード・ツール名をユーザー向け文面に出さない
- **完了形で書けるのは、対応するツールを実際に呼んで成功した後だけ。** 承認を待つ提示では「以下の内容で進めてよいですか」と書き、まだ実行していないことを明示する
- **ID を創作しない。** リッチメニューID・タグID・背景画像の識別子は、ツールの返り値かユーザーから受け取った値だけを使う。用意できなければ管理画面での操作を案内する
- 取得した情報に無い事実（このメニューの表示回数、どのワークフローが使っているか等）を補って語らない
- **できない理由も仕組みで説明しない。** 「作成のエンドポイントが MCP に公開されていない」ではなく「リッチメニューの新規作成は MOSH の管理画面からのみ行えます」と、ユーザーから見える事実だけで説明する

## エラーが返ったとき

**自分の判断で再試行しない。** 原因と対処をユーザーへ平易な日本語で伝え、**再試行するかどうかはユーザーに決めてもらう**。原因と対処の一覧は [references/mcp-tools.md](references/mcp-tools.md) の「エラーの読み方」が正本。

- **入力に原因があるエラー**（件数不一致・文字数超過・URL形式・画像の不備）は、内容を直さずに再送しない。直してから改めて承認を取る
- **LINE 側の不調が疑われるエラー**（「LINEへのリッチメニュー操作に失敗しました。」）は、原因を切り分ける材料（画像の解像度・容量・形式）を先に確認する。それでも原因が分からない場合だけ、**時間を置いてもう一度試すかをユーザーに確認**する。自動で連続再送はしない
- **エラーが返ったときは、状態を確認するまで結果を報告しない。** 更新なら `getCreatorLineRichMenu`、削除なら `getCreatorLineRichMenus` を呼び直して現状を確かめる（更新の巻き戻しも削除の失敗も、エラーメッセージだけからは確定できない）
