# リッチメニューの構造（正本）

作成（`postCreatorLineRichMenu`）・更新（`patchCreatorLineRichMenu`）の body を組み立てる前に読む。**ツールの選び分け・承認の要否・削除の影響は SKILL.md が正本**（本ファイルでは再定義しない）。ここはリッチメニュー1件の中身（レイアウト・エリア・アクション・上限値・タップ時の処理経路）を扱う。


## body の項目

| 項目 | 型 | 制約 | 作成 | 更新 |
|---|---|---|---|---|
| `creatorLineChannelId` | integer | 連携中（`getCreatorLineChannels` で `isConnected: true`）のアカウント | **必須** | **存在しない（変更不可）** |
| `name` | string | 1〜300文字 | 必須 | 必須 |
| `layout` | enum | 下表の10値 | 必須 | 必須 |
| `backgroundMoshImageId` | string | 1文字以上。[image-preparation.md](image-preparation.md) | 必須 | 必須 |
| `areas` | array | 1〜8件。**layout の要求数と一致必須** | 必須 | 必須 |
| `chatBarText` | string | 1〜14文字 | 必須 | 必須 |
| `chatBarOpenByDefault` | boolean | true でトーク画面を開いたときメニューを開いた状態にする | 必須 | 必須 |

- **全項目必須**（部分更新は不可）。余分なキー（`id` / `isDefault` / 日時 / 説明用の `_` 始まりキー等）を入れると入力エラーになる
- 作成の戻り値は新しいリッチメニューの `id` だけ

### 文字数の数え方（`name` / `chatBarText`）

上限は **JavaScript の文字列長（UTF-16 コードユニット数）** で判定される。

- ひらがな・漢字・全角記号は 1
- 絵文字の多く（U+10000 以上）は **2**。異体字セレクタ・肌色修飾子つきはさらに増える
- 超過すると入力エラー（loud fail）

**検証手順（暗算しない）**: 1文字ずつ書き出し、U+10000 以上は 2、それ以外は 1 で加算する（実例: 「👍タップしてメニューを開く」は目視13に見えるが 👍=2 + 12 = **14**、余裕ゼロ）。13〜14 なら短縮を提案する。Bash が使えるなら `node -e "console.log(\"文言\".length)"`（`[...文言].length` はコードポイント数なので使わない）。

## レイアウトの10値

| `layout` | 画面での呼び方 | サイズ | エリア数 | ラベル（配列順） |
|---|---|---|---|---|
| `SIX_SPLIT` | 6分割 | 大 1200×810 | 6 | A〜F |
| `TOP_ONE_BOTTOM_THREE` | 上1＋下3 | 大 1200×810 | 4 | A〜D |
| `LEFT_RIGHT_SPLIT` | 左右2分割 | 大 1200×810 | 2 | A, B |
| `ONE_BLOCK` | 1ブロック | 大 1200×810 | 1 | A |
| `THREE_SPLIT` | 3分割（小） | **小 1200×405** | 3 | A〜C |
| `ONE_BLOCK_SMALL` | 1ブロック（小） | **小 1200×405** | 1 | A |
| `SIX_SPLIT_WITH_TWO_TABS` | 6分割（タブあり） | 大 1200×810 | **8** | TAB1, TAB2, A〜F |
| `TOP_ONE_BOTTOM_THREE_WITH_TWO_TABS` | 上1＋下3（タブあり） | 大 1200×810 | **6** | TAB1, TAB2, A〜D |
| `LEFT_RIGHT_SPLIT_WITH_TWO_TABS` | 左右2分割（タブあり） | 大 1200×810 | **4** | TAB1, TAB2, A, B |
| `ONE_BLOCK_WITH_TWO_TABS` | 1ブロック（タブあり） | 大 1200×810 | **3** | TAB1, TAB2, A |

- **エリア数の不一致は「レイアウトとエリアの数が一致しません。」で拒否**（loud fail）。タブありは**タブ2つ分を含めた数**
- **サイズは分割数の印象で判定しない。** 小は `THREE_SPLIT` と `ONE_BLOCK_SMALL` の2つだけ。`LEFT_RIGHT_SPLIT`（2分割）もタブあり4種も**大**
- 解像度は必ずこの表の値。LINE公式ヘルプの一般的な推奨値（2500×1686px 等）を持ち出さない

### レイアウトを変えるときの画像

| 変更 | 解像度 | 画像の描き直し |
|---|---|---|
| 大 ↔ 小 | 変わる | **必須**（解像度が合わない） |
| 同じサイズで分割だけ変わる（例: 6分割 → 上1＋下3） | 同じ | 解像度は合うが、**画像に描かれた区画と新しい区切りがズレる**ので原則描き直す |
| タブなし ↔ タブあり（同じ分割でも） | 同じ（1200×810） | **必須**。タブありは上 180px がタブの帯になり、ボタンの位置が全て下にずれる |

エリア数が減るレイアウト変更では、減った分のボタン設定（タブの切り替え先を含む）は body から消える。何が消えるかを提示に含める。

## エリアの位置（配列の順序が位置）

位置は**配列のインデックス**で決まり、`label` は表示用で位置決定に使われない（ラベルを入れ替えても保存され、位置とズレたまま公開される。silent fail）。**ラベルは常に上表の順で並べる。**

座標（px。x, y, 幅×高さ。左上原点）:

| `layout` | 位置（配列順） |
|---|---|
| `SIX_SPLIT` | A 左上 (0,0,400×405) / B 中上 (400,0) / C 右上 (800,0) / D 左下 (0,405) / E 中下 (400,405) / F 右下 (800,405) |
| `TOP_ONE_BOTTOM_THREE` | A 上全幅 (0,0,1200×405) / B 左下 (0,405,400×405) / C 中下 (400,405) / D 右下 (800,405) |
| `LEFT_RIGHT_SPLIT` | A 左 (0,0,600×810) / B 右 (600,0,600×810) |
| `ONE_BLOCK` | A 全面 (0,0,1200×810) |
| `THREE_SPLIT` | A 左 (0,0,400×405) / B 中 (400,0) / C 右 (800,0) |
| `ONE_BLOCK_SMALL` | A 全面 (0,0,1200×405) |
| タブあり共通の先頭2件 | TAB1 左タブ (0,0,600×180) / TAB2 右タブ (600,0,600×180) |
| `SIX_SPLIT_WITH_TWO_TABS` | タブ2件 → A (0,180,400×315) / B (400,180) / C (800,180) / D (0,495,400×315) / E (400,495) / F (800,495) |
| `TOP_ONE_BOTTOM_THREE_WITH_TWO_TABS` | タブ2件 → A 上全幅 (0,180,1200×315) / B (0,495,400×315) / C (400,495) / D (800,495) |
| `LEFT_RIGHT_SPLIT_WITH_TWO_TABS` | タブ2件 → A 左 (0,180,600×630) / B 右 (600,180,600×630) |
| `ONE_BLOCK_WITH_TWO_TABS` | タブ2件 → A (0,180,1200×630) |

**背景画像の意匠とこの区切りが合っているかは誰も検証しない**（silent fail）。**LINE はタブを描画しない**ため、タブありでは上 180px にタブ2つの見た目（どちらのタブが選択中か含む）を画像に描き込む必要がある。

## エリアのアクション（`action`）

```json
{ "label": "A", "action": { "url": null, "postbackActions": null, "richMenuSwitch": null } }
```

`url` / `postbackActions` / `richMenuSwitch` の**3キーが常に必須**。使わないキーは `null`（キーごと省くと入力エラー）。旧形式で保存されたメニューも、詳細取得では3キーそろって返る。

| `richMenuSwitch` | `url` | `postbackActions` | タップしたときの動作 | Webhook |
|---|---|---|---|---|
| なし | あり | なし | URL を開く（MOSH の中継ページ経由） | 不要 |
| なし | あり | あり | URL を開き、開くときにアクションも実行。**アクションの失敗は遷移を止めない**（「ページは開いたがタグが付かない」が起こりうる） | 不要 |
| なし | なし | あり | アクション（メッセージ送信 / タグ付与・削除）を実行 | **必要** |
| あり | （無視される） | なし / あり | 指定したリッチメニューに切り替える。アクションがあれば切り替えと合わせて実行 | アクション実行と記録に**必要** |
| なし | なし | なし | **何も起きない。エラーにもならない**（silent fail） | — |

### `richMenuSwitch`（メニュー切り替え）

- 形: `{ "richMenuId": 1181 }` または `null`
- **切り替え先は同じ LINE公式アカウントのリッチメニューだけ**（レイアウトは問わない）。別アカウントのメニュー →「切り替え先のリッチメニューを指定できません。」、存在しない・削除済みのID →「切り替え先のリッチメニューが見つかりません。」
- **タブ以外のエリアにも設定できる**（通常のボタンで別メニューへ切り替える用途）
- **作成時は自分自身を指定できない**（まだIDが無い）。作成するメニュー自身を表すタブは `null` にする。更新時は自分自身も指定できる
- 2つのメニューを互いのタブで行き来させる作成順は SKILL.md §F が正本
- 未設定（`null`）のタブは保存できるが、**タップしても切り替わらない**
- 切り替えが起きると、その友だちは**切り替え先メニューに個別リンクされた状態として記録される**（一覧の個別リンク数に入る。Webhook が届いた場合）
- 切り替え先のメニューには、MOSH が LINE 側に切り替え用の別名（エイリアス）を自動で作る。ユーザーに説明する必要は無い

### `url`

- 1000文字以内、URL として妥当な形式（不正なら入力エラー）
- 「〇〇のページに飛ばして」で URL が分からないときは**推測して組み立てない**。ユーザーに確認する
- タップ時は MOSH の中継ページを経由して遷移し、遷移先 URL に `event` / `slug` などのクエリが付く。**既存の `slug` クエリは削除される**ので、`slug` クエリに依存する URL は意図通り動かない

### `postbackActions`

配列で **1〜3件**（使わないなら配列ごと `null`。空配列 `[]` は入力エラー）。要素は次の3種。

```json
{ "postbackActionType": "sendMessage", "messages": [{ "messageType": "text", "message": "お問い合わせありがとうございます！" }] }
{ "postbackActionType": "addContactTag", "contactTagId": 123 }
{ "postbackActionType": "removeContactTag", "contactTagId": 123 }
```

- `messages` は **1件のみ**、`messageType` は `text` のみ、`message` は 1〜5000文字。本文中の URL は配信時に短縮URLへ置換される
- `contactTagId` は**保存時に実在確認される**。自分のタグでないIDが1つでもあると「指定されたタグが見つかりません。」で拒否（loud fail）。事前に `getCreatorContactTags` で確認しておけば拒否を避けられる

## ボタンを押しても反応しないとき（Webhook の確認）

上の表で「Webhook 必要」のエリア（URL を開かないエリア＝メッセージ送信・タグの付け外しだけ、およびメニュー切り替えに付けたアクション）は、**タップを LINE から MOSH が Webhook で受け取って実行する**。LINE公式アカウントの Webhook が MOSH 以外（別ツール）を向いている、または OFF だと、**保存も表示も正常なのにタップしても何も起きない**（MOSH からは検知できない）。

切り分け:

- **同じメニューの URL を開くボタンは動いている** → メニュー自体は LINE に反映済み。キャッシュ・アプリ再起動の案内は不要。Webhook を疑う
- **URL を開くボタンで、ページは開くがアクションだけ動かない** → Webhook は関係しない経路。Webhook を案内せずサポートへの相談を案内する
- アクションを変えた直後なら、変更が保存（更新が成功）済みかを先に確かめる

ユーザーに案内する確認手順（Webhook の状態は MCP から確認できない）:

1. MOSH 管理画面の「LINE公式アカウント管理」で該当アカウントの「設定」を開き、上部に「Webhook が OFF です」と出ていないか（出ていなくても正常とは限らない）
2. LINE Developers コンソールの Messaging API チャネルの「Messaging API設定」タブで「Webhookの利用」が ON か
3. 同じタブの Webhook URL が、1 の「設定」画面の「Messaging API設定」にある Webhook URL と同じか（別ツールの URL になっていると MOSH に届かない）

3つとも問題なければ MOSH サポートへの相談を案内する。**LINE の Webhook URL は1つしか設定できない**ため、別ツール（Lステップ等）と同じアカウントを併用していると、Webhook が必要なボタンは MOSH では動かせない。その場合は URL を開くボタン（アクション併用）に置き換える案を出す。
