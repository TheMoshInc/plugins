# Creator Context（現状スナップショット）

## Overview

MOSH MCP の参照系ツールを並列に呼び、運用中の SNS はユーザーに聞いて、クリエイターの現状を1枚の Markdown にまとめて保存する。**読み取り専用で、MOSH 側の状態は一切変えない。** 出力は後続の Skill / Agent が読む前提なので、セクション名は [references/snapshot-template.md](references/snapshot-template.md) に固定し、個人情報（名前・メール）は書かない。

完了条件: スナップショットファイルが保存され、会話に要約（5行以内）とファイルパスが返っている。

## When to use

- LP・ワークフローの作成・設計や、レビュー・分析の前に、クリエイターの現状を揃えたい
- 「このクリエイター、何を売っていて、どれくらいの規模か」を一度に知りたい
- 既存のスナップショットが古い（取得日時から7日以上）ので更新したい

## When NOT to use

- 売上の内訳・期間比較・明細 → `sales-reporter`
- 商品やプランの詳細内容（説明文・特典・クーポン） → `product-navigator`（プラグイン `product-navigator-plugin` 側のスキル）
- 特定の顧客・コンタクトを探す、タグを付ける → `customer-manager` / `contact-list-manager`
- ワークフローの中身の点検 → `workflow-review`
- MOSH に何かを作る・変える依頼 → 各構築スキル（本スキルは読むだけ）

## Workflow

収集（並列）→ SNS確認 → 集計 → 保存 → 要約。承認ゲートは無い（不可逆操作が無いため）。ユーザーへの質問は、Step 1 の前提確認（環境・既存ファイル）と Step 2.5 の SNS の1往復だけ（エラー時を除く。後続のヒアリングに渡すときは SNS も聞かない）。

### 1. 前提の確認

- 接続先: MCP サーバーが複数あり、環境が分かれている場合（本番と検証環境など）は、どれを使うかをユーザーに1回だけ確認する。指定が無ければ本番
- 保存先: 引数で指定があればそのパス。無ければカレントディレクトリに `creator_context_{環境}_{YYYYMMDD}.md`（環境をファイル名に含め、同日の本番と検証環境が上書きし合わないようにする）
- 同じ環境の既存ファイルがあり、取得日時が7日以内なら「既存を使うか、取り直すか」を聞く

### 2. 収集

[references/collect-plan.md](references/collect-plan.md) を読み、領域ごとの呼び出しと「書く値」に従う。依存のない呼び出しは1ターンで並列に出す。件数上限・PII・失敗時の扱いは下の「必須ルール」に従う。

### 2.5 SNS の確認（1往復）

運用中の SNS の URL と、分かればフォロワー数をユーザーに聞く（`collect-plan.md` §9）。MCP からは取れないため、この1往復だけはユーザー申告に頼る。回答が無ければ「取得失敗（未回答）」として進める。

**続けてヒアリング（要件の聞き取り）を行う場合は、ここでは聞かない。** 呼び出し元のスキルから指示されたとき、またはユーザーが続けてヒアリングを行うと述べたときは、SNS を「未確認（後続のヒアリングで確認）」と書き、ヒアリングの1画面で聞く（質問の往復を増やさない）。

### 3. 集計と派生値

- 商品の区分（買い切りのみ / サブスクあり。定義は `collect-plan.md` §1）
- 売上の商品別上位（`rows[].plans` を商品で合算。`productId` が null の旧サービス分は `serviceName` 単位で残す。詳細は `collect-plan.md` §5）
- 要約の数字は本文の値と一致させる（別途計算し直さない）

### 4. 保存

[references/snapshot-template.md](references/snapshot-template.md) の雛形にそのまま流し込み、Markdown ファイルとして保存する。セクションの追加・改名・削除はしない。

### 5. 要約を返す

会話には、要約（5行以内）・保存パス・取得できなかった項目だけを返す。表の再掲はしない。5行に収まらない内訳（LP・WF・タグの種類別など）は要約に入れず本文に回し、1行は1テーマにする（テーマは 商品 / 集客の装置 / 売上 / 規模 / SNS）。箇条書きは入れ子にしない（サブ項目も1行に数える）。評価語・傾向語（好調・不調・良い・悪い・多い・少ない・伸びている・落ち着いている 等）は書かず、事実（数字・名前・種別）だけを書く。

## 必須ルール

### A. 個人情報を書かない

スナップショットに名前・メールアドレス・アバターURL・LINE表示名を書かない。件数と ID のみ。名前・メールが返るツール（購読者・顧客・コンタクト）は `limit: 1` で呼び、件数だけ使う。

### B. 推測で埋めず、全件も取らない

取れなかった値は「取得失敗（理由）」と書き、0件とは書き分ける（0件はエラーではない）。1領域が失敗しても他は続ける。一覧の表は各上位20件までで、`totalCount` が超えるときは件数だけ記録する。**状態別の件数（LP・WF の ACTIVE など）は、上位20件の内訳から推測しない**（取り方は `collect-plan.md` §3・§4）。件数を返さないツール（LINE公式・素材）の総数は書かない（理由と書き方は `collect-plan.md` §4・§8）。恒常的に取れない項目の一覧は雛形末尾の節が正本。

### C. 環境を取り違えない

ファイル冒頭に環境（本番 / 検証環境など）を必ず書く。検証環境のスナップショットを本番の判断材料にしない。

### D. 売上は申込ベースと明記する

売上サマリーは申込月に契約満額を計上する定義。入金・手取りではない。ファイル内に「申込ベース」と書き、期間は両端含めて365日以内にする（詳細は `collect-plan.md` §5）。

## よくあるミス

上のセクションでカバー済みの事項は再掲しない。ここは他セクションでカバーされない落とし穴のみ（追記前に既存セクション・references でカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| 商品一覧の件数を「顧客が買える商品の全部」と書く | 旧サービス（2.0移行前）の商品は一覧に出ない。母集団の違いの注記は、雛形の顧客セクションの固定1行で書く |
| 全件を取るために `offset` を回し続ける | 一覧は上位20件まで。黒板は俯瞰用で、網羅は後続 Skill が必要時に行う |
| 全フィールド必須のツールで未使用キーを省略する | `postCustomersSearch` / `postCreatorProductSubscribers` / コンタクト検索は省略すると 400。`collect-plan.md` の既定値をそのまま渡す（コンタクト検索の `tag` は `null`。理由は §7） |
| LP を `status` 未指定の1回だけで数える | 既定は PUBLISHED + DRAFT のみで、ARCHIVED が落ちる。状態別の取り方は `collect-plan.md` §3 |
| 要約で「売上が伸びている」と評価する | 評価・傾向は書かない（後続の設計・分析 Skill の仕事。規則は Step 5） |

## エラーが返ったとき

| 症状 | 対処 |
|---|---|
| 401 | トークン失効。ユーザーに MCP の再認証を依頼し、取得済みの領域だけで保存するか中断するかを聞く |
| 400（売上サマリー） | 期間が366日以上。`startDate` を1年前の翌日にする |
| 400（検索系） | 必須キーの欠落。`collect-plan.md` の既定値と突き合わせる |
| 空配列が多い | エラーではない。検証環境に接続していないか環境を確認し、0件のまま記録する |
| 一部ツールが存在しない | MCP サーバーが古い。その領域を「取得失敗（ツール不在）」として続行する |
