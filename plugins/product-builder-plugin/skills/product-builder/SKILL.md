# MOSH 商品ビルダー

## Overview

MCP ツール（以下ツール名は OpenAPI の operationId で記す。実際のツール名にはサーバー識別子の接頭辞（例: `mcp__<server>__postCreatorProduct`）が付くが、その形は環境により異なるため本書では付けない）を使って、MOSH クリエイターの商品とプランを作成・更新・複製・公開・削除する。

**扱えるのは商品とプラン、そしてプランに紐づく設定**（商品名・説明・画像（手元のファイルのアップロードを含む）・注意事項・キャンセルポリシー・申し込み後の流れ・公開状態、プランの価格・課金サイクル・決済方法・分割払い・受付期間・定員・特典・表示順・公開状態・複製、プランの提供コンテンツ（会員サイトの紐付け）・購入後設定（サンクスページ／メール・自動リダイレクト・感想レポート）・会員サイトのライセンス設定（閲覧できるフォルダ・閲覧期限）・クーポン（発行・有効／無効の切り替え・削除））である。ゲストの購入者情報・決済情報・売上は扱わない。**商品ごとの複製**はこのスキルでは扱えない（管理画面を案内する）。

商品とプランは別々に扱える。**既存の商品にプランを追加する・既存のプランを直すのが最も多い依頼**で、商品の新規作成を伴わない。プランの操作では、まず対象の商品を一覧から特定する。

商品を公開するには**公開中のプランが 1 つ以上必要**である。商品も新しく作る依頼では「商品を作る → プランを作る → 商品を公開する」の順になることを最初に伝える。

プランの設定（提供コンテンツ・購入後設定・ライセンス・クーポン）は、プランを作ったあとに個別のツールで行う。会員サイトの紐付けはゲストが見る画面を変えるので、影響を伝えて承認を取る（手順 7）。

プロダクトの呼称と API の項目名の対応: 申込者向けサイト（旧会員サイト）↔ `isUsingLegacySite` / `useLegacyMembershipSite`、提供コンテンツ ↔ `offeredContents`、ライセンス ↔ `LicenseSetting`（ツール名の一部）、クーポンの割引率 (%) ↔ `percentOff`、値引額 (円) ↔ `amountOff`、発行枚数 ↔ `maxRedemptions`、有効期限 ↔ `expiresAt`、回数設定（初回割引／永久割引）↔ `subscriptionDurationType`。ユーザーにはプロダクトの呼称で話す。

送信を組み立てる前に、商品・プラン本体なら [references/mcp-tools.md](references/mcp-tools.md)（ツールのパラメータ）と [references/content-schema.md](references/content-schema.md)（項目の範囲・組み合わせ・拒否メッセージ）を、プランの設定・複製・クーポンなら手順 7〜11 が示す領域ファイル 1 本（ツール・項目・拒否メッセージを含む）を読む。

## 前提条件

| 必要なもの | MCP で実在確認できるか | できない場合の扱い |
|---|---|---|
| 商品 ID | できる（`getCreatorProducts` の一覧から名前で特定） | — |
| プラン ID | できる（`getCreatorProductPlans` の一覧から名前で特定） | — |
| 商品画像の ID（`imageIds` / `steps[].imageId`） | 既存の画像は**一覧・検索できない**（いま付いている画像だけ `getCreatorProduct` で読める） | 手元の画像は MCP でアップロードして ID を得る（[references/media-upload.md](references/media-upload.md)）。それ以外の既存画像はユーザーから ID を受け取る |
| 公開中のプランの有無 | できる（`getCreatorProductPlans` で公開状態を確認） | — |
| 対象が旧サービスでないか | できる（商品の一覧・詳細の `isLegacyService`。プランの取得には無い） | —（扱いは手順 2） |
| クリエイターの決済代行会社 | **できない**（確認するツールが無い） | 課金回数・初回価格・価格の上限は決済代行会社で変わる。課金回数と価格の上限は拒否されて、初回価格は読み戻して初めて分かる（手順 4）ため事前に断定しない |
| 事業者情報の登録 | **できない**（確認するツールが無い） | 公開時に拒否されて初めて分かる。事前に断定しない |
| プランの購入者の有無 | 部分的にできる（`getCreatorProductPlan` の `isDeletable` が `false` なら購入者がいるか、判定できなかった） | `false` は「購入者がいる可能性がある」と扱う。拒否されたら理由をそのまま伝える |

## When to use

- 商品を新しく作りたい・既存商品の名前・説明・画像・注意事項・キャンセルポリシー・申し込み後の流れを変えたいとき
- 手元の画像を商品画像・サンクスページのバナーとして付けたいとき（アップロードもこのスキルで行う）
- **既存の商品にプランを追加したいとき**（商品を作り直す必要はない）。商品の新規作成に続けてプランを作りたいとき
- 既存プランの価格・定員・受付期間・特典・決済方法などを変えたい・表示順を並び替えたいとき
- 既存のプランをもとに、同じ内容のプランをもう 1 つ作りたいとき（プランの複製）
- 商品やプランを公開・限定公開・非公開に切り替えたい・削除したいとき
- プランのクーポン（割引コード）を発行したい・一覧を見たい・無効にしたい・削除したいとき
- プランに会員サイトを紐付けたい・別の会員サイトに変えたい・紐付けを外したいとき。会員サイト経由で購入したゲストが閲覧できるフォルダや閲覧期限（ライセンス）を変えたいとき
- 購入直後の画面と完了メール（サンクスページ／メール）の本文やバナー、購入完了後の自動リダイレクト、感想レポートの投稿依頼の自動送信を設定・切り替えたいとき

## When NOT to use

- 商品・プランの内容を**見るだけ** → `product-navigator` スキル
- 売上・購入者の確認 → `sales-reporter` スキル
- 会員サイトそのもの（フォルダ・コンテンツ・タグ・サイト設定）の作成・編集 → `membership-site-builder` スキル
- 予約メニューをプランに**紐付ける** → 管理画面（このスキルでできるのは解除だけ）
- **商品ごと**複製する（プランをまとめて別の商品として複製する） → 管理画面（このスキルでできるのはプラン 1 件の複製だけ）
- クーポンの**内容を変える**（コード・割引・枚数・期限・回数設定） → できない。新しいクーポンを作成し、古いクーポンを無効にする（このスキルで案内する）
- 決済リンク・収益分配の設定 → 管理画面
- ファイル共有（共有 URL で配る資料・動画）へのアップロード → `file-share` スキル（商品画像・サンクスページのバナーのアップロードはこのスキル）
- LP（ランディングページ）の作成・編集 → `lp-builder` スキル
- ワークフロー（ステップ配信） → `workflow-builder` スキル

## Workflow

### 1. 要件ヒアリング

ユーザーに以下を確認する（自明なら聞き直さない）:

- 商品とプランのどちらの話か。新規作成か、変更か、削除か
- **プランの話なら、どの商品のプランか**（プランは必ず商品に属する）。名前・キーワードで良い。ID をユーザーに求めない
- 既存プランが対象なら、どのプランか
- 変えたい項目と、その内容
- 公開状態を変えるか

**商品の新規作成**なら、必須 4 項目（商品名・商品説明・注意事項・キャンセルポリシー）をこの段で揃える。**空欄を仮の文言で埋めない**。決まっていない項目があれば、そのまま聞く。

**プランの新規作成**は、次の順で確認する。作成後に変えられない項目（[references/content-schema.md](references/content-schema.md) の「作成後に変更できない項目」）が先に来る順序になっている。

1. 課金サイクル（買い切り / 月額 / 年額）
2. 価格
3. （サブスクリプションのみ）課金回数・初回価格・課金開始日。指定が無ければ無制限・通常価格と同額・購入後すぐ（課金回数と初回価格は決済代行会社によって使えない。手順 4）
4. 決済方法（**買い切りだけ聞く**。クレジットカード / 銀行振込。銀行振込なら振込期限（申込から何日以内か。指定が無ければ標準の 15 日）も聞く）。サブスクリプションはクレジットカードのみで、銀行振込は選べない
5. 分割払いにするか（買い切りのみ）
6. 受付期間（買い切りは販売受付期間、サブスクリプションは申込期間）。買い切りで締切を決めるなら**開始日時も必ず聞く**（手順 4）
7. 定員と残席表示
8. 公開状態

聞き取れなかった項目は [references/content-schema.md](references/content-schema.md) の既定値で埋めてよい。埋めた項目は保存前にユーザーへ提示する。

**プランの設定**（提供コンテンツ・ライセンス・購入後設定）の話なら、次の順で確認する。会員サイトの紐付けが他の設定の前提になり、ライセンスは紐付けたあとにしか設定できないため、この並びになっている。

1. 会員サイトを紐付けるか。紐付けるならどの会員サイトか（名前で良い）。影響の伝え方は手順 7
2. ライセンス（閲覧できるフォルダ・今後追加されるフォルダを含めるか・閲覧期限）
3. サンクスページ／メール（本文 → バナー画像 → バナーのリンク先）
4. 自動リダイレクト（移動先の URL と待機秒数。0〜15 秒）
5. 感想レポートの投稿依頼を自動で送るか

依頼された設定だけを扱えばよく、全部を聞き直す必要はない。複数を頼まれたときはこの順に進め、クーポンは最後にプランの価格が決まってから作る（購入後設定とクーポンは互いに独立）。ただし依頼が「会員サイトを紐付けて」だけのときは、ライセンスの既定値（全フォルダ閲覧可・今後追加分も含む・無期限）で良いかを一言確認する。

**プランの複製**なら、どのプランを複製するかに加えて、**提供コンテンツ（会員サイトの紐付け）も複製するか**を確認する。

**クーポンの発行**は、内容を作成後に変えられないため、[references/coupons.md](references/coupons.md) の「ヒアリング順（発行）」で全項目をこの段で確定させる。

### 2. 対象の特定（商品の新規作成以外はすべて）

**既存商品へのプラン追加も含む。** プランは必ず商品に属するので、作成でも先に商品を特定する。

1. `getCreatorProducts` で一覧を取得し、ユーザーが言った名前から対象の商品を特定する。商品が多いときは `searchQuery`（商品名・プラン名の部分一致）で絞る
2. 完全一致しない場合は候補を提示して選んでもらう（**勝手に決めない**）。対象が旧サービス（商品一覧・詳細で `isLegacyService: true`。プランが対象なら属する商品で見る）なら**書き込まずにここで止め**、[references/content-schema.md](references/content-schema.md) の「旧サービス（isLegacyService: true）」の案内文で返す（旧サービスを「商品」と呼ばず、項目名・値も出さない）
3. `getCreatorProductPlans` でその商品のプランを取得する。既存プランが対象ならプラン名から特定し、プランを追加するなら**既にある同じ内容のプランと重複しないか**を確認する
4. 既存の商品・プランを変更するなら、`getCreatorProduct` / `getCreatorProductPlan` で現在の内容を取得し、**変更前の値を控える**。差分をユーザーに示すために使う
5. プランの設定を変えるなら、対応する取得ツール（`getCreatorProductPlanOfferedContents` / `getCreatorMembershipSiteProductPlanLicenseSetting` / `getCreatorProductPlanSettingsThanks` / `getCreatorProductPlanSettingsRedirect` / `getCreatorProductPlanSettingsReviewReport`）で**現在の設定を読み、変更前の値を控える**
6. クーポンの話なら、`getCreatorProductPlanCoupons` でそのプランのクーポン一覧を取得する。既存のクーポンが対象なら**クーポン名またはコード**で特定し、新しく作るなら**同じコード・同じ内容のクーポンがすでに無いか**を確認する

商品を新しく作る依頼だけ、この手順を飛ばして手順 3 へ進む。

### 3. 商品の作成または更新

**新規作成**は `postCreatorProduct` を呼ぶ。作成された商品は**必ず非公開**で始まる。作成時に公開状態は指定できない。**同じ内容を再送すると別の商品がもう 1 つ作られる。** 失敗したように見えても、再試行の前に `getCreatorProducts` で重複を確認する。

**更新**は `patchCreatorProduct` を呼ぶ。送ったフィールドだけが変わる。ただし次の 2 つは**配列まるごとの置き換え**になる:

- `imageIds` … 送った配列がそのまま新しい画像一覧になる。**1 枚追加したいときも、既存の ID を含めた全件を送る**
- `steps` … 同上。1 ステップだけ直したいときも全ステップを送る

既存の値を保つには `getCreatorProduct` で取得した値をそのまま含めて送る。ここを省くと**黙って消える**。

手元の画像を付けるときは、送る前に [references/media-upload.md](references/media-upload.md) の手順でアップロードし、返った ID を使う。

送信前に下の「セルフレビューチェックリスト」を確認する。`steps` を送る場合は [examples/update-product-steps.json](examples/update-product-steps.json)、新規作成は [examples/create-product.json](examples/create-product.json) の形を参照する。保存したら手順 12 で読み戻す。

### 4. プランの作成

手順 2 で特定した商品（新しく作った商品でも、既存の商品でもよい）に対して `postCreatorProductPlan` を呼ぶ。**1 つの商品に複数のプランを並べられる**ので、プランを足すために商品を作り直さない。リクエストの形は [examples/create-plan-one-time.json](examples/create-plan-one-time.json)（買い切り）と [examples/create-plan-subscription.json](examples/create-plan-subscription.json)（サブスクリプション）を参照する。

- **依頼に「公開で」と書かれていても、まず `PRIVATE` で作成する。** 読み戻して内容を確認してもらい、承認を得てから公開に切り替える
- `orderNum` は必須項目だが、作成時は自動採番されるため送った値は無視される。並び替えは手順 6 で行う
- 課金回数（`iterations`）は Stripe、初回価格（`initialPrice`）は fincode のクリエイターだけが使える。どちらの決済代行会社かは事前に分からない。課金回数は拒否されたら理由をそのまま伝えて代案を相談する
- 初回価格を指定したら、作成後に読み戻して初回価格が空（`null`）になっていないか確かめる。Stripe では拒否されずに無視されるため、空なら「この決済代行会社では初回価格を使えなかった」と伝える（content-schema の「初回価格」）
- **同じ内容を再送すると別のプランがもう 1 つ作られる。** 失敗したように見えても、再試行の前に `getCreatorProductPlans` で重複を確認する
- 買い切りで締切だけを頼まれたら（「12月末まで受付」など）、**開始日時をユーザーに聞いてから送る**。勝手に埋めない（示してよい選択肢は content-schema の「課金サイクルと受付期間の対応」）

### 5. プランの更新

`patchCreatorProductPlan` を呼ぶ。**部分更新には対応していない。** 必ず `getCreatorProductPlan`（詳細）か `getCreatorProductPlans`（一覧）で同じプランの現在値を読み（一覧と詳細は同じ項目を返す）、**変えない項目もそのまま含めた全項目**を送る。

- 課金サイクル・課金回数・初回価格は現在値をそのまま送る（変えたいなら新しいプランを作る。正本は content-schema の「作成後に変更できない項目」）
- 課金開始日は**変えないなら 3 項目とも省略する**（取得値をそのまま送り返すと拒否される。条件は content-schema の「課金開始日」）
- 買い切りで締切を足す・変えるとき、現在の開始日時が未設定（制限なし）なら手順 4 と同じ

割引前の価格（`discountPrice`）は、現在値をそのまま送っても消える・拒否されることがある。特に**買い切りで価格を割引前の価格以上に上げると拒否される**ので、送る前に比べ、割引前の価格も上げるか割引表示をやめるかをユーザーに確かめる（条件は [references/content-schema.md](references/content-schema.md) の「割引前の価格と価格の更新」）。

**公開中または購入者がいるサブスクリプションプランは、プラン名と価格を変更できない。** 取得したプランの `isNameEditable` / `isPriceEditable` で事前に判定できる。変更できないときは送り直さず、**「新しいプランを作成して、このプランを非公開にする」**を案内する。

定員は現在の購読者数未満にできない。保存したら手順 12 で読み戻し、価格を変えたときは**割引前の価格も**確かめる。

**更新がエラーで終わっても、途中まで反映されていることがある**（価格だけは元に戻るが、プラン名・公開状態・定員は新しい値で残りうる）。エラーが返ったら（拒否を含む）、報告の前に `getCreatorProductPlan` で読み戻し、変わってしまった項目があれば提示する。

### 6. プランの表示順を並び替える

`patchCreatorProductProductPlansReorder` を呼ぶ。

- **`productId` は数値で渡す**（他のプラン操作は文字列）
- 先に `getCreatorProductPlans` で全プランを取得し、**非公開を含む全件**を並べたい順に並べて送る
- 含めなかったプランは既存の相対順のまま末尾に回る。一部だけ送ると意図しない順序になる
- 保存したら手順 12 で読み戻す

### 7〜11. プランの設定・複製・クーポン

依頼に該当する領域ファイルを**送信の前に読み**、その番号付き手順に従う。下の表の「抜けやすい決め事」は要約で、正本は各ファイル。

| 手順 | 依頼 | 読むファイル | 抜けやすい決め事 |
|---|---|---|---|
| 7（承認必須） | 会員サイトの紐付け・変更・解除、予約メニューの解除 | [references/membership-link.md](references/membership-link.md) | **申込者向けサイトを使っているプラン（`isUsingLegacySite: true`）は、紐付け・「使わない」の前に「申込者向けサイトは非公開になり、元に戻せない」と伝えて承認を取る**（`false` のプランではこの話をしない）。すでに紐付いているプラン（申込者向けサイトだけのプランも含む）で購入者がいれば呼ばずに伝える |
| 8（フォルダを外すとき承認必須） | 閲覧できるフォルダ・閲覧期限（ライセンス） | 同上 | 5 項目すべて必須の全置換。閲覧可能にするフォルダを全件送る |
| 9（解除は承認必須） | サンクスページ／メール・自動リダイレクト・感想レポート | [references/post-purchase-settings.md](references/post-purchase-settings.md) | サンクスページの本文は毎回必須（変えないときも現在値を送る）。感想レポートは未設定でも「有効」で返る |

### 12. 読み戻してレビュー

保存に成功したら `getCreatorProduct` / `getCreatorProductPlan` で**読み戻し**、意図どおり保存されたかを確認してからユーザーに報告する。商品の `imageIds` と `steps` は置き換えなので、**消えていないこと**をここで確かめる。プランは価格・課金サイクル・受付期間を確かめる。プランの設定は手順 7〜9 の各取得ツールで読み戻す。複製したプランは手順 10、クーポンは手順 11 の読み戻しで確かめる（各領域ファイル）。変更点は「変更前 → 変更後」の形で提示する。

### 13. 公開状態の変更（ユーザー承認が必須）

公開状態の変更は `patchCreatorProduct` / `patchCreatorProductPlan` に `publishingStatus` を渡して行う。**この操作の直前に必ずユーザーの承認を取る**。

商品を公開（`PUBLIC` / `LIMITED`）にする前に確認すること:

1. `getCreatorProductPlans` で**公開中のプランが 1 つ以上あるか**を確認する。無ければ公開できないので、先にプランを作るか公開する
2. プランの公開状態は**販売期間を反映した実効値**で判定される。販売期間が終了したプランは「公開中」に数えられない
3. 事業者情報が未登録だと拒否される。事前に確認する手段が無いため、拒否されたらその旨を伝える

商品を非公開（`PRIVATE`）にするときは、次をユーザーに伝えてから承認を取る:

- **紐づくプランもすべて非公開になる**（公開中の別商品も同じ旧サービスを参照しているプランは非公開にしない）
- 公開に戻しても、プランの公開設定は自動では戻らない

`PUBLIC` / `LIMITED` への変更での波及は content-schema の「公開状態を変えたときのプランへの波及」。

変更後は読み戻し、`publishingStatus` と `publicUrl` を確認して報告する。

### 14. 削除（ユーザー承認が必須）

削除は取り消せない。商品でもプランでも次の順で進める（クーポンの削除は手順 11）。

1. `getCreatorProduct` / `getCreatorProductPlan` で対象を読み戻し、**商品名・プラン名でユーザーに提示**して本当にこれで良いか確かめる
2. `isDeletable` を確認する。`false` なら購入者がいるため削除できない。**ツールを呼ばずに**「購入者がいる（または購入者の有無を確認できない）ため、削除できません」と伝える。`false` は購入者の有無を判定できなかった場合も含むが、どちらでも削除は試さない。「試しに削除してみる」「削除してよいか」は提案せず（削除できない前提で話す）、`isDeletable` の項目名や値（`false`）はそのまま書かない。整理したいだけなら非公開を代案として示す
3. 「この操作は取り消せないこと」、商品の削除では「紐づくプランも同時に削除されること」を伝え、**明示的な承認を取る**
4. 承認を得てから `deleteCreatorProduct` / `deleteCreatorProductPlan` を呼ぶ
5. 一覧を取得し直し、消えたことを確認して報告する

`isDeletable` が `true` でも、削除の直前に購入が入っていれば拒否される。拒否理由はそのまま伝える。

## ユーザーへの提示・コミュニケーション規約

この規約は最終報告だけでなく、**承認を求める発話・作業途中の報告を含むすべての発話**に適用する（特に規約 3 の内部 ID と規約 8 の内部の項目名）。

1. JSON をそのまま見せない。表または箇条書きに整形して提示する（ユーザーが明示的に求めた時だけ JSON を出す。ただし生の内部 ID・リッチテキストの内部形式・enum の英字値は、明示的に求められても出さない）
2. HTTP 用語・ステータスコードを文面に出さない。「保存できました」「◯◯のため公開できませんでした」のように平易な日本語で伝える
3. 生の内部 ID（`id` / `productId` / `productPlanId` / `moshServiceId` / `imageIds` の値 / `slug` / `membershipSiteId` / `offeredContentId` / `calendarBookingItemId` / `folders[].id` / `bannerMediaId` / `couponId` / 画像アップロードの `moshMediaId`・`uploadUrl`）を提示に出さない。商品は商品名、プランはプラン名、会員サイトはサイト名、フォルダはフォルダ名、予約メニューはタイトル、クーポンはクーポン名とコードで示す。作業途中の「対象を特定しました」のような報告でも名前だけで伝え、ID を括弧で添えない。公開ページの案内には `publicUrl` を使う。**クーポンコードはゲストに配る値なので、ID ではなく提示してよい**
4. enum 値は日本語に変換して出す（変換表は [references/content-schema.md](references/content-schema.md) の「enum の日本語変換表」）。`PUBLIC` `MONTHLY` `FREE_SLOT` `once` 等の英字をそのまま見せない。**日本語に英字を括弧で添えるのも不可**（「公開状態（PUBLIC）」ではなく「公開」）
5. **商品の** `description` / `precautions` / `cancellationPolicy` はリッチテキストの内部形式で返ることがある。内部形式のまま見せず、本文テキストを取り出して提示する（プランの `description` はプレーンテキスト）
6. 金額は「12,800 円」のように単位を付けて示す。定員 `0` は「定員なし」、閲覧期限 `null` は「無期限」、待機秒数は「5 秒」のように言い換える。クーポンの割引は「10% OFF」「1,000 円 OFF」、使用状況は「25/100 回使用」（発行枚数が無制限なら「25 回使用」）、発行枚数 `null` は「無制限」、有効期限 `null` は「無期限」と言い換える
7. 書き込みの前後で「何をこれから変えるか」「何が実際に変わったか」を必ず言葉にする。黙って保存しない
8. 内部の項目名（`isDeletable` / `isSuspended` / `isPriceEditable` / `isNameEditable` / `publicUrl` / `publishingStatus` などキャメルケースのフィールド名）を文面に出さない。「`isDeletable: false` となっています」のように**項目名と値を組で書くのも不可**。「購入者がいるため削除できない」「受付を停止中」「価格を変えられない状態」「公開ページの URL」「公開状態」のように平易な言葉で言い換える（値そのもの、たとえば公開ページの URL は示してよい）
9. `isUsingLegacySite: true` は「申込者向けサイト（旧会員サイト）を使っています」と伝える。`publicUrl: null` は非公開の商品の正常な値なので「取得に失敗」と言わない。旧サービスの呼び方・一覧での示し方は content-schema の「旧サービス（isLegacyService: true）」。自動リダイレクトの取得結果が `null` なら「自動リダイレクトは未設定です」と伝える。クーポンの回数設定（初回割引／永久割引）は取得項目に無いので、作成時に送った値だけを提示する

## 必須ルール

複数の手順にまたがる規則だけを置く。手順に固有の規則（置き換えになる項目・送る項目の組み合わせ・各設定の承認条件）は各手順（手順 7〜11 は各領域ファイル）が正本。

- **不可逆・影響の大きい書き込みは直前に承認を取る。** 公開状態の切り替え（手順 13）・削除（手順 14）・手順 7〜11 の表で承認必須とした操作（条件は各領域ファイル）。依頼文に含まれていても実行前にもう一度確かめる。それ以外の書き込みも、送る前に変更内容を示す（提示規約 7）
- **保存したら必ず読み戻して確認する**（手順 12）。保存の成功と意図どおりの内容は別。エラーで終わったときも途中まで反映されていることがあるので、読み戻してから報告する（手順 5・10）
- **送信は取得した現在値を土台に組み立てる。** 置き換え・全項目必須のもの（商品の画像と申し込み後の流れ＝手順 3、プラン＝手順 5、ライセンス＝手順 8、サンクスページの本文＝手順 9）は、変えない値も含めて送る
- **作成後に変えられないもの（プランの課金サイクル・課金回数・初回価格、クーポンの内容）は作る前に確定させる。** 正本は [references/content-schema.md](references/content-schema.md) の「作成後に変更できない項目」と [references/coupons.md](references/coupons.md) の「クーポンの項目」
- **ID・必須項目を捏造しない。** 画像 ID はアップロードで得た値・取得した現在値・ユーザーから示された値だけを使い、必須の文面は仮の文言で埋めずに聞く
- **作成・複製・クーポン発行をやり直す前に、一覧で重複を確認する。** 同じ内容の再送で商品・プランが増える（クーポンはコードの重複で拒否される）
- **旧サービスには書き込まない**（API が受け付ける操作も含む。読み取りと案内だけ。正本は content-schema の「旧サービス（isLegacyService: true）」）
- **拒否されると分かっている・拒否されうる書き込みは試さない。** 購入者がいる（可能性がある）プランの削除・提供コンテンツの変更（手順 7・14）、ロックされたプラン名・価格（手順 5）
- 拒否されたら再試行しない。返ってきた理由を平易な日本語に言い換えて伝える

## セルフレビューチェックリスト

送信前と読み戻し後の両方で確認する。まず上の「必須ルール」と「ユーザーへの提示・コミュニケーション規約」を 1 つずつ照合し、次にそれらに書いていない点検項目を見る（範囲・組み合わせの正本は content-schema と各領域ファイル）。

1. `steps` の `orderNum` が重複していないか。各要素に `imageId` があるか（無いなら `null`）
2. 本文の表示テキストが上限以内か
3. 商品の更新で、変えないつもりの項目を送っていないか
4. プランの更新で、課金サイクル・課金回数・初回価格が現在値のままか。課金開始日を変えないなら 3 項目とも省略しているか
5. プランの価格を変えるとき、割引前の価格との関係（「割引前の価格と価格の更新」）を確かめ、読み戻しで割引前の価格も見たか
6. プランの課金サイクルと受付期間・決済方法・分割払いの組み合わせが content-schema の表どおりか
7. 公開する前に、公開中のプランがあること（販売期間が終わっていないこと）を確認したか
8. ライセンスの期間が membership-link の 3 択のどれかで、日数が範囲内か。日時にタイムゾーンオフセットがあるか
9. 申込者向けサイトの影響を伝えたのは `isUsingLegacySite: true` のプランだけか
10. クーポンを書き込んだあと、回数設定は取得項目に無いので送った値を提示したか

## よくあるミス

ワークフロー・必須ルール・提示規約で書いていない落とし穴だけを置く。**追記する前に、既存の節でカバーできないかを確かめ、できるならそちらを強化する。**

| NG | OK |
|---|---|
| 説明文が長いので適当に切り詰めて送る | 表示テキストの上限（content-schema の「文字数の 2 つの上限」）を超えるなら、どこを削るかをユーザーと相談する |
| 商品のプラン一覧が 0 件だったので「プランが無い」と断定する | 自分の商品でない・存在しない商品 ID でも空で返る。商品の特定が正しいかを先に確かめる |
| 「同じプランをもう 1 つ」と言われて一から作り直す | 手順 10 で複製してから直す。課金サイクルなど作成後に変えられない項目を変えたいときだけ新規作成 |

## エラーが返ったとき

拒否された理由は返ってきたメッセージに入っている。**再試行せず**、理由をそのまま平易な日本語で伝える。商品・プラン本体の主なものは [references/content-schema.md](references/content-schema.md) の「拒否されたときのメッセージ」に、旧サービスで返るものは同じファイルの「旧サービス（isLegacyService: true）」に、プランの設定・複製・クーポンのものは各領域ファイル（手順 7〜11 の表）の「拒否されたときのメッセージ」にまとめてある。

存在しない商品・プランや他のユーザーのものを指定すると「見つからない」旨のエラーが返る。対象の特定からやり直すか、ユーザーに名前を確認する（ライセンス設定・削除済みのクーポンで「見つからない」になる条件は各領域ファイル）。認証エラーの場合は、MOSH との接続（認証）をやり直すよう案内する。
