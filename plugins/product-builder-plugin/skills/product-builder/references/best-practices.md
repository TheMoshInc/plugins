# 商品・プランを作る・直すときの進め方

## 商品作成の組み立て

### 必須 4 項目を先に揃える

商品名・商品説明・注意事項・キャンセルポリシーは作成時に必須。**空欄を仮の文言で埋めない。** 「未定」「後で記入」のような placeholder も入れない。決まっていない項目があれば、そのまま聞く。

ユーザーが文面を持っていない場合は、こちらから案を出してよい。ただし**案であることを明示し、そのまま保存せず確認を取る**。

### 画像は ID をユーザーから受け取る

画像を一覧・検索する MCP ツールは無い。画像 ID はユーザーから受け取るか、既存商品の値を `getCreatorProduct` で取得するしかない。

それらしい文字列を作らない。ユーザーが「画像を付けたい」と言っただけで ID が分からない場合は、管理画面での画像アップロードと ID の確認を案内する。

### 作成後の流れを最初に伝える

作成された商品は非公開で始まり、公開には**公開中のプランが 1 つ以上**必要になる。

商品の新規作成の依頼を受けた時点で「商品を作る → プランを作る → 商品を公開する」の順になることを伝えておくと、「作ったのに公開できない」という行き違いを避けられる。

なお、この順序は商品も新しく作るときの話。**既存の商品には、いつでもプランを足せる。** プランを増やしたいだけの依頼で商品を作り直さない。

## プラン作成の組み立て

### どの商品に足すかを先に決める

プランは必ず商品に属する。新規作成でも `getCreatorProducts` で対象の商品を特定してから組み立てる。ユーザーが「〇〇のプランを作って」とだけ言ったときは、商品名を確かめる。

1 つの商品に複数のプラン（松竹梅、月額と年額、単発と回数券など）を並べられる。**プランを追加するために商品を新しく作らない。**

同じ商品に既にあるプランも `getCreatorProductPlans` で見ておく。名前や価格が重複していれば、意図した追加かどうかを確かめられる。

### 変えられなくなる項目から順に聞く

課金サイクル・課金回数・初回価格・課金開始日は、作成した後は変更できない。あとから直せる項目（プラン名・説明・定員・受付期間）より先に確定させる。

ヒアリングの順序（課金サイクル → 価格 → 決済方法 → 分割 → 受付期間 → 定員 → 公開状態）はこの理由でこの並びになっている。

### 決済代行会社に依存する項目は断定しない

課金回数・初回価格・価格の上限は、クリエイターがどの決済代行会社を使っているかで変わる。**これを事前に確認するツールは無い。**

「この設定はできます」と先に言い切らず、送ってみて拒否されたらメッセージの内容をそのまま伝える。ユーザーが希望した設定が通らなかったときは、代わりに何ができるかを一緒に考える。

### まず非公開で作り、確認してから公開する

依頼文に「公開で」と書かれていても、`PRIVATE` で作成する。`getCreatorProductPlan` で読み戻し、価格・課金サイクル・受付期間を提示して確認を取ってから公開へ切り替える。

課金サイクルのような取り返しのつかない項目を、公開後に間違いだと気づくのが一番痛い。

### 失敗したように見えても、すぐ再送しない

同じ内容をもう一度送ると、同じ内容のプランが 2 つできる。応答が曖昧なときは `getCreatorProductPlans` で一覧を取り、実際に作られていないことを確かめてから送り直す。

## プラン更新の組み立て

### 現在値を読むのは必須手順

プランの更新は部分更新に対応していない。`getCreatorProductPlan` の結果を土台にして、変える項目だけ差し替えて送る。読まずに組み立てると、送らなかった項目でリクエストが弾かれる。

読んだ結果は「変更前 → 変更後」の提示にもそのまま使える。

### ロックは送る前に判定する

`isNameEditable` / `isPriceEditable` が `false` なら、プラン名・価格の変更は必ず拒否される。ツールを呼ぶ前にユーザーへ伝え、**新しいプランを作成して旧プランを非公開にする**流れを提案する。

このとき旧プランを削除しない。購読中のゲストがいると削除できないうえ、削除は取り消せない。

### 並び替えは全件を並べて送る

`getCreatorProductPlans` で全プラン（非公開を含む）を取得し、並べたい順に ID を並べる。一部だけ送ると、送らなかったプランが末尾に回って意図しない並びになる。

## 商品更新の組み立て

### 変更前の値を必ず取得する

`getCreatorProduct` で現在の内容を取得してから組み立てる。理由は 2 つ。

1. `imageIds` と `steps` は置き換えなので、既存の値を含めないと消える
2. 「変更前 → 変更後」をユーザーに示せる

### 送る項目を最小限にする

`patchCreatorProduct` は送ったフィールドだけを更新する。変えない項目は**送らない**のが安全。

例外は `imageIds` と `steps` で、これらは「変えないなら送らない」「変えるなら全件送る」のどちらかにする。一部だけ送るのが一番危ない。

### 長い本文は文字数を確認してから送る

表示テキストの上限は 10,000 文字。超えると拒否される。長文を扱うときは送る前におおよその長さを見て、超えそうならユーザーと削る内容を相談する。

## 公開・非公開の切り替え

### 公開できるかを先に確かめる

`getCreatorProductPlans` で公開中のプランがあるかを確認してから `PUBLIC` / `LIMITED` を送る。無ければ拒否されるので、先にプランを作るか、既存のプランを公開する。

販売期間が終了したプランは公開中に数えられない。プラン一覧の公開状態をそのまま信じず、販売期間も見る。

事業者情報の登録状況は事前に確認できない。**「公開できます」と断定しない。**

### 非公開にする影響を伝えてから承認を取る

非公開にすると紐づくプランもすべて非公開になる。公開に戻してもプランは自動では戻らない。この 2 点を伝えてから承認を取る。

「商品を一時的に隠したいだけ」という意図なら、限定公開（`LIMITED`）で足りることもある。選択肢として示す。

## 削除

削除は取り消せない。商品を削除すると紐づくプランも同時に消える。次の順を崩さない。

1. 対象を読み戻し、**商品名・プラン名で提示して**本当にこれで良いか確かめる
2. `isDeletable` を見る。`false` なら実行せずに理由を伝える
3. 取り消せないこと（商品ならプランも消えること）を伝え、明示的な承認を取る
4. 実行する
5. 一覧を取り直して消えたことを確認する

「削除して」と言われても、2 と 3 を飛ばさない。

プランを整理したいだけなら、削除ではなく非公開で足りることが多い。購読者がいるプランは削除できないので、選択肢として先に示す。

## プランの設定を進める順序

提供コンテンツ・ライセンス・購入後設定は、プランを作ったあとに個別に行う。依頼されたものだけを扱えばよいが、複数を頼まれたときは**会員サイトの紐付け → ライセンス → サンクスページ／メール → 自動リダイレクト → 感想レポート**の順に進める。ライセンスは会員サイトが紐付いていないと設定できず、購入後設定は互いに独立しているからである。

どの設定も「現在値を読む → 変更内容を提示する → 承認が要るものは承認を取る → 送る → 読み戻して提示する」を崩さない。プランの作成と同じで、**保存できたことと意図どおりの内容になっていることは別**。例外は自動リダイレクトで、現在値を読むツールが無いため「ユーザーに現在の設定を確認する → 送る → 送った値を提示する」になる。

## 提供コンテンツ（会員サイト）の紐付け

### 先に現状を読み、影響を伝えてから承認を取る

`getCreatorProductPlanOfferedContents` で、いま何が紐付いているか（会員サイト・予約メニュー・申込者向けサイトの利用有無）を読む。そのうえで、会員サイトを紐付ける・変える・使わないにすると**申込者向けサイト（旧会員サイト）が非公開になる**ことを言葉にして承認を取る。「紐付けるだけ」に見えても、ゲストが見ている画面が変わる操作だと考える。

### 購入者がいるプランで変更・解除を試さない

購入者がいるプランでは、**すでに紐付いている**会員サイトの変更・解除がすべて拒否される。`getCreatorProductPlan` の `isDeletable` が `false` なら、ツールを呼ばずに「購入者がいるため変更できない」と伝える。どうしても別の会員サイトを提供したいなら、新しいプランを作って紐付ける案を示す。

何も紐付いていないプランへの初回の紐付けは、購入者がいてもできる。`isDeletable: false` を理由に初回の紐付けまで断らない。

`isDeletable` が `true` でも、解約済みの購入者がいると拒否されることがある。拒否されたらメッセージをそのまま伝え、再送しない。

### 「変更なし」は成功

すでに紐付いている会員サイトを再指定すると「変更がないためスキップしました。」で成功する。失敗ではないので、「すでにその会員サイトが紐付いています」と伝えて次の設定へ進む。

### 解除の 2 つの経路を使い分ける

| したいこと | 使うもの |
|---|---|
| 会員サイトや予約メニューの紐付けを 1 件だけ外す | `deleteCreatorProductPlanOfferedContent`（対象はタイトルで提示して承認を取る） |
| 申込者向けサイト（旧会員サイト）をやめる・会員サイトの紐付けをまとめて外す | `postCreatorProductPlanOfferedContent` の「会員サイトを使わない」（申込者向けサイトが非公開になる） |

申込者向けサイトの紐付けは前者では外せない。予約メニューの紐付けは後者では変わらない。

### 予約メニューの紐付けは管理画面へ

予約メニューをプランに紐付けるツールは無い。「予約メニューを付けて」と言われたら管理画面を案内する。外すだけならこのスキルでできる。

## ライセンス設定の組み立て

### 自動作成された既定値を確認する

会員サイトを紐付けた直後のライセンスは「全フォルダ閲覧可・今後追加分も含む・無期限」になる。多くの依頼はこれで足りるが、期限付きにしたい・一部のフォルダだけにしたいという希望がないかを一言確かめる。

### 読んでから全置換する

`getCreatorMembershipSiteProductPlanLicenseSetting` の `folders` を土台にする。`isViewable: true` の ID をすべて残したうえで足す・外すを反映し、`viewableFolderIds` / `isNewFoldersIncluded` / `accessDurationDays` の 3 項目をそろえて送る。1 項目だけ変えたいときも 3 項目すべてを送る。

フォルダの提示は `folders[].name` で行う。フォルダ名を別のツールで引く必要はない。

### 閲覧順の固定が有効なら分けられない

会員サイトで閲覧順の固定（`getCreatorMembershipSite` の `isFixedViewingOrder`）が有効だと、全フォルダ + 今後追加分を含める設定しか保存できない。フォルダを分けたい依頼を受けたら、送る前に「先に閲覧順の固定を外す必要がある」ことを伝え、サイト設定の変更は `membership-site-builder` スキルに引き継ぐ。閲覧順の固定を外すとゲストの閲覧完了状態が消えて元に戻せない影響も、このとき一緒に伝える。

### 購入済みのゲストがいるかもしれないプランからフォルダを外すときは承認を取る

公開中・限定公開のプラン（`publishingStatus: PUBLIC` / `LIMITED`）、または `isDeletable: false`（購入者がいる可能性のある）プランで、いま閲覧できるフォルダを外すと、そのフォルダを購入済みのゲストも見られなくなる。どのフォルダを外すのかを名前で示し、影響を伝えてから承認を取る。

## 購入後設定の組み立て

### サンクスページ／メールは「本文は毎回・バナーは差分」

`content` は毎回必須なので、バナーだけ変えるときも `getCreatorProductPlanSettingsThanks` で読んだ本文をそのまま送る。バナーの 2 項目は「省略＝維持、`null`＝削除」。バナー画像を消すときはリンク先も `null` にしないと拒否される。

バナー画像の ID を一覧・検索するツールは無い。ユーザーから受け取った ID だけを使い、分からなければ管理画面でのアップロードと ID の確認を案内する。それらしい ID を作らない。

### 自動リダイレクトは現在値をユーザーに確認し、削除は承認を取ってから・有無の確認は不要

現在値を読むツールが無い。設定があるか・移動先の URL・待機秒数をユーザーに確認し、設定済みなら上書きになることを伝えてから、`redirectUrl` と `pendingSecond`（0〜15 秒）を毎回そろえて送る。送信後は読み戻せないので、送った値を提示する。

削除は「自動リダイレクトを解除します（あとから再設定できます）」と伝えて承認を取ってから呼ぶ。未設定でも成功するので、「有るかどうか分からないが止めたい」という依頼でも有無を確かめる手順は要らないが、確かめる目的で削除を呼ばない。銀行振込のゲストにはリダイレクトが働かないことを添える。

### 感想レポートは「未設定＝有効」

一度も設定していないプランも `true` で返る。「設定されていません」ではなく「自動送信は有効です」と伝え、止めたい依頼なら `false` を送る。

## 提示の組み立て

- 変更点は「変更前 → 変更後」の形にする。項目名は日本語（商品名 / 商品説明 / 注意事項 / キャンセルポリシー / 申し込み後の流れ / 公開状態 / プラン名 / 価格 / 課金サイクル / 決済方法 / 定員 / 受付期間 / 特典 / 会員サイト / 閲覧できるフォルダ / 閲覧期限 / サンクスページの本文 / バナー / 移動先の URL / 待機秒数 / 感想レポートの自動送信）
- 公開状態・課金サイクル・決済方法・分割払いタイプ・予約メニューの枠種別と公開状態は日本語に直して示す
- 金額は「3,000 円」のように単位を付ける。定員 `0` は「定員なし」、閲覧期限 `null` は「無期限」、待機秒数は「5 秒」と言い換える
- 会員サイトはサイト名、フォルダはフォルダ名、予約メニューはタイトルで示す。ID は出さない
- 公開した商品は `publicUrl` を添えて「このページで見られます」と伝える
- 本文が長い項目は全文を貼らず、要約と文字数で示す
