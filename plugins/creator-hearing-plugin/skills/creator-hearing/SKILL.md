# Creator Hearing（1往復ヒアリング）

## Overview

クリエイターが何を売りたく、誰に、何をしてほしいのかを、**先に調べて仮埋めしたシートを1画面で見せ、ユーザーには空欄と誤りだけ直してもらう**ことで確定する。質問を順に投げない（一流のウェブディレクターが、調査済みのシートを渡して面談では確認と訂正だけをするのと同じ立ち回り）。

出力は「ヒアリング結果」ファイル（`hearing_{YYYYMMDD}.md`）で、後続の設計・構築スキルの入力になる。**読み取りと対話だけで、MOSH 側の状態は変えない。**

完了条件: 必須欄がすべて `確定` か `確認` になり、ヒアリング結果ファイルが保存され、要約が会話に返っている。

## When to use

- LP などを作る前に、意向（商品・顧客像・行動先・目的ごとの項目）を揃えたい
- 「何を作るか」がまだ決まっておらず、材料（原稿・参考URL・既存の商品）から整理したい
- 呼び出し元のスキル（LP を作るスキルなど）から、ヒアリングの手順として呼ばれたとき

## When NOT to use

- クリエイターの現状（商品・LP・売上などの件数）を知りたいだけ → `creator-context`
- LP の作成・編集・公開そのもの → `lp-builder`（LP 用の追加項目は、呼び出し元のスキルが持つシートで足す。本スキルは追加シートの有無によらず単独で動く）
- ワークフローの作成 → `workflow-builder`（自前の要件確認を持つ。現状は本スキルと連携しない）

## Workflow

事前調査 → 仮埋めして1画面で提示 → 必須欄の確認 → 確定して保存。人ゲートは「1画面の確認」の1回（必須欄が埋まるまで先へ進まない）。

### 1. 目的とシートを決める

- 目的（lp など）と、**追加の項目を持つシート**を決める。1画面目は前置きなしで、**最初の行が目的（または対象商品）の選択式**になる形にする（`examples/first-screen-sample.md`）。呼び出し元のスキルがシートを持っていれば、それを共通3ブロックに足す（例: LP 用のシート）。持っていなければ共通シートだけで進める
- 呼び出し元がなく、目的に対応するシートを持つスキルがある場合（LP なら LP 用のシート）は、それを追加シートとして使うか、そのスキルの起動を案内する。呼び出し元がなく目的が分からないときは、同じ1画面の冒頭に、選択式の1行で目的を聞く。目的の選択肢にシートの無いものがあるときは、同じ画面の末尾に「この目的で他に決めたいこと」を1行だけ聞く

### 2. 事前調査（ユーザーに聞く前に必ず）

- **既存のヒアリング結果**（保存先と同じ場所の `hearing_*.md`）を探す。「7日以内」は**ファイル名の日付**で数え、追記しても起点は動かさない。複数あるときは、「#1 の商品名が今回の対象商品と一致する（または #3 のプランが一致する）」ものうち最新を使う。クリエイターID（ワークフロー一覧の `moshId` など）が分かるときは、ヘッダーのIDも一致が条件（IDの無い旧ファイルは、ID条件を免除）
- 再利用するのは **#1・#2 の `確定` と `確認`**（聞き直さない）。**#3（行動先）は目的ごとに変わりうる**ので、再利用しても「この目的の行動先はこれでよいですか」を1行で確認する。別の行動先と答えたときは、共通ブロックの #3 を書き換えず、その目的の追加ブロックの節に「#3（この目的の行動先）」を1行足す。追加ブロックは新しく聞く。一致するファイルが無ければ再利用せず、#1〜#3 を作り直す（別の商品・別のクリエイターを取り違えない）
- `creator-context` のスナップショットがあれば読む（商品・プラン・LP・購読者・顧客規模が入っている）。無いか7日を超えて古ければ、`creator-context` を先に実行するか（実行するときは「SNS は聞かない。ヒアリングの1画面で聞く」と指示する）、必要な分だけ MCP から取る（`creator-context` が無い環境では、対象の商品だけ MCP で取る）
- 対象の商品が複数あって決まらないときは、同じ画面の冒頭で、推奨に印を付けた選択式の1行で聞く
- スナップショットに載っているプランの価格・課金・分割は**取り直さない**。無い詳細（商品の説明文・特典・分割条件など）だけ、対象の商品で `getCreatorProduct` / `getCreatorProductPlans` で取る
- スナップショットの **SNS 欄**（運用中のSNS）が7日以内で値があれば、流入元などの仮埋めに使い、**聞き直さない**。「未確認（後続のヒアリングで確認）」「取得失敗（未回答）」のとき、またはスナップショットが7日を超えているときは、SNS 欄を使わず、次の Step 3 の1画面に聞く行を足す
- ユーザーが渡した原稿・参考URL・画像があれば、それを主材料にする（`references/manuscript-input.md`）
- 材料が少ない（MOSH 未登録で原稿も無い）ときは仮埋め率が落ちる。その旨を明記し、必須欄だけ記入を依頼する

### 3. 仮埋めして1画面で提示

[references/common-sheet.md](references/common-sheet.md) の共通3ブロックに、目的ごとの追加ブロックを足して1つの表にする。各行に状態ラベル（`確認` / `要記入` / `仮定` / `確定`。定義と遷移は common-sheet.md）を付け、冒頭の一言と提示フォーマットも同ファイルに従う。`要記入` の行を先頭にまとめる。スナップショットの SNS 欄が未確認のときは、任意行「運用中のSNS（URL・分かればフォロワー数）」を同じ画面に足す（回答が無いまま進むときは `仮定`）。

### 4. 必須欄の確認

- **必須欄**＝共通シートの区分が「必須」の行（#1〜#3）＋呼び出し元シートの必須。**必須欄が埋まるまで、後続の設計・構築へ進まない**。任意欄は空でも `仮定` を明記して進む
- 顧客像は「1人分の状況・困りごと・代替手段が具体名詞」で合格。「幅広く」のときは**書かせず、選ばせる**（候補を 2〜3 人分こしらえて選択）。基準と手順は `common-sheet.md`
- **「おまかせ」「早く作って」と急かされたとき**: **商品情報（説明文・価格）から逆算できる必須欄**（顧客像・ゴール種別・プリセットなど）は、推奨を1つ選んで「これで進めてよいですか」の1行確認を取る（肯定で `確定`）。**逆算できない欄**（価格・行動先の実URL・配布物一覧など）や、商品が未登録で原稿も無く逆算元が無いときの全欄は、推奨を作らず `要記入` のまま、その欄だけを短く聞く。返事が無い・否定されたら先へ進まない（任意欄だけ `仮定` で進む）。**質問リストにしない**: `要記入` にするのは逆算できない必須欄だけで、任意欄（流入と端末・配色・事業者名・画像など）は `仮定` か推奨つきの提案にする。画面の形は `examples/first-screen-sample.md`
- 選択肢は、推奨に印を付けた選択式にする（自由記述を求めない）

### 5. 確定して保存

回答を受けて、状態ラベルを更新する（遷移は `common-sheet.md`）。`hearing_{YYYYMMDD}.md` に保存する。形式は `examples/hearing-result-sample.md`。

- 保存先: 引数で指定があればそのパス。無ければカレントディレクトリ（`creator-context` と同じ）
- 既存ファイルを再利用したときは、そのファイルに目的ごとの追加ブロックを節として追記する（日付違いでもファイル名は変えない）。共通ブロックは書き換えないが、再利用した #1・#2 の `確認` をユーザーが訂正したときは、その行だけ書き換えてよい（#3 は上のとおり追加ブロックに足す）。ヘッダーの目的と状態の集計を更新し（取得日は据え置き、追記した日は節に書く）、同じ目的の節があれば差し替える。7日を超えていれば、または商品が一致しなければ、新規に作成する。同名の別ファイルがあるときは `hearing_{YYYYMMDD}_{商品の短縮名}.md` にする
- ヘッダーには、取得日・入力（使ったものを併記: スナップショットのファイル名、MCP（取得日）、原稿の有無）・目的・状態の集計を書く。**状態の集計は、保存する表の各行のラベルを数え直して書く**（追記・訂正のあとも数え直し、表の実数と一致させる）。クリエイターIDが分かるときは ID も書く。行動先（#3）の行には、取得できているプランIDを書く（画面には出さない）
- 会話には、**要約（5行以内）と保存パス、仮定のまま進めた項目の一覧**だけ返す。**表は再掲しない**（確定後の返答に、項目・内容・状態の表を付けない。仮定の一覧も表にせず、箇条書きの1項目1行にする。確定後の返答に新しい質問を足さない。次の確認は後続の構成案で聞く）

## 呼び出し元のスキルが守ること

- 目的とシートのパスを渡す。ヒアリング結果の `確定` と `確認` の項目は聞き直さず、足りない項目だけ1画面で追加する
- `仮定` は、後続の成果物の「未確認・仮定」の欄に引き継ぎ、承認を取る
- 結果ファイルを書き換えない（回答の追記は本スキルが行う）。シートの作り方は `references/define-sheet.md`

## 必須ルール

### A. 捏造しない

材料が無い項目は、必須欄は `要記入`、任意欄は `仮定` にする。無いものを `確認` 扱いで埋めない。価格・日付・定員・実績の数字・お客様の声・保証は、ユーザーの依頼・原稿・MOSH の商品情報にあるものだけ書く。

### B. 質問を1問ずつ投げない

「急に20問」の体験になる。1画面で、直すところだけを答えてもらう。

### C. 実績の数字は3点セット

「確定値・集計期間・母数」が揃うものだけ採用する（例: 120名・2024年1月〜2026年8月・回答96名）。揃わない数字は載せず、`要記入` にして尋ねる。

### D. 原稿はユーザーの資産

原稿が渡されたら、書き換えず原文を優先する。改善の提案は「未確認・仮定」として出し、承認を得てから反映する。

### E. 個人情報を書かない

ヒアリング結果ファイルにも**会話の返答にも**、顧客の名前・メールアドレス・LINE表示名を書かない（件数と ID のみ。ユーザーが名前を挙げた顧客像は、属性（状況・困りごと）で言い換える）。

### F. 画面にはサービス名・プラン名で出す

ユーザーに見せる表と本文には、サービス名・プラン名を書く。ID・MCP のツール名は出さない（ID は保存ファイルにだけ書く）。保存先のパスだけは、保存の報告として返してよい。

## よくあるミス

上のセクションでカバー済みの事項は再掲しない。ここは他セクションでカバーされない落とし穴のみ（追記前に既存セクション・references でカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| 呼び出し元のシートを無視して共通シートだけで進める | 呼び出し元がシートを持っていれば、共通3ブロックにそのシートの項目を足した1つの表にする |
| スナップショットがあるのに MCP で商品一覧を取り直す | スナップショットを読み、説明文など足りない詳細だけ対象の商品で取る |

## エラーが返ったとき

| 症状 | 対処 |
|---|---|
| 商品が MOSH に未登録で原稿も無い | 仮埋め率が低い旨を伝え、必須欄だけ記入を依頼する（商品名・価格・提供形式・顧客像・行動先） |
| スナップショットが無い・古い | `creator-context` を先に実行するか（無い環境では）、対象の商品だけ MCP で取る |
| MCP の取得が失敗する | その行を `要記入` にし、「取得できなかった」と書く（推測で埋めない） |
