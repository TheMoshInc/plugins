# ファイルのアップロード手順

手元のファイルを新規登録するとき、または画像・PDF の本体を差し替えるときに読む。**承認をいつ取るかは SKILL.md の判定表が正本**（本ファイルでは再定義しない。差し替えも新規作成と同じく「枠を発行する前に1回」）。

> 手順・上限・対応形式は MOSH の API スキーマ定義とバックエンド実装で確認したもの（2026-08-21 時点）。
> 値を書き換えるときは、記憶や推測ではなくスキーマ定義・実装で裏取りする。

## 大前提: ファイル本体の送信は MCP が代行しない

MCP でできるのは「アップロード先URLの発行」と「送信後にファイルとして登録すること」だけ。**実体の送信（発行されたURLへの HTTP PUT）は呼び出す側が行う。** この環境は Bash で `curl` を使えるので一連の手順を完了できる。

**手順の順序は入れ替えられない。** 送信が終わっていない状態で登録しようとすると拒否される。

## 対応形式とサイズ上限

| 種別 | 対応形式（`mimeType` に渡す値） | サイズ上限 |
|---|---|---|
| 動画 | 枠発行時に形式を指定しない（**サーバー側の形式チェックが無い**。変換できない形式は後段の変換で失敗する。管理画面の案内は mp4 / mov） | **10GB** |
| 画像 | `image/jpeg` / `image/png` / `image/webp` のいずれか | **100MB** |
| PDF | `application/pdf` のみ | **100MB** |

- 上限を超えると**枠の発行の時点で**拒否される。**動画はさらに登録時にも再検証される**（画像・PDF は登録時に再検証しない）
- **ファイルサイズは推測せず実測する。** 画像・PDF は登録時にサイズを再検証しないため、申告値がずれてもエラーにならず、表示されるファイルサイズだけが嘘になる

```bash
# サイズ（bytes）を実測する
wc -c < "<ファイルパス>"
# 形式を確認する（mimeType に渡す値の裏取り）
file --mime-type -b "<ファイルパス>"
```

## 画像・PDF: 3手順

### 1. アップロード枠を発行する

`postCreatorMaterialImageUpload` / `postCreatorMaterialFileUpload`

| 項目 | 内容 |
|---|---|
| `fileName` | 拡張子を含むファイル名。**配信時のファイル名に使われる** |
| `mimeType` | 上の表の値。それ以外は拒否される |
| `fileSizeBytes` | 実測したサイズ（bytes） |

返ってくるのは `moshMediaId`（ファイル本体の識別子）と `uploadUrl`（送信先）。
**`uploadUrl` の有効期限は発行から15分。**

### 2. 実体を送る

```bash
curl -sS -X PUT --fail-with-body \
  -H "Content-Type: <mimeType>" \
  --upload-file "<ファイルパス>" \
  "<uploadUrl>"
```

- `Content-Type` は枠発行で渡した `mimeType` と同じ値にする
- 失敗する主な原因は**15分の期限切れ**。切れていたら手順1から発行し直す（`moshMediaId` も変わるので、古い値は使わない）

### 3. 変換完了を待ってから登録する

**送信の完了と、MOSH 側で使える状態になることは同時ではない**（保存完了の通知を受けてから変換が進む。管理画面は5秒間隔で完了を確認している）。**手順2の直後に登録すると「アップロードが完了していません」で拒否されることがある。**

`postCreatorMaterialImage` / `postCreatorMaterialFile`

| 項目 | 内容 |
|---|---|
| `title` | ファイル名ではなく**ユーザーに見せるタイトル**。1文字以上（上限なし） |
| `moshMediaId` | 手順1で返った値 |
| `fileSizeBytes` | 手順1と同じ実測値 |

**拒否されたときの扱い（「再試行してよいクラス」に該当する。クラスの定義は SKILL.md「エラーが返ったとき」が正本）**:

- **同じ `moshMediaId` / `fileSizeBytes` / `title` のまま、5秒ほど待って登録だけをやり直す。最大3回まで。**
- **枠の発行と本体の送信はやり直さない**（`moshMediaId` は生きている。やり直すと孤児のメディアレコードが増える）
- 3回とも拒否されたら止めて、ユーザーに「本体は送信済みだが MOSH 側の処理が終わっていない」ことを伝える。`moshMediaId` は生きているので、後から登録だけを再開できる

成功すると素材 ID が返る。共有リンクの自動発行については [mcp-tools.md](mcp-tools.md) の共有リンクの節、共有URLの組み立て方は SKILL.md §B が正本。

## 動画: 4手順

### 1. アップロード枠を発行する

`postCreatorMaterialVideoUpload`。渡すのは `fileSizeBytes` のみ（形式は渡さない）。返るのは `uploadId` と `uploadUrl`。

**この `uploadUrl` の有効期限は MOSH の仕様として明記されていない**（発行処理は配信側の既定値に任せており、MOSH 側で期限を指定していない）。**明記が無いので当てにせず、発行したらすぐ手順2に進む。**

### 2. 実体を送る

```bash
curl -sS -X PUT --fail-with-body \
  -H "Content-Type: <動画のMIMEタイプ>" \
  --upload-file "<ファイルパス>" \
  "<uploadUrl>"
```

### 3. 変換が終わるのを待つ

`getCreatorMaterialVideoUpload`（パスパラメータは `uploadId`）を、処理状況が `READY` になるまで繰り返し呼ぶ。管理画面は10秒間隔で確認している。

- `READY` になる前は再生時間が 0、サムネイルURLが空文字
- `ERRORED` になったら変換に失敗している（形式が変換できないケースを含む）。ユーザーに伝え、**同じファイルで再試行しない**
- 長い動画では時間がかかる。待っている間はユーザーに進捗を伝える

### 4. ファイルとして登録する

`postCreatorMaterialVideo`

| 項目 | 内容 |
|---|---|
| `title` | ユーザーに見せるタイトル。1文字以上 |
| `uploadId` | 手順1で返った値 |
| `fileSizeBytes` | 実測値 |
| `ogpImageMoshMediaId` | サムネイルに使う画像の識別子。**指定しないなら空文字**（`null` は使えない） |

- 処理状況が `READY` に達していない `uploadId` を渡すと拒否される。**その場合は `READY` を待って登録だけをやり直す**（画像・PDF と同じ「再試行してよいクラス」。枠の発行と本体の送信はやり直さない）
- **一度素材にした `uploadId` は再利用できない**（2回目は「見つからない」扱いになる）。作り直したいときは枠から発行し直す
- OGP画像を付けたい場合、その画像も画像の3手順でアップロードした識別子が必要

## 画像・PDF の本体を差し替える場合

**手順1〜2（枠の発行・本体の送信）は新規登録と同じ。違うのは最後で、登録ではなく更新を呼ぶ**（`patchCreatorMaterialImage` / `patchCreatorMaterialFile`）。待ち方は下記。

- 更新は全項目必須の全置換なので、詳細取得で得たタイトルも一緒に送る（詳細は [mcp-tools.md](mcp-tools.md) の更新の節）
- **更新は本体の変換完了を検証しないため、待たずに送っても拒否されず「表示できないファイル」ができる**（無言の失敗）。しかも**更新経路には「完了したか」を確かめる手段が MCP に無い**（登録のように拒否で気づけない）。したがって:
  1. 送信後に5秒ほど待ってから更新を呼ぶ
  2. 更新後に詳細取得を呼び、**本体URLが返っているかを確認する**
  3. 空文字なら反映されていない可能性があるので、その旨をユーザーに伝える（数分後に管理画面で見え方を確認してもらう）

**動画のファイル本体は差し替えられない。** 新しく登録して、古い方を削除する（削除は復元できない）。
