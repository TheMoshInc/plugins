# MOSH ファイル共有

## Overview

MCP ツール（`*Material*` 系 20 本）で、MOSH クリエイターの「ファイル共有」を操作する。扱えるのは **動画 / 画像 / PDF** の3種と、各ファイルの **共有リンク**。

**共有URLは認証なしで誰でも開ける。** URL を知っている人は購入者でなくても閲覧でき、購入者限定・パスワード・ダウンロード禁止の設定は存在しない。作成・更新・削除はいずれも実配布に影響するため、**どの操作で人の承認を取るかを「承認の判定表」で決める**。

> **ツール名表記について**: 本スキル内では MCP ツールを OpenAPI の `operationId`（例: `postCreatorMaterialFile`）で参照する。MCP クライアントが実際に提示するツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため、本スキルでは付けない。

## When to use

- ファイル共有に何が上がっているかを確認したいとき（一覧・詳細）
- ファイルのタイトルを変えたい、ファイル本体を差し替えたいとき
- 手元のファイル（動画・画像・PDF）をアップロードして共有URLを作りたいとき
- 共有URLを取り出したい・追加で発行したい・止めたいとき
- ファイルを削除したいとき
- `*Material*` 系ツールが必要な文脈

## When NOT to use

- 会員サイトで受講者に見せるコンテンツ → 別モデル（membership site asset）で **MCP ツールが提供されていない**。管理画面での操作を案内する
- LP に置く画像 → `lp-builder`スキル
- LINE配信・メール配信の本文に載せる画像 → `contact-broadcast`スキル。**配信側が要求する値をファイル共有のレスポンスから流用しない**（LINE の画像URLは「MOSH の画像リポジトリのURLを指定する。外部で公開されている画像のURLは指定しない」と定義されており、ファイル共有が返す本体URLはこれに使えない前提で扱う。LINE 動画が要求する識別子はそもそもレスポンスに含まれない）。値は推測せずユーザーから受け取り、用意できなければ管理画面での作成を案内する
- ワークフロー（ステップ配信）の組み立て → `workflow-builder`スキル

## ツールの選び方

| やりたいこと | 動画 | 画像 | PDF |
|---|---|---|---|
| 詳細を見る（本体URL・OGP等を含む） | `getCreatorMaterialVideo` | `getCreatorMaterialImage` | `getCreatorMaterialFile` |
| タイトル等を更新する | `patchCreatorMaterialVideo` | `patchCreatorMaterialImage` | `patchCreatorMaterialFile` |
| 削除する | `deleteCreatorMaterialVideo` | `deleteCreatorMaterialImage` | `deleteCreatorMaterialFile` |
| アップロード枠を発行する | `postCreatorMaterialVideoUpload` | `postCreatorMaterialImageUpload` | `postCreatorMaterialFileUpload` |
| アップロード後にファイルを作る | `postCreatorMaterialVideo` | `postCreatorMaterialImage` | `postCreatorMaterialFile` |
| 変換の進み具合を見る | `getCreatorMaterialVideoUpload` | （不要） | （不要） |

種別をまたぐもの: 一覧 `getCreatorMaterials` / 共有リンク一覧 `getCreatorMaterialContentLinks` / 共有リンク発行 `postCreatorMaterialContentLink` / 共有リンク削除 `deleteCreatorMaterialContentLink`

ルーティング上の注意（可否条件・パラメータの詳細は [references/mcp-tools.md](references/mcp-tools.md) が正本）:

- **種別を間違えたツールを呼ぶと 404 になる。** ID だけ分かっていて種別が不明なときは、先に `getCreatorMaterials` で種別を確認する
- **一覧だけでは共有URLに届かない。** 共有URLが必要なら `getCreatorMaterialContentLinks` を、本体URLが必要なら種別ごとの詳細取得を追加で呼ぶ
- **ファイル本体を差し替えられるかは種別で違う**（動画は不可）。差し替えの依頼を受けたら先に該当節を確認する

## Workflow

基本フロー: 対象の特定 → 内容の提示 → **ユーザーの承認** → 実行 → 結果の報告。読み取りだけなら承認は不要。

### 承認の判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 削除（`deleteCreatorMaterial{Video,Image,File}`） | **必ず停止して承認** | 物理削除で復元できない。発行済みの共有URLが全て開けなくなる（**ただし失効するのは共有URLだけ。§B 参照**） |
| 共有リンクの削除（`deleteCreatorMaterialContentLink`） | **必ず停止して承認** | 物理削除。そのURLを配った相手が即座に見られなくなる |
| 更新のうち **タイトル・OGP画像だけ**（ファイル本体を触らない） | **`patch` の直前に停止して承認** | 全置換のため、渡す値を誤ると他の項目が失われる |
| 更新のうち **ファイル本体の差し替えを含む**（画像・PDF のみ） | **枠を発行する前に1回停止して承認**。承認後は止めずに通す | 下の新規作成と同じ多段手順で、アップロード先URLに期限があるため（画像・PDF は15分） |
| 新規作成（`postCreatorMaterial{Video,Image,File}`）まで進む一連 | **枠を発行する前に1回停止して承認**。承認後は枠発行 → 本体送信 → 作成を止めずに通す | 作成と同時に共有URLが発行され、URLを知る人は誰でも閲覧できる。一方でアップロード先URLには期限があり（画像・PDF は15分。動画は仕様上の明記が無い）、途中で承認を挟むと間に合わなくなる |
| アップロード枠の発行（`postCreatorMaterial*Upload`） | **上2行の承認に含める**（一連の一部なので再度止めない）。枠の発行だけを単独で依頼された場合は、発行前に承認を取る | 素材はできないが、アップロードセッション／メディアのレコードが残り、それを消す手段が無い |
| 共有リンクの発行（`postCreatorMaterialContentLink`） | 停止しない | 削除で取り消せる。既に配ってあるURLには影響しない |
| 参照（`getCreator*`） | 停止しない | 読み取り |

**依頼文がどれだけ具体的でも、上表で「承認」となっている操作は承認なしに実行しない。**

### 1. 依頼内容の確認

何をどうしたいのかと、対象のファイルを把握する。**対象が特定できない依頼（「使ってないファイル消して」等）では、削除・更新に進まず対象を確認する。** どのファイルが使われているかを判定する情報は MCP から取得できない（どこから参照されているかを調べる手段がない）。

「もう配りたくない」は2通りに分かれる。**どちらなのかを確認するまで、どちらも実行しない。**

| ユーザーの意図 | 操作 | 結果 |
|---|---|---|
| そのURLでの配布だけ止めたい | 共有リンクを削除 | ファイルは残る。別の共有リンクを発行すれば再配布できる |
| ファイルごと消したい | ファイルを削除 | 復元できない。発行済みの共有URLは全て開けなくなる |

### 2. 対象の特定

- 一覧が必要なら `getCreatorMaterials`（引数なし・全件返却）。多い場合はユーザーの関心（種別・タイトル・新しい順）に沿って絞って提示する
- 共有URLを扱うなら `getCreatorMaterialContentLinks`
- 更新するなら、必ずその種別の詳細取得を先に呼ぶ（§A）

取得できない値は**推測して埋めず**、ユーザーに確認する。ID・共有URL・ファイル名を創作してはならない。

### 3. 内容の提示

提示する項目:

- 更新: 対象のファイル名と、変更前 → 変更後
- 削除: 対象のファイル名と種別。**復元できないこと**と、**無効になる共有URLが何本あるか**（`getCreatorMaterialContentLinks` で数える。「開けなくなります」だけでは影響範囲が伝わらない）
- 共有リンクの削除: どのURLが使えなくなるか
- 新規作成: どのファイルを（パスまたはファイル名）、どんなタイトルで作るか。**作成すると共有URLが発行され、URLを知っている人は誰でも閲覧できること**

自分で補った項目（タイトルをファイル名から機械的に作った場合など）は「補った」と明示する。

**承認を得るまで次に進まない。**

### 4. 実行

- 更新は「必ず詳細取得 → 取得した値をそのまま載せて更新」（§A）。項目ごとの必須は [references/mcp-tools.md](references/mcp-tools.md)
- 新規作成・本体の差し替えは [references/upload-guide.md](references/upload-guide.md) の手順に従う（順序を入れ替えられない・アップロード先URLに期限がある・登録は変換完了を待つ）
- 手順の通し方に迷ったら [examples/pdf-upload-trace.md](examples/pdf-upload-trace.md)、更新の組み立てに迷ったら [examples/title-update-trace.md](examples/title-update-trace.md)

### 5. 結果の報告

何がどうなったかを伝える（「ユーザーへの提示・コミュニケーション規約」に従う）。共有URLを発行・取得したときは URL をそのまま示す。

## 必須ルール

### A. 更新は全置換。必ず詳細取得から始める

更新（`patchCreatorMaterial*`）は**部分更新できない**。タイトルだけ変えるときも、詳細取得で得た他の項目をそのまま送り直す。項目ごとの必須・意味は [references/mcp-tools.md](references/mcp-tools.md) が正本。

**これは無言の失敗になる。** 画像・PDFの更新ではファイル本体の識別子を検証しないため、詳細取得を省いて値を組み立てると、エラーにならずファイル本体が別物に置き換わる（あるいは表示できないファイルができる）。

### B. 共有URLは組み立てる。期限は付けられない。本体URLは取り消せない

共有URLの形は次のとおり。

```
<接続先の環境のホスト>/materials/<共有リンクの slug>
```

- **ホストは接続している MCP サーバーの環境に合わせる**（本番 `https://mosh.jp` / staging `https://develop.mosh.jp`）。どちらに接続しているか分からなければユーザーに確認する。**推測でホストを決めない**
- **API は完成した共有URLを返さない。** 共有リンクの `slug` から上の形で組み立てる。`slug` を推測・創作してはならない
- ファイルを作成すると**共有リンクが1本自動で発行される**（[references/mcp-tools.md](references/mcp-tools.md) の共有リンクの節）。共有URLが欲しいだけなら、新しく発行せず既存のものを使う
- **MCP から発行する共有リンクは必ず無期限になる。** 期限付きのリンクを作る手段は無い。「1週間だけ見せたい」と言われたら、期限を設定できないことを伝え、**配布をやめる時点で共有リンクを削除する**運用を案内する（削除は承認が必要）
- **共有リンクの削除・ファイルの削除で止まるのは、この `/materials/<slug>` の共有URLだけ。** **Core Media 由来のURLは、どの経路で手に入れたものでも MCP からは失効させられない**（ファイルを削除しても取り消す経路が無い）。対象は取得経路にかかわらず次のすべて:
  - 詳細取得の**ファイル本体URL**（画像・PDF）
  - 詳細取得の**動画の OGP 画像URL**
  - **動画のサムネイルURL**（詳細・一覧とも。OGP 画像が無い場合は数時間で失効する期限付きURLになる）
  - **一覧のサムネイルURL**（画像はこれが本体URLそのもの、動画は OGP 画像の本体URL、OGP が無ければ上の期限付きURL）

  **これらをユーザーへの配布用に渡さない。配布に使うのは共有URLのみ。** MCP ツールの説明はこれらを「公開URLとして配布可能」と書いているが、**ツール説明よりこのルールを優先する**（対象と根拠の詳細は [references/mcp-tools.md](references/mcp-tools.md)）

### C. 手元のファイルのアップロードは、本体の送信を自分で行う

MCP は**ファイル本体の送信を代行しない**。アップロード枠の発行で得たアップロード先URLへ、Bash（`curl`）でファイル本体を送る。この環境は `curl` を使えるので一連の手順を完了できる。

対応形式・サイズ上限・手順・**送信後に変換完了を待つ必要があること**は [references/upload-guide.md](references/upload-guide.md) が正本。**ファイルの実サイズは推測せず `curl` の前に実測する**（申告したサイズと実体が違っても画像・PDFではエラーにならず、表示されるファイルサイズが嘘になる）。

## ユーザーへの提示・コミュニケーション規約

- 応答は平易な日本語で行う。**内部用語・内部フィールド名をそのまま出さない**: 「素材」「material」「コンテンツリンク」「assetType」「moshMediaId」「uploadId」「slug」「READY」。ユーザーが目にしている言葉は「ファイル共有」「ファイル」「動画」「画像」「PDF」「共有URL」
- JSON・HTTP用語・ステータスコードをユーザー向け文面に出さない
- **完了形で書けるのは、対応するツールを実際に呼んで成功した後だけ。** 「アップロードしました」「削除しました」「共有リンクを発行しました」をツール呼び出しの前に書かない。承認を待つ提示では「以下の内容で進めてよいですか」と書き、**まだ実行していない**ことを明示する
- ファイルの用途・視聴数・誰に配ったかなど、取得した情報に無い事実を補って語らない
- **内部の識別子は自分で保持し、ユーザーには見せない。** アップロード先URLだけを伝えて本体の送信をユーザーに任せる場合も、ファイル本体の識別子（`moshMediaId` / `uploadId`）を「控えておいてください」と渡さない。次の登録で使うのは自分なので、ユーザーが持つ必要は無い
- **できない理由を説明するときも、仕組みで説明しない。** ここが最も内部用語が漏れやすい（実測で3件）。「共有リンクの発行は素材IDだけを指定するもので、期限のパラメータが存在しない」ではなく「共有URLに期限を設定する仕組みがなく、必ず無期限になる」と、**ユーザーから見える事実だけ**で説明する。ID・パラメータ名・ツール名・「素材」を持ち出さない
- **配布できないURLは、断る理由を説明するときも本文に書かない。** 「このURLは配布に使えません」と説明するために当のURLを引用すると、結局ユーザーの手に渡ってしまう。対象のファイル名で指し、URL自体は出さない
- 共有URLを示すときは、**URLを知っている人は誰でも開けること**を一度添える（Overview のとおり購入者限定にはできない）

## エラーが返ったとき

**原則として再試行せず**、原因と対処をユーザーへ平易な日本語で伝える。原因と対処の一覧は [references/mcp-tools.md](references/mcp-tools.md) の「エラーの読み方」が正本。

**再試行してよい唯一のクラス**: **アップロードの完了待ちに起因する「登録」の拒否**。この場合だけ、登録のツールだけをやり直す。

| 種別 | やり直し方 |
|---|---|
| 画像・PDF | 同じ値のまま5秒ほど待って登録だけを再実行（最大3回。手順は [references/upload-guide.md](references/upload-guide.md)） |
| 動画 | `getCreatorMaterialVideoUpload` が `READY` になってから登録だけを再実行 |

**いずれも枠の発行と本体の送信はやり直さない**（やり直すと消せないレコードが増える）。これ以外のエラーは再試行しない。
