# MOSH 顧客宛の一斉配信（顧客管理からのメッセージ）

## Overview

MCP ツール5本（`*CustomersMessage*` 系）で、管理画面「顧客・連絡先 > 顧客一覧」から送る**顧客（サービス購入者）宛の一斉配信**を作成・確認・編集・削除する。

- 届き方は**メールと MOSH公式LINE の両方**（登録状況による）。クリエイター自身の LINE公式アカウントは使わない。**プランのメール・LINE配信可能数にはカウントされない**
- **MCP から作れるのは「現在時刻の 10 分後以降の予約配信」だけ**（必須ルールA）。即時配信はできず、**送信されたら取り消せない**
- 宛先は名簿ではなく**検索条件**で、実際の届き先は**送信時点で再評価される**

> **ツール名表記について**: 本スキルでは MCP ツールを OpenAPI の `operationId`（例: `postCustomersMessages`）で参照する。MCP クライアントが提示する実際のツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため本スキルでは付けない。

## When to use

- 顧客（購入者）宛に一斉配信を送りたいとき（全顧客・条件で絞る・個別に指定するのいずれも）
- 予約済みの顧客宛メッセージの本文・メッセージ名・配信日時を変えたいとき
- 予約済みの顧客宛メッセージを取り消したい（削除したい）とき
- 顧客宛メッセージの履歴・予定・送信状態を確認したいとき
- `*CustomersMessage*` 系ツールが必要な文脈

## When NOT to use

- **メルマガ・LINE の一斉配信（コンタクトリスト宛）** → `contact-broadcast` スキル。宛先が LINE友だち・メール購読者で、**プランの配信可能数にカウントされる**別系統の配信（境界は下の判断表）
- **顧客の検索・件数確認・詳細確認だけで、配信はしない** → `customer-manager` スキル
- **顧客へのタグ付け・タグ外し・顧客タグの作成** → `customer-manager` スキル（配信の宛先を絞るためにタグを付けたい場合も、タグ付けは customer-manager で先に済ませる）
- **コンタクト自体の検索・削除・CSVインポート** → `contact-list-manager` スキル
- **何かをきっかけに自動で送る配信（ステップ配信・タグ付与での自動送信）** → `workflow-builder` スキル。本スキルが扱うのは**その場で作る一斉配信のみ**
- **顧客カルテ・プロフィール編集・顧客の削除** → MCP に手段が無い。管理画面「顧客一覧」を案内する

### 顧客宛かコンタクト宛かの判断

| 依頼の言い方 | 行き先 |
|---|---|
| 「顧客に」「購入者に」「申し込んだ人に」「受講生に」「ゲストに」 | 本スキル（**「ゲスト」は MOSH 内部で顧客＝購入者を指す語**。コンタクト＝LINE友だち・メール購読者とは別） |
| 「メルマガ」「LINEで一斉配信」「友だちに」「登録者に」 | `contact-broadcast` |
| 「お客さんに連絡したい」のようにどちらとも取れる | **ユーザーに聞く**（下記） |

**どちらとも取れる依頼で推測して進めない。** 取り違えると宛先も件数も丸ごと違う相手に届く。「購入した方（顧客）宛か、LINE友だち・メール購読者（コンタクトリスト）宛か」を聞いて確定する。顧客とコンタクトの違い・タグID体系が別であることは `customer-manager` の [`references/customer-vs-contact.md`](../customer-manager/references/customer-vs-contact.md) が正本。

## ツールの選び方

| やりたいこと | ツール |
|---|---|
| 新規作成（予約配信） | `postCustomersMessages` |
| 一覧・履歴（本文なし） | `getCustomersMessages` |
| 本文と送信状態の確認 | `getCustomersMessage` |
| 編集（本文・メッセージ名・配信日時） | `patchCreatorCustomersMessage` |
| 削除（予約の取り消し） | `deleteCustomersMessage` |

- **下書き・予約解除に相当する操作は無い。** 作成したものは送られるか削除されるかのどちらかで、`contact-broadcast` のような「文面を残して予約だけ外す」はできない
- **宛先を後から変える手段は無い。** 変えたい場合は削除して作り直す

## Workflow

基本フロー: 依頼内容の確認 → 宛先の件数確認 → **内容を提示して承認を得る** → 実行 → 報告。

### 停止するかどうかの判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 作成（`postCustomersMessages`） | **必ず Step 3 で停止し、承認を得る** | 送信後は取り消せない。ツール定義が「宛先の件数を確認し、title・message・scheduledDateTime・宛先を提示して**合意を得てから実行すること**」を要求している |
| 編集（`patchCreatorCustomersMessage`） | **必ず Step 3 で停止し、承認を得る** | ツール定義が「現在の内容を確認し、**変更内容を提示して合意を得てから実行すること**」を要求している |
| 削除（`deleteCustomersMessage`） | **必ず Step 3 で停止し、承認を得る** | 復元できない。ツール定義が承認を要求している |
| 一覧・詳細（`getCustomersMessages` / `getCustomersMessage`） | 停止しない | 読み取り専用 |

**依頼文がどれだけ具体的でも、書き込みは承認なしに実行しない。**

Step 3 で扱う項目は2種類に分かれる。**「確定すべき項目」が不足していれば、承認を求める前にその項目自体をユーザーに尋ねる。**

| 区分 | 項目 | 不足したとき |
|---|---|---|
| **依頼文から確定すべき項目** | 本文 / 配信日時 / 宛先（全顧客か・絞り込むか・個別指定か） | **承認を求める前に、その項目自体を尋ねる** |
| こちらで機械的に用意してよい項目 | `title`（メッセージ名。管理用でゲストには届かない） | 停止しない。Step 3 で「補った」と明示する |

宛先は「指定が無い＝全顧客」と解釈しない。**触れられていなければ未確定として扱い、全顧客に送ってよいかを Step 3 で確認する。**

### 1. 依頼内容の確認

顧客宛かコンタクト宛かを「When NOT to use」の判断表で確定する。そのうえで本文・配信日時・宛先を把握する。

**「今すぐ送りたい」と言われたときはここで扱いを決める**（必須ルールA）。即時配信はできないので、予約配信として作るか管理画面から送るかを選んでもらう。

編集・削除の依頼なら、`getCustomersMessages` で対象を特定し、編集なら `getCustomersMessage` で現在の本文・メッセージ名・配信日時を取得する（全置換なので変えない項目も必要）。

### 2. 宛先の件数確認

**作成の前に必ず `postCustomersSearch` を同じ検索条件で呼び、宛先の件数を確認する**（必須ルールD）。条件の移し替え表は [references/mcp-tools.md](references/mcp-tools.md) の「宛先の件数確認」。件数が 0 のまま作成するとサーバー側でエラーになるので、条件を見直す。

ID を必要とする条件（サービス・顧客タグ・特定顧客）が依頼に含まれていたら、サービスは `product-navigator`、顧客タグは `getCreatorCustomerTags`、特定顧客は `postCustomersSearch` で解決する。解決できなければその条件は使わずユーザーに確認する（必須ルールC）。

### 3. 内容の提示（人ゲート）

提示する項目:

- 作成: 本文 / 配信日時 / 宛先（条件と件数）/ メッセージ名 / **メールと MOSH公式LINE の両方に届くこと** / **送信後は取り消せないこと**
- 編集: 対象のメッセージ名と現在の配信日時、新旧の変更点
- 削除: 対象のメッセージ名と配信日時。**復元できないこと**を明示する

**宛先は「承認時点の名簿」ではなく「条件」を承認してもらう。** 実際の届き先は配信実行時に再評価されるため、それまでに新規購入・解約・タグの付け外しがあれば件数も相手も変わる。提示にこの点を一言添える（例「今の条件だと 38 名に届きます。配信時点で条件に当てはまる方が対象になるので、それまでに増減すれば人数も変わります」）。

自分で補った項目（メッセージ名のみ）は「補った」と明示する。**本文を補ってはいけない**（提示規約）。

**判定表で停止する操作は、ユーザーの承認を得るまで Step 4 に進まない。**

### 4. 実行

[references/mcp-tools.md](references/mcp-tools.md) の該当する操作の節に従って呼び出す。新規作成のボディは [examples/message-bodies.json](examples/message-bodies.json) の形をそのままベースにする（15フィールド必須で、数値配列と文字列配列が混在する。記憶で組まない）。

### 5. 結果の報告

何がどの状態になったかを伝える（提示規約に従う）。作成したメッセージの ID は返らないので、ID を伝える必要があるときは [references/mcp-tools.md](references/mcp-tools.md) の「レスポンスと、作成後にできること」に従う。

## 必須ルール

### A. 即時配信はできない。予約は現在時刻の 10 分後以降【最重要】

MCP から作れるのは**現在時刻の 10 分後以降の予約配信だけ**で、それより前の日時（過去日時を含む）はすべてエラーになる。日時の形式・検証の詳細は [references/mcp-tools.md](references/mcp-tools.md) の「配信日時」。

**「今すぐ送って」には、予約配信として作るか管理画面から送るかを選んでもらう。勝手に「10 分後」と決めて送らない。**

### B. 送信後は取り消せない。削除は予約日時直前まで、編集は予約日時の10分前まで

**削除**は未送信であれば予約日時の直前まで可能。送信済みのものは 422 になる。

**編集は削除より条件が厳しい。** `patchCreatorCustomersMessage` は本文・メッセージ名を変えない場合でも `scheduledDateTime` を毎回送り直す仕様で、この値は常に「現在時刻の10分後以降」であることを再検証される（変更しない場合の現在値でも同様）。そのため、**予約日時まで残り10分を切ると、日時を変えるつもりがなくても編集自体が422で拒否される**。「配信日時までなら直せます」ではなく「**配信日時の10分前までなら直せます**」と案内する。それを過ぎたら削除（取り消し）しか手段が無いことも併せて伝える。

### C. ID を推測・創作しない

`tagIds` / `excludeTagIds` は、タグ名から `getCreatorCustomerTags`（顧客タグ一覧）で**名前が完全一致するタグ**の id を引いて使う（`customer-manager` 必須ルールBと同じ経路）。完全一致が無い・似た名前が複数あるときは、空配列のままユーザーに確認する。検索結果の顧客の `tags[]` を眺めてタグを探したり、タグ名だけで ID を決め打ちしたりしない。

**`serviceIds` / `subscriptionIds` はこの限りではない。** 商品プランとして売っている商品なら、`product-navigator` スキル（`getCreatorProductPlan` / `getCreatorProductPlans`）の `moshServiceId`（文字列）を数値化したものがそのまま使える（`customer-manager` 必須ルールBと同じ経路。詳細は [references/mcp-tools.md](references/mcp-tools.md)）。商品プランに紐づかない古い形式のサービスにはこの経路が無く、その場合のみ空配列でユーザーに確認する。

**顧客ID（`customerIds`、個別指定の宛先）はこの限りではない。** `postCustomersSearch` 自体が顧客の検索・一覧ツールなので、名前・メールアドレスなど依頼にある手がかりで検索すれば `customers[].id` から正しいIDを取得できる（`customer-manager` 必須ルールBと同じ経路）。この場合も検索結果に実際に含まれていた値だけを使い、名前だけで決め打ちしない。

**【最重要・無言の失敗】IDが分からないからといって、`isAllCustomers: false` のまま `customerIds` を空配列にして「とりあえず作成」しない。** これはエラーにならず、実装上 `isAllCustomers: true`（全顧客）と完全に同じ扱いになる（詳細は [references/mcp-tools.md](references/mcp-tools.md) の「宛先の2モード」）。個別指定の依頼で ID が特定できるまでは、作成に進まずユーザーに確認する。

**顧客タグとコンタクトタグは別のID体系。** `getCreatorContactTags` が返すコンタクトタグの id（整数）を `tagIds` / `excludeTagIds` に渡すと、エラーにならず想定と違う相手に届く（無言の失敗）。正本は `customer-manager` の [`references/customer-vs-contact.md`](../customer-manager/references/customer-vs-contact.md)。

宛先モード（`isAllCustomers`）の切り替え方、15フィールドの既定値、フィールドごとの型は [references/mcp-tools.md](references/mcp-tools.md) と [examples/message-bodies.json](examples/message-bodies.json) が正本。**記憶で組まず必ず例をベースにする**（同じボディ内で数値配列と文字列配列が混在し、個別指定でも他の検索条件が効き続けるという2点を間違えやすい）。

### D. 作成前に必ず件数を確認する

宛先が何名になるかを確認しないまま作成しない。条件を1つ取り違えるだけで、想定の何十倍の購入者に届く。手順は Step 2。

### E. 本文はプレーンテキストのみ。件名も埋め込み変数も無い

- 届くのは `message` の本文だけ。**画像・ボタン・カルーセル・装飾は使えず**、リンクは URL の文字列として出る（1〜4500文字）
- **メールの件名は自動生成される**（「◯◯さんからメッセージが届きました」）。`title` は管理用の「メッセージ名」で、**ゲストには届かない**。件名のつもりで本文の要約を `title` に入れない
- **埋め込み変数は使えない。** `{{line_name}}` など `contact-broadcast` やワークフローで使える変数を書いても置換されず、`{{...}}` の文字列のまま受信者に届く（無言の失敗）
- 本文をこちらで組むときの形式基準（`message` はプレーンテキストなので、吹き出し数・カルーセル・画像に関する基準は存在しない）:
  - **1配信1目的。** 読ませる（お知らせ）と申し込ませる（販売）を混ぜない。別件が2つあるなら配信を2本に分ける
  - **文字数の目安（全角換算）**: 告知・案内 150〜250字（上限500字）/ リマインド 80〜120字（上限200字）/ お礼・短い連絡 50〜100字（上限200字）。本文の上限4500字とは別の実務基準
  - **CTA は1つだけ。** 誘導先の URL は1本に絞る。「こちら」ではなく「詳細を見る」のように動詞で終わる8〜15字にする
  - **スマホ前提の可読性**: 1行20〜25字で改行、3〜4行ごとに空行、数字は半角、絵文字は2〜3個まで。冒頭1〜2行で「誰に向けた何の連絡か」が分かるようにする
  - **使ってはいけない表現**: 収益の断定・効果の保証・誇大表現（「誰でも確実に稼げます」等）。中身のない形容だけの文（「充実の内容でお届けします」）も残さない

### F. 個人情報の取り扱い

宛先確認で得た顧客名・メールアドレスは、**ユーザーに依頼された用途以外に出力・転記しない**。件数を聞かれたら件数を答え、名簿を勝手に展開しない。取得した顧客情報を、依頼されていないファイル・外部サービス・別の会話文脈に書き出さない。

## ユーザーへの提示・コミュニケーション規約

- 平易な日本語で答える。JSON・HTTP用語・ツール名・内部フィールド名（`isAllCustomers` / `scheduledDateTime` / `totalCount` / `isSent` など）をそのまま出さない。ユーザーが管理画面で見ている言葉（メッセージ本文 / メッセージ名 / 予約送信 / ◯名予定）に置き換える
- **完了形で書けるのは、対応するツールを実際に呼んで成功した後だけ。** 「予約しました」「更新しました」「削除しました」をツール呼び出しの前に書かない。承認前の提示と実行後の報告は箇条書きだと同じ見た目になるので、どちらなのかが一読で分かるように書く
  - **承認を待つ提示**（書き込みの前は必ずこちら）: 「以下の内容で予約してよいですか」と書き、**まだ保存していない**ことを明示する
  - **実行後の報告**: 承認を得てツールを呼んだあとに「以下の内容で**予約しました**」と事実として書く
- **配信本文は与えられた情報の言い換え・整形に留める。** 日時・場所・料金・特典・実績など、依頼文にも既存のメッセージにも無い事実を補って書かない。厚みが欲しい場合は Step 3 でユーザーに材料を確認する。**逐語で指定された本文には手を加えない**
- **できない理由を仕組みで説明しない。**「ツールが提供されていない」「APIトークン認証では〜」ではなく「◯◯は MOSH の管理画面からの操作になります」と、ユーザーから見える事実で伝える。**「MCP」「API」という語自体もユーザー向け文面に出さない**（NG:「今すぐの即時配信は MCP からはできません」／OK:「今すぐの配信はできません。作れるのは 10 分後以降の予約配信だけです」）
- **配信日時に曜日を添えるなら必ず検算する。自信が持てないなら曜日を書かない**（日付と時刻だけでも用は足りる。誤った曜日はユーザーが配信日を勘違いする原因になる）
- **未確定の値を推測で埋めない。** 分からない項目は埋めずに聞く

## よくあるミス

上のセクションでカバー済みの事項は再掲しない。ここは他セクション・references でカバーされない落とし穴のみ（追記前に既存セクション・references でカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| `getCustomersMessage` の `customerNames` が空配列なのを見て「宛先は0名です」と報告する | MCP 経由では**必ず空配列**が返る仕様。宛先は条件から `postCustomersSearch` で確認する（[references/mcp-tools.md](references/mcp-tools.md)） |
| 「予約を取り消して」と言われて、`contact-broadcast` と同じ感覚で「下書きに戻す」操作を探す／存在しない `isDraft` を付けて呼ぶ | 顧客宛メッセージに予約解除・下書きは無い。**削除（復元不可）しか無いことを伝えたうえで**、文面を残したいなら手元に控えて作り直す案を添えて確認する |
| 本文を変えずに配信日時だけ遅らせるとき、`scheduledDateTime` だけを送る | 全置換なので `title` と `message` も現在値を入れる。現在値は `getCustomersMessage` で取得する |
| 一覧の `page` に数値 `2` を渡す／詳細・編集・削除の `id` に数値を渡す | どちらも**文字列**（`"2"` / `"123"`）。数値はスキーマ検証で弾かれる。ID が数値で返ってくる（`getCustomersMessages` の `id`）ため、そのまま渡してしまいやすい |
| 即時配信不可・`customerNames` 空配列などの理由を「MCP からは」「API 側の仕様上」と説明する | 「MCP」「API」はユーザーに見えない内部用語。「今すぐの配信はできません。作れるのは10分後以降の予約配信だけです」のようにユーザーから見える事実だけで言う |

## エラーが返ったとき

**再試行を繰り返さず**、返ってきた内容に沿って原因と対処を平易な日本語で伝える。

- **予約日時が近すぎる（422）**: 現在時刻の 10 分後より前を指定している。作成だけでなく**編集でも起きる**（必須ルールB）。ユーザーに日時を確認し直す。勝手に 10 分後へずらして送らない
- **送信対象の顧客が見つからない（400）**: 条件に該当する顧客が0名。Step 2 の件数確認を飛ばしたときに起きる。条件を1つずつ外して切り分けるか、ユーザーに条件を確認する。**タグ条件を使っている場合は、まず必須ルールC のタグ体系の取り違えを疑う**
- **すでに配信済み（422・エラー文言「すでに配信済みのため、更新／削除することができません。」）**: 送信済み、または予約日時を過ぎている。他の手段は無いので、その旨を伝える。**編集はこれとは別に、予約日時の10分前を切った時点で（送信前でも）上記の「予約日時が近すぎる」エラーで先に拒否される**点に注意（必須ルールB）
- **見つからない（404）**: メッセージIDが違うか、別のクリエイターのメッセージ。`getCustomersMessages` で ID を確認し直す
- **認証エラー（401）**: MCP のアクセストークン失効の可能性。同じリクエストを繰り返さず、接続設定の確認を案内する
- **スキーマ検証で弾かれた**: 必須フィールドの欠落・型違い（`customerIds` / `tagIds` / `page` / `id`）・enum 違反・本文の4500文字超過。[examples/message-bodies.json](examples/message-bodies.json) でボディを組み直す
