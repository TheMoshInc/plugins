# MOSH 顧客管理（サービス購入者の検索・絞り込み）

## Overview

MCP ツール `postCustomersSearch` 1本で、クリエイターのサービスを購入した顧客（管理画面「顧客・連絡先 > 顧客一覧」）を検索条件付きで取得する。**参照専用**で、顧客データを変更する手段は無い。

**顧客タグとコンタクトタグは別のID体系。** コンタクトタグの id を `tagIds` / `excludeTagIds` に渡すと、エラーにならずに間違った結果（多くはヒットゼロ）が返る（必須ルールA）。

> **ツール名表記について**: 本スキルでは MCP ツールを OpenAPI の `operationId`（`postCustomersSearch`）で参照する。MCP クライアントが提示する実際のツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため本スキルでは付けない。

## When to use

- 購入者の一覧・件数を知りたいとき（「顧客は何人いる？」「一覧を見せて」）
- 名前・メールアドレス・MOSH ID で特定の顧客を探したいとき
- 購入条件で絞りたいとき（サブスクの継続／解約、支払い方法、支払いタイプ、決済ステータス、メール受信可否）
- 施策の対象者がどれくらいいるかを、実行前に把握したいとき

## When NOT to use

- **コンタクト（LINE友だち・メール購読者）の検索・削除・CSVインポート** → `contact-list-manager` スキル。顧客とは別概念（[references/customer-vs-contact.md](references/customer-vs-contact.md)）
- **メルマガ・LINE の一斉配信を作る／送る** → `contact-broadcast` スキル
- **コンタクトへのタグ付与・ステップ配信の構築** → `workflow-builder` スキル（そこで扱うのは**コンタクトタグ**）
- **顧客へのタグ付け・顧客カルテ・プロフィール編集・削除** → MCP に手段が無い（必須ルールD）。管理画面「顧客一覧」を案内する
- **売上・注文明細の金額集計** → `sales-reporter` スキル
- **商品・プランの内容やプラン価格の確認** → `product-navigator` スキル
- **特定商品のサブスク購読者を登録日順・ステータス別に見る** → `postCreatorProductSubscribers`（商品単位の別ツール。本スキルの守備範囲外）

## Workflow

基本フロー: 依頼の切り分け（顧客かコンタクトか） → 検索条件の組み立て → 実行 → 件数確認とページング → 用途に絞った提示。**書き込みが無いため人ゲートは不要**だが、個人情報を返すので提示は必要最小限にする（必須ルールE）。

### 1. 依頼の切り分け

「顧客（購入者）」の話か「コンタクト（LINE友だち・メール購読者）」の話かを最初に確定する。「登録者」「お客さん」「リスト」のようにどちらとも取れる言い方なら**ユーザーに聞く**。判断表は [references/customer-vs-contact.md](references/customer-vs-contact.md)。

顧客の**編集**（タグ付け・カルテ・削除）を求められている場合は、ここで Workflow を離れ必須ルールD に従って案内する。

### 2. 検索条件の組み立て

依頼の言葉を検索条件に対応づける。**14フィールドすべて必須**なので、使わない条件も既定値（空配列 / 空文字 / `null`）で必ず埋める（必須ルールC）。フィールドと enum の対応表は [references/mcp-tools.md](references/mcp-tools.md)、そのまま渡せるボディは [examples/search-body.json](examples/search-body.json)。

この時点で、**ID を必要とする条件（サービス・タグ・特定ユーザー）が依頼に含まれていないか**を確認する。含まれていて ID が手元に無ければ、その条件は使わず（空配列のまま）ユーザーに確認する（必須ルールB）。

### 3. 実行

`postCustomersSearch` を `{ "bodyParams": { ... } }` の形で呼ぶ。`limit` は通常 10、一覧をまとめて見たい依頼でも最大 100。

### 4. 件数確認とページング

`totalCount` が条件に一致した総件数。取得した件数がこれに満たない場合、**続きがあることを認識する**。

- 件数だけ聞かれている → 1ページ目を1回呼んで `totalCount` を答える。全ページを取りに行かない
- 一覧が必要 → `page` を増やして必要な分だけ取る。何百件も無言で全ページ取得せず、件数を伝えて「何件まで出すか」を確認する
- `totalCount: 0` はエラーではない。条件のどれが効きすぎているかを添えて伝える

### 5. 提示

依頼された用途に必要な項目だけを出す（必須ルールE、提示規約）。適用した検索条件を平易な言葉で1行添えると、条件の取り違えにその場で気づける。

## 必須ルール

### A. 顧客タグとコンタクトタグを混同しない【最重要】

`tagIds` / `excludeTagIds` に指定できるのは**顧客タグ**の id だけ。`getCreatorContactTags` が返す**コンタクトタグ**の id は別体系であり、**渡してはならない**。渡してもエラーにならず、想定と違う結果が返る（無言の失敗）。同名のタグが両方に存在し得るため、名前の一致は同一である根拠にならない。

顧客タグの id を得る MCP ツールは存在しない。唯一の入手経路は `postCustomersSearch` のレスポンス `customers[].tags[]` で、これも**返ってきた顧客が持つタグ**に限られる。詳細は [references/customer-vs-contact.md](references/customer-vs-contact.md)。

### B. ID を推測・創作しない。既定は空配列

`serviceIds` / `subscriptionIds` / `tagIds` / `excludeTagIds` / `userIds` の ID は、**MCP のツールからは取得できない**。ユーザーから具体的な ID を明示された場合を除き、空配列を渡す。

唯一の例外は、**ユーザーが指定した対象（特定の顧客名・メールアドレス等）を検索した結果に実際に含まれていた値**（`customers[].id` は `userIds` と同じ体系、`customers[].tags[].id` は顧客タグ）。それでも、名前だけを手がかりに一致を決めつけない。

**`tagIds` / `excludeTagIds` / `userIds` は文字列の配列。** ユーザーが「顧客タグID 42」「顧客ID 1001」のように数字で言っても、`[42]` のような数値リテラルにせず `["42"]` と文字列にする（[references/mcp-tools.md](references/mcp-tools.md) の型定義どおり。数値のまま渡すとスキーマ検証で弾かれる）。

**タグ名を手がかりにIDを探すためだけに、条件なしで検索を実行しない。** 「タグ『VIP』が付いてる人を出して」を、①条件なしで検索→②返ってきた顧客の`tags[]`をスキャンして「VIP」に近い名前のタグを探す→③そのIDで絞り込む、という手順で処理しない。これは推測・創作ではなく実データから拾っているように見えるが、（a）検索1回で返る範囲にしか無い顧客のタグしか見えず全量を保証できない、（b）似た名前の別タグを取り違えうる、という2点で不確実な結果を確信ありげに報告することになり、無言の失敗と同じ実害を生む。サービス名やタグ名だけで絞りたい依頼は、**ID探索のための検索を挟まず**、ID を埋めずに**管理画面「顧客一覧」のフィルターでの確認を案内する**。

### C. 14フィールドすべて必須。省略できない

使わない条件も既定値で埋める: `serviceIds` / `subscriptionIds` / `tagIds` / `excludeTagIds` / `userIds` は `[]`、`searchQuery` は `""`、`eventDateTime` / `subscriptionState` / `paymentMethod` / `paymentType` / `paymentStatus` / `isEmailReceivingAllowed` は `null`、加えて `page` と `limit`。欠けたボディはスキーマ検証で弾かれ、サーバーに届かない。

**`isEmailReceivingAllowed` の `false` は有効な絞り込み値**（＝受信停止中の顧客）。「絞り込まない」の意味で `false` を使わない（絞り込まないのは `null`）。

**enum の値は綴りをそのまま使う。推測で書き換えない。** 特に `paymentMethod` の `bank-transfer` は**ハイフン区切り**（`bank_transfer` とアンダースコアにしない。一般的なAPI設計のスネークケースに引きずられやすい、実例で確認済みの罠）。[examples/search-body.json](examples/search-body.json) の `bank-transfer-installment` にそのまま使える完成形があるので、`paymentMethod` を使うときは必ずここの綴りをコピーする。

### D. 参照専用。顧客データは変更できない

顧客へのタグ付け・タグ剥がし、カルテの編集、プロフィール変更、削除はいずれも MCP に手段が無い（[references/mcp-tools.md](references/mcp-tools.md) の「MCP に無いもの」）。**できない操作を、別のツールで代用したり、できるかのように答えたりしない。** 管理画面「顧客・連絡先 > 顧客一覧」での操作を案内する。

### E. 個人情報の取り扱い

レスポンスには顧客名・メールアドレスが含まれる。**ユーザーに依頼された用途以外に出力・転記しない。**

- 件数を聞かれたら件数を答える。名簿を勝手に展開しない
- メールアドレスは、依頼が明示的にそれを必要とする場合だけ出す
- 取得した顧客情報を、依頼されていないファイル・外部サービス・別の会話文脈に書き出さない

### F. `eventDateTime` は範囲検索ではない。原則 `null`

指定した日時の**分単位の完全一致**でしか絞り込めず（[references/mcp-tools.md](references/mcp-tools.md)）、「今月の申込者」のような期間指定には使えない。開催日で絞りたい依頼は管理画面のフィルターを案内する。

## ユーザーへの提示・コミュニケーション規約

- 平易な日本語で答える。**内部の値・フィールド名をそのまま出さない**（`active` / `bank-transfer` / `one_time` / `approved` / `isEmailReceivingAllowed` / `totalCount` など）。ユーザーが管理画面で見ている言葉に置き換える。enum と画面ラベルの対応表は [references/mcp-tools.md](references/mcp-tools.md) が正本（`totalCount` は「該当件数」）
- JSON・HTTP用語・ツール名・エンドポイント名をユーザー向け文面に出さない
- **できない理由を仕組みで説明しない。**「ツールが公開されていない」ではなく「◯◯は MOSH の管理画面からの操作になります」と、ユーザーから見える事実で伝える
- **ID・件数・条件を推測で埋めない。** 分からない項目は埋めずに聞く
- 該当ゼロのときは「いません」で終わらせず、効いている条件を伝えて絞り込みの見直しを提案する

## よくあるミス

上のセクションでカバー済みの事項は再掲しない。ここは他セクション・references でカバーされない落とし穴のみ（追記前に既存セクション・references でカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| `totalCount` が 250 なのに、1ページ目の 10 件だけを見て「顧客は10人です」と答える | `totalCount` が総件数。取得件数と混同しない（Workflow 4） |
| 「解約した人を除いて」と言われて反射的に `subscriptionState: "active"` を入れる | `subscriptionState` はサブスク契約の状態を見る条件で、画面でもサブスク型サービスを選んだときだけ出る。単発購入だけの顧客が結果からこぼれないか、対象範囲をユーザーと確認してから使う |
| 「50件見せて」に対し `limit: 50` を入れ、返ってきた 50 件をそのまま名簿として全部書き出す | 件数と、依頼に必要な項目だけを出す。名前・メールの一括展開は依頼された用途に必要なときだけ（必須ルールE） |
| 依頼に無い条件（例: `paymentStatus: "approved"`）を「たぶんこうだろう」と足す | 依頼された条件だけを入れる。足すべきか迷ったらユーザーに聞く |

## エラーが返ったとき

- **該当ゼロ（`customers: []` / `totalCount: 0`）**: エラーではない。同じ条件で再実行せず、条件を1つずつ外して原因を切り分けるか、ユーザーに条件を確認する。**タグ条件を使っている場合は、まず必須ルールA の取り違えを疑う**
- **401（認証エラー）**: MCP のアクセストークン失効の可能性。同じリクエストを繰り返さず、接続設定の確認をユーザーに案内する
- **500 / タイムアウト**: サーバー側で検索が失敗している。同じリクエストを連続で繰り返さず、時間を置いて1度だけ再試行する。それでも失敗するならサーバー側の問題として伝える。**条件を勝手に変えて通った結果を、依頼どおりの結果として出さない**
- **スキーマ検証で弾かれた**: 必須フィールドの欠落・enum 違反・`limit` の範囲外（1〜100）。Workflow 2 に戻ってボディを組み直す（[examples/search-body.json](examples/search-body.json)）
