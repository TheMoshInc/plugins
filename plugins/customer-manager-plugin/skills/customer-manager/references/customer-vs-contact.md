# 顧客とコンタクトの違い（境界判断とタグID体系の正本）

「顧客」と「コンタクト」は MOSH の別機能・別データ・**別のタグID体系**。依頼をどちらとして扱うかを最初に確定するために読む。

> 本ファイルの区分・タグID体系・管理画面の対応は、MOSH の管理画面と API スキーマ定義で確認したもの（2026-09 時点）。
> 値を書き換えるときは、記憶や推測ではなく MOSH の API スキーマ定義で裏取りする。

## 2つの概念

| | 顧客 | コンタクト |
|---|---|---|
| 何者か | クリエイターのサービス・商品を**購入した人** | LINE友だち・メール購読者（マーケティング用の連絡先リスト） |
| 管理画面 | 「顧客・連絡先」>**顧客一覧**（`/creator/customers`） | 「顧客・連絡先」>**コンタクトリスト**（`/creator/contacts/line`） |
| 主な用途 | 購入者の把握、購入条件での絞り込み | 一斉配信・ステップ配信の宛先 |
| 検索する MCP ツール | `postCustomersSearch`（本スキル） | `postCreatorContactsEmailSearch` / `postCreatorContactsLineSearch`（contact-list-manager スキル） |
| ID | ユーザーID（数値。レスポンスの `customers[].id`） | コンタクトID（メール／LINE で別々） |
| タグ | **顧客タグ** | **コンタクトタグ** |

**購入したからといって自動的にコンタクトになるわけではなく、逆も同じ。**両者は別々に管理される。「LINE友だちのうち購入した人」のような突き合わせは、どちらのツールでもできない。

## タグID体系が別物であること（最重要）

| | 顧客タグ | コンタクトタグ |
|---|---|---|
| 使う場所 | `postCustomersSearch` の `tagIds` / `excludeTagIds`、顧客への付与・解除 | ワークフローのタグ付与・条件ステージ、コンタクト検索の `filters.tag` |
| 一覧を取る MCP ツール | `getCreatorCustomerTags` | `getCreatorContactTags` |
| 作成する MCP ツール | `postCreatorCustomerTags`（顧客1人への付与とセット） | `postCreatorContactTags` |
| 付与・解除する MCP ツール | `postCreatorCustomerTagCustomers` / `deleteCreatorCustomerTagCustomer` | workflow-builder（ワークフローのタグ付与アクション） |

どちらの一覧ツールも呼べてしまうが、**コンタクトタグの id を顧客タグとして使ってはならない**（逆も同じ）。ID空間が違うのに、**エラーになるとは限らない**:

- コンタクトタグの id は**整数**（`8821`）、顧客タグの id は**数字だけの文字列**（`"12"`）。文字列化すると見た目では区別できない
- 付与・解除のサーバー処理は「その id の顧客タグが存在するか」しか見ない。コンタクトタグ `5` を `"5"` として渡し、たまたま顧客タグ `"5"` があれば、**404 にならず無関係の顧客タグが付く／外れる**
- 検索に渡した場合も、ヒットゼロになるか別タグの顧客が返るかは偶然次第

どちらでも**無言の失敗**になる。手元の id が整数なら、コンタクトタグ由来を疑う。

同じタグ名（例:「VIP」）が顧客タグとコンタクトタグの両方に存在することもあり得るため、**名前が一致していることは同一である根拠にならない**。「顧客にタグを付けて」なら顧客タグ、「LINE友だちにタグを付けて」ならコンタクトタグ。どちらか曖昧なら聞く。

### 顧客タグIDの入手経路

- **タグ名から引く**: `getCreatorCustomerTags`（全一覧）で名前の完全一致を探す。これが正規の経路
- **特定の顧客に付いているタグ**: `getCreatorCustomer` の `tags[]`、`postCustomersSearch` の `customers[].tags[]`
- **作成直後**: `postCreatorCustomerTags` のレスポンス

検索結果の `customers[].tags[]` は返ってきた顧客のタグにすぎないので、タグ名から id を探す用途には使わない。条件なしで検索して `tags[]` を眺めても、（a）1回の検索で返る範囲の顧客に付いたタグしか見えず全量を保証できない、（b）似た名前の別タグを取り違えうる、の2点で不確実な結果を確信ありげに報告することになる。

## 依頼の振り分け

| 依頼の例 | 行き先 |
|---|---|
| 「顧客一覧を見せて」「このサービスの購入者は？」「サブスク継続中の人は何人？」 | 本スキル |
| 「この顧客の電話番号・タグ・申込履歴を見せて」「顧客にタグを付けて／外して」「顧客タグの一覧」 | 本スキル |
| 「LINEの友だちは何人？」「メールのコンタクトを探して」「コンタクトを削除して」「CSVで取り込んで」 | contact-list-manager |
| 「メルマガを送りたい」「LINEで一斉配信したい」 | contact-broadcast |
| 「購入者にお知らせを送りたい」「顧客に一斉連絡」 | customer-broadcast |
| 「コンタクトにタグを付けたい」「ステップ配信を組みたい」 | workflow-builder |
| 「顧客カルテを見たい・書きたい」「顧客を削除したい」「顧客タグの名前を変えたい・タグ自体を消したい」 | MCP に手段が無い。管理画面「顧客一覧」を案内 |
| 「売上・注文の明細と金額が見たい」 | sales-reporter |
| 「この商品のサブスク申込者を登録日順に見たい」 | `postCreatorProductSubscribers`（商品単位のサブスク購読者検索。本スキルの守備範囲外） |

**どちらか判断がつかないとき**（「登録者リスト出して」「お客さんの一覧」など）は、購入者のことか連絡先リストのことかをユーザーに聞いてから進める。取り違えると、件数も対象も丸ごと違うリストを渡すことになる。
