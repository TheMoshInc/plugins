# MOSH コンタクトリスト向け一斉配信（コンタクトメッセージ）

## Overview

MCP ツール（`*ContactMessagesEmail*` / `*ContactMessagesLine*`）を使って、MOSH クリエイターの一斉配信（メール / LINE）を作成・編集・運用する。配信は必ず「予約配信」または「下書き」として作成する（即時配信はしない）。

配信は実顧客に届く操作なので、**どの操作で人の承認を取るか**を「Workflow」の判定表で決める。管理画面のフォームが行っている入力チェックの一部は API 側では検証されないため、本スキルのルールは呼び出す側（このスキルに従うエージェント）が守る。

> **ツール名表記について**: 本スキル内では MCP ツールを OpenAPI の `operationId`（例: `postCreatorContactMessagesLine`）で参照する。MCP クライアントが実際に提示するツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため、本スキルでは付けない。

## When to use

- コンタクトリスト（顧客・LINE友だち）向けの一斉配信を新規に作りたいとき（予約配信・下書きのどちらも）
- 既存の配信の内容・配信日時・配信対象を変更したいとき
- 予約を解除したい（文面は残す）／配信を削除したいとき
- 配信の履歴・予定を一覧・検索したいとき
- `*ContactMessages*` 系ツールが必要な文脈

## When NOT to use

- 何かをきっかけに自動で送る配信（ステップ配信・タグ付与での自動送信など） → `workflow-builder` スキル。本スキルが扱うのは**その場で作る一斉配信のみ**
- ゲスト（サービス購入者）向けの配信 → 別系統で **MCP ツールが提供されていない**。管理画面での操作を案内する
- LP（ランディングページ）の作成・編集 → `lp-builder` スキル
- 配信するコンタクト自体の作成・タグ付け・インポートなど、コンタクト管理そのもの

## ツールの選び方（メール / LINE で対称）

| やりたいこと | メール | LINE |
|---|---|---|
| 新規作成（予約 or 下書き） | `postCreatorContactMessagesEmail` | `postCreatorContactMessagesLine` |
| 編集・下書きの予約確定 | `patchCreatorContactMessagesEmail` | `patchCreatorContactMessagesLine` |
| 予約解除（文面を残して下書きに戻す） | `postCreatorContactMessagesEmailDraft` | `postCreatorContactMessagesLineDraft` |
| 削除（文面ごと消す） | `deleteCreatorContactMessagesEmail` | `deleteCreatorContactMessagesLine` |
| 一覧・検索 | `postCreatorContactMessagesEmailSearch` | `postCreatorContactMessagesLineSearch` |
| 詳細取得 | `getCreatorContactMessagesEmail` | `getCreatorContactMessagesLine` |

- **下書きの新規作成は `post〜Email` / `post〜Line` の `isDraft: true`**。`post〜Draft` は「既存の配信予定を下書きに戻す」専用で、新規作成には使えない。
- 「キャンセルしたい」と言われたら、文面を残すか（→ 予約解除）完全に消すか（→ 削除）を確認して使い分ける。

## Workflow

### 停止するかどうかの判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 即時配信（`isDraft: false` + `scheduledAt: null`） | **実行しない** | 取り消せない |
| 作成（`post`。予約確定・下書きとも） | **必ず Step 3 で停止し、承認を得る** | ツール定義が「作成前に taskName・件名・配信日時・配信対象・本文を提示し、**合意を得てから実行すること**」を要求している |
| 編集・予約確定（`patch`） | **必ず Step 3 で停止し、承認を得る** | ツール定義が「**変更内容を提示し、合意を得てから実行すること**」を要求している |
| 削除（`delete`） | **必ず Step 3 で停止し、承認を得る** | 復元できない |
| 予約解除（`post〜Draft`） | 停止しない | 文面は残り再度予約できる。ツール定義に承認の要求は無い |

**依頼文がどれだけ具体的でも、書き込み（予約解除を除く）は承認なしに実行しない。** 「可逆だから省いてよい」とは判断しない — 予約配信は解除できるが、気づかなければ実顧客に届く。

Step 3 で提示・確認する項目は2種類に分かれる。**「確定すべき項目」が不足していれば、承認を求める前にその項目自体をユーザーに尋ねる。**

| 区分 | 項目 | 不足したとき |
|---|---|---|
| **依頼文から確定すべき項目** | 配信チャネル / 配信日時 / 配信対象 / 本文（メールは件名も）/ **送信元の LINE公式アカウント（候補が2件以上のとき）** | **承認を求める前に、その項目自体を尋ねる** |
| こちらで機械的に用意してよい項目 | `taskName`（管理用の名前）/ 送信元の LINE公式アカウント（`getCreatorLineChannels` の候補が**1件のときのみ**） | 停止しない。Step 3 で「補った」と明示する |

配信対象は「指定が無い＝全員」と解釈しない。**触れられていなければ未確定として扱い、全員に送ってよいかを Step 3 で確認する**（絞り込みを外すと想定より広く届く）。

### 1. 依頼内容の確認

配信チャネル（メール / LINE）・配信日時・配信対象・件名・本文を把握する。「メルマガ」はメール。LINE と迷う文脈では配信チャネルを確認する。

上の判定表に照らして、どこで停止するかを決める。**依頼文が完備していても承認は省けない**（省けるのは不足項目のヒアリングだけ）。

### 2. 参照リソースの確認

- LINE の場合は `getCreatorLineChannels` で送信元の LINE公式アカウントを確定する。**候補が2件以上あるときは推測で選ばず、アカウント名を並べてユーザーに選んでもらう**（別のアカウントから配信すると友だちでない相手には届かず、意図しない送信元名で届く）。候補が1件ならそれを採用し、Step 3 で「補った」と明示する
  候補の絞り方・ユーザーに見せる名前の作り方は [references/mcp-tools.md](references/mcp-tools.md) の「送信元 LINE公式アカウントの確定」を参照
- 配信対象をタグで絞る場合は `getCreatorContactTags` でタグの id を確認する
- 既存の配信を編集・解除・削除する場合は、一覧（`post〜Search`）で対象の `taskName` と `scheduledAt` を確認する
- 本文にクリック計測対象の URL を含める場合は [references/tracking-consent.md](references/tracking-consent.md) の手順に入る

取得できない値は**推測して埋めず**、ユーザーに確認する。

### 3. 内容の提示

提示する項目:

- 作成・予約確定: `taskName` /（**LINE は**）送信元の LINE公式アカウント /（メールは）件名 / 配信日時 / 配信対象 / 本文
- 予約解除・削除: 対象の `taskName` と配信日時。**削除は復元できないこと**を明示する

**送信元の LINE公式アカウントは ID ではなくユーザーが識別できる名前で示し、LINE の作成・予約確定・編集では省略しない** — 公式アカウントを複数持つクリエイターでは、送信元を確認しないまま承認されると意図しないアカウントから配信される。**送信元が1件に確定していないうちは承認を求めない**（Step 2 に戻って選んでもらう）。編集（`patch`）で送信元を変える場合は新旧のアカウント名を並べて示す。

自分で補った項目（上の2区分表の下段＝`taskName` / 候補1件の送信元 LINE公式アカウントのみ）は「補った」と明示する。**本文や件名を補ってはいけない**（コミュニケーション節の規約）。

**配信対象は「承認時点の固定リスト」ではなく「条件」を承認してもらう。** 実際の受信者は予約時ではなく**配信実行時に再評価される**ため、それまでにタグの付け外し・LINE のブロック・メールの購読解除などがあれば、承認時に見えていた対象者と実際の届き先は変わる。提示するときはこの点を一言添える（例「タグ『VIP』が付いている方に届きます。配信時点で付いている方が対象になるので、それまでに増減すれば届く人も変わります」）。

**判定表で停止する操作は、ユーザーの承認を得るまで Step 4 に進まない。** 確定すべき項目が揃っていない場合は、承認を求める前にその項目を尋ねる。

### 4. 実行

「ツールの選び方」でツールを選び、[references/mcp-tools.md](references/mcp-tools.md) の該当節に従って呼び出す。

新規作成のリクエストボディは、**メールなら [examples/email-scheduled-tag-filter.json](examples/email-scheduled-tag-filter.json)、LINE なら [examples/line-scheduled-tag-filter.json](examples/line-scheduled-tag-filter.json) の形をそのままベースにする**。メールと LINE でボディの形が違い、特に **`filterConditions` のキー構成**と **`isTrackingEnabled` を置く場所**を間違えやすい。正しい形は例と [references/mcp-tools.md](references/mcp-tools.md) を見て、記憶で組まない。

**MCP からの即時配信は行わない**（判定表参照）。ユーザーが「今すぐ送りたい」と希望した場合は、MCP では即時配信ができないことを伝え、予約配信として作成するか管理画面から送るかを選んでもらう。

## LINE の素材制約

**画像・動画は MOSH にアップロード済みの素材のみ指定できる。** 外部で公開されている画像・動画を検索して指定したり、URL を推測して組み立てたりしてはならない。**API 側で URL の検証は行われないため、外部の URL を指定するとそのまま LINE に配信される**（エラーにならない）。

**素材の用意そのものは MCP でもできる**（「ファイル共有」機能。`file-share` スキル）。ただし、そこで得られる値がこの配信の項目にそのまま使えるとは限らない:

- **`imageUrl`**: MOSH の画像リポジトリのURL形式である必要がある。ファイル共有の画像本体URLがこの形式と一致するかは未確認なので、**値はユーザーから受け取る**（推測して組み立てない）
- **`muxAssetId` / `previewMoshImageId`（LINE 動画）**: **ファイル共有のレスポンスには含まれない。** 流用できないので、管理画面から用意してもらう

指定に必要な値が用意できない場合は、管理画面での作成を案内する。

項目ごとの上限・形式（文字数・`imageUrl` の形式・`rich_message` の `cells` 件数など）は [references/mcp-tools.md](references/mcp-tools.md) の「LINE の `contents` の項目別制約」を参照。

## 埋め込み変数（`{{line_name}}`）

**使えるのは `{{line_name}}`（LINEプロフィール名）1つだけで、LINE の `text` タイプのみ。** 綴りは一字一句そのまま（`{{ line_name }}` のように波括弧内に空白を入れると置換されない）。

| 条件 | 可否 |
|---|---|
| LINE の `contents` の `text` | **使える**（宛先ごとに LINE の表示名へ置換される） |
| LINE の `carousel` / `image_carousel` / `rich_message` の文字列 | **使えない**（置換処理が走らない） |
| メールの `title` / `body` | **使えない**（メール配信に置換処理は無い） |

- **上表の「使えない」欄と、`{{line_name}}` 以外の変数名は、エラーにならず `{{...}}` の文字列が見えたまま受信者に届く**（無言の失敗）。`{{guest_name}}`・`{{name}}`・`{{customer_name}}` 等を創作してはならない。ワークフロー（`workflow-builder`）では他の変数が使えるが、**一斉配信では `line_name` だけ**なので混同しない。
- カルーセルやメールで名前を差し込みたいと言われたら、できないことを伝えて LINE の `text` の併用（メールなら LINE 配信）を提案する。
- **LINE の表示名が未取得のコンタクトでは空文字になる**（「{{line_name}}さん、こんにちは」→「さん、こんにちは」）。文頭を変数で始める文面はこの見え方を伝えたうえで使うか、「{{line_name}}様、いつもありがとうございます」のように空でも成立する形にする。
- Step 3 で本文を提示するときは、`{{line_name}}` が宛先ごとの LINE 表示名（管理画面の表示は「LINEプロフィール名」）に置き換わることを一言添える。

## コミュニケーション

- ユーザーへの応答は平易な日本語で行い、JSON・HTTP 用語・内部フィールド名（isDraft・isTrackingEnabled・ステータスの生値など）をそのまま出さない。
- **完了形で書けるのは、対応するツールを実際に呼んで成功した後だけ。** 「作成しました」「予約しました」「予約を解除しました」「削除しました」をツール呼び出しの前に書かない。提示した内容を箇条書きで並べる形は承認前でも実行後でも同じ見た目になるため、次のどちらなのかが一読で分かるように書く。
  - **承認を待つ提示**（書き込みの前は必ずこちら）: 「以下の内容で作成してよいですか」と書き、**まだ保存していない**ことを明示する。
  - **実行後の報告**: 承認を得てツールを呼んだあとに「以下の内容で**作成しました**」と事実として書く。
- 実行後の報告は「何がどの状態になったか」（例: 下書きとして保存済み・◯月◯日◯時に配信予約済み・予約を解除して下書きに戻した）が一読で分かるように伝える。
- **配信本文は与えられた情報の言い換え・整形に留める。** 所要時間・対象者・持ち物・実績など、依頼文にも
  既存の配信内容にも無い事実を補って書かない。文面を厚くしたい場合は Step 3 でユーザーに材料を確認する。
  本文・件名・カードのコピーを**こちらで組む**場合の形式基準（1配信1目的・文字数と吹き出し数の上限・
  CTA・NG表現・スマホ前提の可読性）は [references/best-practices.md](references/best-practices.md) に従う。
  **逐語で指定された本文・件名には手を加えない**（この規約が形式基準より優先する）。
- **後から直せる期限を伝えるなら「配信予定時刻の5分前まで」と正確に言う。** 「配信日時までは変更できます」は誤り
  （予約解除・編集・削除はいずれも配信予定時刻の5分前が締め切り）。期限に自信が無いなら期限に触れない。
- **配信日時に曜日を添えるなら必ず検算する。自信が持てないなら曜日を書かない。** 基準日から数えた曜日は1日ずれやすく、誤った曜日はユーザーが配信日を勘違いする原因になる（日付と時刻だけでも用は足りる）。

## エラーが返ったとき

操作が業務ルールに反する場合（配信可能数の上限超過、配信済みメッセージの編集、5 分前を過ぎた予約解除など）は、理由を示すエラーが返る。**再試行せず**、返ってきた内容に沿って原因と対処をユーザーへ平易な日本語で伝える（内部的なコードや用語は出さない）。状態による可否条件は [references/mcp-tools.md](references/mcp-tools.md) の該当節を参照。
