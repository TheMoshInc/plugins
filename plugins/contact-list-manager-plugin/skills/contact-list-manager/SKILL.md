# MOSH コンタクト名簿（LINE友だち / メール購読者）

## Overview

MCP ツール7本で、MOSH クリエイターの**コンタクトそのもの**を扱う。できるのは「探す・数える・1件を詳しく見る・削除する・メールアドレスをCSVで取り込み始める」の5つで、コンタクトを1件ずつ新規作成することも、タグを付け外しすることもできない。

**このドメインの削除は取り消せない。** ツール名は `patch...`（更新）だが、MCP から実行できるのは実質「削除（非表示化）」だけで、解除は API 権限上できず管理画面にも復元の導線がない。LINE コンタクトは削除で表示名とプロフィール画像そのものが消える。**どの操作で人の承認を取るかは「承認の判定表」だけで決める。**

> **ツール名表記について**: 本スキル内では MCP ツールを OpenAPI の `operationId`（例: `postCreatorContactsLineSearch`）で参照する。MCP クライアントが実際に提示するツール名にはサーバー識別子のプレフィックスが付くが、その形はユーザー環境により異なるため、本スキルでは付けない。

## When to use

- コンタクトを探したい・条件に合う人が何人いるか数えたいとき（「タグAの友だち何人？」「配信対象は何件？」）
- 1件のコンタクトの登録日・受け取った特典・タグ・流入経路・表示中リッチメニューを確認したいとき
- コンタクトを削除したいとき（LINE友だち / メール購読者）
- メールアドレスの一覧を CSV で一括登録したいとき
- 上記の `*ContactsEmailSearch*` / `*ContactsLineSearch*` / `*ContactEmail*` / `*ContactLine*` 系ツールが必要な文脈

## When NOT to use

- メルマガ・LINE一斉配信を作る／予約する／履歴を見る → `contact-broadcast` スキル。本スキルは配信そのものには踏み込まない（配信対象が何人いるかを**数えるだけ**なら本スキル）
- コンタクトへのタグ付与・解除、ステップ配信、流入経路の作成 → `workflow-builder` スキル（タグの付け外しはワークフローの `ADD_CONTACT_TAG` / `REMOVE_CONTACT_TAG` ステージが担当）
- サービスを購入した「顧客（ゲスト）」の検索・詳細 → 本スキルの対象外（`*Customer*` 系の別ツール）。コンタクト（LINE友だち・メール購読者というマーケティングリスト）とは別概念なので、どちらの話か曖昧なときは実行前にユーザーに確認する
- リッチメニューの内容編集・デフォルト設定 → `line-rich-menu` スキル（本スキルはリッチメニューを**検索条件と表示項目として読むだけ**）
- LP の作成・編集 → `lp-builder` スキル

## ツールの選び方

| やりたいこと | メール | LINE |
|---|---|---|
| 探す・数える（一覧） | `postCreatorContactsEmailSearch` | `postCreatorContactsLineSearch` |
| 1件を詳しく見る（特典を全件） | `getCreatorContactEmail` | `getCreatorContactLine` |
| 削除する | `patchCreatorContactsEmail` | `patchCreatorContactsLine` |
| CSV で一括登録を開始する | `postCreatorContactsEmailCsvImportJobs` | 提供なし（下の「MCP からはできないこと」） |

条件に使う ID は必ず次のツールで解決する（推測・創作は禁止）: タグ `getCreatorContactTags` / 流入経路 `getCreatorScenariosInflowActions` / リッチメニュー `getCreatorLineRichMenus` / LINE公式アカウント `getCreatorLineChannels`。

ルーティング上の注意（パラメータ・エラーの詳細は [references/mcp-tools.md](references/mcp-tools.md) が正本）:

- **ID は検索でしか手に入らない。** 詳細取得・削除は ID 指定のみ。名前やメールアドレスしか分かっていないときは、必ず先に検索する
- **一覧と詳細の違いは特典だけ。** 一覧は最初に取得した特典1件、詳細は取得済みの特典すべてを返す。特典の全件が要らなければ詳細取得は呼ばない
- **メール・LINE・`contactId` は3つとも独立した ID 体系で、同じ数値が別の相手を指しうる。** 取り違えても 404 になるとは限らず、**別人の情報を返す・別人を削除する**（無言の失敗）。詳細取得・削除に渡す `id` は、**同じ系統の検索結果から取ったものだけ**を使う（`contactId` は両者をつなぐ「メイン連絡先ID」で、各ツールが取る `id` ではない）
- **メール検索は氏名で引けない。** `postCreatorContactsEmailSearch` に「名前」を絞り込む項目はそもそも無い（`filters` は `contact.active/subscribed` と `email.createdAt/address` のみ）。`keyword` もメールアドレスにしか当たらない。「山田さんを検索して」と言われても、氏名では検索できない（メールアドレス・タグ・登録日でしか絞り込めない）。名前しか分かっていない依頼は、メールアドレスの提供を求めるか、LINE側の話でないか確認する。存在しない「名前」条件をでっち上げて検索したことにしない
- **「〜じゃない人」「〜が付いていない人」は `ne` で1回の検索で表現できる。全体件数から引き算しない。** `tag` / `inflowAction`（流入経路） / `richMenu` はいずれも `{ id: { value: <id>, operator: "eq" | "ne" } }` の形で、`ne` は「別の値を持つ人」ではなく**その条件の記録・設定が一切無い人も含む**という意味（例: `richMenu` の `ne` は他のメニューが表示中の人だけでなく、リッチメニューが何も紐付いていない人も含む）。`ne` が使えることを知らずに「全体件数−該当件数」で代用しない。**`inflowAction` と `richMenu` は `filters` 直下の独立したキー**（`line` オブジェクトの中に `currentRichMenuId` のような項目は無い）。構造の正本は [references/search-schema.md](references/search-schema.md)

## Workflow

基本フロー: 対象・条件の確認 → 検索 → 結果の提示 → **（書き込み操作なら）ユーザーの承認** → 実行 → 結果の報告。読み取りだけなら承認は不要。

### 承認の判定表（唯一の分岐条件）

**この表だけが「実行前に止まるか」を決める。** 他の節でこの条件を再定義しない。

| 操作 | 判定 | 根拠 |
|---|---|---|
| 削除（`patchCreatorContactsEmail` / `patchCreatorContactsLine`、`active: false`） | **必ず停止し、対象を提示して承認を得る** | 復元できない（API では解除不可・管理画面にも導線なし）。ツール定義も「検索で対象を取得してユーザーに提示し、同意を得てから実行」を要求している |
| 非表示の解除（`active: true`） | **実行しない** | MCP の認証（APIトークン）では拒否され、管理画面にも復元の導線が無い。試行しても復元はできない |
| CSV インポート（`postCreatorContactsEmailCsvImportJobs` 以降の一連） | **ジョブを作る前に1回停止し、ファイルと取り込み内容を提示して承認を得る。承認後はジョブ作成 → アップロードを止めずに通す** | 取り込みは自動で始まり、取り消す手段が MCP にない。一方でアップロード先URLは15分で失効するため途中で止められない |
| 検索・詳細取得（`post...Search` / `getCreatorContact*`） | 停止しない | 読み取り |

**依頼文がどれだけ具体的でも（「◯◯さんを今すぐ削除して」等）、上表で「承認」となっている操作は承認なしに実行しない。**

### 1. 依頼内容の確認

次を把握する。曖昧なまま検索・削除に進まない。

- **メールか LINE か**（「コンタクト」「友だち」「リスト」はどちらにも取れる）。どちらか判断できない依頼では両方を検索して件数を並べて示すのは可。ただし**削除は対象を確定してからでないと実行しない**
- **顧客（購入者）の話ではないか**（「お客さん一覧」「購入者を探して」は別ドメイン。When NOT to use 参照）
- 削除依頼なら、**対象が ID または検索条件で一意に特定できるか**。「もう使ってない人を消して」のような依頼は対象を確定するまで削除に進まない
- LINE で複数の LINE公式アカウントを運用している場合、どのアカウントの話か（未指定なら全アカウント横断で検索される）

### 2. 検索して対象を特定する

[references/search-schema.md](references/search-schema.md) を読み、リクエストを組み立てる（`filters` は使わないキーも含めて**全キー必須**で、未使用は `null`。この構造を毎回そこで確認する）。

- 件数だけ知りたいときは `limit: 1` で呼び、`filteredCount` を読む（全件を取得しない）
- 「配信対象は何人か」を数えるときは、メールなら `subscribed: true`、LINE なら `blocked: false` を条件に入れる。入れないと届かない相手を含んだ数になる
- 既定では削除済み（非表示）は結果に含まれない
- 100件を超える対象は `offset` を進めて取得する。ページングを省いて「全部で N 件」と言わない

### 3. 結果をユーザーに提示する

「ユーザーへの提示規約」に従って、件数と代表例を自然文・表で示す。削除依頼の場合は、**削除対象そのもの**（何件・誰か・何が起きるか）を提示する。

### 4. 承認を取る（書き込み操作のみ）

判定表で「承認」となる操作は、ここで必ず止まる。削除で伝える内容:

- 何件を削除するか、対象が誰か（LINE は表示名、メールはメールアドレス）
- **復元できないこと**。LINE は表示名とプロフィール画像が消え、後から元に戻せないこと
- 削除後は検索結果に出なくなり、配信も届かなくなること（メールアドレス自体は保持される）

CSV インポートで伝える内容は [references/csv-import.md](references/csv-import.md) の「承認時に伝えること」に従う。

### 5. 実行して結果を報告する

- 削除は ID の明示指定のみ・1回あたり最大100件。101件以上は分割して実行し、**分割の各回に対する承認は Step 4 の1回にまとめてよい**（対象一式を提示済みのため）
- 削除は成功しても「何件消えたか」は返らない。件数は**こちらが渡した ID の件数**として報告する（API の返り値から件数を作らない）
- CSV インポートは完了を断定しない（次節）

### 6. 完了を断定してよい操作／してはいけない操作

| 操作 | 報告の仕方 |
|---|---|
| 削除 | 断定してよい（成功応答＝反映済み） |
| CSV インポート | **断定しない。** 「取り込みを開始しました。取り込み結果（件数・エラー行）は MOSH に登録されているメールアドレス宛の通知でご確認ください」と伝える。MCP には進捗・結果を確認するツールが無い |

## MCP からはできないこと

依頼を受けたら、できない旨と代替手段を伝える。**できるふりをして別のツールで代用しない。**

| 依頼 | 実際 | 案内 |
|---|---|---|
| 削除の取り消し・復元 | API 権限上できず、管理画面にも復元の導線がない | 削除前に必ず伝える（Step 4）。削除後の依頼には復元不可であることを伝える |
| 「ブロックした人を全部削除」など条件での一括削除 | 条件指定の一括更新ツールは MCP に公開されていない | 検索 → ID を提示 → 承認 → ID 指定で分割実行（Step 5） |
| LINE友だちの一括取り込み・LINE公式アカウントとの友だち同期 | MCP に公開されていない（CSV 取り込みはメールのみ） | MOSH 管理画面での操作を案内 |
| CSV インポートの進捗・結果・取り込み件数の確認 | MCP に公開されていない | クリエイター宛の通知メールで確認するよう案内 |
| コンタクトを1件ずつ手で追加 | 作成ツールが無い | メールは CSV インポート、LINE は友だち追加・管理画面 |
| コンタクトへのタグ付け・タグ外し | 本ドメインにツールが無い | 自動付与はワークフロー（`workflow-builder`）、手動は管理画面 |
| 購読解除された人を配信対象に戻す | CSV で再インポートしても購読解除は維持される | 本人による再購読が必要であることを伝える |

## ユーザーへの提示規約

- **個人情報を目的外に出さない。** メールアドレス・LINE表示名・プロフィール画像URLは、依頼された用途に必要な範囲だけ提示する。件数を聞かれただけなら件数を答え、一覧を貼らない。依頼と無関係なファイルへの転記・保存はしない
- **内部表現を見せない。** JSON、`filters` のキー名、HTTPステータスコード、`operationId` をそのまま出さない。ID は削除対象の確認など、ユーザーが指し示す必要があるときだけ「コンタクトID: 123」の形で添える
- **ID を創作しない・使い回さない。** コンタクトID・タグID・流入経路ID・リッチメニューID・LINE公式アカウントIDは、必ず対応する取得ツールの返り値から取る。ユーザーや会話の前半で出てきた ID を削除に使う前には、**同じ系統の検索・詳細取得で、その ID が誰を指すかを確認する**（ID 体系が独立しているため、取り違えても 404 にならず別人に当たることがある）
- **数を推測しない。** 件数は `filteredCount` を根拠に答え、取得できていない範囲を「たぶん◯件」と補わない。条件に合う人が0件のときはエラーではなく「該当なし」として伝える
- **どの条件で数えたかを添える。** 「配信対象（購読中）で 120名」のように、絞り込み条件を1行で明示する（同じ「友だち数」でもブロック済みを含むかで数が変わるため）

## よくあるミス

上のセクションでカバー済みの事項は再掲しない。ここは他セクション・references でカバーされない落とし穴のみ（追記前に既存セクションでカバーできないか確認し、できるならそちらを強化する）。

| NG | OK |
|---|---|
| `patch...` を「更新」と解釈し、名前やタグの変更に使おうとする | このツールで変えられるのは表示状態だけで、実質は削除。編集の依頼は管理画面を案内する |
| 検索結果の `totalCount` を「条件に合う件数」として報告する | 条件に合うのは `filteredCount`。`totalCount` は絞り込み前の有効件数（[references/search-schema.md](references/search-schema.md)） |
| タグを2つ指定して「どちらかを持つ人」を数える | タグ条件の複数指定は AND（すべて満たす人）。OR が必要なら1タグずつ数える |
| LINE の「友だち数」を、ブロック済みを含めたまま報告する | ブロック状態は結果に含まれる。配信文脈なら `blocked: false` で絞ってから数える |
| メールコンタクト一覧の `name` を本人が入力した氏名として扱う | `name` は同一コンタクトの LINE プロフィール名で、無ければ空文字。氏名として断定しない |

## エラーが返ったとき

コード別の意味は [references/mcp-tools.md](references/mcp-tools.md) が正本。ここでは状況別の対処だけを示す。

| 状況 | 対処 |
|---|---|
| 詳細取得・削除で「見つからない」 | ID の取り違え（メール↔LINE、`id` と `contactId`）か、既に削除済み。検索で対象を引き直してから再実行する。ユーザーには「該当のコンタクトが見つかりませんでした」と伝える |
| 詳細取得の結果が、ユーザーの言う相手と一致しない | ID 体系の取り違えで別人を引いている可能性が高い（エラーにならない）。**削除には進まず**、名前・メールアドレス・登録日で検索し直して対象を確定する |
| 削除で「すでに非表示」と返る | 対象は既に削除済み。再実行せず、その旨を伝える |
| 削除が権限エラーで拒否される | `active: true`（解除）を渡していないか確認する。解除は MCP からはできない |
| 検索がリクエスト不正で返る | `filters` のキー欠落（全キー必須）か `limit` が範囲外（1〜100）の可能性が高い。[references/search-schema.md](references/search-schema.md) で構造を確認して組み直す |
| CSV アップロードが失効した | アップロード先URLの有効期限は15分。ジョブ作成からやり直す（[references/csv-import.md](references/csv-import.md)） |
