# LP設計ベストプラクティス

構造ルール（必須フィールド・許可プロパティ・クラッシュ防止）は `content-schema.md` が正。本書は「売れる・読みやすい LP」にするための設計指針と、送信前のセルフレビュー観点をまとめる。

## 構成計画（構築を始める前に必ず）

プラン・サービスの情報を分析し、LP 全体の構成を先に計画してから content を組み立てる。計画は `section-plan.md` の構成案表としてユーザーに提示し、**承認を得てから** JSON を組む:

- `hearing-sheet.md` で確定した顧客像（1人分）が「このサービスを今すぐ購入すべき理由」を納得するストーリーを組み立てる
- 各セクションで伝えるメッセージを、見出しだけでなく本文テキストの内容まで具体的に決める
- セクション数は **ヒアリングシート #4 でユーザーが選んだゴール種別で決める**。下表の目安を基準にし、**ユーザーがセクション構成や規模を明示的に指定した場合はその指定を優先し、勝手に増減しない**

> 配色・骨格・部品の具体はプリセット（`presets.md`）とプリセット JSON（`examples/catalog/`）が正本。本書はプリセットに無いものを組むときの原則と、セルフレビューの基準。

### ゴール別の構成目安

**1つの LP で求める行動は1つだけ。** 「無料相談を予約」と「この内容で申し込む（高額）」を同じページに置くと、読者はどちらを求められているか分からず離脱する。高額商品で主CTAが「無料相談」なら、LP 全体を無料相談の獲得に絞って作る: 料金カード＋申込ボタンの章は置かず、その位置に「無料相談でお話しすること」（内容3〜4項目・所要時間・勧誘なしの明記・料金は1行だけ）を置き、ボタンは無料相談に統一する。料金を見せること自体は可だが、申込の導線は作らない。高額バックエンドへのアップセルは LP の外（相談・LINE・会員サイト）で行う。CTA が3箇所あっても、文言と遷移先は全部同じにする。

MOSH のクリエイターが作る LP の主戦場は **(A) LINE 友だち登録などのリード獲得**と **(D) 高額・講座の相談誘導**。D2C・サブスクの即決販売 LP は少ない。ポップで短いトーン（橙×緑 等）は (A) と相性がよく、(D) には高級・信頼系のトーンを選ぶ。

| LP のゴール | 判定材料 | 目安 | 必ず入れる要素 | 省いてよい要素 |
|---|---|---|---|---|
| リード獲得（LINE登録・無料DL・無料セミナー） | CV先が LINE / 無料DL（**無料相談は含めない**。高額商品の相談誘導は D） | **4〜6** | ヒーロー（何がもらえるか＋CTA）/ 得られるもの / 信頼（講師 or 実績のどちらか）/ 登録手順＋CTA / フッター | 料金・FAQ・受講の流れ・フッターCTA |
| 告知・イベント（日程が主役） | 開催日・会場・定員がある | **5〜7** | ヒーロー / 概要 / 日程（`schedule`）/ 登壇者 / 申込CTA / フッター | 悩み共感・実績バー |
| 低〜中価格の販売（即決型・数万円まで） | 有料プラン・単発 | **7〜9** | ヒーロー / 悩み / 解決策 / メリット / 声 or 実績 / 料金＋CTA / FAQ / フッター | 受講の流れ・講師紹介（どちらか1つに） |
| 高額・講座販売（検討型・主CTAは無料相談） | 数万円超・継続・面談前提 | **8〜10** | ヒーロー / 画像＋テキスト / 特徴 / 実績 / 声 / 無料相談の内容 / FAQ / CTA帯（骨格は `presets.md` が正）＋素材があれば 悩み / 受講の流れ / 講師 を追加（上限10） | —（8章が最小） |

シートの仮埋め段階で LLM が推奨を選ぶときは**売り物の価格で決める**: LINE登録・無料DLのみ→A、日程が主役→B、〜数万円→C、数万円超→D（CV が無料相談でも D）。割れたら短い側を推奨にする。長いほど良いわけではなく、**リード獲得 LP に料金や FAQ を足すと登録率が落ちる**（読ませる量が CV の重さに釣り合っていない）

### テンプレートから調整する場合

テンプレートの content には既に `button` の `attributes.href` 等、動作に必要な値が入っている。見出し・本文のコピーを依頼内容に合わせて書き換える際、**指示されていない attributes（`href` 等）は変更・削除せず、テンプレートの値をそのまま引き継ぐ**（新しいリンク先が明示された場合のみ差し替える）。コピーを丸ごと新しい要素として組み直すと既存の `href` を落としやすいので注意する。

### 禁止パターン（セクションの中身）

- `heading` だけのセクション（必ず説明テキストを添える）
- `text` だけのセクション（見出しか画像を添える）
- セクション内に要素が1つだけ（最低2つ以上の要素を配置）
- 子要素ゼロの空セクション

## テキストの具体性原則

- テキストは具体的に書く: 「充実のサポート」ではなく「24時間以内に返信するチャットサポート」
- 「充実した」「丁寧な」「安心の」など、具体性のない抽象表現は使わない。何がどう充実しているのかを数字・固有名詞・手段で書く
- 見出しはベネフィット（受講後にどうなるか）を語り、本文がその根拠を語る構成にする
- **ユーザーの原稿がある場合は原文を優先し、この原則で勝手に書き換えない**。具体化の提案は構成案の「未確認・仮定」列に書いて承認を得てから反映する（`hearing-sheet.md` の「原稿が渡された場合」）

### 日本語テキストの規律

- テキストは全て正確な日本語で書く。文字化けは絶対 NG
- **簡体字は禁止**（例: 「踏袭」「业务」「电话」は不可 → 「踏襲」「業務」「電話」）。繁体字の伝統字形（「國」「體」「學」等）も禁止。現代日本語の標準字体（新字体）とひらがな・カタカナのみを使う
- 少しでも自信がない漢字はひらがなにする
- 「✓」「✔」等の記号・チェックマークは使わない（環境により文字化けする）

## 余白の原則

余白ゼロは絶対 NG。詰まって見える LP は安っぽくなる。

- セクション間: `padding` 上下 **80px 以上**（モバイルは 48px 以上）
- カード内部: `padding` **32px 以上**
- 見出しと本文の間: **16〜24px**（`text` / `heading` の `padding` で確保する。`margin` は使わない）
- ボタンの上下: **24px 以上**の余白
- テキストの左右: 端に張り付かないよう左右 `padding` を入れる（デスクトップ 48〜60px、モバイル 16〜20px）

高さの演出は `height` ではなくセクションの `padding` 上下値で行う（`height` 指定は編集画面が崩れるため禁止 — `content-schema.md` 参照）。ヒーローで迫力を出したい場合は `padding: "120px 24px"` のように上下を大きく取る。

## 表現テクニック

いずれも `content-schema.md` の許可スタイルプロパティの範囲内で実現する。

### 骨格を変える（色より先に骨格が見られる）

骨格・部品の具体は `presets.md` と `examples/catalog/` が正。プリセットに無い新しいトーンを起こすときだけ、次の3つをトーンごとに変える（同じ章の並び・同じヒーローの幾何で色だけ変えると「同じLPの色違い」に見える）:
- **章の順番**: 例) 高級・信頼系＝ヒーロー→写真→特徴→実績→声→無料相談の内容 / テック系＝ヒーロー→**実績を先出し**→ステップ→写真→声→無料相談の内容 / リード獲得（LINE）系＝ヒーロー（特典＋登録ボタン）→特典3つ→声→FAQ 2問→CTA帯（料金・数字の章は置かない）
- **ヒーローの幾何**: 左テキスト右写真 / 中央積み＋全幅画像 / 白地に大きな文字 / ダーク中央、のどれか。同じ幾何を全トーンで使わない
- **部品の形**: 特徴は「3列カード / 番号リスト / ステップ（番号の丸）」、声は「3カード / 引用1本 / 引用2本」、料金は「中央カード / 2カラム」から、トーンに合うものを選ぶ

### 面のリズム（交互ではなく「物語の切り替わり」で変える）

背景色を機械的に交互（ゼブラ）にすると壁紙のように単調になる。面の色を変えるのは**読者の気持ちが切り替わる場所だけ**（説明→証拠、証拠→申込 など）。それ以外は白のまま余白で区切る。

- ダーク帯・アクセント面は、ヒーローとフッターを除いて 1 本の LP で **1〜2 回が上限**（例: 実績バーと最終CTA）。多用すると全部が主役になり、何も主役でなくなる
- 変化は色だけでなく**密度**でも作る: 写真を全幅で置く、大きな引用を1本だけ置く、余白を倍にする
- 帯パターンはプリセット（トーン）ごとに決める。高級・信頼系はダークヒーロー＋ダーク実績、ナチュラル系は明るい面だけでフッターのみダーク、モダン系は白地に黒帯1本、など
- 背景色は `attributes.background: { "type": "color", "color": "#..." }` と `styles.background` の両方に設定する

### カード表現

外枠 `section` の `children` に内枠 `section` を置き、内枠に薄い背景色 + `borderRadius`（8〜16px）+ `padding` 32px 以上を設定してカードに見せる。特徴カードやお客様の声で使う。背景色は外枠との階調差で選ぶ（外枠が白ならカードは `#f4f6fa` 系、外枠が薄色ならカードは白）。**面で作ったカードに枠線を足さない**（「囲いの原則」）。

背景色を付けずに線だけで区切る場合は**辺別 border プロパティ**（`borderTopStyle` / `borderTopWidth` / `borderTopColor` を四辺ぶん。詳細は `content-schema.md` の許可プロパティの項）で薄い線（例: `rgba(0,0,0,0.08)` の 1px）を指定する。`border` ショートハンドは編集画面のパネルに反映されないため使わない。影（`boxShadow`）は引き続き禁止 — 強調は枠線と背景色のコントラストで表現する。

### 囲いの原則（グルーピングは余白と整列が先）

一流のデザイナーは要素を囲わない。**グルーピングはまず余白（近接）と整列で作る**。囲い（背景面・枠線・パネル）は次の場合だけ使う:

- 素の要素（テキストだけ・数字だけ）が**画像や賑やかな背景の上**に乗って読みにくいとき → 半透明パネル（`hsla(0,0%,100%,0.06〜0.08)` 等。`content-schema.md` の `background.color`）
- 異質な要素（見出し＋本文＋ボタン＋注記）を**1つの申込ブロックとして束ねる**とき → 白カード1枚
- 同型の繰り返し（メリット・声）を**個々に区切る**とき → カード。ただし**カード群をさらにパネルで囲まない**（二重の囲い）

守ること:
- **1つの階層に容器は1種類**。面（背景色）か線（枠線）かのどちらか。白カードに1px枠線を重ねない。面の階調差（白 / `#f4f6fa` / ダーク）だけで容器を作る
- 線を使うのは**アクセント**に限る: 料金カードの上枠4px、FAQ の左線3px、区切りの下線1px。装飾ではなく「ここが要点」の合図として1箇所に1本
- 数字バー・ステップのような**整列だけで読める並び**は囲わない。中央揃え・等幅・十分な gap で足りる
- 迷ったら**囲いを外して**確認する。外して読めるなら囲いは不要

### ファーストビューは4点セット（殺風景にしない）

ヒーローは「続きを読みたくなる」ための場所。白地に文字だけでは足りない。次の4点を1画面に置く: ①視線の錨（写真・キービジュアル）②具体的な約束（見出し）③その裏付け（実績のミニ表示 2〜3 点。数字は 24px 太字＋単位 14px のサイズ差、ラベルは 12px 薄色、細い上罫線で区切る。プレーンな 14px 一行だけだとミスに見える）④行動（primary CTA＋不安を消す注記）。画像が無い場合は面の色・大きな数字・余白で密度を作り、白地に文章だけのヒーローにしない。

### 3層見出しパターン（アイブロウは案内が要る章だけ）

セクション導入を「小さいラベル → 大きい見出し → 説明文」の3層で組むと視覚的な階層が明確になる。ただし**小さいラベル（アイブロウ）は毎回付けない**。役割は「ここは何の章か」を先読みさせることなので、見出し自体で分かる章（料金・よくある質問）には不要。1本の LP で 1〜2 箇所（ヒーローと最重要の章）に限る。毎回付けると装飾になり意味が消える:

1. `text`（`fontSize: "12px"` または `"14px"`、アクセント色、英語ラベル等）
2. `heading`（`fontSize: "30px"` または `"36px"`）
3. `text`（本文サイズ、グレー系）

### 数字・実績バー

大きな数字（`48px`）+ 小さいラベルのペアを `display: "flex"` で横並びに配置する。**訴える力は「太さ・単位の落差・根拠」で決まる**:
- 数字は**太字**にする。プレーン文字列の `text` は太字にできないので、tiptap のインライン装飾（`content-schema.md`「インライン装飾」。使えるのは色・太字・サイズ。下地マーカーは不可）で `bold` マークを付け、**数字 48px・単位 20px** のようにサイズ差をつける（「120名」を全部同じサイズで書くと弱い）
- 列の間は 1px の縦罫線（ダーク帯は `rgba(255,255,255,0.22)`、明るい面は文字色の10%）で区切り、SP では罫線を消して縦積み
- 上に短い見出し（「数字で見る、12週間の成果」）、下に**集計期間と母数**を12pxで添える。根拠の無い数字は載せない
- ダーク帯では数字を白か金属色にする（赤・橙は禁止。「テキスト色と背景色のコントラスト」参照）

### グラデーション背景

セクションの背景は単色・画像のほか、構造化形のグラデーション（`attributes.background` の `type: "gradationColor"`）を設定できる。フラットな単色よりモダンで洗練された印象になり、ヒーローや CTA セクションで効果的。指定方法と値の制約（`angle`・`colorStops`・hsl 形式）は `content-schema.md` の「背景グラデーション」を参照。`styles.background` に `linear-gradient(...)` 文字列を書く方法は禁止（描画はされるがユーザーが後から編集できなくなる）。

### 横並びレイアウト（推奨は3列まで）

親 `section` に `styles: { "display": "flex", "gap": "16px" }`、子 `section` に `width`（例 `"31%"`）を指定して横並びにする。列数に構造上の上限はないが、**推奨は3列まで**。4列以上はテキストが狭くなり読めなくなる（6項目なら 3列×2段か縦積みにする）。ユーザーが4列以上を明示指定した場合はそれに従う。モバイルでは必ず `mobileStyles: { "display": "block" }` で縦積みに切り替える（詳細は `content-schema.md` の「PC/SPでレイアウト方向を変える方法」）。

### フォントの使い分け

見出しと本文でフォントを変えるとメリハリが出る（例: 見出し `'Noto Serif JP'` × 本文 `'Noto Sans JP'`）。使えるのは `content-schema.md` 記載の4種のみ。LP 内での組み合わせは1パターンに統一する。

### テキスト色と背景色のコントラスト

ダーク背景セクションには白系テキスト（見出し `#ffffff`、補助 `#e3e8f2`。`#cccccc` 以下は 14px 以下で読みにくい）、ライト背景にはダーク系テキスト（`#1a1a2e` / `#212529` / `#666666`）を使う。テキスト色と背景色が同系・近似になっていないか必ず確認する。

**ダーク帯の大きな数字・見出しに彩度の高い赤・橙を使わない。** 黒地×赤文字は警告・危険の連想で、信頼を担う実績バーに最も向かない。数字は白か金属色（金・シルバー）、アクセント色は小さな罫線やラベルに限る。

**黄・ライム・シアンなど高明度の色を広い面に敷かない。** 明度が高い色相は彩度100%のまま面にすると目が休まる場所が無くなり眩しく感じる（白との明度差も小さく輪郭が浮く）。使い方は①CTAボタン②細い罫線・番号ラベル、の小面積に限る（文字の下地マーカー `backgroundColor` は編集画面に操作が無いので使わない。見出しの部分強調はブランド色の文字色で行う）。面に使うなら明度85〜92%まで薄める。 高明度色を**文字・記号（引用符「“」等）に使うのも不可**。薄い面の上では読めない。記号や見出しの部分色はブランド色（青・紺・茶など中明度）で。

**ただしアクセント色を締め出しすぎない。** パレットの識別色（黄・朱・金など）は LP の中で**主CTA（D=3 / A=2 箇所）＋2種類の小面積**（番号の丸・細い罫線・薄めた面 など）に必ず現れるようにする。CTA 1箇所だけだと「青のLPにボタンが1つ」になりパレットの正体が消える。高明度色の場合は「主CTA（濃い文字を載せる）＋**鮮やかなまま面に使う章を1つだけ**（数字・実績の帯が最適。文字は深色）＋番号の四角・左罫線」が定石。明度90%以上に薄めた面は識別色として機能しない（薄黄は「クリーム色のLP」に見え、フレッシュさが消える）。淡色の面が欲しければ無彩色寄りのクールグレー（#f2f6fa 等）にして、識別色は鮮やかなまま小〜中面積で出す。

**印象語→造形の対応（パレット定義に「印象・想定業種」を1行必ず持つ）。** 色だけでは印象は出ない。フレッシュ＝鮮やかな識別色の帯1本＋白地＋余白多め。テック＝直線的（角丸0〜4px）＋深色の帯1〜2本＋英字の小ラベル（1〜2箇所）＋4pxの左罫線など幾何的な部品。高級＝角丸8〜12px・セリフ・金の細線・ダーク帯。温かい＝角丸4〜8px・茶系・明るい面だけ・写真面積大。ポップ＝角丸16px以上・丸ゴシック・複数色の面。

## モバイルファースト（必須）

MOSH のユーザーの多くはスマートフォンからアクセスする。全セクションでモバイル対応を必ず行う。

- **全セクションに `mobileStyles` を必ず指定する**（省略禁止。省略すると PC 用の大きな余白・横並びがそのまま SP に出る）
- padding: デスクトップ `"80px 60px"` → モバイル `"48px 20px"` 程度
- 見出し: デスクトップ `30px` / `36px` / `48px` のいずれか → モバイル `20px` / `24px` / `30px` のいずれか（`styles.fontSize` と `mobileStyles.fontSize` の両方を、`content-schema.md`「fontSize（固定スケール・px）」の10値からのみ選ぶ。中間値・レンジ内挿は禁止）
- 本文: デスクトップ `16px` / `18px` のいずれか → モバイル `14px` / `16px` のいずれか。**12px 未満は禁止**（`10px` は注釈など補助テキストに限る）
- ボタン: モバイルでは `mobileStyles: { "width": "100%" }` で全幅にし、行の高さ（`lineHeight`）でタップ領域を44px以上にする。`fontSize` はデスクトップより1段下げる（`content-schema.md` 参照）
- 横並び（`display: "flex"`）は `mobileStyles: { "display": "block" }` で縦積みに
- 画像はモバイルで幅 100% 基本。固定幅の要素がモバイル画面幅（375px）を超えないこと（横スクロールの発生は禁止）

## CTA の設計

### 大きさはトーンで決める（大きいほど良い、ではない）

主CTA（primary）と補助CTA（secondary）の2段を用意し、**プリセットのトーン**でスケールを選ぶ。幅・高さ（padding）を変えたら fontSize も連動させる（文字だけ小さいボタンは間延びする）。

大きさは編集画面の項目で作る: **高さ＝行の高さ（`lineHeight`）、幅＝ボタンの幅（`width`）、外側の余白＝余白（`layout.styles.padding`）**。`styles.padding`（内側）は UI 既定のまま触らない（`content-schema.md`「ボタンの大きさの決め方」）。

| トーン | 例 | primary: fontSize / lineHeight / width（PC） | secondary |
|---|---|---|---|
| 控えめ（高級・信頼・専門職）`restrained` | 紺×金、茶×金、黒×朱 | 16px / 1.6 / 320px（約54px高） | 14px / 1.6 / 240px |
| 標準 `medium` | 黄×青 | 18px / 1.8 / 360px（約60px高） | 16px / 1.6 / 260px |
| 大きく（カジュアル・リード獲得）`bold` | 橙×緑 | 20px / 2 / 400px（約68px高） | 16px / 1.8 / 280px |

- SP は `mobileStyles.width: "100%"`、fontSize は PC より1段下げる（primary 20px→18px、18px→16px）
- 1つの LP で primary は1色1形に固定する（ヒーロー・料金・最終CTAで同じ見た目）。**塗りボタンは唯一の行動（CV）だけ**
- secondary（「詳細を見る」等の補助動線）は**テキストリンク型**にする: `background` 透明 `hsla(0, 0%, 100%, 0)`・文字はブランド色・`width: "auto"`・文言末尾に「→」。主と同じ塗りにすると主CTAと競合して離脱動線になる。ボタンに枠線プロパティは無いのでアウトライン型は作れない
- 角丸は 8 / 10 / 12px を高さに合わせる。pill（完全丸）はカジュアルトーンのみ


- CTA ボタンは販売型（即決・高額）では**最低3箇所**（ヒーロー直後・中盤・最終セクション）、リード獲得・告知（4〜7セクション）では**2箇所**（ヒーロー直後・最終セクション）
- MOSH のプラン・サービスへ誘導する場合、`href` は `https://mosh.jp/services/{id}?openExternalBrowser=1` の形式にする。**末尾の `?openExternalBrowser=1` は必須**（LINE 等のアプリ内ブラウザでの決済不安定を回避するため）。`{id}` はユーザーから確認した実在のプラン・サービス ID のみ使う
- `href` が確定しないボタンにダミー URL（`#` や `https://example.com/...`）を捏造しない（`content-schema.md` の既存ルールどおり。ユーザーに確認するか、その旨を伝えて保留する）。唯一の例外はプリセット JSON（`examples/catalog/`）の差し替えトークン `https://mosh.jp/services/REPLACE_WITH_SERVICE_ID?openExternalBrowser=1` / `https://lin.ee/REPLACE_WITH_LINE_ID`。形式を示すためのもので、保存前に必ず実 ID へ置換する（チェックリスト #11）

## 画像の運用

- `image` の `src` に入れてよいのは **①ユーザー提供の実URL ②下書き専用のプレースホルダ素材**（`https://mosh.jp/images/522545e4fca64345a420e594e1b2f6c1`、グレー地に IMAGE 表記、16:10、alt「仮画像（差し替え前提）」）の2つだけ（ルールの正本は SKILL.md 必須ルール）。`src: ""`・ダミー URL（`https://example.com/...` `#`）・テンプレのサムネや無関係な写真は禁止
- 実画像はヒアリングシート #7 で MOSH 内から収穫（商品画像・既存 LP・素材ライブラリ）し、足りない分だけ依頼する。公開前にプレースホルダを実画像へ差し替えるか要素を削除する（Step 7）
- 実 URL を配置する場合のサイズ目安: アイコンは `width` 60〜100px、装飾画像は 150〜300px、写真・メイン画像は幅 100%（モバイル）
