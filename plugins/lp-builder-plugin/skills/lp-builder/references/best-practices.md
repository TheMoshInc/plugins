# LP設計ベストプラクティス

構造ルール（必須フィールド・許可プロパティ・クラッシュ防止）は `content-schema.md` が正。本書は「売れる・読みやすい LP」にするための設計指針と、送信前のセルフレビュー観点をまとめる。

## 前提: 訪問者は読まない、信用しない

MOSH の LP を訪れる人は文章を上から下まで読まない。見出し・写真・数字だけを拾って読み飛ばし（スキャン）、少しでも作りが雑・怪しいと感じた瞬間に離脱する。**本書の個別ルールの多くはこの2つの前提から導かれている。** 設計判断に迷ったら「読まれない」「信用されない」のどちらを崩す変更かをまず疑う。個別チェック（セルフレビューチェックリスト #1〜25）を全部満たしていても、最後にこの前提に立って「初見の訪問者が本当に読むか・信じるか」をもう一段疑う。

- **読まない**への対策: ヒーローは3秒診断5問に即答できる形にする（「ファーストビューは4点セット」）、本文は1行35〜45字で折り返す（「1行の文字数は35〜45字に収める」）、見出しは孤立行・語中割れを作らない（「改行はスマホ基準で決める」）、見出しはベネフィット先行で書き根拠は本文に回す（「テキストの具体性原則」）
- **信用しない**への対策: 実績数字は集計期間・母数がセットでなければ載せない（「数字・実績バー」）、反論処理（なぜこの価格／なぜ無料／なぜ今／なぜ自分にもできるのか）を必ず1箇所に置く（「構成計画」）、無料オファーは作り手（顔・肩書）と現物を早期に見せる（「特典・オファーの見せ方」）、最大級表現・効果の言い切りは根拠なく使わない（ヒアリングシート #10）

## 構成計画（構築を始める前に必ず）

プラン・サービスの情報を分析し、LP 全体の構成を先に計画してから content を組み立てる。計画は `section-plan.md` の構成案表としてユーザーに提示し、**承認を得てから** JSON を組む:

- `hearing-sheet.md` で確定した顧客像（1人分）が「このサービスを今すぐ購入すべき理由」を納得するストーリーを組み立てる
- 各セクションで伝えるメッセージを、見出しだけでなく本文テキストの内容まで具体的に決める
- セクション数は **ヒアリングシート #4 でユーザーが選んだゴール種別で決める**。下表の目安を基準にし、**ユーザーがセクション構成や規模を明示的に指定した場合はその指定を優先し、勝手に増減しない**

> 配色・骨格・部品の具体はプリセット（`presets.md`）とプリセット JSON（`examples/catalog/`）が正本。本書はプリセットに無いものを組むときの原則と、セルフレビューの基準。

### ゴール別の構成目安

**1つの LP で求める行動は1つだけ。** 「無料相談を予約」と「この内容で申し込む（高額）」を同じページに置くと、読者はどちらを求められているか分からず離脱する。高額商品で主CTAが「無料相談」なら、LP 全体を無料相談の獲得に絞って作る: 料金カード＋申込ボタンの章は置かず、その位置に「無料相談でお話しすること」（内容3〜4項目・所要時間・勧誘なしの明記・料金は1行だけ）を置き、ボタンは無料相談に統一する。料金を見せること自体は可だが、申込の導線は作らない。高額バックエンドへのアップセルは LP の外（相談・LINE・会員サイト）で行う。CTA が3箇所あっても、文言と遷移先は全部同じにする。

MOSH のクリエイターが作る LP の主戦場は **(A) LINE 友だち登録などのリード獲得**と **(D) 高額・講座の相談誘導**。D2C・サブスクの即決販売 LP は少ない。ポップで短いトーン（橙×緑 等）は (A) と相性がよく、(D) には高級・信頼系のトーンを選ぶ。

| LP のゴール | 判定材料 | 目安 | 必ず入れる要素 | 省いてよい要素 |
|---|---|---|---|---|
| リード獲得（LINE登録・無料DL・無料セミナー） | CV先が LINE / 無料DL（**無料相談は含めない**。高額商品の相談誘導は D） | **4〜6** | ヒーロー（何がもらえるか＋CTA）/ 得られるもの / 信頼（講師 or 実績のどちらか）/ 登録手順＋CTA / フッター | 料金・FAQ・受講の流れ・フッターCTA |
| 告知・イベント（日程が主役） | 開催日・会場・定員がある | **5〜7** | ヒーロー / 概要 / 日程（`schedule`）/ 登壇者 / 申込CTA / フッター | 悩み共感・実績バー |
| 低〜中価格の販売（即決型・数万円まで） | 有料プラン・単発 | **7〜9** | ヒーロー / 悩み / 解決策 / メリット / 声 or 実績 / 料金＋CTA / FAQ / フッター | 受講の流れ・講師紹介（どちらか1つに） |
| 高額・講座販売（検討型・主CTAは無料相談） | 数万円超・継続・面談前提 | **8〜10** | ヒーロー / 画像＋テキスト / 特徴 / 実績 / 声 / 無料相談の内容 / FAQ / CTA帯（骨格は `presets.md` が正）＋素材があれば 悩み / 受講の流れ / 講師 を追加（上限10） | —（8章が最小） |

**反論処理は全ゴール共通で必須。** 読者が最後に残す疑問（なぜこの価格なのか／なぜ無料なのか／なぜ今なのか／なぜ自分にもできるのか）に、LP の中で必ず1箇所答える。専用の章を立てても、FAQ の1問として置いてもよいが、**FAQ を省くゴール（A・B）では省略せず、CTA 直前に1〜2行で置く**。価格・無料の理由を説明しないまま申し込ませようとすると、中身の良さに関わらず「裏があるのでは」で止まる。

シートの仮埋め段階で LLM が推奨を選ぶときは**売り物の価格で決める**: LINE登録・無料DLのみ→A、日程が主役→B、〜数万円→C、数万円超→D（CV が無料相談でも D）。割れたら短い側を推奨にする。長いほど良いわけではなく、**リード獲得 LP に料金や FAQ を足すと登録率が落ちる**（読ませる量が CV の重さに釣り合っていない）

### 推奨セクション構成

「役割」は設計上の呼び名で、実際に `attributes.sectionType` に入れる値は「`sectionType`」列の値を使う（`"hero"` や `"cta"` は無効値。許容値の一覧は `content-schema.md` の「`sectionType` の許容値」を参照）。

| 順 | 推奨 ID | 役割 | 内容 | `sectionType` |
|---|---|---|---|---|
| 1 | `sec-01-hero` | ヒーロー | キャッチコピーとメインビジュアル、CTA | `main` |
| 2 | `sec-02-pain` | 悩み共感 | ターゲットの課題・悩みへの共感 | `description` |
| 3 | `sec-03-solution` | 解決策 | 提供する解決策の提示 | `description` |
| 4 | `sec-04-merit` | 特徴・メリット | プラン・サービスの特徴・受講後の変化 | `merit` |
| 5 | `sec-05-proof` | 実績・数字 | 実績を大きな数字で見せる（下記「数字・実績バー」）。実績が無ければ立てない | `merit` または `description` |
| 6 | `sec-06-flow` | 受講の流れ | 申込みから受講までのステップ | `description` |
| 7 | `sec-07-voice` | お客様の声 | 受講者の声（カード形式）。許諾済みの声のみ | `description` |

| 10 | `sec-10-faq` | FAQ | よくある質問（見出し + テキストの繰り返し） | `faq` |

ID は順番＋役割の意味的 ID（規約は `section-plan.md`）。承認済み構成案の ID は変えない（途中挿入は枝番）。

この表は素材が全部揃ったときの最大構成（12章）。実際の骨格はプリセット（`presets.md`）が正で、D は 8〜10 章に絞る。他のゴールは上の「ゴール別の構成目安」に従って必要な行だけ選び、ID の順番は選んだ順に振り直す。**フッター（コピーライト）は全ゴール共通で最終セクションに必ず置く**（目安のセクション数には含めない）。事業者名はヒアリングシート #7 の値、西暦は今日の日付から。

### テンプレートから調整する場合

テンプレートの content には既に `button` の `attributes.href` 等、動作に必要な値が入っている。見出し・本文のコピーを依頼内容に合わせて書き換える際、**指示されていない attributes（`href` 等）は変更・削除せず、テンプレートの値をそのまま引き継ぐ**（新しいリンク先が明示された場合のみ差し替える）。コピーを丸ごと新しい要素として組み直すと既存の `href` を落としやすいので注意する。

### 禁止パターン（セクションの中身）

- `heading` だけのセクション（必ず説明テキストを添える）
- `text` だけのセクション（見出しか画像を添える）
- セクション内に要素が1つだけ（最低2つ以上の要素を配置）
- 子要素ゼロの空セクション

## 参考LP・雰囲気を意匠に変換する（6軸観察）

ヒアリングシート #7 で「参考LP1本」「避けたい雰囲気」「このLPみたいにしたい」が渡されたとき、または既存LPを「テンプレっぽい」「安っぽい」と指摘されて原因を診断するとき、印象語（例: 高級・信頼・落ち着き、ポップ・親しみ）のまま扱わず、次の6軸で観察できる造形要素に分解する。単一の参考LPを表層だけ模倣すると、プリセットの骨格や自社ブランドと衝突する要素まで持ち込みやすい。

| 軸 | 観察する要素 |
|---|---|
| 色 | 色相・明度・彩度、ベース/メイン/アクセントの面積比、CTAとの競合有無 |
| タイポグラフィ | 書体（見出し/本文）、ジャンプ率（見出しと本文のサイズ差）、行間 |
| 余白・構図 | セクション間隔、密度、角丸の大きさ、帯の使用頻度 |
| 写真・図版 | 被写体・画角・面積比、装飾（背景画像・角丸画像）の有無 |
| UI | ボタン形状・角丸、カードの容器形式（面 or 線）、CTAの強さ |
| 言語表現 | 見出しの長さ・語調、英字ラベルの有無 |

観察した要素は、対象商品の価格帯・顧客・オファーに適合するものだけ採用する。コピーやブランドを損なう要素（例: 高額講座にポップな丸ゴシック）は採用しない理由を一言添えてユーザーに伝える。プリセット（`presets.md`）のブランド色・書体を差し替える程度の調整はこの軸に沿って行い、骨格（章順・面のリズム）まで作り変える場合は別プリセットへの切り替えを検討する。

## テキストの具体性原則

- テキストは具体的に書く: 「充実のサポート」ではなく「24時間以内に返信するチャットサポート」
- 「充実した」「丁寧な」「安心の」など、具体性のない抽象表現は使わない。何がどう充実しているのかを数字・固有名詞・手段で書く
- 見出しはベネフィット（受講後にどうなるか）を語り、本文がその根拠を語る構成にする
- **ユーザーの原稿がある場合は原文を優先し、この原則で勝手に書き換えない**。具体化の提案は構成案の「未確認・仮定」列に書いて承認を得てから反映する（`hearing-sheet.md` の「原稿が渡された場合」）

### 日本語テキストの規律

- テキストは全て正確な日本語で書く。文字化けは絶対 NG
- **簡体字は禁止**（例: 「踏袭」「业务」「电话」は不可 → 「踏襲」「業務」「電話」）。繁体字の伝統字形（「國」「體」「學」等）も禁止。現代日本語の標準字体（新字体）とひらがな・カタカナのみを使う
- 少しでも自信がない漢字はひらがなにする
- 「✓」「✔」等の記号・チェックマークは使わない（環境により文字化けする）

## 余白の原則

余白ゼロは絶対 NG。詰まって見える LP は安っぽくなる。

- セクション間: `padding` 上下 **80px 以上**（モバイルは 48px 以上）
- カード内部: `padding` **32px 以上**
- 見出しと本文の間: **16〜24px**（`text` / `heading` の `padding` で確保する。`margin` は使わない）
- ボタンの上下: **24px 以上**の余白
- テキストの左右: 端に張り付かないよう左右 `padding` を入れる（デスクトップ 48〜60px、モバイル 16〜20px）

高さの演出は `height` ではなくセクションの `padding` 上下値で行う（`height` 指定は編集画面が崩れるため禁止 — `content-schema.md` 参照）。ヒーローで迫力を出したい場合は `padding: "120px 24px"` のように上下を大きく取る。

## 表現テクニック

いずれも `content-schema.md` の許可スタイルプロパティの範囲内で実現する。

### 強調は3種まで（種類を絞り、量で振る）

**素人っぽい LP になる原因は要素が多いことではなく、強調手段が5〜7種類あってどれも弱いこと。** 1本の LP で使う強調手段を**最大3種**に決め、以降はその3種だけを繰り返す。4種目を使いたくなったら、既存3種のどれかに寄せる。

**数える対象＝「ここが重要」と示すための手段**（この中から3つ）:
- 識別色・ブランド色の文字（見出しの部分色を含む）
- アクセント面ベタ（識別色・ダークの帯）
- 罫線アクセント（上端4px・左3〜4px）
- 下線・マーカー風の下地
- 囲み枠（枠線で囲う）
- 吹き出し・リボン・バッジ型の飾り
- 特大サイズ（本文の3倍以上に跳ねる文字）

**数えないもの**（常用の組版・部品であって強調手段ではない）: 太字、カード（面の階調差による容器）、数字バーや実績ミニの級数差、ステップの番号丸・番号四角、アイブロウの小ラベル。

決めた3種はプリセットの部品定義（`presets.md`）と揃える。たとえば `navy_gold` は「ブランド色文字／ダーク帯／左罫線3px」の3種で、そこにマーカー風の下地や囲み枠を足さない。`orange_green` は「ブランド色文字／ブランド色ベタ帯／上端4px罫線」の3種。「囲いの原則」（容器は面か線の一方）と「面のリズム」（アクセント面は1〜2回）は、このルールの下位にある個別規定。

### 級数（見出しサイズ）は役割ごとに固定する

階層が消える原因は段数の多さではなく、**同じ役割の見出しに違うサイズが混ざること**。役割とサイズを1対1で固定し、LP 全体で使い回す。

| 役割 | PC | SP |
|---|---|---|
| ヒーローの主見出し（1本の LP に1つだけ） | `48px` | `30px` |
| 章の見出し | `36px` | `24px` |
| 小見出し（カード内・FAQ の Q など） | `24px` | `20px` |
| ミニ見出し（箇条書きの見出し・注記の題） | `20px` | `18px` |

- **使うのはこの4段まで。`10px`〜`48px` の固定スケール外の値（`22px` / `28px` / `32px` / `44px` 等）は使わない**（`content-schema.md`「fontSize（固定スケール・px）」に反する）
- 章の主見出しと本文の比は **2〜3倍**を保つ（36px ↔ 16px）。見出し 20px・本文 16px のように差が1.25倍しかない組み合わせを章見出しに使わない
- 同じ役割の見出しを、章によって 36px と 30px に振り分けない。強弱を付けたいときはサイズではなく面・余白で付ける
- アイブロウ（12px / 14px の小ラベル）と数字（48px）は見出しの段数に数えない。役割が別のため

### 改行はスマホ基準で決める（横幅の前提）

**MOSH の LP を見る人の大半はスマホ。改行位置を気にするなら SP で設計し、PC はその結果を受け入れる**（PC の方が広いので、SP で成立すれば PC では必ず収まる）。

**基準幅**: SP は **375px**（iPhone SE/標準幅。390px ではなく狭い方を取る）／PC は **1080px**（LPコンテナの最大幅。2026-09-12 実機確認）。`padding` を引いた内寸で数える。

**満たすべきは次の3つ。「1行に収めること」ではない。**

1. **孤立行を作らない** — 最終行が2字以下（「〜です／か？」「〜をやめ／る。」）。**判定は必ず SP 基準**。PC で収まっていても SP で割れることが多い
2. **語の途中で割らない** — ブラウザ任せだと「遠回／りをやめる」のように分断される
3. **級数の階層を壊さない** — ヒーロー > 章 > 小 の順序（「級数は役割ごとに固定する」）

**打ち手はこの優先順で試す**
- **狭いカラムに置く見出しは PC でも折り返す。** 38% などのカラムに 36px の見出しを置くと PC でも2行になる。SPで1行に収まっていても、**PCで2行になるなら `hardBreak` で意味の切れ目に固定する**（ブラウザ任せだと「無料相談でお話しす／ること」と語中で割れる）


| 順 | 手段 | 使いどころと限界 |
|---|---|---|
| 1 | **文言を削る** | 最も効く。見出しは短いほど強い。まずここを疑う |
| 2 | **`hardBreak` で折り返し位置を固定** | 2行にしてよい場合。句点・読点の意味の切れ目に入れる（tiptap の明示改行。`content-schema.md`「インライン装飾」）。**PC/SP 共通の位置で折れる**点に注意 |
| 3 | **SP の `fontSize` を1段下げる** | `mobileStyles.fontSize` で**PC/SP 別に指定できる**（インライン装飾なら `mobileFontSize`）。ただし**下の役割と同値になる下げ方はしない**（ヒーロー30→24 は章見出しと衝突）。実質は1段まで |
| 4 | **枠を広げる** | 2カラムの比率（PC でテキスト側を58%以上に）、`padding` を詰める |

**サイズ切り替えだけでは解けない**（実測）: ヒーロー17字を SP で1行に収めるには18pxまで下げる必要があり、本文14pxとほぼ同サイズになってヒーローが消える。FAQ の「Q. コーチング未経験でも大丈夫ですか？」も16pxまで下げないと入らず、Q と A の区別が消える。**どちらも文言短縮か `hardBreak` が正解**。逆に、枠が狭くて3行以上になる場合（分割ヒーローのパネル内など）は**サイズ下げが正解**。

### 骨格を変える（色より先に骨格が見られる）

骨格・部品の具体は `presets.md` と `examples/catalog/` が正。プリセットに無い新しいトーンを起こすときだけ、次の3つをトーンごとに変える（同じ章の並び・同じヒーローの幾何で色だけ変えると「同じLPの色違い」に見える）:
- **章の順番**: 例) 高級・信頼系＝ヒーロー→写真→特徴→実績→声→無料相談の内容 / テック系＝ヒーロー→**実績を先出し**→ステップ→写真→声→無料相談の内容 / リード獲得（LINE）系＝ヒーロー（特典＋登録ボタン）→特典3つ→声→FAQ 2問→CTA帯（料金・数字の章は置かない）
- **ヒーローの幾何**: 左テキスト右写真 / 中央積み＋全幅画像 / 白地に大きな文字 / ダーク中央、のどれか。同じ幾何を全トーンで使わない
- **部品の形**: 特徴は「3列カード / 番号リスト / ステップ（番号の丸）」、声は「3カード / 引用1本 / 引用2本」、料金は「中央カード / 2カラム」から、トーンに合うものを選ぶ

### 山場を1つ作る（これが無いと「整っているだけ」になる）

**ここまでの規約（級数・コントラスト・階調差・孤立行）は"事故を防ぐ"ためのもの。全部満たしても、全章が均等に整った"無音のLP"になる。** 優れたLPには必ず**ページ全体の主役＝山場**が1〜2箇所ある（赤ゴリ式＝縦書きの大見出し、eduGate＝実績36枚のタイル）。
- **濃い面を複数持つトーン（紺・黒・黄×紺など）では、面だけでは山場にならない。** ダーク帯が 数字バー・声・CTA と3つあると、どれも「濃いだけ」になって主役が消える。**1章だけ見出しを 48px にして級数で主役を立てる**


- **1本のLPに山場は1つ**（多くても2つ）。そこだけ**極端に振る**。振り方は次の3つのどれか1つ以上:
  - **級数**: その章の見出しだけ48px（他章が36pxなら1.3倍の差がつく）
  - **面**: その章だけ深色・ダーク・識別色のベタにする
  - **写真**: その章だけ全幅（フルブリード）にする
- 山場は**中盤〜後半**に置く（ヒーローは「入口」であって山場ではない。ヒーローだけが大きいLPは、スクロールするほど失速する）
- 山場に選ぶのは「**このLPで一番見せたいもの**」。実体（配布物の中身）・実績の数字・受講者の変化のいずれか

**山場が無いことの判定**: 章の背景色が2色の往復だけ／画像が全部同じ幅／章の `padding` が全部同じ、のどれかに当てはまったら山場が無い。

### 写真は強弱を付ける（3枚を同じ大きさで置かない）

同じサイズの写真を各章に1枚ずつ置くと、**全部が添え物**になる。

- 写真が3枚あるなら、**1枚は全幅か背景で大きく**、残りは小さく（2カラムの中）。同じ `width` を全画像に使わない
- 大きく見せる1枚は「実体」か「証拠」から選ぶ（「雰囲気」を主役にしない。「画像の置き方」参照）
- 寄り引きも変える: 主役は引き（状況が分かる）、脇は寄り（手元・表情）

### 余白は章の役割で変える（固定値で全章を通さない）

全章を同じ `padding` で通すと、リズムが均等＝無音になる。**3段階を使い分ける**。

| 役割 | PC の上下 padding | SP |
|---|---|---|
| 山場・ヒーロー・最終CTA | **120px** | 72px |
| 通常の章 | 88px | 56px |
| 補助の章（FAQ・注記・短い章） | **64px** | 48px |

- 山場の**前後**を広く取ると、そこだけ「間」が生まれて主役に見える
- 全幅写真の上下は `0`（面として繋げる）

### アクセント色は「見える量」を確保する

細い罫線とボタンだけに識別色を使うと、**ブランドカラーが記憶に残らない**。

- 識別色は**1本のLPで最低1回、面か大型文字（24px以上）として出す**。罫線・番号ラベルだけで終わらせない
- ただし塗り面は1章まで（「CTA色の再利用」）。**面にしないなら、数字バーの数字など大型文字で出す**

### 面のリズム（交互ではなく「物語の切り替わり」で変える）

背景色を機械的に交互（ゼブラ）にすると壁紙のように単調になる。面の色を変えるのは**読者の気持ちが切り替わる場所だけ**（説明→証拠、証拠→申込 など）。それ以外は白のまま余白で区切る。

- ダーク帯・アクセント面は、ヒーローとフッターを除いて 1 本の LP で **1〜2 回が上限**（例: 実績バーと最終CTA）。多用すると全部が主役になり、何も主役でなくなる
- 変化は色だけでなく**密度**でも作る: 写真を全幅で置く、大きな引用を1本だけ置く、余白を倍にする（見せ場の全幅は LP 全体で1〜2回。定義は「画像の置き方」）
- **密集ブロックの直後には余白＋CTA を置く**。実績バー・料金カード・長い箇条書き・比較表のような密度の高い章は、読者の熱が最も上がる場所であると同時に疲れる場所でもある。直後を白地＋大きめ `padding` にして、そこに CTA（主 or 補助）を置く。密集章を2つ連続させない
- 帯パターンはプリセット（トーン）ごとに決める。高級・信頼系はダークヒーロー＋ダーク実績、ナチュラル系は明るい面で進めて**最終CTAと フッターだけ濃い面**、モダン系は白地に黒帯1本、など。**明るい面だけで通すトーンでも、最終CTAを一番弱い面にしない**（申し込ませたい場所の視覚的優先度が最下位になる）
- 背景色は `attributes.background: { "type": "color", "color": "#..." }` と `styles.background` の両方に設定する

### カード表現

外枠 `section` の `children` に内枠 `section` を置き、内枠に薄い背景色 + `borderRadius`（8〜16px）+ `padding` 32px 以上を設定してカードに見せる。特徴カードやお客様の声で使う。背景色は外枠との階調差で選ぶ（外枠が白ならカードは淡い面、外枠が淡い面ならカードは白）。

**階調差は HSL の明度で6以上**（2026-09-12 実機確認）。淡い面は **L91〜95**（白との差5〜9）に置く。`#f4f6fa`（L96.9）のように白との差が3〜4しかない面は、PCでかろうじて見えてもSPではカードの輪郭が完全に消える。

**カードの軸は見出しの整列に合わせる。** 中央揃えのプリセットでカードを中央に置くには、`display: flex` の子がカード1つだけだと左寄せになるため **20% / 60% / 20%** の3列にする（`margin` は使えない）。**左揃えのプリセットでは逆にスペーサーを入れない**（見出しが左・カードが中央になると軸がずれて見える）。整列はプリセットごとに1種（「級数…」「整列」）。**面で作ったカードに枠線を足さない**（「囲いの原則」）。

背景色を付けずに線だけで区切る場合は**辺別 border プロパティ**（`borderTopStyle` / `borderTopWidth` / `borderTopColor` を四辺ぶん。詳細は `content-schema.md` の許可プロパティの項）で薄い線（例: `rgba(0,0,0,0.08)` の 1px）を指定する。`border` ショートハンドは編集画面のパネルに反映されないため使わない。影（`boxShadow`）は引き続き禁止 — 強調は枠線と背景色のコントラストで表現する。

### 囲いの原則（グルーピングは余白と整列が先）

一流のデザイナーは要素を囲わない。**グルーピングはまず余白（近接）と整列で作る**。囲い（背景面・枠線・パネル）は次の場合だけ使う:

- 素の要素（テキストだけ・数字だけ）が**ダーク帯や賑やかな面の上**に乗って区切りが要るとき → 薄い面（`hsla(0,0%,100%,0.06〜0.08)` 等。`content-schema.md` の `background.color`）。**写真の上の可読性を確保する用途には効かない**。そちらは「背景画像で装飾密度を作る」のスクリム（α 0.55〜0.95）を使う
- 異質な要素（見出し＋本文＋ボタン＋注記）を**1つの申込ブロックとして束ねる**とき → 白カード1枚
- 同型の繰り返し（メリット・声）を**個々に区切る**とき → カード。ただし**カード群をさらにパネルで囲まない**（二重の囲い）

守ること:
- **1つの階層に容器は1種類**。面（背景色）か線（枠線）かのどちらか。白カードに1px枠線を重ねない。面の階調差（白 / `#f4f6fa` / ダーク）だけで容器を作る。この「面」は単色に限らず**背景画像**でもよい（ヒーロー・CTA帯限定。「画像の運用」の「背景画像で装飾密度を作る」を参照）。囲いの原則は装飾そのものを禁じているのではなく、容器を面と線の二重にしないことが趣旨
- 線を使うのは**アクセント**に限る: 料金カードの上枠4px、FAQ の左線3px、区切りの下線1px。装飾ではなく「ここが要点」の合図として1箇所に1本
- 数字バー・ステップのような**整列だけで読める並び**は囲わない。中央揃え・等幅・十分な gap で足りる
- 迷ったら**囲いを外して**確認する。外して読めるなら囲いは不要

### ファーストビューは4点セット（殺風景にしない）

ヒーローは「続きを読みたくなる」ための場所。白地に文字だけでは足りない。次の4点を1画面に置く: ①視線の錨（写真・キービジュアル）②具体的な約束（見出し）③その裏付け（実績のミニ表示 2〜3 点。数字は 24px 太字＋単位 14px のサイズ差、ラベルは 12px 薄色、細い上罫線で区切る。プレーンな 14px 一行だけだとミスに見える）④行動（primary CTA＋不安を消す注記）。画像が無い場合は面の色・大きな数字・余白で密度を作り、白地に文章だけのヒーローにしない。

**4点セットは要素の有無のチェック。伝わっているかは別に確認する（3秒診断）**: ヒーローだけを見て次の5問に即答できるか自問する。①誰向けか ②何が得られるか ③他の選択肢と何が違うか ④なぜ信じられるか ⑤次に何をすべきか。要素（写真・見出し・実績・CTA）が揃っていても、コピーが総花的だと①③に答えられない。答えられない問いがあれば、その要素の追加ではなく見出し・リード文の書き直しで直す（セルフレビューチェックリスト #12）。

### 3層見出しパターン（アイブロウは案内が要る章だけ）

セクション導入を「小さいラベル → 大きい見出し → 説明文」の3層で組むと視覚的な階層が明確になる。ただし**小さいラベル（アイブロウ）は毎回付けない**。役割は「ここは何の章か」を先読みさせることなので、見出し自体で分かる章（料金・よくある質問）には不要。1本の LP で 1〜2 箇所（ヒーローと最重要の章）に限る。毎回付けると装飾になり意味が消える:

1. `text`（`fontSize: "12px"` または `"14px"`、アクセント色、英語ラベル等）
2. `heading`（`fontSize: "30px"` または `"36px"`）
3. `text`（本文サイズ、グレー系）

### 数字・実績バー

大きな数字（`48px`）+ 小さいラベルのペアを `display: "flex"` で横並びに配置する。**訴える力は「太さ・単位の落差・根拠」で決まる**:
- 数字は**太字**にする。プレーン文字列の `text` は太字にできないので、tiptap のインライン装飾（`content-schema.md`「インライン装飾」。使えるのは色・太字・サイズ。下地マーカーは不可）で `bold` マークを付け、**数字 48px・単位 20px** のようにサイズ差をつける（「120名」を全部同じサイズで書くと弱い）
- 列の間は 1px の縦罫線（ダーク帯は `rgba(255,255,255,0.22)`、明るい面は文字色の10%）で区切り、SP では罫線を消して縦積み
- 上に短い見出し（「数字で見る、12週間の成果」）、下に**集計期間と母数**を12pxで添える。根拠の無い数字は載せない
- ダーク帯では数字を白か金属色にする（赤・橙は禁止。「テキスト色と背景色のコントラスト」参照）

### グラデーション背景

セクションの背景は単色・画像のほか、構造化形のグラデーション（`attributes.background` の `type: "gradationColor"`）を設定できる。フラットな単色よりモダンで洗練された印象になり、ヒーローや CTA セクションで効果的。指定方法と値の制約（`angle`・`colorStops`・hsl 形式）は `content-schema.md` の「背景グラデーション」を参照。`styles.background` に `linear-gradient(...)` 文字列を書く方法は禁止（描画はされるがユーザーが後から編集できなくなる）。

### 横並びレイアウト（推奨は3列まで）

親 `section` に `styles: { "display": "flex", "gap": "16px" }`、子 `section` に `width`（例 `"31%"`）を指定して横並びにする。列数に構造上の上限はないが、**推奨は3列まで**。4列以上はテキストが狭くなり読めなくなる（6項目なら 3列×2段か縦積みにする）。ユーザーが4列以上を明示指定した場合はそれに従う。モバイルでは必ず `mobileStyles: { "display": "block" }` で縦積みに切り替える（詳細は `content-schema.md` の「PC/SPでレイアウト方向を変える方法」）。

### フォントの使い分け

見出しと本文でフォントを変えるとメリハリが出る（例: 見出し `'Noto Serif JP'` × 本文 `'Noto Sans JP'`）。使えるのは `content-schema.md` 記載の4種のみ。LP 内での組み合わせは1パターンに統一する。

### テキスト色と背景色のコントラスト

ダーク背景セクションには白系テキスト（見出し `#ffffff`、補助 `#e3e8f2`。`#cccccc` 以下は 14px 以下で読みにくい）、ライト背景にはダーク系テキスト（`#1a1a2e` / `#212529` / `#666666`）を使う。テキスト色と背景色が同系・近似になっていないか必ず確認する。

**数値基準（WCAG のコントラスト比）。** 「近すぎないか」を目視で判断せず、比率で確認する。HEX が分かっていれば計算できる。

| 対象 | 必要な比 |
|---|---|
| 本文・注記・ラベル（〜17px） | **4.5:1 以上** |
| 大きな見出し（24px 以上、または 18px 以上の太字） | **3:1 以上** |
| ボタンのラベル（16px など**20px未満**） | **4.5:1 以上** |
| ボタンのラベル（**20px 以上の太字**＝大文字サイズ扱い） | **3:1 以上** |
| 装飾の罫線・アイコン | 規定なし（ただし 1.5:1 未満は見えない） |

- プリセットの組み合わせ（文字/地・補助文字/地・文字/淡い面・白/深色）は**全6本とも 5:1 以上**を実測済み。プリセットの色をそのまま使う限りこの基準は自動的に満たされる。**独自の色を足したときだけ確認する**
- よくある違反: 淡い面の上に補助文字より薄い色を置く／識別色（黄・ライム）を文字色に使う／ダーク帯に `#cccccc` 以下の小さい文字
- **アクセント色は「面・罫線・ボタン地」用。文字に使うときは濃色版（文字用アクセント）を用意する。** 金・緑・水色などの中明度アクセントは、白地でも 2.5〜3.5:1 しかなくアイブロウや番号ラベルが読めない。**明るい面では明度を落とした値**（白地と淡い面の両方で4.5:1を満たす値）を使い、**ダーク面の上では逆に元の明るいアクセントを使う**（濃色版をダーク帯に置くと今度は読めない）。各プリセットの値は `presets.md` の「文字用アクセント」
- **色面に白い小文字を載せない。** 白文字は面が十分濃いときだけ成立する（例: 橙 `#fa6400` に白14pxは 3.05:1 で不足 → 面を `#c75000` まで濃くすると 4.59:1）。**鮮やかな暖色（朱・橙）の塗りボタンで白文字が 4.5:1 に届かないときは、塗りを暗くするのではなく、ラベルを 20px 太字にして大文字サイズ基準（3:1）に載せる**。ブランドの鮮やかさを保ったまま基準を満たせる
- **例外: SNS公式ブランドカラーのボタン。** LINE緑 `#06c755` × 白文字は 2.26:1 で基準を満たさないが、プラットフォームの認知（「これはLINEのボタンだ」と一目で分かる）を優先してそのまま使ってよい。その場合は**ラベルを 18px 以上の太字にし、ボタンを大きく取り、周囲に十分な余白を置く**こと。ボタン以外のテキストでは例外を認めない

### 特典・オファーの見せ方（オプトイン／無料配布）

**無料オファーのLPは「怪しく見えない」ことが最優先の設計要件。** 無料配布は、作りが同じでも読み手の警戒心が最初から高い。怪しさは装飾の量ではなく、次の3つの欠落から生まれる。

1. **オファーが第一声になっている。** 見出しが「◯◯を無料で差し上げます」から始まると、通販・情報商材の記号そのものになる。**見出しはベネフィット**（読み手が手に入れる状態）にし、**オファー（無料・特典）はアイブロウとリードに従属**させる。例: ✕「3点セットを、無料で差し上げます。」→ ○「『もう一度話したい』と言われる30分に。」＋リードで「その流れを穴埋め式にした3点セットを、LINE登録で無料でお渡しします」
2. **作り手が見えない。** 誰が何のために配るのかが後半にあると、最後まで警戒が解けない。**ヒーロー内に作成者の行**（丸アバター48px＋氏名・肩書＋実績1行）を置く。章順を変えずに信頼を前倒しできる
3. **現物が見えない。** 「3点お渡しします」と書いてあるのに現物が1枚も出てこないと、存在そのものを疑われる。写真が無いときは、特典カードの頭に**資料モック**（淡色の縦長の面＋48pxの番号。幅60%・中央。左右にスペーサー列）を置き、「3つの資料が並んでいる」状態を作る。下端の分量・形式の行と合わせて実在感が出る

- **彩度の高いベタ面（明度35〜85%の鮮やかな色）は2章まで。** グラデ＋マゼンタ＋緑のように3つ以上になると、配色が綺麗でも安っぽく見える。3つ目からは**明度で作る**（濃色・淡色）。ただし**深い紺・濃茶などの暗い面はこの数に含めない**（鮮やかさではなく重さの表現）
- 受講者の声に顔写真が無いときは、**イニシャルの丸バッジ**（淡いアクセント面＋頭文字20px）で実在感を作る。別人のストックフォトで埋めない

**無料配布LPで最も効く装飾は「価値の可視化」で、飾りではない。** カードが「タイトル＋説明」だけだと、読み手は**何をもらえるのか実感できない**。

- **分量と形式をカードの中に置く。** 「PDF・A4 8ページ」「スプレッドシート」「メール全4回」＋「3分で読み切れる」を、カード下端に **1pxの罫線＋2行** で入れる。これが「もらえる実感」を作る唯一の情報
- **同じ内容を2つの章で言わない。** 特典カードの章と「配布物の仕様」表の章を分けると、読み手は同じ3つを2回見せられ、カードは空洞・表は退屈になる。**仕様はカードに畳み、表の章は作らない**
- **オプトインLPの山場は特典章。** ダーク面の上に**白カード**を置く図地反転にすると、ページで最も大事な章がページで最も強い面になる。番号は **48px**（12pxの番号は順序のリズムを作れない）
- **特典の直後の中間CTAが本当の勝負どころ。** 白地に小さいボタンで済ませず、**淡い暖色の面＋36pxの見出し＋一行＋社会的証明（実績数）**を置く
- **プラットフォームの行動色を使うLPでは、その色をCTA以外に一切使わない。** LINE友だち追加が目的なら CTA は LINE公式緑に統一し、**装飾の緑は全部やめて識別色（橙など）に寄せる**。CTAの色がページ内で唯一になり、どこを押すか迷いが消える。※ブランドのアクセント色をCTAに使うLP（識別色＝CTA色）では逆に、ラベル・罫線・数字にも回して「見える量」を確保する（「アクセント色は『見える量』を確保する」）。混同しない

**1行の文字数は35〜45字に収める。** 1080pxのコンテナで 16px の本文を全幅に流すと **1行60字**になり読めない。**2列にする**か、その章だけ左右の `padding` を広げて本文の幅を絞る。箇条書きの**記号列は `width: "20px"` の固定幅**にする（`%` にすると幅の広いカードで記号と本文が離れる）

**罫線は「引用」か「区切り」の記号。装飾として引かない。** 左罫線を引いたブロックは、読み手に「これは引用です」と伝える。**章見出しを含むブロック全体に左罫線を引くと、「この章まるごとが引用」という嘘の信号**になり、36px の章見出しが罫線の内側＝本文の一部に降格する。さらに `padding-left` のぶんだけその章の左端だけ内側にずれ、ページの左のエッジが崩れる。

- 左罫線を使ってよいのは **①受講者の声などの実際の引用 ②FAQ の Q など同型の項目の区切り** の2つだけ。同じ太さ・色の罫線を3つ以上の異なる役割に使うと、記号として意味を失う
- 悩み・症状の列挙に必要なのは罫線ではなく**囲い**。箇条書きを**淡い面の上の白カード**（`padding: "28px 32px"`）に入れれば、明度差だけで「これが症状リストだ」と伝わり、見出しはカードの外＝階層が守られる
- **「・」始まりの箇条書きは、折り返すと2行目が記号の下に潜る**（MOSH にぶら下げインデントの指定が無い）。SPで折り返す長さなら **記号列6% ＋ 本文列94% の2カラム**に分けて組む

**実績の枠に、実績でない数字を入れない。** ヒーローの実績ミニや数字バーは**証拠**の場所。「登録30秒」「たった3ステップ」のような**所要時間・手続きの手軽さはコストの説明**で、CTA直下の注記が担当する。実績の枠に置くと、①証拠の枠を1つ潰し ②注記と同じことを2回言い ③「盛っている」印象になる。**3つに揃えるために仕様やコストを混ぜるくらいなら2つにする。** 入れてよいのは**人数・率・満足度・期間の実績**まで。**配布物の分量・形式（「A4 8ページ」「PDF」）は仕様**なので、実績枠ではなく**特典カード下端の分量・形式の行**に置く（「特典・オファーの見せ方」）。同じ数字を実績枠とカードの両方に出すと、証拠の枠を仕様が占有したうえに重複掲載になる。

**数字は「面の上に印刷された文字」にしない。** 実績の数字を大きくしただけだと、単色の面に文字が乗っているだけで装飾密度が出ない。数字に**形**を与える手を上から順に試す。

| 手 | やり方 | 効き方 |
|---|---|---|
| **図地反転のカード**（最も強い） | 識別色の面の上に**ブランド色のカード**を置き、数字を**識別色**で入れる（黄面→紺カード→黄の数字48px、ラベルは淡色14px） | 面→カード→数字で図地が2回反転し、2色だけで密度が出る |
| 太いベースライン | 数字の下に幅60px前後・4pxのブランド色の罫線を敷き、その下にラベル | カードより軽い。淡い面や白地向き |
| 上罫線＋列 | 各列の上に2〜3pxの罫線。**罫線は必ず暗い側の色**（下記） | 一番軽い。ヒーロー内の実績ミニ向き |

- **識別色の罫線を淡い面・白地に引かない。** 黄 `#ffe600` × 白は **1.27:1**、淡い面でも 1.09:1 で、引いても見えない。線には**文字用アクセント（暗い側）**を使い、識別色は面とボタン地に回す
- **実績ミニの軸は章の軸に合わせる。** 中央寄せのヒーローの直下に左寄せ3列を置くと、一番目立つ差が「揃っていないこと」になる

**ダーク帯の大きな数字・見出しに彩度の高い赤・橙を使わない。** 黒地×赤文字は警告・危険の連想で、信頼を担う実績バーに最も向かない。数字は白か金属色（金・シルバー）、アクセント色は小さな罫線やラベルに限る。

**黄・ライム・シアンなど高明度の色を広い面に敷かない。** 明度が高い色相は彩度100%のまま面にすると目が休まる場所が無くなり眩しく感じる（白との明度差も小さく輪郭が浮く）。使い方は①CTAボタン②細い罫線・番号ラベル、の小面積に限る（文字の下地マーカー `backgroundColor` は編集画面に操作が無いので使わない。見出しの部分強調はブランド色の文字色で行う）。面に使うなら明度85〜92%まで薄める。 高明度色を**文字・記号（引用符「“」等）に使うのも不可**。薄い面の上では読めない。記号や見出しの部分色はブランド色（青・紺・茶など中明度）で。

**ただしアクセント色を締め出しすぎない。** パレットの識別色（黄・朱・金など）は LP の中で**主CTA（D=3 / A=2 箇所）＋2種類の小面積**（番号の丸・細い罫線・薄めた面 など）に必ず現れるようにする。CTA 1箇所だけだと「青のLPにボタンが1つ」になりパレットの正体が消える。明度90%以上に薄めた面は識別色として機能しない（薄黄は「クリーム色のLP」に見え、フレッシュさが消える）。淡色の面が欲しければ無彩色寄りのクールグレー（#f2f6fa 等）にして、識別色は鮮やかなまま小〜中面積で出す。

**CTA色の再利用は「塗り面だけ1章まで」で線引きする。** 「CTA色は CTA 専用にして他に一切使わない」は行き過ぎ（上記のとおりパレットの正体が消える）。逆に識別色のベタ面を何章にも置くと、塗りボタンが背景に埋もれてクリック対象が識別できなくなる。境目は**面積と用途**で引く:

| 用途 | CTA色（識別色）の使用 |
|---|---|
| 主CTAの塗りボタン | 必ず。LP 全体で1色1形（「CTA の設計」）。黄など高明度色なら載せる文字は深色にする |
| ベタ塗りの面（帯・セクション背景） | **1本の LP で1章まで**（実績帯 or CTA帯のどちらか一方）。その章にボタンを置く場合はボタンを白抜き等に反転させ、面とボタンを同色で重ねない |
| 罫線・番号ラベル・アイコン・見出しの部分色 | 自由に再利用してよい（むしろ2種類は出す） |
| カード背景・本文の下地 | 使わない（薄めても識別色として機能しない） |

判断に迷ったら「このページで**塗りつぶされた識別色**はいくつあるか」を数える。ボタンを除いて2つ以上あれば1つに減らす。

**印象語→造形の対応（パレット定義に「印象・想定業種」を1行必ず持つ）。** 色だけでは印象は出ない。フレッシュ＝鮮やかな識別色の帯1本＋白地＋余白多め。テック＝直線的（角丸0〜4px）＋深色の帯1〜2本＋英字の小ラベル（1〜2箇所）＋4pxの左罫線など幾何的な部品。高級＝角丸8〜12px・セリフ・金の細線・ダーク帯。温かい＝角丸4〜8px・茶系・明るい面だけ・写真面積大。ポップ＝角丸16px以上・丸ゴシック・複数色の面。

## モバイルファースト（必須）

MOSH のユーザーの多くはスマートフォンからアクセスする。全セクションでモバイル対応を必ず行う。

- **全セクションに `mobileStyles` を必ず指定する**（省略禁止。省略すると PC 用の大きな余白・横並びがそのまま SP に出る）
- padding: デスクトップ `"80px 60px"` → モバイル `"48px 20px"` 程度
- 見出し: **役割ごとに PC / SP のサイズを固定する**（ヒーロー `48px`→`30px` / 章 `36px`→`24px` / 小 `24px`→`20px` / ミニ `20px`→`18px`。対応表と使い方は「級数（見出しサイズ）は役割ごとに固定する」が正）。`styles.fontSize` と `mobileStyles.fontSize` の両方を、`content-schema.md`「fontSize（固定スケール・px）」の10値からのみ選ぶ（`22px` `28px` のようなスケール外の値・レンジ内挿は禁止）
- 本文: デスクトップ `16px` / `18px` のいずれか → モバイル `14px` / `16px` のいずれか。**12px 未満は禁止**（`10px` は注釈など補助テキストに限る）
- ボタン: モバイルでは `mobileStyles: { "width": "100%" }` で全幅にし、行の高さ（`lineHeight`）でタップ領域を44px以上にする。`fontSize` はデスクトップより1段下げる（`content-schema.md` 参照）
- 横並び（`display: "flex"`）は `mobileStyles: { "display": "block" }` で縦積みに
- 画像はモバイルで幅 100% 基本。固定幅の要素がモバイル画面幅（375px）を超えないこと（横スクロールの発生は禁止）

## CTA の設計

### 大きさはトーンで決める（大きいほど良い、ではない）

主CTA（primary）と補助CTA（secondary）の2段を用意し、**プリセットのトーン**でスケールを選ぶ。幅・高さ（padding）を変えたら fontSize も連動させる（文字だけ小さいボタンは間延びする）。

大きさは編集画面の項目で作る: **高さ＝行の高さ（`lineHeight`）、幅＝ボタンの幅（`width`）、外側の余白＝余白（`layout.styles.padding`）**。`styles.padding`（内側）は UI 既定のまま触らない（`content-schema.md`「ボタンの大きさの決め方」）。

| トーン | 例 | primary: fontSize / lineHeight / width（PC） | secondary |
|---|---|---|---|
| 控えめ（高級・信頼・専門職）`restrained` | 紺×金、茶×金、黒×朱 | 16px / 1.6 / 320px（約54px高） | 14px / 1.6 / 240px |
| 標準 `medium` | 黄×青 | 18px / 1.8 / 360px（約60px高） | 16px / 1.6 / 260px |
| 大きく（カジュアル・リード獲得）`bold` | 橙×緑 | 20px / 2 / 400px（約68px高） | 16px / 1.8 / 280px |

- SP は `mobileStyles.width: "100%"`、fontSize は PC より1段下げる（primary 20px→18px、18px→16px）
- 1つの LP で primary は1色1形に固定する（ヒーロー・料金・最終CTAで同じ見た目）。**塗りボタンは唯一の行動（CV）だけ**
- secondary（「詳細を見る」等の補助動線）は**テキストリンク型**にする: `background` 透明 `hsla(0, 0%, 100%, 0)`・文字はブランド色・`width: "auto"`・文言末尾に「→」。主と同じ塗りにすると主CTAと競合して離脱動線になる。ボタンに枠線プロパティは無いのでアウトライン型は作れない
- 角丸は 8 / 10 / 12px を高さに合わせる。pill（完全丸）はカジュアルトーンのみ


- CTA ボタンは販売型（即決・高額）では**最低3箇所**（ヒーロー直後・中盤・最終セクション）、リード獲得・告知（4〜7セクション）では**2箇所**（ヒーロー直後・最終セクション）
- MOSH のプラン・サービスへ誘導する場合、`href` は `https://mosh.jp/services/{id}?openExternalBrowser=1` の形式にする。**末尾の `?openExternalBrowser=1` は必須**（LINE 等のアプリ内ブラウザでの決済不安定を回避するため）。`{id}` はユーザーから確認した実在のプラン・サービス ID のみ使う
- `href` が確定しないボタンにダミー URL（`#` や `https://example.com/...`）を捏造しない（`content-schema.md` の既存ルールどおり。ユーザーに確認するか、その旨を伝えて保留する）。唯一の例外はプリセット JSON（`examples/catalog/`）の差し替えトークン `https://mosh.jp/services/REPLACE_WITH_SERVICE_ID?openExternalBrowser=1` / `https://lin.ee/REPLACE_WITH_LINE_ID`。形式を示すためのもので、保存前に必ず実 ID へ置換する（チェックリスト #11）

## 画像の運用

- `image` の `src` に入れてよいのは **①ユーザー提供の実URL ②下書き専用のプレースホルダ素材**（`https://mosh.jp/images/522545e4fca64345a420e594e1b2f6c1`、グレー地に IMAGE 表記、16:10、alt「仮画像（差し替え前提）」）の2つだけ（ルールの正本は SKILL.md 必須ルール）。`src: ""`・ダミー URL（`https://example.com/...` `#`）・テンプレのサムネや無関係な写真は禁止
- 実画像はヒアリングシート #7 で MOSH 内から収穫（商品画像・既存 LP・素材ライブラリ）し、足りない分だけ依頼する。公開前にプレースホルダを実画像へ差し替えるか要素を削除する（Step 7）
- **`examples/catalog/*.json` 内の写真は例外的に③イラストレーション用のダミー写真**（フリー素材由来。骨格の見せ方を実演するための仮の中身で、①のユーザー提供実URLではない）。プリセットを写す際は、この写真も②の灰色プレースホルダと同じ扱いで、必ずユーザーの実画像に差し替えるか要素を削除する。差し替えずにそのまま新規LPへコピーしない
- 実 URL を配置する場合のサイズ目安: アイコンは `width` 60〜100px、装飾画像は 150〜300px、写真・メイン画像は幅 100%（モバイル）
- **人物写真は同一人物・同一トーンで通す。** 講師・運営者が登場する LP では、ヒーロー・講師紹介・CTA 帯に出る人物を1人に統一し、服装・背景・色調も揃った写真を選ぶ。**別人のストックフォト（笑顔のビジネスパーソン等）を賑やかしで混ぜない**（受講者の声のアバターや、実在の受講者写真は対象外）。人物が入れ替わると「素材を寄せ集めたページ」に見え、信頼感が最も落ちる。手持ちが1枚しかない場合は、同じ写真を複数セクションで使い回す方が別人を足すより良い

### 画像点数の目安（役割ベース・ゴール別）

写真が1〜2枚しかない LP は白地・カード・数字ばかりの「テキスト LP」に見え、装飾が足りない印象の主因になる。**ユーザーへの依頼枚数を減らすことと、LP が使う画像の総枚数を減らすことは別**（ヒアリングシート #7 で「多く求めない」のは依頼負荷の話）。収穫できた画像は複数セクション（ヒーロー・画像＋テキスト・声の背景・講師紹介 等）に使い回してよい。

**枚数より役割が先**。日本語の縦長 LP は目安5〜10枚だが、「枚数を埋める」ために意味の薄いストックフォトを足すと情報量は増えても広告っぽさが強まり信頼感が落ちる。次の4役割が埋まっていれば少ない枚数でもLPは成立する。逆にこの4つが揃わないまま枚数だけ多いのは失敗:

| 役割 | 伝えること | 使う場所 |
|---|---|---|
| Hero（必須） | ターゲットと得られる未来を一瞬で伝える | ヒーローのメインビジュアル or 背景画像 |
| Problem（悩み・課題） | 顧客が「自分だ」と感じる | 悩み共感セクション、無ければヒーロー直後 |
| Solution（利用シーン） | サービスの利用シーン・仕組みを理解させる | 画像＋テキスト、特徴セクション |
| Trust（信頼） | 人物・実績・運営者で信頼させる | 講師紹介、声、実績バー周辺 |

任意で追加: Before/After・成果イメージ（1〜2枚）、最終CTA付近の補強画像（0〜1枚）。

**Solution は「実体ブロック」で満たしてもよい。** 配布物の中身（カリキュラム表・成果物の一覧・仕様）を**画像ではなく組版**（表・区切り線・見出し）で見せる形は、イメージ写真より強く、MOSH では画像アップロードなしで作れる。この場合はゴール別の最低枚数から1枚引いてよい（例: A で Hero・Trust の2枚＋実体ブロック）。**実物が無いからといってイメージ写真で枠を埋めない**（「写真の選び方」1.）。

| ゴール | 最低枚数の目安 | 必須役割 |
|---|---|---|
| D（高額・講座、8〜10章） | 5枚以上 | Hero・Problem・Solution・Trust（声 or 講師）を最低1枚ずつ |
| C（即決販売、7〜9章） | 4枚以上 | Hero・Problem・Solution（商品・成果物）・Trust |
| B（告知、5〜7章） | 3枚以上 | Hero・Solution（会場・登壇者）・Trust |
| A（リード獲得、4〜6章） | 3枚以上 | Hero・Solution（特典の中身）・Trust |

収穫元（ヒアリングシート #7）で集まった枚数・役割がこれに満たない場合、①スロットを追加依頼する ②同じ画像を複数セクションに使い回す ③足りない分はプレースホルダのまま進め公開前に依頼、のいずれかをユーザーに選ばせる（黙って1枚のまま進めない）。逆に役割の無い画像（説明が無くても意味が変わらない写真）は足さない。

### ファーストビューの強さは「面積」ではなく「対比」で作る

**見出しは 48px で頭打ち**（固定スケールの上限）。章見出し36pxとの差は1.33倍しかないので、**サイズで勝つことはできない**。ファーストビューが弱いときに効くのは、次の5つ。上から順に効く。

1. **CTAはブランド色ではなくアクセント色（識別色）で塗る。** ブランド色のボタンは「暗いだけ」で彩度が跳ねず、写真に負ける。**淡い面には暗いアクセント＋白文字**（本文と同じ 4.5:1 を満たす明度まで落とす。例: 金 `#b8860b` ではなく `#8a6508`）、**ダーク面には明るいアクセント＋濃色文字**。この明・暗2変種以外は使わない＝LP内でCTAの見た目を割らない
2. **見出しを部分色で割る。** 提供価値の核になる1語だけを文字用アクセントにする（「初案件まで**12週間**。」）。サイズを上げられない以上、**同じ級数の中で色の量を振る**のが唯一の増幅手段。1つの見出しで1語まで
3. **2カラムは左右の高さを揃える。** 写真カラムが短いと右下に大きな空白が残り、版面が「左に寄った半端な形」になる。実績ミニ3点などを写真の下へ移して高さを合わせる（左＝コピーとCTA／右＝写真と実績）
4. **左右の余白は全章で揃える。写真だけを端まで出さない。** `padding` の左右を非対称にして写真をコンテナの端まで出すと、他の章の右端と一直線に並ばず、演出ではなく**ズレ**として読まれる。ブリードが「わざと」に見えるのは、**セクションが画面幅いっぱいに広がり、かつ上下の章もその幅で切り替わるとき**（全幅の写真帯・ダーク帯）だけ。2カラムのヒーローでは左右対称の余白を保ち、写真の存在感は**カラム比（45%まで）と左右カラムの高さ揃え**で作る
5. **SPの第一画面（375×667）に、写真かCTAのどちらかを必ず入れる。** 実績3点はSPでも3列のまま（`mobileStyles` に `display: "flex"` と `width: "30%"`）。縦積みにすると200px近く食って、第一画面が文字だけになる。ラベルは1行に収まる長さへ短縮する
6. **ヒーローで写真を縦積みにするなら、写真は最後に置く。** アイブロウ・見出し・本文・CTA・注記を積むと、写真の上端は **約500px** になる（1080px幅・実測）。**その後ろに実績ミニなどを置くと、初期表示から完全に外れる**。実績は必ず写真より前に。写真そのものを初期表示に入れたいなら、縦積みでは両立しないので**背景（スクリム付き）か横のカラム**にする

### 写真の選び方（役割が決まった後）

「画像点数の目安」で**どの役割に何枚要るか**が決まったら、次は**その役割にどの写真を充てるか**。同じ役割でも、選び方でLPの説得力は大きく変わる。

**1. 実物を見せる（いちばん効く）**

イメージ写真より、**読者が受け取る現物そのもの**が強い。抽象的な風景・イメージカットを1枚足すより、実物を1枚見せる方が「本当にあるんだ」に直結する。

| 役割 | 実物として見せられるもの |
|---|---|
| Solution | 教材のPDF・スライド・テキストの中身、ワークシート、会員サイトや管理画面のスクリーンショット、特典一式を並べたカット |
| Trust | 受講生の提出物、実際のチャット画面、セッション中の画面、掲載メディアの誌面（使用許諾があるもの） |
| Problem | 顧客が今使っている散らかったスプレッドシート・手帳など、困っている状態そのもの |

- ヒアリングシート #7 で**「特典・成果物の実物が分かる画像（スクリーンショット可）」を必ず1スロット聞く**。「イメージ写真でいいです」と流さない
- 画面のスクリーンショットは個人情報・氏名・メールアドレスが写り込んでいないか必ず確認し、写っていれば差し替えかマスクを依頼する
- 実物が無い／まだ作っていない場合は、**無理にイメージ写真で埋めない**。その枠は文字と余白で組み、公開前に差し替える（「役割の無い画像を足さない」の原則どおり）

**2. 視線・体の向きをコピー側へ**

人物写真は、**視線や指先の向いている方向に読者の視線も流れる**。人物が画面外を向いている写真をヒーローの右に置くと、読者の視線は見出しではなく画面の外へ抜ける。

- 左テキスト・右写真なら、人物は**左（＝テキスト側）を向いている**写真を選ぶ。逆なら左右を入れ替える
- 正面向きは中央積みのヒーローに合う（読者と目が合う＝呼びかけになる）
- 被写体距離を役割で使い分ける: Trust＝バストアップ以上（表情が見える距離）/ Solution＝手元・画面のクローズアップ / Problem＝引き（状況が分かる）
- 文字を重ねる写真は、**被写体の逆側に余白がある**ものを選ぶ。中央に被写体が詰まった写真は、スクリムを濃くするしかなくなり写真の良さが消える

**3. トリミング事故を避ける（MOSH 固有）**

`section` の背景画像は `background-size` / `background-position` を指定できない（`content-schema.md`）。**表示範囲をこちらで制御できない**ため、写真の側で事故を防ぐ。

- 顔・商品・文字など**主要被写体が画像の端にある写真を背景に使わない**。中央寄りに写っているものを選ぶ
- 縦横比は正方形〜横長（16:9〜16:10）。極端な縦長・パノラマは使わない。**迷ったら白銀比（1:1.414、A判用紙と同じ比）をデフォルトにしてよい**（この範囲内に収まる）
- 文字が写り込んでいる画像（バナー・チラシ・スクリーンショット）は背景にしない。端が切れて意味が変わる。文字入り画像は `image` 要素として貼る
- 端が切れると困る画像は、背景ではなく `image` 要素（幅100%）で貼る。こちらは全体が必ず表示される

### 画像の置き方（実体 / 証拠 / 雰囲気）

**どこに置くかは好みではなく、その画像が何をする画像かで決まる。** 役割（Hero/Problem/Solution/Trust）が「何のために要るか」なら、こちらは「どう置くか」。

| 類型 | 何をする画像か | 置き方 | 誤用 |
|---|---|---|---|
| **実体** | 教材・ワークシート・管理画面など**現物を見せる** | 単独で**全幅**、または**幅80%＋中央**。周囲は余白だけにして他の要素と並べない | 背景にする（端が切れて何か分からなくなる） |
| **証拠** | 人物・実績・利用シーンで**主張を裏づける** | テキストの**隣**（2カラム）。対応する文と同じ章に置く | 背景にする（読ませたい文と競合して両方死ぬ） |
| **雰囲気** | トーンを作る。単体の情報量は低い | **背景**（スクリム必須。次項の4条件を満たすときだけ） | 全幅で主役にする（意味のない面積を取る） |

**ヒーローだけは例外**: 人物写真は「証拠」でありながらトーンも作るため、ヒーローに限り**全面スクリム付きの背景**にしてよい（`navy_gold` の `dark_center_bgimage` がこの形）。ただし次項の4条件は満たすこと。ヒーロー以外の章では、人物写真は背景にせずテキストの隣に置く。

**段組みの比率と位置**

- **列の幅は「合計 = 親の幅」になるように決める。** `gap` は px、`width` は % なので、`31% × 3 + gap 0` のようにすると合計が親に **67px 足りず、右端だけ他の章と揃わない**。計算式は `幅%の合計 ÷ 100 × 親の幅 + gap × (列数-1) = 親の幅`。**`gap: "0"` にして列間の空きを列の `padding` で作る**のが一番ずれない（ヒーローの 55% + `padding: "0 48px 0 0"` / 45% がこの形）

- 画像:テキスト = **38:58**（テキストが主役）か **58:38**（画像が主役）。50:50 は主従が消えてぼやける
- **列の比率に迷ったら白銀比（1:1.414、41:59 相当）をデフォルトにしてよい**（既存の38:58／58:38はこの比率に近い）。画像:テキスト以外の2カラム（カードの内訳・要素の左右分割など、他に明確な根拠が無い場合）でも、まず41:59を起点に調整する
- **写真はページの外側（左端か右端）に置く**。中央にテキストが集まり、写真が外枠になる。写真を内側・テキストを外側にすると視線が外へ逃げる
- 人物の視線・体の向きはテキスト側（「写真の選び方」2.）

**「見せ場の全幅」は LP 全体で1〜2回**

- ここでの全幅とは、**セクション幅いっぱい＋上下に大きな余白（80px 以上）を取って単独で置く見せ場**のこと。章の切れ目の記号として働くので、3回以上使うと切れ目としての意味が消える
- カード内の写真・2カラムの中の写真・丸アバターなど、**他の要素と並んでいる `width: "100%"` は数えない**（これらは何枚あってもよい）
- 画像の周囲の余白は面積に比例させる。見せ場の全幅は上下 80px 以上、インセット（幅80%）は 32px 以上。全幅を余白なしで詰めると、写真ではなく帯に見える

**全幅の写真には「一言」を載せる（裸で置かない）**

- 全幅の雰囲気写真に文言が無いと、**ページで最も大きい要素が最も情報量の少ない要素**になる。読み手は「大きい＝大事」と読むので、用意した山場が写真に食われる
- 直し方は上から順に試す。①**帯にする**（`section` の背景画像＋スクリム＋ラベル1行＋見出し1行。高さが `padding` で決まるので、写真の元寸に引きずられない） → ②**段組みに入れる**（38:58） → ③**削る**
- **例外は実体の画像**（教材・ワークシート・管理画面など現物）。見せる中身が画像そのものなので、裸の全幅でよい
- 山場（ダーク帯など）の直前・直後に写真帯を置くなら、写真帯は**明幕**にする。暗い面が連続すると章の切れ目が消え、山場が「ただの長い暗い区間」になる

**配置のリズム**

- **同じ幾何を3章続けない**。左画像→左画像→左画像 は、背景色を変えても単調に見える。左右を交替させるか、間に見せ場の全幅を1つ挟む
- 横並びに置く画像は**縦横比を揃える**（3カードで 16:9 と 1:1 が混ざると、揃っていないことだけが目立つ）。角丸の有無も LP 内で統一する

**SP では縦積みの順序が固定される（PC の左右で決めない）**

PC で「テキスト左・画像右」にすると SP は テキスト→画像、「画像左・テキスト右」にすると SP は **画像が最初**に来る。`mobileStyles` では順序を変えられない（`order` / `flexDirection` は許可プロパティに無い）。

- SP の読ませ順（例: 見出し→写真→本文）が PC の左右配置と両立しないときだけ、`content-schema.md` の `showDesktop` / `showMobile` で PC 用・SP 用の構造を分ける。**順序の問題以外では従来どおり `mobileStyles` での調整を優先**する（構造を二重に持つと保守対象が増えるため）

### 背景画像で装飾密度を作る（写真は面としても使える）

`image` 要素として貼るだけでなく、`section` の `attributes.background` に `type: "image"` を指定してセクション背景そのものを写真にする技法がある（仕様・保存確認済みの記法は `content-schema.md`「`section` の背景画像」）。ヒーローや CTA 帯を白地・単色ベタで済ませず、収穫した写真を**スクリム**（`hsla` の面を子要素に重ねる。下表）付きの背景として使うと、装飾が薄い印象を避けられる。

- 使う場所は**ヒーローと CTA 帯の1〜2箇所まで**（多用すると文字が読みにくくなる・「囲いの原則」の面の使いすぎと同じ理由）

**背景にしてよい4条件（すべて満たすときだけ）**

1. **その章の連続する本文が3行を超えない**（見出し＋リード1〜2行＋CTA まで。アイブロウ・実績ミニ・ラベル・CTA注記は本文に数えない）
2. **写真の情報量が低い**（空・壁・ボケ背景・広い床など、平坦な面が画面の半分以上）。顔・文字・細かい物が詰まった写真は不可
3. **スクリムを重ねられる**（下表）。**写真の上に直接文字を置くのは常に禁止**。写真の明度は場所によって変わるため、どこかで必ず読めなくなる
4. **主要被写体が中央寄り**（表示範囲を制御できないため。「写真の選び方」3.）

**1つでも欠けたら、背景にせず `image` 要素として貼る。** 単色ベタに戻すのではなく、画像要素で置いて装飾密度を作る（「画像の置き方」）。スクリムを 0.7 より濃くしないと読めない写真は、条件2を満たしていない＝背景に向いていない。

**スクリム・パネル・薄い面は別物（混同しない）**

| 用途 | 形 | 透過率 |
|---|---|---|
| **全面スクリム（暗幕）** — 写真を完全に背景化し、白文字を載せる | 写真の上に全面 `hsla(ブランドの色相, S%, 12%, α)` | α = **0.55〜0.70**（文字が小さいほど濃く） |
| **全面スクリム（明幕）** — 濃い文字を載せる | 全面 `hsla(0, 0%, 100%, α)` | α = **0.72〜0.86** |
| **片側パネル** — 写真の主役を残し、片側だけで文字を読ませる | 左（右）カラムだけに淡い面色の `hsla` | α = **0.88〜0.95** |
| **薄い面** — ダーク帯の上でカードを作る（「囲いの原則」）。**写真の可読性確保には効かない** | `hsla(0, 0%, 100%, 0.06〜0.08)` | 0.06〜0.08 |

- 実装例: `navy_gold` は全面スクリム `hsla(226, 88%, 12%, 0.62)`、`orange_green` は片側パネル `hsla(30, 70%, 97%, 0.93)`
- **薄い面（0.06〜0.08）を写真の上の文字に使わない**。ほぼ透明で可読性は上がらない
- `background-size`/`background-position` を明示指定するプロパティはスキーマに無く、表示範囲を制御できない。**どの写真を背景に選ぶか（被写体の位置・縦横比・文字入り画像の扱い）は「写真の選び方（役割が決まった後）」の3. が正**
- プレースホルダのまま背景画像を試作してよいが、公開前に実画像へ差し替える（通常の `image` 要素と同じ運用）

### 角丸画像

`image` に `borderRadius` は無いため、写真を角丸に見せたい場合は「画像を角丸にする（`section` で包む）」の技法（`content-schema.md`）を使う。プリセットの角丸値（`presets.md`）に揃え、写真を使う章（特徴・声・講師紹介など）で統一トーンにする。

**丸いアバター（顔写真バッジ等）を `display: "flex"` の行に横並びで置く場合、`mobileStyles.width` を画像側の包み `section` に必ず明示する**（2026-09-10 実機で確認）。省略すると、隣のテキストが2行に折り返してモバイルで縦に伸びたときに、flex の高さ揃えで画像側が引き伸ばされたり圧縮されたりして、円が欠けて見える・下端が切れる不具合が起きる。行（親 `section`）にも `mobileStyles` を明示する。それでも PC/SP で崩れが直らない場合は、`content-schema.md` の `showDesktop`/`showMobile` でPC用・モバイル用の構造を分けるフォールバックを使う。
