# 構成案ゲート（JSON 構築前の承認）

content JSON を組む**前**に、テキストの構成案をユーザーに見せて承認を取る。JSON を一気に生成して保存し、後から直すと 1 箇所の修正ごとに content 全量を再送することになる（`patchCreatorLandingPageDraft` は部分更新不可）。構成案は JSON の 1/10 以下のトークンで、ストーリーの薄さ・素材不足・CTA 先の未確定を保存前に露呈させる。

## セクション ID の規約（意味的 ID）

- セクション ID は `sec-{2桁の順番}-{役割slug}` とする。例: `sec-01-hero`, `sec-02-pain`, `sec-07-voice`, `sec-09-price`。承認後に途中挿入する場合のみ順番に枝番を許す（`sec-03b-bonus`）。既存 ID は振り直さない（参照がずれる）
- 子要素は `{プレフィックス}-{順番}-{役割}`。`text` は追加しやすさのため常に連番を付ける。例: `hd-01-hero`, `tx-01-hero-1`, `tx-01-hero-2`, `btn-01-hero`
- 構成案の表に出した ID を JSON でそのまま使う。**構成案の表が ID マップ**になり、ユーザーは「3番目」「お客様の声のセクション」と言えばよく、LLM が ID に解決する。ユーザーに ID を探させない
- テンプレートから起こす場合、テンプレート由来の要素は既存 ID を表に転記してリネームしない。追加するセクションだけ意味的 ID を振る

## 構成案の書式

`hearing-sheet.md` で確定した内容と `best-practices.md` の「推奨セクション構成」を元に、以下の表を出す。

| ID | 役割 | 見出し案 | 伝えること（1行） | 素材 / CTA 先 | レイアウト型 | 未確認・仮定 |
|---|---|---|---|---|---|---|
| sec-01-hero | ヒーロー | 「初案件まで12週間。独学の遠回りをやめる」 | 顧客像の困りごと→約束 | CTA: プランID 12345 | 縦積み / ダーク背景 | — |
| sec-02-pain | 悩み共感 | … | … | — | 縦積み / ライト | 仮定: 代替手段は独学 |
| sec-05-proof | 実績 | 「受講生120名」 | 数字で信頼 | 実績: 120名（既存LPより） | 数字バー / ダーク | 未確認: 声の使用許諾 |
| … | … | … | … | … | … | … |

- **レイアウト型**は `best-practices.md` の語彙で書く: 縦積み / 画像左・テキスト右 / 横並びカード（列数） / 数字バー / 3層見出し / FAQ 縦積み。背景は ライト / ダーク / アクセント。細部（枠色・角丸・余白）は書かない。ユーザーは保存後に MOSH エディタの実物で判断する
- **素材 / CTA 先**は実在するもののみ（プラン ID・提供された画像 URL・実績数字）。無ければ「なし → セクションを立てない」か「未確認」と書く。ダミーで埋めない
- **未確認・仮定**列は、ヒアリングシートの `仮定` と、その行を作るのに足りない情報を書く。ここが多いセクションほど薄くなるので、ユーザーに優先して埋めてもらう
- 表の後に 2〜3 行で LP 全体のストーリー（誰が・何に困り・なぜ今この商品か・どう行動するか）を書く
- **原稿がある場合**は「伝えること」列に原稿の該当箇所（「原稿 3〜5 段落目」等）を書き、原文をどのセクションに置くかのマッピング表にする。原稿に無いセクションは「原稿外: 新規作成」と明示し、原稿の文章は要約・書き換えしない（改善案は未確認・仮定列に提案として書く）

## 承認と修正

- 「この構成で MOSH に LP を作ってよいですか？ 直したいところがあれば番号か見出しで教えてください」と確認し、**承認が出るまで JSON を組まない**。ユーザー向けの文言に JSON・ID・content・patch などの内部用語を出さない（「構成」「セクション」「下書き」「公開」で言う）
- 修正は**表を直して再提示**する（JSON を作り直さない）。承認後、表の ID・見出し・メッセージをそのまま JSON に落とす
- セクション数はヒアリングシート #4 で選ばれたゴール種別に対応する `best-practices.md` の「ゴール別の構成目安」で決め（数値は同書が正）、構成案の冒頭に「ゴール: ○○ → ○セクション」と1行書く。ユーザーが構成・規模を明示指定した場合はそれを優先する
- 外部 URL 再現の場合も同じ表を出す。「原文にあった要素」と「MOSH で再現できない要素（動画・実申込 URL 等）」を未確認列に書く

## 保存後の修正ループ

1. 保存後、ユーザーには **MOSH エディタで実物を見てもらう**（LLM 側でプレビューを再現しない。近似は見たい細部ほどずれる）
2. 修正指示は「3番目のカードの枠を薄く」「お客様の声の余白を広く」のように受け、構成案の表で ID に解決する
3. 修正は該当セクションの JSON だけ書き換え、content 全量を再送する（現状の制約）。修正のたびに構成案を作り直さない
4. 修正が構成そのものに及ぶ（セクションの追加・削除・順序変更）なら、表を更新してから JSON に反映する
