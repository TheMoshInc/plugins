# ヒアリングシート（LP 用の追加項目）

進め方（1往復・状態ラベル `確認` / `要記入` / `仮定` / `確定`・必須欄のゲート・原稿の扱い・顧客像の合格基準）と、共通3ブロック（#1 商品・オファー / #2 顧客像 / #3 CV先）は、**`creator-hearing` スキルが正**（`creator-hearing/references/common-sheet.md`）。このファイルには、LP に固有の差分（#3 の補足と #4〜#8、画像スロット、デザインの3点、LP 固有の禁止）だけを書く。

## 手順（LP 固有の差分）

1. **事前調査の LP 固有分**: `getCreatorLandingPages` → 既存 LP のトーン・実績表現・使っている画像の有無（共通の事前調査＝商品・プラン・スナップショットは `creator-hearing` に従う）
2. 冒頭の一言は共通と同じ。LP では「次の段階で確認します」を「構成案で確認します」に読み替える
3. **必須欄（1〜4。#4 は種別の選択のみ）が埋まるまで構成案には進まない**。任意欄は空でも `仮定` を明記して進む。ゴール種別は LLM の推奨に印を付けた4択で示し、選ばせる（書かせない）
4. **デザインの3点は、急かされても必ず通す**: ①プリセット（#7、4〜5択＋おすすめ印）②画像スロット（#7、収穫→空きスロットだけ依頼）③山場の材料（#8(a)、配布物・カリキュラムの一覧）。この3つが無いと「配色は選べたが中身が薄い LP」になる。ユーザーが「おまかせ」「早く作って」と言った場合も、共通の規則（商品情報から逆算できる欄は推奨を選んで1行確認、肯定で確定）で**この3点だけは必ず通す**（#7 の区分は任意だが、この3点は通す。山場の材料のうち配布物の一覧は逆算できないので、`要記入` のまま短く聞く。回答が無いまま進むときは `仮定` に変える。それ以外の任意欄は `仮定` で進めてよい）
5. **ユーザーの一言に、次の確認を必ず1画面に含める**（下の表の行を、そのまま追加ブロックの行にする。聞かずに自分で決めて進めない）:

| ユーザーの一言 | 1画面に入れる行（原文のまま使ってよい） |
|---|---|
| 「画像は無い」「写真を用意できない」 | 画像: 画像が無いとのことなので、どれで進めますか: ①あとで用意する（URL か手元のファイルをください）／②見送る（文字と背景色だけで組みます。写真があるときより印象は弱くなります）／**③下書きは仮の画像で進め、公開前に差し替える ← おすすめ**。あわせて、配布物・カリキュラムの一覧を表にして山場にする案を出す |
| 「実績の数字を載せて」（受講生◯名・満足度◯%など） | 証拠: 数字は、**確定値・集計期間（いつからいつまで）・母数（何人中か）の3点**が揃えば載せます（揃わなければ載せません）。ヒーローに大きく出す3点は、**数字＋単位＋12字以内のラベル**（例「120名｜受講生」）で使ってよいですか。3点それぞれ、確定値・期間・母数を教えてください |
| 「ロゴがある」 | ロゴ・配色: ロゴの画像（PNG）**と**ロゴの色（#RRGGBB）の両方をください。ロゴの色から配色を起こす選択肢もあります（本文の読みやすさ＝コントラストの基準を満たすか、こちらで確認します） |
| 「No.1」「最短」など強い表現を入れて | 表現の禁止事項: 次を載せてよいか○×で: ①「No.1」「最短」などの最大級表現（根拠・出典はありますか）②効果・効能の言い切り ③競合の名前 ④価格・募集の表示（二重価格・限定数・募集ごとに変わる日付）。根拠を出せないものは載せません |

6. 回答を受けてシートを確定し、`section-plan.md` の構成案へ

## 原稿が渡された場合（LP 固有の差分）

共通の扱い（原稿から抽出して確認だけにする、原文は書き換えない、原稿に無い実績・声・保証を補わない）は `creator-hearing/references/manuscript-input.md`。LP では次を足す。

- **ゴール種別**は**売り物の価格**から推奨を選ぶ（LINE/無料DLのみ→A、日程→B、〜数万円→C、数万円超→D。CVが無料相談でも D）。原稿があっても、推奨に印を付けた選択式で出し、ユーザーが肯定して `確定` にする
- 改善提案（抽象表現・具体化等）は、構成案の「未確認・仮定」列に提案として書き、承認を得てから反映する

## 画像（#7）の収穫と依頼

画像はデザイン品質の最大レバー（テンプレ・配色より効く）。シートの #7 では、**ゴール別に必要な画像スロットを表で示し、MOSH 内で見つかった候補を先に埋めてから、空いたスロットだけを依頼する**。「画像ありますか？」と漠然と聞かない。

| スロット | 役割 | 使う場所 | ゴール別の要否 | 収穫元（先に埋める） | 無いときの依頼文 |
|---|---|---|---|---|---|
| プロフィール／講師の顔写真 | Trust | ヒーロー横 or 講師紹介 | A・D は必須、B は登壇者分、C は任意 | 既存 LP の画像（`getCreatorLandingPages`）・素材ライブラリ（`getCreatorMaterials`） | 「ご本人の顔写真を1枚（明るい場所・正面〜斜め、縦横どちらでも。横顔寄りなら**文章側を向いている**ものだと視線が誘導できます）」 |
| 商品・サービスの写真 | Solution | ヒーロー・画像＋テキスト | C・D は必須、A は特典の見た目があれば | 商品画像（`getCreatorProducts` の画像）・既存 LP | 「商品（教材・会場・成果物）が分かる写真を1〜2枚」 |
| **特典・成果物の実物**（スクリーンショット可） | Solution | 特典紹介・画像＋テキスト | A は必須（特典そのもの）、D は教材・ワークシートがあれば | 既存 LP・素材ライブラリ・会員サイトの画面 | 「お渡しする資料やワークシート、会員サイトの画面などを1枚（スクリーンショットで構いません。個人情報が写っていないかだけご確認ください）」 |
| 活動・受講の風景 | Solution | 画像＋テキスト・声の横 | A・B で効く、D は任意 | 既存 LP・素材ライブラリ | 「セッション中や受講中の写真を1枚（顔出し不可なら後ろ姿・手元でも可）」 |
| 悩み・課題が伝わる写真（任意） | Problem | 悩み共感セクション（無ければヒーロー直後） | あれば効果的、C・D で特に効く | 既存 LP・素材ライブラリ（実写が無ければ無理に用意しない。イラストの捏造は不可） | 「顧客が困っている場面が伝わる写真があれば1枚（無理に用意しなくてOKです）」 |
| ロゴ・屋号 | — | ヒーロー上部・フッター | 任意（あれば全ゴール） | 既存 LP・MOSH の表示アイコン | 「ロゴがあれば PNG で」 |
| 実績・メディア | Trust | 数字バー下・信頼章 | あれば（捏造禁止） | 既存 LP | 「掲載メディアのロゴ・資格証など、使用許諾があるもの」 |
| 背景・雰囲気素材（任意） | Hero | ヒーロー背景 or CTA帯背景（`best-practices.md`「背景画像で装飾密度を作る」） | あれば効果的、無くても単色背景で組む | 既存 LP・素材ライブラリ | 「雰囲気に合う写真（活動風景・商品・空間など）が1枚あれば背景に使えます。無ければ単色背景で組みます」※背景は表示範囲を指定できないため、**主要な被写体が中央寄り**の横長写真を選ぶ（`best-practices.md`「写真の選び方」） |

- 収穫したスロットを**どう置くか**は `photo-patterns.md`（構成案の章ごとに型を1つ選ぶ。おすすめは付けない）。埋まらないスロットの「見送り」を選んだ場合の代替は、同ファイルの「F. 写真がないときの埋め方」
- 表は**そのゴールで要否が「必須」「効く」のスロットだけ**出す（D なら顔・商品の2〜3行）。**依頼する枚数**は1スロット1枚で足りる（多く求めない）。ただし収穫できた画像は複数セクションに使い回してよく、LP 全体で使う画像の総枚数・役割はゴール別の目安（`best-practices.md`「画像点数の目安」＝Hero/Problem/Solution/Trustの4役割）を満たすようにする
- **Solution の枠はイメージ写真より実物を優先する**（教材・ワークシート・会員サイトの画面など。理由と使い分けは `best-practices.md`「写真の選び方（役割が決まった後）」）。実物が無ければその枠は文字と余白で組み、イメージ写真で埋めない
- 完成形は `examples/hearing-screen-sample.md`。埋まらないスロットは、①依頼（URL か手元ファイル）②見送り（テキスト・背景色で組む。品質が落ちる旨を一言）③下書きはプレースホルダで進め公開前に差し替え、の3択をユーザーに選ばせる。黙って格下げしない
- 収穫した画像は用途（ヒーロー用など）と一緒に列挙し、「この写真をヒーローに使ってよいですか」と使用可否を確認する（他人が写る写真・メディアロゴは使用許諾も）
- 形式は JPEG / PNG / WebP。SVG は不可。手元ファイルは MCP から直接アップロードできる（`mcp-tools.md`「画像・動画のアップロード」）。編集画面の「パーツの追加 > 画像」からアップロードしてもらい URL を受け取る方法でもよい

## 禁止（LP 固有。共通の規則は `creator-hearing` の必須ルール）

- 実績数字の3点セット（`creator-hearing` 必須ルール C）が揃わないなら、**実績セクションを立てない**
- **価格・募集の表示で誤認させる**: 通常価格との並記（二重価格）、日付の過ぎた募集、「限定◯名」の表示は、本人に確認するまで載せない。**原稿・指示に無い日付を Claude が補わない**（日付に限らない一般則は `creator-hearing` の必須ルール A（LP 本文の仮置きの書式は SKILL.md「必須ルール」の事実情報ルール）が正。ここは日付固有の補足: 視聴期限・申込締切・開講日など、募集ごとに変わる日付。LP は募集をまたいで使われ、すぐ古くなる）。**原稿や指示に日付があるときは、それに従う**（カウントダウンの絶対期限も同じ）。そのうえで「募集が変わると日付の書き換えが要る」と1行添えて確認に出す。日付が決まっていないが要る所は、`（要記入：締切日）` のような仮置きにして確認に回す（最初の画面と申込カードには置かない）。「資料は期限なく見られる」のように募集で変わらない条件は書いてよい。告知・イベント（B）の開催日は日程部品（サービス連携）で出す
- デザインの3点（手順4）を聞かずに JSON 構築へ進む
