# 申込者・購読者確認のベストプラクティス

用途別の進め方と、提示前のセルフレビュー。ツールのパラメータは [mcp-tools.md](mcp-tools.md)、status の意味は [content-schema.md](content-schema.md) を参照する。

## ID 参照の確認手順

| 参照 | 手順 |
|---|---|
| 商品 | ユーザーが言った商品名で `getCreatorProducts` を引き、`name` が一致する `id` を使う。複数一致・不一致はユーザーに確認する |
| プラン | `getCreatorProductPlans` で商品配下のプランを取り、名前から `id` を解決する。全プランなら `planIds: []` |
| 人 | `keyword` に名前かメールアドレスを入れる。表記揺れ（ひらがな・旧姓・別メールアドレス）がありうるので、該当なしのときはその可能性を添える |

## 共通の下準備

1. 商品を確定する
2. その商品がサブスクか単発かを確認する。両方のプランがあれば申込者一覧と購読者一覧を両方呼ぶ
3. 最初の呼び出しは `limit: 20`、`offset: 0` で件数を見る
4. 全員分の名簿が必要かをユーザーに確認する。件数だけで済む依頼に全員のメールアドレスを出さない

---

## 1. サロンの入退場管理用に、今の参加者名簿を出す

**依頼例**: 「オンラインサロンの今のメンバー一覧を出して」「入退場管理に使う名簿が欲しい」

1. 購読者一覧を `statuses: ["active", "pastDue"]` で呼ぶ（決済エラー中も購読は続いているため含める）
2. `totalCount` が 50 を超えるなら件数を伝え、全員出すか確認する。全員出すなら `limit` を上げるか `offset` で続きを取る
3. 名前・メールアドレス・MOSH ID・購読開始日・状態を表にする。`pastDue` の人は「決済エラー（購読は継続）」と明示する
4. 単発プランの参加者も含めるなら申込者一覧を `paymentPattern: ["oneTimeApproved", "installmentActive", "installmentFulfilled", "bankPaid"]` で呼び、手順 2 と同じく件数を確認してから別の表として示す
5. 分割決済（一括入金）の参加者は `cardInstallmentsApproved` を含めると `limit` / `offset` が無視され全件が返るため、手順 4 には含めず、`planIds` や `approvedDateTime` で対象を絞ってから別の呼び出しで取る（「5. 分割決済（一括入金）の申込者を出す」）

## 2. 特定の人が申し込んでいるか確認する

**依頼例**: 「田中さんは申し込んでますか」「このメールアドレスの人の購読を確認して」

1. `keyword` に名前またはメールアドレスを入れて、申込者一覧・購読者一覧の該当する方（分からなければ両方）を呼ぶ
2. 該当が複数あれば全部示す（同姓同名や複数プランの申込がありうる）
3. 該当なしなら「見つかりませんでした」と伝え、表記揺れの可能性を添える

## 3. 対応が必要な人を洗い出す

**依頼例**: 「振込待ちの人を教えて」「決済エラーになっている人は」「解約した人の一覧」

| 依頼 | ツール | 条件 | 添える情報 |
|---|---|---|---|
| 振込待ち | 申込者一覧 | `paymentPattern: ["bankPending"]` | `order.bankTransferExpirationDateTime`（振込期限） |
| 振込期限切れ | 申込者一覧 | `paymentPattern: ["bankRejected"]` | — |
| 反映待ち | 申込者一覧 | `paymentPattern: ["bankPaid"]` のうち `status` が `unapproved` | — |
| 分割決済（分割入金）の決済エラー | 申込者一覧 | `paymentPattern: ["installmentPastDue"]` | `installmentsOrder.count` / `iteration`（何回目で止まっているか） |
| サブスクの決済エラー | 購読者一覧 | `statuses: ["pastDue"]` | `billingDurationMonths` |
| 解約済み | 購読者一覧 | `statuses: ["canceled"]` | `canceledDateTime` / `scheduleEndDateTime` |

対応そのもの（再請求・キャンセル・解約）はこのツールでは実行できない。管理画面へ誘導する。

## 4. 期間内の申込者を出す

**依頼例**: 「9 月に申し込んだ人」「キャンペーン期間中の申込者」

1. 期間を日本時間の日付で確定する。「最近」のような曖昧な指定は推測せずユーザーに確認する
2. 申込者一覧は `approvedDateTime: { startDateTime, endDateTime }`、購読者一覧は `startDateTime` / `endDateTime` で絞る。終了日はその日の終わりまで含まれる
3. 件数と名簿を示す。金額の合計を求められたら `sales-reporter` スキルに切り替える

## 5. 分割決済（一括入金）の申込者を出す

**依頼例**: 「カード会社の分割で払った人」「一括入金型の分割の申込者」

1. `paymentPattern` に `cardInstallmentsApproved` を含めると `limit` / `offset` が無視され全件が返る。先に `planIds` や `approvedDateTime` で対象を絞ってから指定する
2. 返った件数がそのまま総件数。`offset` で続きを取りに行かない
3. 応答が大きくなりそうなときは、ユーザーに対象期間やプランを狭めてよいか確認する

## セルフレビューチェックリスト

ユーザーに提示する前に一度実行する。

| # | 確認項目 |
|---|---|
| 1 | 商品・プランは一覧ツールで実在確認した ID を使った（推測していない） |
| 2 | サブスクと単発の両方がある商品で、両方のツールを呼んだ。表を混ぜていない |
| 3 | 「継続中」は `active` と `pastDue` の両方を含めた |
| 4 | `status` を日本語の状態名に変換した。「決済済み」と「反映待ち」を区別した |
| 5 | 個人情報は依頼された用途の範囲だけ出した。件数だけの依頼にメールアドレスを列挙していない |
| 6 | `totalCount` が多いとき、全件取得の前にユーザーに確認した |
| 7 | `cardInstallments*` を含めた結果に対して `offset` で続きを取りに行っていない |
| 8 | 金額・詳細など取得できないものを推測して書いていない |
| 9 | HTTP 用語・生の ID・JSON をそのまま出していない |
